# 알림관리 — 어떤 이벤트를 어느 역할이 어느 길로 받나

「어떤 롤에 어떤 이벤트를 연결하고 어떤 알림을 받게 할 것인가」를 화면에서 정한다.
포털관리 › 시스템관리 › **알림관리**(`/admin/system/notify-policy`).

```
 포털 화면                 NotificationServer                      받는 사람
 ┌──────────────┐         ┌──────────────────────────┐
 │ 이벤트 고르기 │  저장   │ scom.notification_events │
 │ 역할 고르기   │ ──────▶ │ scom.notification_policies│
 │ 길 고르기     │         └───────────┬──────────────┘
 └──────────────┘                     │ 발송 직전에 읽는다
                          ┌───────────▼──────────────┐      ┌───────────┐
  다른 서비스가 ─────────▶ │ PushSender · EmailEndpoints│ ───▶ │ 푸시·메일 │
  「알림을 보내라」        │  ① 정책  ② 본인 설정  ③ 구독 │      └───────────┘
                          │  푸시만 보내던 이벤트는      │
                          │  PushSender 가 메일도 낸다   │
                          └──────────────────────────┘
```

## 무엇을 푸는가 — 답이 코드와 설정 파일에 흩어져 있었다

「이 알림은 누가 받나」의 답이 세 군데에 따로 적혀 있었다.

| 알림 | 어디에 적혀 있었나 |
|---|---|
| 배포 완료 | `appsettings.json` 의 `DeployNotify:RoleId` |
| 헬프데스크 요청 | **소스에 박힌** `SYSTEM_ADMINISTRATOR`(`RequestEndpoints.cs`) |
| AI 작업 요청 | `appsettings.json` 의 `AiTasks:RequestNotifyRoles` |
| 문의 접수 메일·푸시 | `appsettings.json` 의 `InquiryMail:ToRole` **(2026-10-12 걷어냈다 — 아래)** |
| 보고서 메일 | 그 화면의 역할 고르기(유일하게 화면에 있었다) |

하나를 바꾸려면 **저장소를 고쳐 배포**해야 했고, 어떤 알림이 있는지 세어 보려면
다섯 서비스를 뒤져야 했다. 이 화면이 그 답을 DB 로 옮긴다.

## 화면이 생긴 모양 (2026-10-11 고침 — 탭 분리: 이벤트 중심 / 역할 중심)

화면은 **「이벤트 중심」** 탭과 **「역할 중심」** 탭 둘로 구성된다 (`DxTabs` · `.ad-nptabs`).

### 1. 이벤트 중심 탭
```
 ┌── 알림 이벤트 ☑정책밖제외 ───┬──│─ (고른 이벤트) ────────────────┐
 │ ┃ 배포 완료             [ON] │  ║  발생처 · 알림구분 · 대상 · 길  │
 │ ┃ 배포가 끝나면 …            │  ║  [띠] 지금 어떤 상태인가        │
 │ ┃ 앱푸시 2 · 이메일 1  deploy│  ║  [ON] 이 이벤트의 알림을 쓴다   │
 │ ┏━━━━━━━━━━━━━━━━━━━━━━━━━┓ │  ║                                 │
 │ ┃ 헬프데스크 요청    [ON] ┃ │  ║  역할별 수신 (체크 즉시 저장)  │
 │ ┗━━━━━━━━━━━━━━━━━━━━━━━━━┛ │  ║  [받는 사람]                    │
 └─────────────────────────────┴──│─────────────────────────────────┘
                              끌어서 폭을 정한다
```

- **왼쪽**: 알림 이벤트 목록 카드 (이름, 설명, 나가는 길 요약, 발생처)
- **오른쪽**: 고른 이벤트의 상세 정보 및 각 역할별 앱 푸시, 이메일 수신 지정 (체크 즉시 저장)

### 2. 역할 중심 탭
```
 ┌── 역할 목록 ─────────────────┬──│─ (고른 역할) ──────────────────┐
 │ ┃ 시스템관리자 [SYSTEM_...]  │  ║  이벤트별 수신 권한              │
 │ ┃ 5명 · 이벤트 4건 (푸시4·메일2)│  ║  ☑ 앱 푸시 전체  ☑ 이메일 전체  │
 │ ┏━━━━━━━━━━━━━━━━━━━━━━━━━┓ │  ║  배포 완료 (앱푸시☑ 이메일☑)     │
 │ ┃ 파트너관리자            ┃ │  ║  헬프데스크 (앱푸시☑ 이메일□)   │
 │ ┗━━━━━━━━━━━━━━━━━━━━━━━━━┛ │  ║                                 │
 └─────────────────────────────┴──│─────────────────────────────────┘
```

- **왼쪽**: 역할 목록 카드 (역할명, 식별자, 소속 사용자 수, 연결된 이벤트 및 채널 요약)
- **오른쪽**: 고른 역할에 대해 알림 이벤트별 앱 푸시, 이메일 권한 부여 현황을 확인하고 지정 (체크 즉시 저장, 전체 선택 지원)

**폭은 사람이 정한다.** 격자로 26% 에 못 박아 두었더니 양쪽이 서로 다른 폭을
바랐다 — 왼쪽은 이름과 설명이 들어가는 카드라 넓을수록 읽기 쉽고, 오른쪽은
역할/이벤트 표가 칸 다섯을 펴야 한다. 역할 관리·프로시저 결과와 **같은 부품**
(`DxSplitter` · admin.css 의 `.ad-vsplit`)으로 끌어서 나눈다. 좁은 화면
(992px 미만)에서는 구분선이 사라지고 판 둘이 위아래로 쌓인다.

**왼쪽은 표가 아니라 카드다.** 칸이 둘(이벤트 · 받는 설정)뿐인 표였는데, 정작
고르는 데 필요한 것 — **설명과 발생처** — 은 오른쪽을 눌러 봐야 보였다.
이벤트가 열여섯뿐이라 한 장씩 펴 두어도 목록이 길지 않다. 각 카드의 상단에
**사용 여부 스위치**가 달려 있어, 오른쪽을 누르지 않고도 목록에서 바로 사용 여부를
확인하고 즉시 켜고 끌 수 있다. 지금 상태는 카드 왼쪽의 굵은 선으로도 말한다(`.np-card--*`) —

| 선 | 뜻 |
|---|---|
| 초록 | 권한/역할이 걸려 있다 |
| 파랑 | **제한 없음** — 걸린 역할이 없어 지금까지와 똑같이 나간다 |
| 주황 | 이 이벤트를 꺼 두었다 — 또는 **받는 역할의 정본이 이 표인데 한 줄도 안 걸렸다**(`policy_required`, 아래 「소개 사이트 문의」) |
| 회색 | 정책이 안 걸리는 이벤트(「정책 밖」) 또는 지정된 권한 없는 역할 |

색으로만 가르지 않는다 — 카드 아래 줄에 요약이 늘 글자로 선다.

## 가장 중요한 성질 — **조용히 막지 않는다**

> **정책 줄이 하나도 없는 이벤트는 제한이 없다.** 지금까지와 똑같이 나간다.

기본을 「아무도 못 받음」으로 두면 표가 생긴 날 포털의 알림이 통째로 멎는다.
그 증상은 「알림이 안 온다」 하나라서, 원인이 이 표로 보이지 않는다.

그래서 **설치 SQL 은 정책 줄을 하나도 넣지 않는다.** 이벤트 목록만 깔리고,
역할을 한 줄이라도 적은 순간부터 **그 이벤트만** 정책을 탄다.

화면은 그 상태를 띠로 못 박아 말한다 — 체크가 하나도 없는 표는 사람 눈에
「아무도 못 받는다」로 읽히고, **그 오해는 알림을 끄려다 못 끄는 쪽**이다.

같은 까닭으로 **표를 못 읽어도 보낸다**(`NotificationPolicyService.ResolveAsync`
의 `catch`). DB 가 잠깐 흔들린 순간을 「권한 없음」으로 다루면 그 순간의 알림이
통째로 사라진다.

## 순서는 **정책 → 본인 설정 → 구독**

| | 누가 정하나 | 어디서 고치나 |
|---|---|---|
| ① 정책 | **회사** — 「배포 알림은 시스템관리자가 받는다」 | 포털관리 › 알림관리 |
| ② 본인 설정 | **그 사람** — 「나는 안 받겠다」 | 내 정보 › 환경설정 |
| ③ 구독·주소 | 기기와 계정 | 브라우저 알림 허용 · 계정 관리 |

**정책이 보내라고 해도 본인이 껐으면 안 간다.** 반대는 성립하지 않는다 — 본인이
켜 두어도 정책에 없으면 안 간다. 그래서 정책을 **맨 앞**에 둔다: 정책에서 빠진
사람을 먼저 덜어 내야 「본인이 껐다」는 기록이 실제로 껐던 사람에게만 남는다.

화면의 「받는 사람」 창이 셋을 **갈라서** 보여 준다. 고칠 자리가 서로 다르다 —
정책은 이 화면, 본인 설정은 그 사람의 환경설정, 주소는 계정 관리다.

## 정책이 하는 일은 **대상의 성격에 따라 갈린다**

이벤트마다 `target_kind` 가 있고, 같은 체크 칸이 그 값에 따라 뜻이 달라진다.
화면이 오른쪽 머리에 그 한 줄을 늘 적는 까닭이다.

### `ROLE` — 역할로 가는 알림 (배포 · 가입신청 · 헬프데스크 요청 · AI 작업 · 보고서 메일 · 문의 접수)

**정책의 역할이 부르는 쪽이 적어 둔 역할을 대신한다.** 설정 파일을 고치고
서비스를 다시 띄우지 않고 수신 역할을 바꾸는 길이 이것 하나다.

**문의 접수는 그보다 한 걸음 더 갔다** — 부르는 쪽이 역할을 아예 안 적어
보낸다(2026-10-12). 두 자리에 적혀 있으면 화면에서 다 풀어도 설정 파일로
되돌아가기 때문이다. 그런 이벤트는 `policy_required` 가 참이고, 역할을 비우면
**아무에게도 안 간다**(아래 「소개 사이트 문의」).

다만 **사람을 짚어 보낸 몫**(`owners` · `toUser`)은 그대로 둔다. AI 작업 결과가
시킨 본인에게 돌아가는 것 같은 몫은 「회사가 정하는 수신자」가 아니라 **그 일의
일부**라, 역할로 가리면 기능이 통째로 깨진다.

### `USER` — 당사자에게 가는 알림 (쪽지 · 댓글 · 요청 처리상태 · 생일 · 날씨 · 기기 구독)

**정책의 역할이 거름막이다.** 받을 사람이 그 역할을 하나도 안 가졌으면 뺀다.

짚어 보낸 몫이 곧 그 알림의 전부라, 거기에 거름막을 걸지 않으면 정책이 아무
일도 못 한다 — 「쪽지 알림은 이 역할들만 받는다」를 적을 자리가 사라진다.

### 포털 계정이 아닌 주인은 못 가린다

역할표(`scom.role_accounts`)는 포털 계정의 것이라 `ownerType` 이 `jsini` 가
아닌 주인은 역할을 물을 길이 없다. 그런 주인은 **거름막을 그냥 지난다** —
가릴 근거가 없는데 막으면 틀리는 방향이 조용히 안 가는 쪽이 된다.

### ※ 메일이 나가는 길은 **두 갈래**다

「이메일」 체크를 켠 뒤에 받는 것이 이벤트마다 다르다. 가르는 칸이
`notification_events.email_from_push` 다.

| | 메일을 누가 내나 | 받는 글 |
|---|---|---|
| `SIGNUP` · `AI_TASK` · `NOTE` · `HELPDESK_COMMENT` · `HELPDESK_STATUS` · `SITE_INQUIRY` · `REPORT_MAIL` | **보내는 쪽**이 `/emails/send` 를 따로 부른다 | 그쪽이 만든 제 틀의 메일 |
| ※ 가 붙은 다섯 (`DEPLOY` · `HELPDESK` · `BIRTHDAY` · `WEATHER` · `SUBSCRIPTION`) | **`PushSender` 가 함께 낸다** (`FanOutEmailAsync`) | 앱 알림과 **같은 글** |

**왜 갈라야 하나.** 앞 갈래는 이미 메일 경로가 있어서 체크가 벌써 들었다.
뒤 갈래는 푸시만 보내는 이벤트라 체크를 켜도 메일을 낼 사람이 아무 데도 없었고
(그래서 한동안 `supports_email = false` 로 **칸 자체를 잠가** 두었다 —
「켰는데 왜 안 오지」를 만들지 않으려고), 이제 푸시 경로가 그 몫을 낸다.
**둘 다 참인 줄을 만들면 같은 알림이 두 통 간다.**

> `TEST` 는 열지 않았다. `governed = false` 라 정책이 아예 안 걸리고, 곁가지는
> 정책이 고른 역할로만 나가므로 거기서는 영영 안 돈다 — 칸만 열면 또
> 「켰는데 안 온다」가 된다.

#### `SITE_INQUIRY` 는 **푸시와 메일을 각각 제 손으로** 낸다 (2026-10-11)

소개 사이트 문의 접수는 한동안 **메일로만** 나갔다(`supports_push = false`).
이제 `SiteServer` 가 길 둘을 **각각** 부른다 —

| 길 | 부르는 자리 | 무엇이 오나 |
|---|---|---|
| 앱 푸시 | `InquiryPushNotifier` → `/notifications/push` | 「새 문의가 접수됐습니다」 · 누르면 [사이트 문의내역](`/site/inquiries`)이 열린다 |
| 이메일 | `InquiryMailNotifier` → `/emails/send` | 접수번호 · 본문 · 답장 안내가 든 제 틀의 메일 |

둘 다 `eventCode = SITE_INQUIRY` 를 실어 보내므로 **이 화면의 체크 둘이 각각
듣는다.** 한쪽이 넘어져도 다른 쪽은 간다(둘 다 예외를 삼키고 로그만 남긴다) —
알림이 못 간 것을 접수 실패로 만들면 문의한 사람이 같은 글을 다시 쓴다.

> **`email_from_push` 는 거짓으로 둔다.** 푸시가 생겼다고 메일 곁가지를 켜면
> 문의 하나에 메일이 **두 통** 간다 — 위 표의 앞 갈래 그대로다.

#### 그리고 **받는 역할이 이 화면 하나로 옮겨 왔다** (2026-10-12)

그때까지 문의 알림의 「누가 받나」는 **두 자리**에 적혀 있었다 — 이 표와,
SiteServer 의 `InquiryMail:ToRole`(= `SYSTEM_ADMINISTRATOR`). 그런데 정책은
**줄이 하나도 없으면 「제한 없음」**이고, 제한이 없으면 발송 경로가 설정 파일로
되돌아간다. 그래서 —

> **관리자가 화면에서 체크를 다 풀어도 알림이 계속 갔다.**
> 끄려다 못 끄는 쪽이고, 화면만 보아서는 까닭이 안 보인다.

실제로 그 꼴이었다. 이 표의 `SITE_INQUIRY` 줄들은 `push_enabled = false`
(앱 푸시 칸이 잠겨 있던 때 저장된 값)인데 **앱 푸시는 설정 파일의 역할로 나가고
있었고**, 화면은 「앱 푸시 켠 역할 0」이라고 말하고 있었다.

**설정 파일의 역할을 비우고 표로 옮겼다**(`notify-policy-site-inquiry-2026-10-12.sql`).

| | 그 전 | 지금 |
|---|---|---|
| SiteServer 가 보내는 역할 | `InquiryMail:ToRole` = SYSTEM_ADMINISTRATOR | **안 적어 보낸다** (`roles: []` · `toRole: ""`) |
| 받는 역할을 정하는 곳 | 설정 파일 **과** 이 화면 | 이 화면 하나 |
| 체크를 다 풀면 | 설정 파일의 역할로 계속 나간다 | **아무에게도 안 간다** |

받던 사람은 그대로다 — 설정 파일이 보내던 `SYSTEM_ADMINISTRATOR` 를 표의
「앱 푸시」에 적어 넣었다(이메일은 이미 두 역할이 켜져 있었다). `ADMINISTRATOR`
에는 일부러 **안 켰다**: 지금 그 역할은 이메일만 받고 있어서, 여기서 켜 주면
관리자가 고른 적 없는 사람에게 알림이 느는 쪽이다. 화면에서 체크 한 번이면 된다.

`InquiryMail:ToRole` · `InquiryPush:ToRole` 은 지워지지 않았다 — **표가 한 줄도
없을 때만** 쓰이는 비상 통로로 남았고 평소에는 비어 있다. `InquiryMail:To`(주소)는
역할이 아니라 주소라 정책이 가리지 않는다.

##### 그래서 **「제한 없음」의 뜻이 이 이벤트에서만 반대다**

다른 이벤트는 역할을 안 걸면 「지금까지와 똑같이 나간다」인데, 여기서는 보내는
쪽에 기본 역할이 없으니 **한 통도 안 나간다.** 같은 「체크 0 개」가 뜻이
정반대라 화면이 그것을 갈라 말해야 한다 — 이벤트 표에 칸을 하나 더했다.

| `policy_required` | 역할이 0 개일 때 | 화면 |
|---|---|---|
| 거짓(이벤트 열다섯) | 보내는 쪽이 적은 역할로 나간다 | 파란 띠 「제한 없음」 |
| 참(`SITE_INQUIRY`) | **아무에게도 안 간다** | 주황 띠 「받는 역할이 하나도 없습니다」 · 카드도 주황 · 목록 요약은 「받는 역할 없음」 |

기본값은 **거짓**이다. 참으로 두면 이 칸이 생긴 날 포털의 알림이 통째로 멎는다.

##### 부르는 쪽이 **받는 사람을 안 적어도** 받아 준다

`/emails/send` 는 `to`·`toUser`·`toRole` 이 모두 비면 400 으로 막고 있었다.
그대로 두면 이 옮김이 **메일을 통째로 끊는다** — 화면에서 역할을 켜 두어도
한 통도 안 나가고, 부르는 쪽 로그에는 「받는 사람이 필요합니다」만 남아 고칠
자리가 안 보인다. 그래서 **이벤트 코드(또는 구분)가 실려 있으면 통과시키고**,
정책으로 푼 뒤에도 0 명이면 그때 까닭을 적어 400 으로 답한다.

```
받는 사람이 없습니다 (알림관리에 받는 역할이 없습니다 — 포털관리 › 알림관리에서
이 이벤트의 「이메일」을 켠 역할이 하나라도 있어야 보냅니다.)
```

#### `HELPDESK` 는 **겹칠 수 있다** — 켜기 전에 알고 켜야 한다

헬프데스크는 새 요청이 올라오면 **제 관리자 목록**으로 메일을 이미 보낸다
(`HelpDeskServer` 의 `AdminService.GetAdminEmailsForNotificationAsync` →
`EMailUtil` — `helpdesk` DB 의 `receiveEmail` 을 켠 사람들). 그 길이
`HELPDESK_LEGACY` 다.

받는 사람 목록이 **다르다** — 저쪽은 헬프데스크의 관리자 표이고 이쪽은 포털의
역할표다. 그래서 「두 통 가니까 켜지 마라」가 아니라, **두 목록에 다 든 사람은
두 통을 받는다**가 맞는 말이다. 이벤트 설명에 그 한 줄을 적어 두었다.

겹침이 사라지는 때는 `HELPDESK_LEGACY` 를 알림 서버로 옮길 때다(아래 「다음에
할 일」). 그 겹침은 **요청 등록**의 것이다 — 접수·완료 메일은 2026-10-12 에
`HELPDESK_STATUS` 로 옮겨 가 옛 길로는 더 안 나간다.

### 메일은 **적어 둔 때만** 나간다 — 푸시와 기본값이 반대다

> **「조용히 막지 않는다」의 짝은 「조용히 늘리지 않는다」다.**

푸시는 정책 줄이 없으면 「제한 없음」이다(지금까지와 똑같이 나간다).
**메일 곁가지는 그 반대다** — 「이메일」을 켠 역할이 하나도 없으면 한 통도 안 낸다.

같은 기본값을 쓰면 이 기능이 켜진 날 배포·생일·기상 알림이 **전 직원
메일함으로** 쏟아진다. 틀리는 방향을 고를 수 있을 때는 **되돌릴 수 있는 쪽**을
고른다 — 안 간 알림은 다시 보내면 되지만, 간 메일은 되돌릴 수가 없다.

화면이 그 비대칭을 못 박아 말한다(「제한 없음」 띠와 체크 옆 안내 한 줄).

### 메일은 **켠 역할 안에서만** 나간다 — 여기서 푸시와 갈라선다

역할 대상 이벤트(`ROLE`)에서 푸시는 **짚어 보낸 몫에 거름막을 걸지 않는다** —
정책은 받는 역할을 더할 뿐, 그 일의 일부로 가는 몫까지 가로채지 않는다는 규칙이다.

**메일에 같은 셈을 쓰면 적어 두지 않은 사람에게 메일이 간다.** 배포 알림이
그렇다 — `DeployEventEndpoints` 는 슈퍼관리자 전원을 역할이 아니라 `Owners` 로
직접 실어 보내므로, 역할 **하나**에만 「이메일」을 켜도 슈퍼관리자 전원의
메일함으로 들어간다.

그래서 곁가지는 대상 성격을 가리지 않고 **언제나** 「이메일을 켠 역할」로 한 번
더 거른다(`SendFanOutMailAsync`). 당사자 대상(`USER`)은 이미 걸러져 있어 이
걸음이 하는 일이 없다.

### 한 사람에 한 통씩 보낸다

직발송(`/emails/send`)은 주소를 쉼표로 이어 한 통으로 보낸다. 거기는 보내는
사람이 받는 이를 **직접 고른** 자리다. 곁가지는 역할을 펴서 받는 이를 **서버가
모으므로**(배포 알림이면 슈퍼관리자 전원) 같은 꼴로 보내면 **전 직원 주소가
서로의 메일 머리에 보인다.** 받는 사람이 고르지 않은 노출이라 나눠 보낸다.

### 그래도 지키는 것 둘

- **이벤트를 꺼 두었으면 메일도 안 낸다.** 끈 것은 「이 알림을 보내지 마라」이지
  「앱 푸시만 보내지 마라」가 아니다.
- **본인이 메일을 껐으면 안 낸다**(환경설정의 「이메일 알림」). 순서는 푸시와
  같다 — 정책 → 본인 설정.

**푸시가 못 갔어도 메일은 나간다.** 곁가지를 부르는 자리가 「VAPID 가 없다 ·
구독한 기기가 없다 · 다들 푸시를 껐다」로 되돌아가는 갈래보다 **앞**이다.
뒤에 두면 푸시를 못 받는 사람에게 메일도 안 가는데, 메일을 켜 둔 뜻은 정확히
그 반대다.

### 정책이 **안 걸리는** 넷을 목록에 두는 까닭

목록에서 빼면 관리자가 「그 알림은 없다」로 읽고, 걸 수 있는 것처럼 두면
**껐는데도 계속 온다.** 그래서 **보이되 못 거는** 상태를 표에 둔다
(`governed = false`) — 화면이 그 줄에 「정책 적용 안 됨」을 적어 준다.

| | 왜 안 거나 |
|---|---|
| `NOTICE` | 사람이 **그 자리에서** 받는 사람을 고르는 발송이다. 정책이 가로채면 「파트너」를 골랐는데 시스템관리자에게 간다 |
| `TEST` | 「눌렀는데 오나」를 보려고 보낸다. 정책이 막으면 시험의 뜻이 없다 |
| `ACCOUNT_MAIL` | 비밀번호 재설정은 업무 메일이다. 막으면 사용자가 얻는 것이 아무것도 없는데 화면에는 「보냈습니다」가 뜬다 |
| `HELPDESK_LEGACY` | **알림 서버를 안 거친다.** 서비스 점검 알림을 헬프데스크가 직접 SMTP 와 웹푸시로 부른다 — 접수·완료·종료는 2026-10-12 에 떼어 냈다(아래) |

> **그 마지막 줄의 절반이 2026-10-12 에 끝났다.** 헬프데스크의 접수·완료·종료
> 알림이 `/notifications/push` · `/emails/send` 로 옮겨 가 새 이벤트
> `HELPDESK_STATUS`(정책이 걸린다)가 되었다 — 옮기기 전에는 보내던 구독표가
> **0 줄**이라 완료 알림이 한 통도 안 나갔다
> ([docs/helpdesk-status-notify.md](helpdesk-status-notify.md)).
> `HELPDESK_LEGACY` 에는 **서비스 점검**만 남았고, 그 둘(`HealthCheckWorker` ·
> `AutoCheckWorker`)을 옮기면 `governed` 를 켜는 것으로 끝난다.

## 이벤트 코드와 알림구분은 다른 것이다

| | 무엇인가 | 어디서 쓰나 |
|---|---|---|
| 알림구분 `category` | 쌓인 **기록**을 갈래로 묶는 이름표 | 알림함 · 발송 이력의 조회 조건 |
| 이벤트 `eventCode` | **설정**이 걸리는 열쇠 | 알림관리 |

지금은 대부분 **같은 글자**다 — 세어 보니 구분 하나에 사건 하나였다. 그래서
보내는 쪽이 `eventCode` 를 안 적어도 `category` 로 찾는다. 구분이 없는 하나
(`REPORT_MAIL`)만 제 이름을 적어 보낸다.

> `SITE_INQUIRY` 도 한동안 그쪽이었다 — 메일로만 나가 **알림함에 쌓이지 않아서**
> 붙일 갈래가 없었다. 앱 푸시가 생기며 줄이 쌓이기 시작해 구분을 붙였다
> (`notify-policy-site-inquiry-push-2026-10-11.sql`). 안 붙이면 그 줄들이
> 「구분 없음」으로 모이는데, 거기는 **구분을 빠뜨린 발송 자리를 찾는 자리**다.

같은 구분 아래에서 사건을 더 잘게 갈라야 할 날이 오면 `구분.하위` 꼴로 적는다.
푸는 쪽은 **정확히 맞는 줄 → 앞머리(구분) 줄 → 둘 다 없으면 제한 없음** 순서로
본다 — 그래야 「HELPDESK 를 설정해 두었는데 세부 사건 하나가 그물을 빠져나간다」가
안 생긴다.

**표에 없는 코드로 보내도 된다.** 정책이 안 걸린 채 그냥 나간다.

## 보고서 메일과 겹치는 자리

보고서 메일 화면(`/admin/system/report-mail`)에도 「받는 역할」을 고르는 자리가
있다. 둘이 겹치면 **알림관리가 이긴다** — `REPORT_MAIL` 은 역할 대상 이벤트라,
정책에 역할이 한 줄이라도 걸려 있으면 배치가 고른 역할 대신 그것이 쓰인다.

그래서 **설치 SQL 은 `REPORT_MAIL` 정책을 넣지 않는다.** 아무것도 안 걸린
동안에는 배치 화면이 정한 대로 가고, 거기 역할을 적는 순간부터 회사 규칙이
배치를 덮는다. 두 화면이 서로 다른 말을 하기 시작하면 그때는 배치 화면의
역할 고르기를 걷는 것이 다음 단계다.

## 「보냈습니다」가 거짓이 되지 않게

정책이 막은 발송은 **실패가 아니다.** 400 으로 답하면 부르는 쪽 로그에 오류가
쌓이고, 설정을 존중한 결과가 고장으로 읽힌다. 그렇다고 「보냈습니다」라고도
하지 않는다.

| 길 | 어떻게 답하나 |
|---|---|
| 푸시 | 결과의 `policyExcluded` 에 세고 `message` 에 까닭을 적는다 |
| 메일 | **200 + `data: false`** + `message` 에 까닭 |

메일의 그 모양 때문에 `AccountMailClient` 가 **상태 코드만 보면 안 나간 메일을
「보냈습니다」로 적는다.** 그래서 200 응답의 `data` 를 읽어 가른다
(`OutcomeAsync`) — 보고서 메일 화면의 「마지막 결과」가 그 한 줄을 그대로
보여 주기 때문이다.

발송 이력(`/admin/push/logs`)에는 사유가 **갈라서** 남는다.

| 사유 | 고칠 자리 |
|---|---|
| `알림관리 정책에서 제외` | 포털관리 › 알림관리 |
| `알림관리에서 이벤트를 끔` | 포털관리 › 알림관리 |
| `본인이 푸시를 끔` | **그 사람의** 환경설정 |
| `구독한 기기 없음` | 그 사람의 브라우저 |

### 「성공」과 「도착」은 다른 칸이다 (2026-10-12)

발송 이력의 **결과** 칸은 「푸시 서비스가 받아 주었다」까지다. 그 옆의 **도착**
칸이 「그 기기가 실제로 띄웠다」이고, 서비스워커가 되알려 줘야 찍힌다.

> **성공인데 도착이 빈 줄이 곧 못 받고 있는 기기다.** 브라우저 자료를 지우거나
> 알림 권한을 끈 구독에도 푸시 서비스는 한동안 성공을 돌려주므로, 이 칸이 없을
> 때는 「기기 넷에 등록했는데 하나만 울린다」를 화면 어디에서도 확인할 수 없었다
> ([docs/push-delivery.md](push-delivery.md)).

기기마다의 요약은 **포털관리 › 계정 앱 현황**과 **환경설정의 기기 목록**에 선다.

## 미리받아보기 — 이벤트가 안 일어나도 한 통 받아 본다

이벤트 중심 탭 오른쪽 아래의 단추 둘이다(`POST …/notification-policies/{코드}/preview-send`,
`NotificationPolicyPreviewSender`).

| | 미리받아보기 | 대상자 미리받아보기 |
|---|---|---|
| 받는 사람 | 누른 사람 본인 | **저장된** 정책으로 푼 사람 모두(「받는 사람」 창과 같은 셈) |
| 정책 | 안 거친다 — 내 역할이 그 이벤트에 안 걸려 있어도 온다 | 켠 길만 — 푸시를 켠 역할엔 푸시, 메일을 켠 역할엔 메일 |
| 본인 설정 | 푸시는 따른다 · 메일은 주소 하나로 보내 안 막힌다 | 둘 다 따른다(실제 발송과 같다) |
| 안 되는 때 | — | 이벤트가 꺼짐 · 역할을 하나도 안 걸었음(대상을 알 수 없다) |

- 글은 `[미리받아보기] {이벤트 이름}` + 설명이다. 실제 발송 글은 보내는 쪽이 그때 짓는 것이라 여기서 만들 수 없다.
- 푸시에 **이벤트 코드·구분을 싣지 않는다.** 실으면 정책이 다시 걸러 본인 받아보기가 막히고, 메일 곁가지가 한 통 더 낸다.
- 누르면 여는 화면: `SERVER_PING` 은 `/admin/status/server-ping`, 나머지는 알림관리.
- 발송 기록(`push_send_logs`)에 `sent_by` = 누른 사람으로 남는다 — 받은 사람의 「내 알림함」에도 뜬다.

## 내부 서버 Ping — 두절 · 두절 지속 · 복구 (2026-10-28, 2026-10-29 확장)

`SERVER_PING` 을 내는 것은 화면이 아니라 AuthServer 의 배경 작업(`ServerPingWatcher`)이다.
화면(`/admin/status/server-ping`)은 10초마다 상태를 **보여 줄 뿐** 알림을 내지 않는다 —
이 작업이 생기기 전에는 그 화면만 있어서 **두절 알림이 한 통도 안 나갔다**.
2026-10-29부터 기존 그리드 중계 장비(192.168.219.229)에 더해 jin sm 장비(192.168.219.244)도 함께 독립적으로 감시하고 알린다.

| 언제 | 알림 |
|---|---|
| 30초마다 Ping 해서 **3회 연속** 실패(첫 실패부터 약 1분) | `[서버 두절] {장비명}({IP}) 응답 없음` |
| 두절이 이어지는 동안 **60분마다** | `[서버 두절 지속] {장비명}({IP}) … N시간 M분째` |
| 두절을 알린 뒤 처음으로 응답 | `[서버 복구] {장비명}({IP}) … 두절 시간 약 N분` |

- 한두 번 튀는 실패는 알리지 않고, 두절을 알리지 않았으면 복구도 알리지 않는다(`ServerPingAlertPlan`). 장비마다 독립된 상태를 유지한다.
- 숫자는 `appsettings.json` 의 `ServerPing`(`IntervalSeconds` · `FailThreshold` · `RepeatMinutes` — 0 이면 한 번만) 및 `Targets` 목록.
- 받는 사람·길은 이 표의 정책이다. 정책에 역할이 없으면 `SYSTEM_ADMINISTRATOR` 로 간다. 메일은 `email_from_push` 로 함께 나간다.
- 같은 장비의 알림은 기기에서 한 장으로 겹친다(`tag = server-ping:{targetIp}`) — 복구가 두절 알림을 덮으며, 장비별로는 분리된다.
- 상태는 메모리에만 있다. 두절 중에 AuthServer 가 다시 뜨면 두절 알림이 한 번 더 간다.

## 권한

메뉴 권한은 `SYSTEM_ADMINISTRATOR` 하나다. 이 화면은 회사의 알림 규칙을 통째로
바꾸는 자리라, 넓게 열면 역할 하나를 더하는 것으로 수십 명의 휴대폰과 메일함에
알림을 걸 수 있고 — 반대로 이벤트 하나를 꺼서 **배포 알림이 아무에게도 안
가게** 만들 수도 있다.

**서버도 같은 표를 본다**(`NotificationServer/Services/MenuViewAccess`). 게이트웨이의
알림 경로는 로그인만 보므로, 막지 않으면 일반 사용자가 주소를 알아내 자기를 모든
알림의 수신자로 걸 수 있다. 더 줄 역할이 생기면 메뉴 권한 화면
(`/admin/auth/menu-role`)에서 더하면 되고 **코드를 고칠 일이 없다.**

읽기와 쓰기를 같은 문으로 막는다 — 이 화면은 열람 권한이 곧 관리 권한이고,
권한 항목을 쪼개면 「볼 수는 있는데 저장하면 403」이 되는 자리를 하나 더 만든다.

## 카카오 알림톡은 아직 칸이 없다

`IKakaoAlimtalkSender` 는 확장점만 서 있고 실제로 나가는 길이 없다
(`Kakao:Enabled` 가 거짓이고, 포털 계정에 전화번호 칸이 없어 받을 번호를 들고
있는 표도 없다). **눌러도 아무 일 없는 체크 칸을 만들지 않는다** — 그 길이
열리는 날 `NotificationChannel` 에 값 하나, 두 표에 칸 하나를 더하면 된다.
