## 1. 마이그레이션 가이드 (Migration Guide)

### 1) 백엔드 SignalR 활성화 및 배포
- 백엔드 서버 프로젝트(`funeralv2Api`)에 `Microsoft.AspNetCore.SignalR` 의존성이 통합되었습니다.
- REST API 서버 구동 시 포트 충돌이 나지 않도록 실행 환경 변수를 점검하고, 방화벽 규칙에서 **SignalR 포트(기본 5000) 및 WebSocket 프로토콜**이 허용되어 있는지 확인해야 합니다.
- **CORS 설정**: 신규 플레이어가 다른 IP나 에뮬레이터 루프백(`10.0.2.2`)에서 소켓 세션을 열 수 있도록 허용되어 있으므로 배포 환경에 따라 도메인을 제한하도록 프로덕션 설정(`.env.production` 또는 `appsettings.Production.json`)을 정비하십시오.

### 2) 사이니지 플레이어 초기 세팅 및 연결
1. `run_player.bat` 파일을 실행하여 안드로이드 에뮬레이터 또는 실기 디바이스를 준비합니다.
2. 최초 앱 구동 시 **사이니지 설정 화면**이 팝업됩니다.
   - **REST/SignalR API 서버 주소**: 백엔드 REST 서버의 IP 및 포트 (에뮬레이터의 경우 호스트 로컬 루프백인 `http://10.0.2.2:5000` 입력)
   - **미디어 파일 서버 주소**: `FileServer` 주소 (에뮬레이터의 경우 `http://10.0.2.2:5001` 입력)
   - **장비 식별 코드**: 관리 도구에서 할당한 장비 고유 코드 (예: `DEV-001`) 입력 후 저장합니다.

## 2. 롤백 계획 (Rollback Plan)

### 1) 백엔드 롤백 프로세스
- SignalR 및 새로운 엔드포인트 연동이 문제를 일으키거나 안정성에 의심이 생길 경우 다음 절차를 밟습니다:
  1. `funeralv2Api` 리포지토리의 커밋 히스토리에서 해당 변경 커밋을 리버트(`git revert`)합니다.
  2. `Program.cs` 내 `AddSignalR()` 및 `MapHub()` 구문을 주석 처리합니다.
  3. `DeviceHubSender` 및 `DeviceHub` 코드를 무시하고 서비스를 빌드 및 재배포합니다.
  4. 데이터베이스 스키마나 테이블 데이터 파괴가 발생하지 않는 순수 API 및 메모리 매핑 추가이므로 롤백으로 인한 데이터 유실 리스크는 **0%**입니다.

### 2) 클라이언트 롤백 프로세스
- `funeralv2_player/` 디렉토리를 통째로 백업해 두고, 이전 빌드로 환원하거나 프로젝트 폴더를 삭제하면 완전한 원복이 완료됩니다.

## 3. 영향 분석 (Impact Analysis)

| 영역 | 영향 분석 내용 |
| :--- | :--- |
| **사용자 (Users)** | - 백엔드 어드민 화면에서 현황 카드 내 장비 미디어나 고인 정보가 변경되면 플레이어가 즉시 반응하여 화면 연출을 갱신하므로, 기존 수동 재부팅 작업이 완전히 배제되어 운영 만족도가 크게 상승합니다. |
| **데이터 (Data)** | - 데이터베이스 스키마 변경 사항은 없으며, 순수 DTO의 속성 4개 추가에 한정됩니다.<br>- 플레이어 로컬에 SQLite DB 및 디바이스 저장소 용량(동영상/음악 크기만큼의 캐시 용량 약 100~500MB)이 확보되어 있어야 합니다. |
| **인프라 (Infrastructure)** | - 웹소켓 커넥션(SignalR)이 사이니지 단말 수만큼 늘어나게 됩니다. (예: 단말 100대면 커넥션 100개 증가).<br>- 단, 시그널링 통신이 극도로 가볍고 REST API 호출을 중계받는 구조이므로 서버 CPU 및 대역폭에 주는 영향은 미미합니다. |
| **비용 (Cost)** | - 웹소켓의 지속 연결 상태 관리 비용 외에 클라우드 서버나 라이선스 추가 지출은 발생하지 않습니다. |
