# 업무 비서 화면 설계 — RAG 자료 + 포털 업무 데이터

2026-10-24

## 무엇을 만드나

업무 중에 떠오른 궁금증을 아무 때나 묻는 화면이다. 지금은 궁금한 것이 생기면
**헬프데스크 요청글을 뒤지고, 프로젝트관리 일정을 열어 보고, 메일을 찾아본다** —
세 군데를 사람이 손으로 돌아다니는 그 일을 한 번 물어서 끝내는 것이 목표다.

묻는 것은 세 갈래다.

| 갈래 | 보기 | 답이 나오는 곳 |
|---|---|---|
| 일정 | "오늘 이후 할일목록 제공해줘" | 포털 업무 데이터 |
| 예전에 있었던 일 | "홍길동의 10-17일 이후에 내용이 있으면 모두 보여줘" | 포털 업무 데이터 |
| 보관된 자료 | "피복 주문일자가 언제인가?" | RAG 문서함 |

한 질문이 양쪽을 다 건드릴 수도 있다("지난달 피복 건 진행 어디까지 갔나" —
규정은 문서에, 진행은 요청글에 있다).

## 왜 지금 만드나

RAG 조각은 다 있다. 임베딩 서버 · 색인 · 검색 · 문서함 · 대화 결합까지 돈다
(`docs` 아래 흩어진 글과 `AIAgentServer/Services/Rag/`). **빠진 것은 포털이
실제로 들고 있는 업무 데이터다.** 지금 AI쳇에 "오늘 이후 할일" 을 물으면
모른다고 답한다 — 할 일은 문서가 아니라 `projmng.home_todo` 에 있기 때문이다.

## 목표 · 비목표 · 실패

**목표**

- 사람 이름과 날짜로 물으면 세 시스템을 가로질러 모아 답한다.
- 답에는 **근거가 붙는다** — 요청글 번호, 일정 제목, 문서 파일 이름. 눌러서
  원래 화면으로 갈 수 있다.
- RAG 카테고리를 골라 자료 범위를 좁힐 수 있다.
- 누가 무엇을 물어 무엇을 받아 갔는지 **기록이 남는다.**

**비목표**

- 쓰기. 이 화면은 **읽기만 한다.** 일정을 잡거나 글을 쓰거나 메일을 보내지 않는다.
- 웹 검색. 사내 질문에 바깥 자료가 섞이면 해롭다(기존 AI쳇이 그 자리다).
- 장례식장(`funeralv2Api`) · 운송관리 데이터. 1차 범위 밖이다.
- 기존 AI쳇(`AiChatPanel`) 을 고치는 것. 저쪽은 그대로 둔다.

**실패로 치는 것**

- 자료에 없는 것을 그럴듯하게 지어낸다. 숫자 하나가 틀려도 실패다.
- 날짜를 잘못 센다. "오늘 이후" 가 어제 것을 끌어오면 쓸 수 없다.
- 느려서 안 쓴다. 한 질문에 30초를 넘기면 사람은 그냥 헬프데스크를 연다.

## 누가 쓰나 · 무엇이 보이나

**슈퍼관리자와 임원만 연다.** 다른 사람에게는 메뉴가 안 보이고 주소로도 안 열린다
(`docs/screen-access.md` 의 기본 차단).

이 화면은 **묻는 사람의 평소 권한을 넘어서 답한다.** 홍길동의 글을 볼 권한이
없는 임원도 내용을 받는다. 그것이 이 화면을 둘로 묶은 까닭이다.

그 대가로 **모든 질문과 답이 기록된다**(아래 「기록」). 권한을 넘는 자리에
기록이 없으면 나중에 되짚을 방법이 없다.

## 고른 길 — 검색이 아니라 도구다

**포털 업무 데이터를 RAG 색인에 넣지 않는다.** 두 가지가 맞지 않는다.

1. "10-17일 이후", "오늘 이후" 는 **범위 질의**다. 벡터 검색은 뜻이 가까운 것을
   찾지 날짜로 자르지 못한다. 10월 17일과 10월 18일의 임베딩은 거의 같다.
2. 업무 데이터는 **매분 바뀐다.** 색인을 다시 만드는 데 CPU 임베딩으로 몇 분씩
   걸리는데(문서 780토막에 4분 40초), 그 사이 들어온 요청글은 안 보인다.

대신 **모델에게 도구를 쥐어 준다.** `Services/Mcp/WebChatAgent.cs` 가 이미
OpenAI 규격 `tool_calls` 루프를 돌리고 있고(최대 4라운드), 로컬 모델
(Qwen3-Next-80B)이 그것을 잘 받는 것이 웹 검색에서 확인됐다. 같은 얼개를
**바깥 MCP 가 아니라 안쪽 포털 도구**에 쓴다.

```
질문 ──→ AIAgentServer /assistant/chat
            │
            ├─ 시스템 프롬프트: 오늘 날짜(KST) · 고른 카테고리 · 규칙
            │
            └─ 도구 루프 (최대 N 라운드, 스트리밍 아님)
                  find_user            → AuthServer   (사람 이름 → 아이디)
                  search_requests      → HelpDesk     (요청글 목록)
                  get_request          → HelpDesk     (본문 + 댓글)
                  search_schedules     → ProjMng·HelpDesk (일정)
                  search_todos         → ProjMng      (할 일)
                  search_mails         → Notification (보낸 메일·발송 기록)
                  search_documents     → RagStore     (RAG 문서)
                  ↓
            마지막 답만 스트리밍으로 흘린다
```

**RAG 도 도구로 바꾼다**(이 화면에서만). 지금 `RagAugmenter` 는 마지막 발언
하나로 한 번 검색해 프롬프트에 붙이고 끝이다. 도구로 주면 모델이 **다시 물을 수
있다** — 첫 검색이 빗나가면 낱말을 바꿔 또 찾는다. 메모리에 적어 둔 "되묻기가
약하다" 는 숙제가 여기서 자연히 풀린다. **기존 AI쳇의 `RagAugmenter` 는 건드리지
않는다.**

### 왜 McpServer 가 아닌가

`McpServer`(:5510)는 **바깥 도구**(웹 검색)를 여는 자리다. 포털 도구는
DB 와 사내 서비스에 닿아야 하고, 권한을 넘는 호출이라 부른 사람이 누구인지
들고 다녀야 한다. AIAgentServer 안에 두는 것이 맞다(`Services/Portal/`).

## 만들 것

### 1. 백엔드 — AIAgentServer

```
Services/Portal/
  PortalToolSet.cs        도구 목록(JSON 스키마)과 이름→실행 매핑
  PortalToolRunner.cs     도구 한 번 실행. 결과를 글로 바꾼다(토큰 상한 포함)
  HelpDeskGateway.cs      HelpDeskServer 호출
  ProjMngGateway.cs       ProjMngServer 호출
  MailGateway.cs          NotificationServer 호출
  UserDirectory.cs        사람 이름 → 포털 사용자(동명이인은 후보를 다 준다)
AssistantAgent.cs         도구 루프 + 마지막 답 스트리밍
Endpoints/AssistantEndpoints.cs
```

**엔드포인트**

| 길 | 하는 일 |
|---|---|
| `POST /assistant/chat` | 질문 → 도구 루프 → 답 스트리밍(SSE). 기존 `/chat/stream` 과 같은 모양 |
| `GET  /assistant/scopes` | 고를 수 있는 RAG 카테고리 (이 화면은 전부 본다) |
| `GET  /assistant/audit` | 기록 조회 (슈퍼관리자) |

**도구 계약** (요지)

| 도구 | 받는 것 | 주는 것 |
|---|---|---|
| `find_user` | `name` | 후보 목록: 아이디 · 이름 · 회사 · 부서 |
| `search_requests` | `user_id?` `from?` `to?` `status?` `keyword?` `limit` | 번호 · 제목 · 상태 · 요청일 · 담당 · 회사 |
| `get_request` | `id` | 본문 + 댓글 전부 |
| `search_schedules` | `user_id?` `from?` `to?` `keyword?` | 제목 · 기간 · 완료 여부 · 출처 |
| `search_todos` | `user_id?` `from?` `to?` `done?` | 제목 · 목표일 · 완료 여부 |
| `search_mails` | `user_id?` `from?` `to?` `keyword?` | 제목 · 받는 사람 · 보낸 때 |
| `search_documents` | `query` `category?` | 토막 본문 + 출처 파일 |

날짜는 **한국 달력 날짜(`YYYY-MM-DD`)로 주고받는다.** 안에서 UTC 로 바꿔 질의하고
돌려줄 때 다시 한국 시각으로 적는다 — `docs/utc-time.md` 의 "보여 주기 직전에
한 번만" 규칙이 여기서는 도구 경계다. `AppTime` 을 쓴다.

**결과 크기를 반드시 자른다.** "10-17일 이후 전부" 가 300건이면 문맥이 터진다.
목록 도구는 기본 30건 · 최대 100건으로 자르고, **잘랐다는 것을 결과에 적는다**
(`"총 312건 중 30건"`). 모델이 "전부 보여줬다" 고 말하지 않게 하려는 것이다.

### 2. 권한을 넘는 호출

사내 서비스들은 지금 토큰의 주인으로 범위를 좁힌다(`UserContext`). 이 화면은
그것을 넘어야 하므로 **내부 호출용 자격**이 하나 필요하다.

- `Assistant:InternalToken` — `scripts/secrets.env` 와 운영
  `appsettings.Local.json` 에 같은 값. `DeployNotify:Token` 과 같은 방식이다.
- 받는 쪽(HelpDesk · ProjMng · Notification)에 **조회 전용 내부 엔드포인트**를
  연다. 기존 사용자 엔드포인트에 우회로를 뚫지 않는다 — 그러면 그 구멍이
  다른 화면에도 열린다.
- 값이 없으면 **도구가 조용히 꺼진다**(문서 질문만 받는다). 터지지 않는다.

### 3. 기록

새 표 `scom.ai_assistant_audit` (EF 마이그레이션이 아니라
`deploy/sql/ai-assistant-audit-2026-10-24.sql`. RAG 표들과 같은 길).

| 칸 | 담는 것 |
|---|---|
| `asked_by` · `asked_at` | 누가 · 언제(UTC) |
| `question` | 물은 글 그대로 |
| `scope_category` | 고른 카테고리 |
| `tool_calls` | 어떤 도구를 어떤 조건으로 불렀나 (JSON) |
| `sources` | 답의 근거 — 요청글 번호 · 문서 파일 이름 |
| `answer` | 답 전문 |
| `elapsed_ms` · `error` | 걸린 시간 · 실패 까닭 |

**답을 통째로 남긴다.** 권한 밖 자료가 나간 자리라 "무엇이 나갔나" 가 곧
질문·도구 조건이 아니라 답 그 자체다.

### 4. 프론트 — 새 화면

`web/src/Apps/JSini.Web.Admin/Components/Pages/Assistant.razor`
`@page "/admin/ai/assistant"` · `RouteKey("admin.ai.assistant")` ·
메뉴 `SYS_AI_ASSISTANT`.

> **놓는 자리는 내 판단이다.** 요청에는 "funeral-portal" 이라고 적혀 있었는데,
> 장례식장 모듈(`/funeral`)에 두면 쓰는 사람(슈퍼관리자·임원)과도, 보는
> 자료(헬프데스크·프로젝트관리·메일)와도 맞지 않는다. 이미 AI 화면들이 모여
> 있는 포털관리(`/admin/ai/*`) 옆에 둔다. 다른 데를 뜻하셨으면 옮기면 된다.

화면은 **전체 폭 대화 화면**이다(서랍 `AiChatPanel` 이 아니다 — 답에 표와
목록이 실려 좁은 서랍에서는 읽히지 않는다).

```
┌──────────────────────────────────────────────┐
│ 업무 비서            [자료 범위: 전체 ▾]      │  ← 카테고리 고르기
├──────────────────────────────────────────────┤
│                                              │
│   (대화)                                      │
│   나: 홍길동의 10-17일 이후 내용 모두 보여줘     │
│                                              │
│   비서: ⚙ 사람 찾기 → 요청글 뒤지는 중…        │  ← 도구 진행 띠
│                                              │
│        홍길동 님의 10월 17일 이후 기록입니다.    │
│        ▸ 요청글 4건                           │
│          #1042 피복 발주 지연  완료 10-21      │  ← 누르면 원래 화면
│        ▸ 일정 2건 · 할 일 1건                 │
│                                              │
├──────────────────────────────────────────────┤
│ [ 물어보세요…                        ] [보내기]│
└──────────────────────────────────────────────┘
```

**도구 진행을 보여 준다.** 세 시스템을 도는 동안 몇 초가 흐른다. 빈 화면이면
사람은 멈춘 줄 안다. 기존 스트리밍의 `ChatStreamPart.Info(…, "rag")` 자리에
`"tool"` 갈래를 더해 "요청글 뒤지는 중" 을 흘린다.

**근거는 링크로 만든다.** 요청글 번호는 `/helpdesk/requests/{id}`, 일정은
프로젝트관리 화면, 문서는 RAG 문서함의 그 파일로.

재사용: `AiChatClient`(스트리밍·받아쓰기), 기존 대화 기록 표
(`scom.ai_chat_sessions` · `ai_chat_messages`), `CommPopup`·`CommCont` 등
공용 부품.

## 프롬프트에서 반드시 말할 것

RAG 에서 배운 것이 그대로 간다 — **"자료가 관련 없으면 무시하고 모른다고 하라"**
한 줄이 없으면 모델이 엉뚱한 자료로 그럴듯한 답을 짓는다.

- 오늘 날짜(한국)를 시스템 프롬프트에 **반드시 박는다.** 모델은 오늘이 며칠인지
  모른다. "오늘 이후" 가 여기서 갈린다.
- 도구가 **빈 결과**를 주면 "없습니다" 라고 답한다. 다른 도구 결과로 메우지 않는다.
- 도구 결과가 **잘렸으면** 몇 건 중 몇 건인지 말한다.
- 숫자·날짜·번호는 **도구가 준 것을 그대로 옮긴다.** 고쳐 쓰지 않는다.
- 근거(요청글 번호 · 파일 이름)를 **반드시 밝힌다.**

## 만드는 차례

| 단계 | 무엇 | 끝났다고 할 수 있는 때 |
|---|---|---|
| 1 | 내부 조회 엔드포인트 셋(HelpDesk · ProjMng · Notification) + 내부 토큰 | 토큰으로 curl 해서 남의 자료가 나온다 |
| 2 | `PortalToolSet` + `PortalToolRunner` (도구 단위 시험) | 도구마다 조건을 주면 맞는 줄이 나온다 |
| 3 | `AssistantAgent` 도구 루프 + 기록 표 | 세 질문 예시가 끝까지 답이 된다 |
| 4 | 화면 + 메뉴 + 권한 | 임원 계정으로 열리고 다른 계정은 막힌다 |
| 5 | 실측 — 예시 질문 20개로 맞는지·몇 초 걸리는지 | 아래 「재는 것」 |

## 재는 것

RAG 를 세울 때 실측으로 갈랐던 것처럼, 여기도 숫자로 본다.

- **맞음**: 예시 질문 20개(일정 · 과거 · 문서 · 섞인 것 각 5). 사람이 손으로 찾은
  답과 맞는지. 숫자 하나라도 다르면 틀린 것으로 센다.
- **빠뜨림**: "10-17일 이후 전부" 에 실제 몇 건 중 몇 건을 집었나.
- **지어냄**: 자료에 없는 질문 5개를 섞는다. "모른다" 가 안 나오면 실패다.
- **시간**: 질문 하나에 몇 초. 30초를 넘으면 도구 라운드 수를 줄인다.

## 아직 안 정한 것 — 만드는 사람이 정한다

- 도구 루프 최대 라운드 수. `Mcp:MaxToolRounds` 가 4 다. 세 시스템을 도는
  질문은 더 필요할 수 있다 — 실측해서 정한다(6 쯤으로 시작).
- `search_mails` 가 보는 것이 「보낸 메일함」인지 「발송 기록」인지, 아니면 둘 다인지.
  `docs/mail-send.md` 가 둘을 가르고 있다. 먼저 자료를 보고 정한다.
- 일정이 두 군데(프로젝트관리 WBS · 헬프데스크 `Schedules`)에 있다. 한 도구로
  합쳐 줄지 나눌지. 합치는 쪽을 권한다 — 묻는 사람은 어디에 있는지 모른다.
- 동명이인 처리. `find_user` 가 여럿을 돌려줬을 때 모델이 되묻게 할지, 전부
  훑을지.

## 내가 정한 것 — 돌려세우시면 바꾼다

문서를 처음 읽는 사람 눈으로 다시 훑어 보니, 답이 없으면 못 짓는 자리가 셋
남아 있었다. 더 묻지 말라 하셔서 내 판단으로 메우고 여기 적어 둔다.

**1. 회사 경계도 넘는다.** 포털은 회사가 여럿이고(`scom.companies`) RAG
카테고리마저 회사별로 갈린다(`company_id`). 임원이 **다른 회사** 자료까지
보느냐가 안 정해져 있었다. 권한을 넘기로 한 것의 자연스러운 연장으로 보고
**회사를 가리지 않는다**로 둔다. 회사별로 막아야 하면 도구마다 회사 조건이
하나씩 더 붙는다 — 되돌리기 어렵지 않지만 지금 정해 두는 편이 낫다.

**2. "홍길동의 내용" 은 쓴 것 · 맡은 것 · 댓글 단 것 전부다.** 헬프데스크는
글쓴이(`Customer`)와 담당자(`Admin`)가 다른 표이고 포털 사용자와는
`AuthUserLink` 로 이어진다. 묻는 사람은 그 구분을 모르고 묻는다. 셋을 다
모아 **무엇으로 걸렸는지 표시해서** 돌려준다(`쓴 글` · `맡은 글` · `댓글`).

**3. 메일은 보낸 사람 기준으로, 보낸 메일함과 발송 기록을 함께 본다.**
`docs/mail-send.md` 가 둘을 가르고 있지만 묻는 쪽에는 같은 "홍길동이 보낸
메일" 이다. 받은 메일은 포털에 없다(메일 수신함은 이 시스템이 아니다) —
그래서 "홍길동에게 온 메일" 은 **답할 수 없다고 말한다.**
