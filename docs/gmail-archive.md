# Gmail 보관함 — 받아 오는 길 셋과 겹침을 지우는 열쇠

업무 비서가 메일까지 가로질러 답하게 하려고 Gmail 을 포털 DB 로 받아 온다.
받는 계정은 **본인 둘**이다 — Workspace(`syl@imrbiz.co.kr`)와 개인(`quristyle@gmail.com`).

표는 `deploy/sql/gmail-archive-2026-10-25.sql`, 코드는
`microservices/AIAgentServer/Services/Gmail/`.

## 왜 길이 셋인가 — 계정 종류가 인증을 가른다

`gmail.readonly` 는 구글이 **제한된 스코프**로 묶어 둔 것이라, 쓰려는 계정이
어디 속하느냐에 따라 길이 통째로 달라진다.

| 계정 | 길 | 까닭 |
|---|---|---|
| Workspace `@imrbiz.co.kr` | Gmail API | 동의 화면을 **내부(Internal)** 로 두면 구글 심사가 면제되고 리프레시 토큰이 안 죽는다 |
| 개인 `@gmail.com` | IMAP + 앱 비밀번호 | 내부 앱으로 동의할 수 없고, 외부 앱은 제한 스코프라 **보안 심사(CASA)** 에 걸린다 |
| 둘 다 (과거분) | Takeout mbox | API 할당량을 안 쓰고 과거 전체를 한 번에 붓는다 |

**동의 화면을 「외부」로 두면 테스트 상태에서 리프레시 토큰이 7일 만에 죽는다.**
배치가 일주일마다 조용히 멎으므로, Workspace 쪽은 반드시 내부로 둔다.

`imrbiz.co.kr` 이 Workspace 인 것은 MX 로 확인했다(`aspmx.l.google.com`).

## 겹침은 `Message-ID` 로 지운다

길 셋이 한 표(`scom.gmail_messages`)에 쌓인다. Takeout 을 내보낸 시점과 증분이
시작된 시점 사이는 **반드시 겹치므로** 겹침을 가를 열쇠가 필요하다.

그 열쇠는 헤더의 `Message-ID`(`rfc822_message_id`)다 — 보낸 서버가 붙이고 길이
달라져도 안 바뀐다. 반대로 **Gmail 메시지 id 와 IMAP UID 는 같은 메일에도 서로
다른 번호**라 겹침을 못 가른다. 그래서 고유 색인은
`(account_id, rfc822_message_id)` 에 건다.

### 열쇠가 하나도 없는 메일

`Message-ID` 가 없는 메일이 드물게 있다(직접 만든 메일 · 아주 옛 메일).
부분 고유 색인은 NULL 에 안 걸리므로, 그대로 두면 **같은 파일을 두 번 적재할 때
그런 메일만 줄이 불어난다.** 실제로 그렇게 됐다(1회차 1통 → 2회차에 또 1통).

그래서 `Message-ID` 도 `X-GM-MSGID` 도 없으면 보낸이·날짜·제목·본문 머리(4KB)를
섞어 **내용 지문**(`sha256:…`)을 만들어 `provider_msg_id` 에 넣는다. 같은 메일이면
같은 값이 나오므로 두 번째 적재가 걸러진다.

## 적재가 서버 파일을 읽는다 — 폴더를 못 벗어나게 묶었다

Takeout mbox 는 GB 단위라 HTTP 로 올리지 않고 서버 디스크에 둔다. 그래서 적재
엔드포인트는 **경로가 아니라 파일 이름**만 받고, 설정(`Gmail:ImportRoot`)에 적힌
한 칸 안에서만 푼다. 설정이 비어 있으면 적재 자체가 막힌다(열어 두는 쪽이 아니라
막는 쪽이 기본이다).

`../` 가 섞인 이름과 절대 경로는 이름 단계에서 거절한다. 계정의
`owner_login_id` 와 부르는 사람이 다르면 **남의 메일함에 붓지 못한다.**

## 누가 누구 메일을 보는가

지금은 본인 둘만 받으므로 모으는 것 자체는 문제가 없다. 그런데 **업무 비서는
슈퍼관리자·임원이 함께 쓰는 화면**이고, 설계상 묻는 사람의 평소 권한을 넘어서
답한다([portal-ai-assistant.md](portal-ai-assistant.md)).

그래서 `search_gmail` 도구만은 다른 도구들과 달리 **`account_id` 를 묻는 사람이
주인인 계정으로 좁혀야 한다.** 그러지 않으면 다른 임원이 이 사람의 개인 메일을
읽는다. `gmail_accounts.owner_login_id` 가 그 열쇠다.

## 화면 — 포털관리 › 시스템 › 「Gmail 보관함」

`/admin/ai/gmail` (`admin.ai.gmail` · 메뉴 `SYS_GMAIL_ARCHIVE`). **시스템관리자에게만**
열려 있다(`deploy/sql/gmail-archive-menu-2026-10-25.sql`) — 다루는 것이 사람의 메일
원본이라, 메일함마다 주인이 있는 것(`owner_login_id`) 앞에 메뉴 권한으로 한 번 더 좁힌다.

단계가 순서대로라 세로로 쌓는다.

| 자리 | 하는 일 |
|---|---|
| 조회줄 | 메일함 고르기 · 메일함 등록 |
| 1. mbox 파일 | 적재 폴더의 목록 · 줄마다 **적재** · 브라우저로 올리기(크기 제한 없음) |
| 진행 띠 | 읽음 · 넣음 · 겹침 · 실패 (2초마다 되묻는다. **끝난 뒤에도 남는다**) |
| 2. RAG 문서 만들기 | 올릴 **카테고리와 분류** · 한 번에 몇 통 · 실행 |
| 쌓인 메일 | 메일함 x 받은 길별 통수와 기간 |

### 올리기에 크기 제한을 두지 않는다

Takeout 은 메일함 하나가 GB 단위다. 숫자를 박으면 **그 자리가 곧 막히는 자리**가
되므로 네 자리를 모두 풀었다 — 어느 자리에도 파일이 통째로 쌓이지 않기 때문에
풀어도 되는 것이다.

| 자리 | 전 | 지금 |
|---|---|---|
| 고르개(`FilePicker`) | 300MB | `MaxBytes = 0` = 제한 없음. DevExpress 도 0 이 「무제한」이다 |
| 포털 → 게이트웨이 | 30분 | 시간을 재지 않는다 — 재면 그 숫자가 곧 크기 상한이다 |
| 게이트웨이 | 1GB | **이 경로만** 푼다(`/api/ai/gmail/import/upload`). 다른 길은 그대로 1GB |
| AIAgentServer | Kestrel 30MB · 폼 128MB | 이 요청만 푼다 |

**`ReadFormAsync` 를 쓰면 안 된다.** `FormOptions.MultipartBodyLengthLimit`(기본
128MB)에 걸리고, 넘지 않더라도 본문을 통째로 받아 둔 뒤에야 돌려준다.
`MultipartReader` 로 조각을 직접 읽어 그대로 파일에 붓는다 — 메모리에 남는 것은
버퍼 한 칸(1MB)뿐이다.

**재어 확인했다**(2026-10-25): 200MB 를 직접 넣어 1.0초, 게이트웨이를 거쳐 0.9초.
바이트 수가 정확히 같다(209,715,519). 옛 한도로는 30MB 에서 413 이었다.

> 그래도 **GB 단위는 서버의 적재 폴더에 직접 두는 쪽이 훨씬 빠르다.** 브라우저로
> 올리면 회로 → 셸의 임시 파일 → 게이트웨이 → 적재 폴더로 네 번을 거친다.
- **진행 띠는 끝난 뒤에도 남는다.** 사라지면 몇 통이 들어갔는지 알 수 없다.
- **되묻기는 상태만 한다.** 적재가 도는 동안 파일·통계까지 매번 읽으면 긴 적재에서
  DB 를 쓸데없이 긁는다 - 끝난 뒤 한 번만 다시 읽는다.

### 분류까지 골라 올린다

RAG 문서함은 카테고리 아래에 분류(폴더) 나무를 둔다. 문서를 카테고리 바로 아래에만
쌓으면 메일이 수백 장씩 들어오는 순간 그 카테고리의 다른 자료가 묻힌다.

- **카테고리를 바꾸면 분류를 다시 읽고 고른 분류를 버린다.** 안 버리면 다른
  카테고리의 분류 번호가 그대로 올라가고, 서버가 거절하므로 「분류를 골랐는데
  안 된다」가 된다.
- **분류가 없는 카테고리에서는 고르개를 아예 안 세운다.** 고를 것이 없는 칸이다.
- **고르개는 나무를 「상위 › 하위」로 펴서 한 줄씩 보여 준다.** 깊이를 안 보이면
  이름만 같은 분류가 여럿일 때 어느 것인지 알 수 없다.
- **분류를 안 고르면 카테고리 바로 아래**로 간다(전과 같다).

**서버가 그 분류가 그 카테고리의 것인지 다시 본다.** 화면만 믿으면 남의 카테고리
폴더에 메일을 넣을 수 있고, 그 문서는 고른 적 없는 카테고리의 색인에 들어가
거기서 검색된다. 실제로 걸어 보니 「고른 분류가 그 카테고리의 것이 아닙니다」로
막힌다(2026-10-25 실측).

### 메뉴를 SQL 로 넣으면 AuthServer 를 다시 올려야 보인다

AuthServer 가 메뉴 나무를 통에 담아 두고(`MenuTreeCache`), 그 통은 **메뉴 관리
화면으로 고칠 때만** 비워진다. `deploy/sql` 로 직접 넣으면 통이 그대로라 화면이
「이 화면을 열 권한이 없습니다」로 막힌다 - 표에는 줄이 멀쩡히 있어서 DB 만 보면
원인이 안 보인다. 실제로 이 메뉴에서 한 번 밟았다.

운영에 올릴 때도 같다: 메뉴 SQL 을 돌린 뒤 **auth 컨테이너를 다시 올린다.**

## 찾는 길 둘 — 가르지 않고 겹쳐 둔다

```
Takeout mbox ─┐                       ┌→ search_gmail 도구 (날짜·보낸이·낱말)
Gmail API ────┼→ scom.gmail_messages ─┤
IMAP ─────────┘                       └→ 오래된 것은 RAG 문서로도 묶어 색인
```

처음에는 「최근은 도구, 오래된 것은 RAG」로 **가를** 생각이었으나, 그렇게 하지
않았다. 보관해도 표에서 지우지 않으므로(`rag_doc_id` 만 찍는다) 도구는 그 뒤로도
전 기간을 날짜·낱말로 찾을 수 있고, **도구를 일부러 눈감게 할 까닭이 없다.**

둘은 서로를 대신하는 것이 아니라 못 하는 일이 다르다.

- **도구**는 「10월 이후」 같은 **범위 질의**와 **최신성**을 맡는다. 벡터 검색은
  날짜로 자르지 못하고, 새 메일은 색인될 때까지 안 보인다.
- **RAG** 는 **낱말이 안 떠오르는 질문**을 맡는다. 「작년에 계약 관련해서 뭐라고
  했더라」는 낱말 검색에 안 걸린다.

## `search_gmail` 은 본인 메일함만 본다

업무 비서의 다른 도구들은 묻는 사람의 평소 권한을 넘어서 답한다. 메일만은 그러면
안 된다 — 슈퍼관리자·임원이 함께 쓰는 화면이라 범위를 안 좁히면 다른 임원이 이
사람의 개인 메일을 읽는다.

그래서 이 도구에는 **계정을 받는 인자가 아예 없다.** 모델이 범위를 정할 길을
두지 않고, 서버가 `gmail_accounts.owner_login_id` 로 좁힌다. 메일함이 하나도 없는
사람에게는 「없다」가 아니라 **「메일함이 없다」**고 답한다 — 둘을 같게 말하면
모델이 "메일이 없다"고 단정한다.

## 증분 — 길 둘이 표식도 다르다

`POST /gmail/sync` 하나가 계정의 `kind` 를 보고 수집기를 고른다.

| | 이어받는 표식 | 끊겼을 때 |
|---|---|---|
| Gmail API | `last_history_id` | 이력 번호가 만료되면(404) 표식을 비우고 **다음 번에 처음부터** |
| IMAP | `last_uid` + `uid_validity` | `UIDVALIDITY` 가 바뀌면 UID 가 딴 메일을 가리키므로 **처음부터** |

둘 다 처음부터 다시 받아도 줄이 안 불어난다 — 겹침은 `Message-ID` 가 지운다.
그래서 「애매하면 다시 받는다」를 안전하게 고를 수 있다.

**첫 수집에서 이력 번호를 목록보다 먼저 잡는다.** 목록을 다 훑은 뒤에 잡으면 그
사이 들어온 메일이 목록에도 증분에도 안 걸려 영영 빠진다.

**API 는 `format=raw` 로 받는다.** 파싱된 JSON 을 받으면 길마다 다른 모양을 따로
풀어야 하지만, raw 는 그냥 MIME 이라 Takeout·IMAP 과 똑같이
`MailNormalizer` 하나를 탄다 — 겹침 열쇠도 같은 자리에서 나온다.

**IMAP 은 「전체보관함」(`\All`) 한 곳만 읽는다.** Gmail 의 IMAP 은 라벨을 폴더로
보여 주므로 폴더를 모두 돌면 라벨이 둘 붙은 메일이 두 번 걸린다. 폴더 이름은 계정
언어에 따라 다르므로(`[Gmail]/전체보관함` · `[Gmail]/All Mail`) 이름이 아니라
특별 폴더 표시로 찾는다.

## 실측 (2026-10-25, 개발 장비)

까다로운 자리를 섞은 mbox 6통으로 쟀다.

| 본 것 | 결과 |
|---|---|
| 겹친 메일(같은 Message-ID 둘) | 읽음 6 · **넣음 5** · 겹침 1 |
| 같은 파일 재적재 | 읽음 6 · **넣음 0** · 겹침 6 |
| 라벨에 든 쉼표(`"프로젝트, 중요"`) | 한 라벨로 보존 — 단순 `Split(',')` 이면 둘로 쪼개진다 |
| HTML 만 있는 메일 | 태그·script·style 을 걷고 글자 본문 생성 |
| 날짜 헤더가 깨진 메일 | `sent_at` 이 NULL (엉뚱한 값을 넣지 않는다) |
| 한국 시각 헤더 | UTC 로 변환(09:00+09:00 → 00:00Z) |
| 첨부 | 이름·형식·크기만 (실물 바이트는 안 받는다) |
| 폴더 밖 경로(`../../etc/passwd`) | 거절 |
| 남의 메일함에 붓기 | 거절 |

`search_gmail` 과 RAG 보관은 메일함 둘(본인 것 5통 · 남의 것 1통)로 쟀다.

| 본 것 | 결과 |
|---|---|
| 본인이 제 메일을 찾기 | 보낸이로 2건 정확히 ✓ |
| 본인이 **남의** 메일을 낱말로 찾기 | 못 찾음 ✓ |
| 남이 제 메일을 찾기 | 제 것 1건만 ✓ |
| 메일함이 없는 사람 | 「연결된 메일함이 없다」로 갈라 답함 ✓ |
| 보관 배치 | 6개월 지난 2통 → 달별 문서 2장, `rag_doc_id` 찍힘 ✓ |
| 보관 재실행 | 0건 (이미 올린 것은 안 집는다) ✓ |
| 보관된 메일을 RAG 로 묻기 | 「개당 단가 1,200원」을 문서 인용과 함께 답함 ✓ |

## 아직 안 된 것

- **증분 수집기 둘은 짰지만 <span>한 번도 못 돌려 봤다</span>.** 구글 자격이
  아직 없어서다(`Gmail__OAuth__*`, `Gmail__Credentials__*`). 자격 없이 부르면
  터지지 않고 「무엇이 없다」를 말하는 것까지만 확인했다. **자격이 들어온 뒤
  첫 수집은 반드시 `maxMessages` 를 작게 주고(예: 10) 결과를 눈으로 본다.**
- **`Rag:MinVectorScore` 가 0.60 이라 보관한 메일이 잘 안 걸린다.** 위 실측에서
  「개당 단가」 질문은 문턱을 0.25 로 낮춰야 답했다. 메일 토막은 짧고 말투가
  일상적이라 규정 문서보다 점수가 낮게 나온다. 그 문턱은 **지어냄을 막으려고**
  올려 둔 값이라(`PortalToolRunner.MinScore` 머리말) 함부로 내리면 안 되고,
  메일 카테고리에만 따로 문턱을 두는 쪽이 맞다. **아직 안 했다.**
- **보관 배치를 부르는 것이 아직 사람이다.** `POST /gmail/archive` 를 0 이
  돌아올 때까지 불러야 한다. 주기 실행이 없다.
- **본문을 자르지 않고 담는다.** 전체 과거를 받으면 수 GB 가 될 수 있다. RAG 로
  옮긴 줄(`rag_doc_id` 가 찬 줄)은 `body_html` 을 비워 자리를 아낄 수 있는데,
  그 비우는 배치가 아직 없다.
- **첨부 실물은 안 받는다.** 이름·형식·크기만 담는다. 첨부 안의 글까지 찾으려면
  따로 받아 RAG 에 넣어야 한다.
