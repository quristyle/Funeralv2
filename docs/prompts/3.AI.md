# 프로젝트 디렉터리 레이아웃 (Directory Layout)

이 섹션은 FuneralV2 프로젝트의 전체 구조와 각 구성 요소의 역할을 정의합니다. AI 에이전트는 파일 생성 및 수정 시 이 레이아웃을 반드시 준수해야 합니다.

## 1. 전체 구조 (Global Structure)
```text
/home/quri/Funeralv2/
├── ApiGateway/             # .NET Ocelot 기반 API 게이트웨이
├── microservices/          # 백엔드 마이크로서비스 모음
│   ├── Common/             # 공통 공유 라이브러리 (Shared Kernel)
│   ├── AuthServer/         # 인증 및 시스템 관리 서비스
│   └── funeralv2Api/       # 장례식장 도메인 핵심 비즈니스 서비스
├── fronts/                 # Vue3 기반 프론트엔드 모노레포
│   ├── apps/               # 실행 가능한 웹 애플리케이션 (funeralv2)
│   ├── packages/           # 재사용 가능한 내부 패키지 (@core, ui-kit 등)
│   └── internal/           # 빌드 및 린트 설정 패키지
├── docs/                   # 프로젝트 문서 및 가이드라인

```

## 2. 백엔드 마이크로서비스 레이아웃 (Backend Layout)
각 마이크로서비스는 다음과 같은 통일된 구조를 가집니다.

```text
microservices/[ServiceName]/
├── Program.cs              # 애플리케이션 진입점 및 의존성 주입(DI) 설정
├── appsettings.json        # 환경 설정 파일
├── Entities/               # 데이터베이스 테이블 매핑 객체 (Shared.Domain 상속)
├── DTOs/                   # 데이터 전송 객체 (Request/Response 모델)
├── Services/               # 비즈니스 로직 처리 인터페이스 및 구현체
├── Endpoints/              # Minimal API 엔드포인트 정의 (라우팅)
├── Data/                   # DbContext 및 마이그레이션 설정
└── Properties/             # 실행 환경 설정 (launchSettings.json)

microservices/Common/       # 공유 라이브러리
├── Funeralv2.Shared.Domain/# 전역 엔티티 베이스, Enum, 상수
└── Funeralv2.Shared.DTOs/  # 전역 ApiResponse, 공통 DTO, Mapster 설정
```

1. **위치 선정**: 새로운 기능을 추가할 때 위 레이아웃에서 가장 적합한 위치를 먼저 선정합니다. (예: 시스템 공통 모델은 `Common`, 특정 도메인 로직은 해당 서비스의 `Services`)
2. **일관성 유지**: 기존 파일들의 네이밍 규칙(예: `[Name]Service.cs`, `[Name]Dto.cs`)을 그대로 따릅니다.
3. **참조 관계**: 개별 서비스는 반드시 `Common` 프로젝트를 참조하여 공통 기능을 재사용해야 합니다.
4. **문서화**: 새로운 디렉터리나 중요한 구조 변경이 발생할 경우 이 가이드를 즉시 업데이트합니다.
5. **코드 무결성 유지 (중요)**: TypeScript 코드(`api/*.ts`, `data.ts` 등)나 컴포넌트를 수정할 때 `replace` 도구를 사용함에 있어 **기존에 존재하는 함수, 변수, export 구문을 절대 누락하거나 덮어쓰지 않도록 각별히 주의**해야 합니다. 새로운 함수를 추가할 때는 파일의 끝이나 논리적으로 적합한 빈 공간에 "삽입"하는 방식을 취해야 합니다.
6. **다크 모드 및 테마 대응 (중요)**: UI 개발 시 `bg-white`, `text-black`과 같은 절대적 색상 클래스 사용을 엄격히 금지합니다. 반드시 프로젝트의 테마 시스템(`tailwind-config`)에서 제공하는 시맨틱 클래스를 사용해야 합니다.
   - 배경색: `bg-card`, `bg-background`, `bg-muted` 등
   - 텍스트색: `text-card-foreground`, `text-foreground`, `text-muted-foreground` 등
   - 테두리색: `border-border`
   - 브랜드색: `bg-primary`, `text-primary-foreground`
   이를 통해 다크 모드 전환 시 UI가 자동으로 대응되도록 작성해야 합니다.
7. **반응형 디자인 및 모바일 최적화 (중요)**: 프론트엔드의 모든 화면은 모바일 기기를 포함한 다양한 해상도에서 완벽하게 동작하도록 반응형으로 설계되어야 합니다. 모바일 화면에서 복잡한 테이블(VXETable 등)은 가로 스크롤을 최소화하고, 그리드 레이아웃은 수직으로 쌓이도록 유연하게 대응하며, 폼 입력 필드 및 버튼 등은 터치 조작이 편리하도록 크기와 레이아웃을 최적화하여 작성해야 합니다.
8. **데스크탑/모바일 화면 분리 설계 (중요)**: 데스크탑과 모바일 화면의 레이아웃이 상이하여 단일 Vue 파일 내에 함께 작성하기 어려울 때는 다음 폴더 구성을 적용하여 로직과 뷰를 분리해 관리해야 합니다.
   - `composables/use-[feature].ts`: 모든 비즈니스 데이터 로직 및 상태 관리 (SRP 준수)
   - `modules/[feature]-desktop.vue`: 데스크탑 전용 레이아웃 컴포넌트
   - `modules/[feature]-mobile.vue`: 모바일 전용 레이아웃 컴포넌트
   - `list.vue` (혹은 메인 화면): 해상도 감지 및 데스크탑/모바일 컴포넌트 스위칭 엔트리 포인트
   이를 통해 비즈니스 로직의 중복을 막고 가독성과 독립성을 향상시킵니다.
   - **모바일 마스터-디테일(1:N) 레이아웃**: 마스터-디테일 형태의 복잡한 화면을 모바일용으로 구현할 때는 수평 분할이나 단순 탭 분리 대신 **Drill-Down 방식**(마스터 목록 전체 노출 -> 클릭 시 상세 디테일 목록 화면으로 슬라이드/전환 및 뒤로가기 버튼 제공)을 적극 적용하여 좁은 모바일 가로폭을 100% 활용하도록 설계해야 합니다.

# 다국어(i18n) 시스템 관리 가이드

본 프로젝트는 **Vben Admin** 프레임워크를 기반으로 하며, 초기 로딩 성능을 보장하면서도 운영 중 실시간으로 번역문을 수정할 수 있도록 **로컬 JSON 파일과 데이터베이스(DB)를 병합하는 하이브리드 방식**을 채택하고 있습니다.

## 1. 다국어 처리 개념 (Hybrid Architecture)

1.  **초기 로딩 (Fast Boot):** 앱 시작 시 `src/locales/langs` 하위의 JSON 파일을 즉시 로드하여 화면을 렌더링합니다. (네트워크 지연 없음)
2.  **동적 동기화 (Dynamic Sync):** 앱 로딩 직후, 백그라운드에서 백엔드 API를 호출하여 DB에 저장된 최신 번역 정보를 가져옵니다.
3.  **데이터 병합 (Merge):** DB 정보를 로컬 메시지에 병합(`mergeLocaleMessage`)하며, 동일한 키가 있을 경우 **DB 정보가 우선순위**를 가집니다.
4.  **실시간 반영 (Reactivity):** 병합된 데이터를 즉시 화면에 반영하기 위해 `i18n` 인스턴스의 로케일을 일시적으로 전환하여 전역 리렌더링을 유도합니다.

---

## 2. 데이터베이스 구조 (Backend)

### 테이블: `scom.i18n_resources`
다국어 자원은 평면적인 키(Dot Notation) 구조로 관리됩니다.

| 컬럼명 | 타입 | 설명 | 예시 |
| :--- | :--- | :--- | :--- |
| `key` | VARCHAR | 다국어 식별 키 | `common.operation`, `vxe.pager.total` |
| `locale` | VARCHAR | 언어 코드 | `ko`, `en-US` |
| `value` | TEXT | 번역된 문구 | `작업`, `전체 {0} 건` |
| `category`| VARCHAR | 관리 분류 | `common`, `vxe`, `system` |

### 주요 엔드포인트 (`AuthServer`)
-   `GET /auth/system/i18n/paged`: 페이징 및 필터링 검색
-   `GET /auth/system/i18n/{locale}`: 특정 언어 전체 조회
-   `POST/PUT/DELETE /auth/system/i18n`: CRUD 관리

# AI 번역 작업 가이드 (i18n Automation Guide)

이 문서는 AI 에이전트가 프론트엔드 코드의 텍스트를 번역 키로 전환하고, 필요한 번역 데이터를 DB에 자동으로 반영하기 위한 지침서입니다.

## 1. DB 정보 및 스키마 (Context)

### 테이블 구조
번역 데이터는 PostgreSQL의 `scom.i18n_resources` 테이블에 보관됩니다.

### DB 연결 정보 확인 방법
DB 연결 문자열은 다음 파일에서 확인할 수 있습니다.
- 파일 경로: `microservices/AuthServer/appsettings.Local.json`
- 주요 항목: `ConnectionStrings.jsinicore` (Host, Port, Database, Username, Password 확인)

## 2. 번역 작업 절차 (Workflow)

AI는 번역 요청을 받으면 다음 단계를 순차적으로 수행해야 합니다.

### 단계 1: 코드 분석 및 키 추출
1. 대상 파일에서 하드코딩된 텍스트를 식별합니다.
2. 기존 번역 키 컨벤션을 준수하여 새로운 키를 명명합니다.
   - 공통 요소: `common.xxxx`
   - UI 요소: `ui.[화면명].[요소명]`
   - 메시지: `ui.actionMessage.[상태]`

### 단계 2: 프론트엔드 코드 수정
- 식별된 텍스트를 `$t('key')` 또는 `{{ $t('key') }}` 형태로 교체합니다.

### 단계 3: SQL 생성 및 보관
- `docs/` 폴더 내에 작업 단위별 SQL 파일을 생성합니다 (예: `docs/[오늘날짜]i18n_feature_name.sql`).
- SQL에는 `ko-KR`과 `en-US` 데이터를 모두 포함하며, 중복 방지를 위해 `DELETE` 구문을 선행합니다.

### 단계 4: DB 직접 반영
- `psql` 명령어를 사용하여 원격 DB에 직접 쿼리를 실행합니다.
- 실행 예시: `PGPASSWORD=xxxx psql -h [Host] -p [Port] -U [User] -d [DB] -f docs/xxxx.sql`

# 백엔드 공유 라이브러리 가이드 (Shared Library Guide)

이 섹션은 백엔드 마이크로서비스 간의 모델 중복을 방지하고 코드 재사용성을 높이기 위한 **Shared Library** 관리 지침입니다.

## 1. 아키텍처 구조 (Architecture)

모든 서비스가 공통으로 사용하는 로직과 모델은 `microservices/Common/` 디렉토리 내에 위치합니다.

- **`Funeralv2.Shared.Domain`**: 공통 엔티티 베이스, Enum, 상수(Constants), 커스텀 예외 등 핵심 도메인 지식 관리.
- **`Funeralv2.Shared.DTOs`**: 서비스 간 통신(API, gRPC, Message Queue)에 사용되는 요청/응답 데이터 모델 관리.

## 2. 모델 관리 원칙 (Model Management Rules)

AI 에이전트는 새로운 모델을 생성하거나 수정할 때 다음 원칙을 준수해야 합니다.

### 2.1 엔티티(Entity) 관리
- **중복 방지**: 여러 서비스에서 공통으로 필요한 데이터 속성(예: `Id`, `CreatedAt`, `CreatedBy`)은 `Shared.Domain`의 `BaseEntity`에 정의합니다.
- **서비스 격리**: 각 서비스의 고유한 비즈니스 엔티티는 해당 마이크로서비스 내부에 정의하되, 필요 시 `BaseEntity`를 상속받습니다.
- **DB 공유 금지**: 마이크로서비스 원칙에 따라 엔티티 자체를 여러 서비스가 공유하여 같은 DB 테이블을 바라보게 하는 설계는 지양합니다.

### 2.2 DTO(Data Transfer Object) 관리
- **계약 중심**: 서비스 간에 주고받는 데이터 규격은 반드시 `Shared.DTOs`에 정의하여 변경 시 모든 관련 서비스가 인지할 수 있도록 합니다.
- **재사용성**: 페이징 처리(`PagedRequest`), 공통 응답 구조(`ApiResponse<T>`) 등은 공유 DTO 프로젝트에서 관리합니다.
- **ApiResponse 표준 사용**: 모든 API는 `Shared.DTOs.ApiResponse<T>`를 사용하여 응답을 표준화해야 합니다.

#### ApiResponse 사용 및 비즈니스 코드 지침
AI 에이전트는 응답 생성 시 다음 규칙을 따릅니다.

1.  **성공 응답**: `ApiResponse<T>.Ok(data, "메시지", "S000")`를 사용합니다.
2.  **실패 응답**: `ApiResponse<T>.Fail("메시지", "코드", errors)`를 사용합니다.
3.  **비즈니스 코드 체계**:
    - `S***` (Success): 정상 처리 (`S000`: 기본 성공)
    - `C***` (Client Error): 클라이언트 요청 오류 (`C400`: Bad Request, `C401`: Unauthorized)
    - `V***` (Validation): 입력값 검증 실패 (`V001`: 필수값 누락 등)
    - `B***` (Business): 비즈니스 로직 위반 (`B101`: 중복 데이터 등)
    - `E***` (System Error): 서버 내부 오류 (`E500`: Internal Error)
4.  **에러 상세 정보**: 유효성 검사 실패 시 `ErrorDetail` 리스트를 포함하여 어떤 필드에서 에러가 발생했는지 명시합니다.
5.  **전역 예외 처리**: 모든 마이크로서비스는 `UseGlobalExceptionHandler()` 미들웨어를 필수적으로 등록하여, 예상치 못한 런타임 예외가 발생하더라도 표준 `ApiResponse` 형식을 반환해야 합니다.

#### 객체 매핑 (Mapster) 지침
AI 에이전트는 엔티티와 DTO 간의 변환 시 Mapster를 사용합니다.

1.  **단일 객체 변환**: `source.Adapt<Destination>()`를 사용합니다.
2.  **기존 객체 업데이트**: `source.Adapt(destination)`를 사용하여 기존 객체의 속성을 덮어씁니다.
3.  **IQueryable 변환**: DB 쿼리 레벨에서 성능 최적화를 위해 `.ProjectToType<Destination>()`를 사용합니다.
4.  **공통 설정**: `Funeralv2.Shared.DTOs.MapsterConfig.Configure()`를 통해 전역 설정을 관리하며, 특수한 매핑 규칙은 해당 서비스의 초기화 시점에 `TypeAdapterConfig`를 통해 등록합니다.
5.  **순환 참조 오류 방지**: 부모-자식 관계와 같이 계층적 자가 참조를 가지는 엔티티의 매핑 시, EF Core 쿼리 단에서의 `.ProjectToType<T>()`는 컴파일 시점 순환 참조 예외(Circular Reference Exception)를 유발할 수 있습니다. 이러한 계층 구조 조회 시에는 DB에서 일반 엔티티 리스트로 선 조회(`ToListAsync()`)한 뒤 메모리 상에서 `.Adapt<List<Dto>>()`를 통해 변환하는 방식을 사용해야 하며, 전역 `MaxDepth(3)` 설정을 통해 무한 재귀 매핑을 차단해야 합니다.

## 3. 개발 프로세스 (Workflow)

1. **분석**: 신규 모델이 여러 서비스에서 쓰일 가능성이 있는지 판단합니다.
2. **이동**: 공통 모델로 판단될 경우 `Shared` 프로젝트로 코드를 이동하거나 생성합니다.
3. **참조**: 개별 서비스(`.csproj`)에서 `Shared` 프로젝트를 프로젝트 참조(Project Reference)로 추가합니다.
4. **검증**: `dotnet build`를 통해 모든 마이크로서비스가 변경된 공유 모델과 호환되는지 확인합니다.

> **AI 주의사항**: `Shared` 라이브러리를 수정할 때는 파급 효과가 크므로, 하위 호환성을 유지하거나 관련된 모든 서비스를 함께 업데이트해야 합니다.
