# 포털 보안 점검 (2026-11-27)

[security-hardening.md](security-hardening.md) 의 「남아 있는 것」에 더해, 포털 화면 · 인증 ·
게이트웨이 · 업무 서비스 · 인프라를 한 번 더 훑었다. **이번에 고친 것**과
**고치지 않고 남긴 것(개선 방향)**을 나눠 적는다.

「확인」 칸 — **실측**은 실제로 두드려 재현·검증한 것, **판독**은 코드를 읽고 판단한 것이다.

## 가장 급한 것 — DB 가 바깥에 열려 있다 (고치지 않았다)

| | 실측 값 |
|---|---|
| 듣는 자리 | `listen_addresses = '*'`, 호스트 `0.0.0.0:31015` |
| 들여보내는 곳 | `pg_hba` 126행 `host all all 0.0.0.0/0 md5` (복제 133행도 `0.0.0.0/0`) |
| 공인 주소로 닿나 | `175.200.10.40:31015` 열림 (같은 장비에서 공인 IP 로 붙어 확인 — 바깥망에서는 재지 못했다) |
| 슈퍼유저 로그인 | `funeral` `funeralv2` `ghub` `goldb` `jsini` `postgres` — 여섯 |
| 비밀번호 = 계정 이름 | `funeral` `funeralv2` `ghub` `goldb` `helpdesk` `projmng` — 여섯 (넷이 슈퍼유저) |
| 접속 기록 | `log_connections = off` — 누가 붙었었는지 남지 않는다 |

**뜻:** 인터넷의 누구든 `funeralv2/funeralv2` 로 붙으면 슈퍼유저다. 모든 DB(포털 계정 · 고인 정보 ·
헬프데스크 · 프로젝트)를 읽고 고칠 수 있고, 슈퍼유저의 `COPY … PROGRAM` 으로 **운영 서버에서
`postgres` 계정으로 명령을 돌릴 수 있다.** 앱 쪽 보안을 아무리 막아도 이 문 하나로 전부 우회된다.

**왜 여기서 고치지 않았나:** 비밀번호를 바꾸거나 `pg_hba` 를 좁히면 운영 컨테이너가 그 순간
DB 를 잃는다. 각 서비스의 접속 문자열은 `/srv/jsini/config/*/appsettings.Local.json` 에 있고
이 작업 환경에서는 읽을 수도 고칠 수도 없다. 사람이 순서를 잡아 한 번에 해야 한다.

**개선 순서 (권장):**

1. **공유기/방화벽에서 31015 포트 포워딩을 먼저 끊는다** — 서비스는 컨테이너망(172.18/19)과
   루프백으로 붙으므로 바깥 포워딩이 없어도 운영은 그대로다. 가장 싸고 가장 효과가 크다.
   바깥에서 DB 를 써야 하는 사람은 VPN 이나 SSH 터널로 붙는다.
2. `pg_hba.conf` 를 `127.0.0.1/32` · `172.16.0.0/12`(도커망) · 사내망 대역으로 좁히고
   `md5` → `scram-sha-256`. 복제 줄(133행)은 쓰지 않으면 지운다.
3. 계정마다 **긴 무작위 비밀번호**로 바꾸고 `appsettings.Local.json` / `.env` 를 함께 고친 뒤
   서비스를 재기동한다(저장소 시크릿 → `/srv/jsini/.env` → Override 열쇠로 넘기는 길).
4. 앱 계정의 `SUPERUSER` 를 걷는다(`ALTER ROLE funeralv2 NOSUPERUSER`). 서비스마다 제 DB 만 쓰는
   계정을 둔다 — 지금은 `funeralv2` 하나가 `jsiniportal` · `cargotrust` 등 여러 DB 를 연다.
5. `log_connections = on` 으로 바꿔 이후의 접속을 남긴다. 지금까지 바깥에서 붙은 흔적이 있는지는
   기록이 없어 알 수 없다 — **이미 새었다고 보고** 비밀번호와 JWT 서명 키를 함께 바꾸는 것을 권한다.

같은 줄기의 것:

- `projmng.devdbinfo` 21줄이 **대상 DB 비밀번호를 평문으로** 들고 있다(`db_pwd`). 루프백
  `127.0.0.1:5450/api/dev/sql` 은 신원 없이 그 접속으로 아무 SQL 이나 돌린다(알려진 구멍).
  비밀번호는 Data Protection 등으로 암호화해 두고, `dev/sql` 은 루프백이라도 내부 토큰을 요구한다.
- nginx 가 `wremote.jin114.co.kr` 로 **사내 PC 원격제어 시스템(192.168.219.240)** 을, `pgadm.jin114.co.kr`
  로 pgAdmin(:5050, 지금은 502)을 바깥에 내놓고 있다. 포털 범위 밖이지만 같은 장비의 입구다 —
  IP 제한이나 접근 인증(`auth_basic`·SSO)을 앞에 둔다.

## 남은 것 — 개선 방향

중요도 순. 「확인」이 **판독**인 줄은 코드를 읽고 판단한 것이라 고치기 전에 한 번 재현해 본다.

### 높음

| 무엇이 | 왜 위험한가 | 개선 방향 | 확인 |
|---|---|---|---|
| **계정 목록 개인정보** — `GET /system/account/list` 가 전 직원의 이메일 · 전화 · 마지막 로그인 IP 를 준다. 문지기는 **바꾸는 호출만** 관리자로 막고 읽기는 로그인만 본다. 게다가 「계정 관리」 메뉴가 `PARTNER` · `FUNERAL_OPERATOR` · `PARTNER_ADMINISTRATOR` 에게도 열려 있다 | 협력사 사람이 관리자 아이디·메일 목록을 받아 비밀번호 대입·재설정 피싱에 쓴다 | 읽기에도 메뉴 권한을 본다(`MenuViewAccess` 처럼). 협력사 역할에는 **자기 회사 계정만** 돌려주고 IP·전화는 관리자에게만. 역할마다 그 메뉴가 꼭 필요한지 먼저 정한다 — 그냥 막으면 그 사람들의 화면이 깨진다 | 실측(DB 권한표) + 판독 |
| **아이디 혼동** — 여러 곳이 `a.UserId == x \|\| a.Id == x` 로 계정을 찾는다. 가입은 `UserId` 중복만 본다 | 남의 계정 `Id`(위 목록에서 보인다)를 아이디로 가입하면 프로필·메일 인증이 그 사람 줄을 집을 수 있다 | `UserId` 로만 찾는다. 아이디에 GUID 꼴을 금지한다 | 판독 |
| **RAG 검색이 회사 경계를 안 본다** — `GET /rag/search` 는 카테고리를 안 주면 전 회사 문서를 뒤진다. `/rag/reindex` 는 누구나 전체 재색인을 건다 | 다른 회사 문서 내용이 샌다 · 임베딩 서버를 묶어 둔다 | `/chat/stream` 이 쓰는 `ChatCategoriesAsync(user)` 를 같이 건다. 재색인은 관리자만 | 판독 |
| **헬프데스크 대시보드** — `all-admin-stats` · 기여 통계 · `/push-logs`(모든 사람의 푸시 제목·본문) 가 로그인만 본다. 첨부 올리기는 남의 요청글에도 붙일 수 있고 WBS 다이어그램은 누구나 덮어쓴다 | 남의 알림 내용 열람 · 남의 글 훼손 | 각 처리기에 `RequireAdmin()` · 올리기는 글 주인/담당자/관리자만 | 판독 |
| (이미 알려진 것) 장례식장 API 회사 경계 · 익명 장비 허브 · ProjMng `$이름` SQL 주입 · 루프백 `dev/sql` | [security-hardening.md](security-hardening.md) 「남아 있는 것」 그대로 | 그쪽 순서대로 | — |

| 무엇이 | 개선 방향 | 확인 |
|---|---|---|

### 낮음

- 대리 로그인 창이 **바깥에 열린 로그인 화면**에 있다. 관리자 비밀번호를 맞춰 보는 길이 하나 더 있는 셈이다 —
  로그인한 관리자 화면으로 옮기거나 사내 IP 로 묶는다.
- 가입 화면이 「이미 있는 아이디」 · 「다른 사람의 메일」을 알려 준다(계정 존재 노출).
- 게이트웨이가 모든 경로에 본문 1GB 를 받는다 — 기본을 낮추고 올리기 경로만 키운다.
- 소셜 로그인 상태 쿠키가 `Secure = Request.IsHttps` 에 기댄다 — 운영은 늘 `Secure`, 포털 컨테이너에 `Portal__BaseUrl` 을 준다.
- `funeralv2Api/appsettings.Development.json` 에 쓰이지 않는 JWT 키가 남아 있다 — 지운다.
- nginx 가 판(`Server: nginx/1.24.0`)을 알린다 — `server_tokens off`. CSP 는 DevExpress · Monaco 때문에
  `Content-Security-Policy-Report-Only` 로 먼저 걸어 보고 좁힌다.
- HSTS 가 30일(`max-age=2592000`)이다 — 1년으로.

## 막혀 있음을 확인한 것 (다시 찾지 않아도 된다)
