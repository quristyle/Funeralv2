# 로그인 세션 · 계정 잠금 · 이메일 인증번호 (2026-11-27)

[security-audit-2026-11-27.md](security-audit-2026-11-27.md) 의 「설계를 바꿔야 하는 것」 넷 중
셋이 AuthServer 의 일이라 여기 모은다(넷째인 본문 거르개는 그 문서의 표에 있다).

## 토큰은 세션을 가리킨다

| | 전 | 지금 |
|---|---|---|
| 접근 토큰 수명 | 7일 (`Auth:AccessTokenDays`) | **15분** (`Auth:AccessTokenMinutes`) |
| 갱신 토큰 | 서명만 본다 — DB 에 없다 | `SessionId` 클레임 → `scom.auth_sessions` 한 줄 |
| 로그아웃 | 셸 쿠키만 지웠다 | 셸이 `POST /api/auth/logout` 을 불러 **세션을 닫는다** |
| 비밀번호 변경·재설정·관리자 초기화 | 비밀번호 시각으로 갱신만 거절 | 그 계정의 세션을 **전부 닫는다** |
| 세션 없는 옛 토큰 | — | 게이트웨이가 거절(`Id` 는 있는데 `SessionId` 가 없는 토큰) |

- 세션을 닫으면 **갱신이 거절되고**, 이미 나간 접근 토큰은 15분 안에 죽는다. 게이트웨이가
  요청마다 DB 를 묻지는 않는다 — 그 15분이 「즉시」 대신 받아들인 값이다.
- 세션의 끝(`expires_at`)은 로그인 때 정해지고 **갱신해도 늘지 않는다**(30일). 갱신 토큰도
  그 시각을 넘지 않게 잘린다.
- **배포 순간 모두가 한 번 다시 로그인한다.** 그 전에 나간 7일짜리 토큰과 갱신 쿠키에는
  세션이 없어서 게이트웨이와 `/refresh` 가 둘 다 거절한다. 일부러 그렇게 두었다 — 새었을지
  모르는 토큰을 그대로 받아 주면 고친 뜻이 없다.
- 셸의 인증 쿠키(8시간 미끄럼 · 「로그인 유지」 30일)는 그대로다. 그 안에 든 갱신 쿠키로
  `AuthTokenHandler` 가 15분마다 조용히 새 토큰을 받는다.

### 갱신 토큰을 한 번 쓰고 버리게(회전 + 재사용 감지) 하지 않은 까닭

셸(BFF)은 **로그인 때 받은 갱신 쿠키를 인증 쿠키 안에 넣고 계속 그것으로 갱신한다.**
갱신 응답의 새 쿠키는 메모리(`RefreshedTokens`)에만 두는데 그 통은 셸을 다시 띄우면
비워진다. 한 번 쓰면 버리게 하면 배포·재기동 때마다 옛 쿠키가 「재사용」으로 읽혀
**모두의 세션이 끊긴다.** 갱신 쿠키는 브라우저로 내려가지 않고 셸의 암호화된 인증 쿠키
안에만 있으므로, 세션 폐기로 막는 것을 택했다.

### 실측 (시험 기동 AuthServer + 운영 DB, 버리는 계정)

로그인 → `SessionId` 가 실린 15분 토큰 · 같은 갱신 쿠키로 갱신 두 번 200(셸 방식) ·
로그아웃 → 같은 쿠키 갱신 401, 줄에 `LOGOUT` · 세션 둘을 연 뒤 한쪽에서 비밀번호 변경 →
다른 쪽 갱신 401, 두 줄 다 `PASSWORD_CHANGED` · 세션 없는 갱신 토큰 401.

## 계정(아이디) 단위 로그인 잠금 — `LoginThrottle`

게이트웨이 시도 제한은 IP 당 분당 10회라 IP 를 돌리면 안 걸린다. 그래서 **두드린 아이디**로
한 번 더 센다. 표를 따로 두지 않고 `scom.account_login_logs` 의 연속 실패를 센다(성공 한 번이
사슬을 끊는다 · 24시간 안 · `login_id` 색인이 이미 있다).

| 연속 실패 | 잠금 |
|---|---|
| 1~4 | 없음 |
| 5 | 1분 |
| 6 · 7 · 8 · 9 | 2 · 4 · 8 · 16분 |
| 10~ | 30분 (`Auth:Lockout:MaxMinutes`) |

- 잠긴 동안은 **비밀번호를 보지도 않는다** — 맞는 비밀번호도 429(`Retry-After`)다.
- **없는 아이디도 똑같이 잠근다.** 있는 아이디만 잠그면 429 로 아이디가 갈린다.
- 잠긴 채 들어온 시도는 `LOCKED` 로 남지만 **세지 않는다** — 세면 공격이 이어지는 동안
  주인도 영영 못 들어온다.
- 같은 잠금을 받는 길: 로그인 · 대리 로그인(관리자 아이디) · 잠금화면 비밀번호 확인 ·
  비밀번호 변경. 뒤의 둘의 실패는 `BAD_PASSWORD_RECHECK` 로 쌓인다.
- 패스키·소셜 로그인은 잠그지 않는다(비밀번호를 맞춰 보는 길이 아니다).
- 셸 로그인 화면은 서버가 준 안내(「N분 뒤에 다시」)를 그대로 보인다.

실측: 다섯 번 틀린 뒤 맞는 비밀번호로 429 · 「1분 뒤」, 없는 아이디도 여섯째에 429.

## 이메일 인증번호

- 번호 하나에 **5번 틀리면 번호를 버린다**(남은 횟수를 알려 준다). 비교는 고정 시간.
- 계정당 **60초에 한 번 · 한 시간에 다섯 번**만 보낸다(주소를 바꿔도 같은 통).
- 프로필 저장 때 인증 토큰이 **반드시** 맞아야 한다(비워 보내면 통과하던 것을 막았다).
- 게이트웨이: 보내기·맞추기·비밀번호 변경 경로를 `auth-attempts`(IP 당 분당 10회)에 넣었다.

이 셋은 메일 발송이 끼어 있어 실측하지 않았다(판독 + 빌드).
