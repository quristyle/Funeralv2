# 누가 마지막으로 들어왔고, 마지막으로 썼나 — 계정 활동

**포털관리 › 시스템관리 › 「계정 관리」**(`/admin/system/account`)의 칸 둘 —
**마지막 로그인** · **마지막 사용**.

## 왜 값이 둘인가

「이 계정 아직 쓰나」를 묻고 목록을 여는데, 여태 답할 값이
`scom.accounts.last_login_at` 하나뿐이었고 **그 값으로는 그 물음에 못 답한다.**

access token 이 7일이고 갱신 쿠키가 30일이다(`Auth:AccessTokenDays` ·
`RefreshTokenDays`). 브라우저를 안 닫는 사람 — 포털을 홈 화면에 깔아 둔 사람이
특히 — 은 **로그인 화면을 한 달에 한 번도 안 거친다.** 그래서 매일 쓰는 사람이
「한 달 전에 들어온 사람」으로 보이고, 정말 안 쓰는 계정과 구별되지 않는다.

운영에서 바로 드러난다(2026-10-18) —

| 아이디 | 마지막 로그인 | 마지막 사용 |
|---|---|---|
| `jupark` | 10-12 22:29 | **10-18 00:01** (닷새 뒤) |
| `kdh` | 10-07 01:02 | **10-13 06:46** |

| | 뜻 | 어디에 |
|---|---|---|
| 마지막 로그인 | **들어온** 때 | `scom.accounts.last_login_at` |
| 마지막 사용 | 마지막으로 **무언가를 한** 때 | `scom.accounts.last_seen_at` |

## 어떻게 쌓나

```
 브라우저            포털 셸(:5557)           게이트웨이        AuthServer
    │                     │                       │                │
    │ 로그인              │                       │                │
    ├────────────────────▶│──────────────────────▶│───────────────▶│
    │                     │                       │   LoginCompletion.CompleteAsync
    │                     │                       │     last_login_at · last_login_ip
    │                     │                       │     last_seen_at          ─┐
    │                     │                       │                │           │
    │ 메뉴를 누른다       │                       │                │           │
    ├────────────────────▶│                       │                │           │
    │              MenuUsageRecorder.Record       │                │           │
    │                     ├──────────────────────▶│───────────────▶│           │
    │                     │  POST /api/auth/menu-usage             │           │
    │                     │                       │   MenuUsageService.RecordAsync
    │                     │                       │     ① 기록 한 줄 INSERT    │
    │                     │                       │     ② AccountActivityService.TouchAsync ◀┘
```

**적는 자리가 둘이고, 뒤엣것이 쓸모의 거의 전부다.** 포털은 **한 회로 안에서
라우팅만 바뀌어** 화면을 옮겨도 HTTP 요청이 한 건도 안 나간다
([menu-usage.md](menu-usage.md)). 그래서 게이트웨이나 미들웨어에 얹을 자리가
없고, 셸이 스스로 적어 보내는 사용기록 길이 「지금 쓰고 있다」를 아는 거의
유일한 신호다.

**그래서 「화면에 머문 시간」은 안 센다.** 한 화면을 열어 두고 두 시간 일한
사람의 「마지막 사용」은 그 화면을 연 때다 — 「마지막으로 **화면을 연** 때」로
읽어야 맞다. 타임라인의 `+12분` 이 머문 시간이 아닌 것과 같은 자리다.

### 1분 안에 또 불리면 건너뛴다

사람 하나가 한 시간에 화면을 수십 번 옮긴다. 그때마다 계정 줄을 고치면
**쓰기가 잦은 표**(권한·로그인·목록이 모두 읽는다)에 쓸데없는 갱신이 쌓인다.
문턱은 1분이다(`AccountActivityService.TouchInterval`) — 이 칸을 보는 물음이
「어제 썼나 · 석 달째 안 쓰나」라 분 단위 아래는 아무도 안 쓴다.

**간격 판정을 메모리에 들고 있지 않는다.** 컨테이너가 여럿이면 서로 모르고,
미리 읽어 보면 화면을 옮길 때마다 조회가 하나 는다. 조건을 `WHERE` 에 넣어
**한 문장**으로 간다 — 밀 때가 아니면 0줄이 고쳐지고 끝난다.

```sql
UPDATE scom.accounts
   SET last_seen_at = @now
 WHERE user_id = @id AND NOT is_deleted
   AND (last_seen_at IS NULL OR last_seen_at < @cutoff)
```

## 왜 기록 표를 집계하지 않고 칸으로 두나

「마지막으로 쓴 때」는 `scom.menu_usage_logs` 를 `user_id` 로 묶어
`max(occurred_at)` 하면 나온다. 그래도 칸을 둔 까닭이 둘이다.

- 그 표는 **한 해가 지나면 스스로 걷어낸다**(`MenuUsageService.RetentionDays`
  = 365). 집계로 셈하면 일 년 넘게 안 쓴 계정이 **한 번도 안 쓴 계정과 같은
  그림**이 된다 — 가려내려는 것이 바로 그 계정들이다.
- 목록은 예순 줄을 한꺼번에 그린다. 줄마다 수만 줄짜리 기록 표를 훑게 하면
  화면 하나를 여는 값이 너무 비싸진다.

## 화면

시각 밑에 **「며칠 전」**을 흐리게 덧붙인다. 예순 줄을 훑는 눈이 찾는 것은
날짜가 아니라 오래된 정도이고, `2026-07-02` 를 보고 오늘과 빼는 일을 줄마다
시키면 아무도 안 한다.

- **「오늘·어제」는 한국 달력으로 센다.** 서버가 주는 것은 UTC 라 그대로 빼서
  24시간으로 나누면 한국의 오전 아홉 시 전 아홉 시간 동안 **오늘 아침에 쓴
  것이 「어제」**로 나온다([utc-time.md](utc-time.md)).
- 정렬은 **원래 값(UTC)**으로 돈다(`FieldName` 은 그대로 두고 그림만
  `CellDisplayTemplate` 이 바꾼다). 글자로 정렬하면 빈 줄과 섞여 흐트러진다.
- 접속 IP 는 제 칸을 안 쓰고 **마지막 로그인 칸의 설명 풍선**에 들어간다.
  이 화면은 칸이 이미 열몇 개라 하나를 늘리면 그만큼 가로로 더 구른다.

## 표 — 이미 있던 것과 새로 만든 것

| 표 | 무엇이 | 언제부터 |
|---|---|---|
| `scom.accounts.last_login_at` · `last_login_ip` | 마지막 로그인 한 점 | 전부터 |
| `scom.account_login_logs` | 로그인 시도 **한 줄씩** (실패도) | 전부터 |
| `scom.menu_usage_logs` | 화면 열람 **한 줄씩** | 2026-10-09 |
| `scom.blocked_access_logs` | 막힌 접근 | 2026-10-13 |
| **`scom.accounts.last_seen_at`** | **마지막 사용 한 점** | **2026-10-18** |

곧 **접근기록은 이미 셋이 쌓고 있었고**, 모자랐던 것은 「마지막 한 점」
하나다. 칸·되채우기 SQL 과 까닭은
[deploy/sql/account-last-seen-2026-10-18.sql](../deploy/sql/account-last-seen-2026-10-18.sql)
(EF 마이그레이션 `20261017145946_AddAccountLastSeenAt` 을 뽑은 것이다 —
AuthServer 는 기동할 때 마이그레이션을 안 돌리므로 운영 반영은 손으로 한다).

### 되채우기에서 드러난 것 — 계정 결합은 `last_login_at` 을 안 옮긴다

칸만 만들고 두면 **전원이 「한 번도 안 씀」**으로 보인다. 그것은 사실이 아니라
「아직 안 적기 시작했다」이고, 둘은 화면에서 구별되지 않는다. 그래서 이미
있는 자취 셋(로그인 시각 · 로그인 기록 · 열람 기록) 중 가장 늦은 것으로 한 번
채웠다.

그러면서 **로그인 기록에는 성공이 쌓여 있는데 `last_login_at` 이 빈 계정**이
하나 나왔다(`uspuni`). 계정 결합(merge)이 기록 줄의 `account_id` 는 받는
계정으로 옮기면서 `last_login_at` 은 안 옮긴 자국이다. 같은 SQL 이 그것도
함께 되채운다 — **비어 있을 때만** 채우고, 들어 있는 값은 기록보다 일러도
덮지 않는다(덮으면 결합으로 옮겨 온 **남의 계정 기록**이 이 사람의 로그인
시각이 된다).

## 재어 본 것 (2026-10-18)

버리는 계정 하나(`aiprobe729`)를 만들어 5만번대 포트의 AuthServer 로 몰아 봤다.

| 해 본 것 | 결과 |
|---|---|
| `POST /menu-usage` (로그인 없이) | `last_seen_at` 이 선다. **`last_login_at` 은 빈 채다** — 이 칸이 메우는 그 틈이다 |
| 1분 안에 또 `POST /menu-usage` | `last_seen_at` 그대로. `UPDATE` 가 0줄 |
| `POST /login` | `last_login_at` · `last_login_ip` · `last_seen_at` 셋이 함께 선다 |
| `GET /system/account/list` | 세 칸이 응답에 실린다 |

끝나고 그 계정과 그 계정의 기록 줄을 지우고 개수를 되돌렸다.
