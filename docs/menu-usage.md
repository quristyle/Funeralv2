# 누가 어떤 화면을 언제 보았나 — 메뉴 사용기록

**포털관리 › 상태관리 › 「메뉴 사용기록」**(`/admin/status/menu-usage`)에서 본다.
메뉴 권한은 **시스템관리자(`SYSTEM_ADMINISTRATOR`)에게만** 주어져 있다.

## 왜 표가 필요했나 — 서버 로그에는 안 남는다

포털은 **한 회로 안에서 라우팅만 바뀐다**(`PortalTabs` 머리말). 사람이 화면을
옮겨도 브라우저는 문서를 새로 받지 않고, 그래서 **HTTP 요청이 한 건도 나가지
않는다.** 나중에 nginx 접근 로그를 뒤져도 거기에는 로그인 한 번과 WebSocket
하나뿐이다.

로그인 기록(`scom.account_login_logs`)은 **들어온 것까지만** 안다. 컨테이너
로그는 10MB 세 개를 돌려 쓰므로 바쁜 날에는 그날 안에 밀려 나간다.

「누가 어떤 화면을 보았나」를 아는 자리는 **레이아웃 하나뿐**이고, 그래서
거기서 한 줄씩 적어 보낸다.

## 어떻게 도나

```
 브라우저            포털 셸(:5557)           게이트웨이        AuthServer
    │                     │                       │                │
    │ 메뉴를 누른다       │                       │                │
    ├────────────────────▶│                       │                │
    │              ① MainLayout.Track             │                │
    │                 주소로 메뉴를 찾아           │                │
    │                 탭을 열고 ─ 그 자리에서      │                │
    │              ② MenuUsageRecorder.Record     │                │
    │                 (기다리지 않는다)            │                │
    │                     ├──────────────────────▶│───────────────▶│
    │                     │  POST /api/auth/menu-usage      ③ 한 줄 INSERT
    │  화면이 그려진다 ◀──┤                       │       scom.menu_usage_logs
```

① **그 자리까지 왔다는 것은 메뉴에 있는 화면이고 볼 권한도 있다는 뜻**이라
로그인 화면·오류 화면·「준비 중」이 저절로 빠진다.

② 기다리지 않고 실패해도 조용하다. 기록은 곁다리고 화면이 본일이다 —
그래서 **회로가 그 사이에 끊기면 몇 건은 잃는다.** 이 숫자는 회계가 아니다.

③ 적히는 사람은 **게이트웨이가 붙여 준 `X-User-Id`** 다. 몸체에서 받지 않으므로
남의 이름으로 쌓을 수 없다.

### 같은 이동을 두 번 적지 않는다

`MainLayout.Track` 은 한 번 옮길 때 **두 번 이상** 불린다 — 주소가 바뀔 때 한 번,
늦게 도착한 메뉴·권한표가 브레드크럼을 다시 셈할 때 또 한 번. 그대로 두면
화면 하나를 연 것이 기록에는 둘로 남는다.

그렇다고 「같은 주소면 안 적는다」로 두면 **같은 메뉴를 다시 누른 것**이 영영
안 적힌다. 그것은 사람이 실제로 한 일이다. 그래서 가르는 기준이 **시간**이다 —
같은 주소라도 **2초**를 넘겨 다시 오면 새 열람이다
(`MenuUsageRecorder.DedupeWindow`).

## 표

`scom.menu_usage_logs` — DDL 과 까닭은
[deploy/sql/menu-usage-2026-10-09.sql](../deploy/sql/menu-usage-2026-10-09.sql).
EF 마이그레이션 `20261009141510_AddMenuUsageLogs` 를 그대로 뽑은 것이다.

| 칸 | 무엇 |
|---|---|
| `occurred_at` | 본 때. **UTC 다** — 한국 시각은 보여 주기 직전에 만든다 |
| `user_id` | 로그인 아이디 |
| `menu_id` · `route_key` · `menu_path` | 같은 메뉴를 가리키는 열쇠 셋 (아래) |
| `menu_title` | **그때** 화면에 적혀 있던 제목 |
| `href` | 실제로 열린 주소. 메뉴 경로와 다를 수 있다(`RouteAliases`) |
| `from_path` | 직전에 보던 화면. 첫 화면이면 비어 있다 |

### 열쇠를 셋이나 적는 까닭

`menu_id` 는 메뉴가 지워지면 가리킬 곳이 없어지고, `route_key` 는 아직 안 채운
메뉴가 있고([docs/menu-route-key-backfill.sql](menu-route-key-backfill.sql)),
`menu_path` 는 권한표의 열쇠라 안 바뀌지만 Vue 시절 값이 섞여 있다. 셋 중 하나만
들고 있으면 **그 하나가 빈 줄이 조회에서 사라진다.**

`menu_id` 에 외래키를 걸지 않는다 — 메뉴를 지우면 그 화면을 본 기록까지 함께
사라지는데, 지난 일을 적어 둔 표에서 그것은 자료 손실이다. `menu_title` 을 함께
적어 두는 것도 같은 까닭이다. **즐겨찾기(`menu_favorites`)와 반대**인데, 저쪽은
「지금 어디로 가나」라 메뉴 쪽 값이 정본이고 이쪽은 「그때 무엇을 보았나」다.

### 한 해만 들고 있다

적는 길에 하루 한 번 청소가 얹혀 있다(`MenuUsageService.RetentionDays` = 365).
「작년 이맘때와 견주어 본다」가 이 표로 할 수 있는 가장 먼 물음이고, 그보다
오래 들고 있어 봐야 아무도 묻지 않는다. 아무도 포털을 안 쓰는 동안에는
지울 것도 안 생기므로 배경 작업을 따로 두지 않았다.

## 화면 — 보기 넷

같은 자료에 묻는 물음이 넷이라 보기가 넷이다. 바꾸는 자리는 **조회판**이다
(「내 이동경로」의 ‘원시 기록으로 보기’와 같은 자리).

| 보기 | 답하는 물음 | API |
|---|---|---|
| 사용자별 | 누가 포털을 많이 쓰나 | `GET /api/auth/menu-usage/by-user` |
| 화면별 | 어떤 화면이 **실제로** 쓰이나 (안 쓰는 메뉴를 가려낸다) | `.../by-menu` |
| 기록 | **누가 어떤 화면을 언제 보았나** | `GET /api/auth/menu-usage` |
| 타임라인 | 하루가 어떻게 흘렀나 | `.../timeline` |

사용자별 표에서 줄을 **두 번 누르면** 그 사람의 타임라인으로 간다(오른쪽 클릭
창에도 같은 것이 있다).

### 건수만으로는 모자란다

「한 화면을 백 번 새로고친 사람」과 「백 개를 돌아본 사람」은 건수만으로는 같아
보인다. 그래서 사람별 표가 **화면 수**·**기록이 있는 날 수**·**가장 많이 본
화면**을 함께 들고 있다.

### 타임라인의 `+12분` 은 **머문 시간이 아니다**

**앞 칸에서 다음 칸까지**다. 떠난 순간은 아무도 재지 않는다 — 그날 마지막으로
연 화면은 포털을 닫을 때까지 떠 있었을 수도 있고 1초 뒤에 닫혔을 수도 있다.
「내 이동경로」가 머문 시간을 모자라는 쪽으로 두는 것과 같은 자리이고
([utc-time.md](utc-time.md) 가 아니라 그 화면 머리말), 여기서는 아예 다른
이름으로 부른다.

### 잘린다

기록은 **500줄**, 타임라인은 **1000칸**에서 서버가 자른다. 잘렸으면 화면이
안내 줄로 말한다 — 말 없이 자르면 「이 기간에 그만큼뿐」으로 읽힌다.

## 권한 — 판정이 한 곳이다

게이트웨이의 `auth-route` 는 `/api/auth/**` 를 통째로 **익명**으로 열어 둔다
(로그인이 그 길로 간다). 그래서 **보는 길은 서버가 스스로 막는다.**

막는 판정은 역할 이름을 코드에 적는 것이 아니라 **사이드바와 같은 표**
(`scom.role_menus`)에 묻는다(`AuthServer/Services/MenuViewAccess.cs`).
AI 사용량이 그 교훈을 남겼다 — 역할 이름을 적어 두었다가 `SERVER_ADMIN` 에게
메뉴를 열어 준 날 **사이드바에는 보이는데 조회하면 403** 이 됐다.

그래서 **메뉴 권한 화면(`/admin/system/menu-role`)에서 역할을 더하면 조회도 그
순간부터 따라간다** — 서버를 고칠 일이 없다. 메뉴 줄을 아예 못 찾으면 막는다
(틀리는 방향은 「안 보이는」 쪽이어야 한다).

**넣는 길에는 권한을 묻지 않는다.** 자기가 연 화면을 적는 일이고, 메뉴 권한을
또 따지면 권한 없이 열린 화면이 기록에서 빠지는데 그것이야말로 가장 알고 싶은
줄이다.

## 쌓기 시작한 날 이전은 없다

2026-10-09 에 표를 만들었다. 그 앞의 기간을 고르면 빈 목록이고, 그것은 고장이
아니다.
