# 도움말 — 자료실 (`/help/archive`)

> 지시: "`/help/archive` 는 자료실이다. 자료의 설명을 확인하고 다운로드 할 수 있도록 만들어라."

작업일: 2026-08-26

---

## 1. 손대기 전 상태

`/help/archive` 는 "백엔드 연동 준비 중" 임시 화면이었다. 백엔드도 표도 없었다.

형제 파일 `archive-custom/index.vue` 는 없는 API(`#/api/funeral/help`)를 import 하는
고아였다. 다만 그 그리드 컬럼(`자료명 · 첨부파일명 · 파일 크기 · 다운로드 수 · 등록일자`)이
원래 의도를 알려 주어 화면을 설계할 때 참고했다.

F.A.Q · Q&A 가 이미 같은 구조로 만들어져 있어서(관리자가 쓰고 모두가 읽는다)
**그 방식을 그대로 따랐다.** 도움말 메뉴 안에서 권한 판정과 조작이 일관된다.

## 2. 만든 것

### 2.1 DB — [`docs/sql/help_archive.sql`](../sql/help_archive.sql) (실행 완료)

표를 둘로 나눴다.

| 표 | 쓰임 |
|---|---|
| `scom.help_archives` | 자료 항목 — 분류 · 자료명 · **설명** · 순서 · 상태 · 다운로드 수 |
| `scom.help_archive_files` | 첨부 — `file_id` · 파일명 · 크기 · MIME · 순서 · 다운로드 수 |

**자료 하나에 파일 여럿**을 붙일 수 있게 했다. 설치 파일 + 설명서 + 예제처럼 묶이는 것이
자료실의 보통 모습이고, 파일마다 항목을 따로 만들면 같은 설명을 여러 번 적게 된다.

첨부 표의 모양은 `scom.notice_files` 와 똑같이 맞췄다. 파일은 전부 FileServer 로 가고
우리는 FileServer 가 발급한 `file_id` 만 들고 있다(공지와 같은 구조).

### 2.2 AuthServer

```
Entities/HelpArchive.cs          HelpArchive · HelpArchiveFile
DTOs/HelpArchiveDto.cs           목록 응답에 canManage 를 함께 담는다
Services/HelpArchiveService.cs   권한 판정 · 목록 · CRUD · 내려받기 해석
Endpoints/HelpArchiveEndpoints.cs  /help/archives  (목록·단건·등록·수정·삭제·내려받기)
```

권한은 `scom.role_menus` 의 `/help/archive` 를 그대로 쓴다(F.A.Q 와 같다).
등록·수정·삭제 중 하나라도 있으면 관리자로 본다 — 셋을 따로 보면
"수정은 되는데 목록에 비활성이 안 보인다" 같은 어긋남이 생긴다.

**쓰기 권한은 화면을 믿지 않고 서비스가 다시 확인한다.** 화면의 버튼 숨김은
장치일 뿐이고 요청을 직접 보내면 통과한다.

### 2.3 다운로드 수를 세는 방법

파일은 FileServer 가 내려준다. 브라우저가 그 주소를 직접 열면 AuthServer 는
아무것도 모르므로 셀 수가 없다. 그래서 **세는 경로를 한 번 거친다.**

```
GET /api/auth/help/archives/{id}/files/{fileId}/download
    → download_count + 1 (파일 · 항목 둘 다)
    → 302  /api/file/download/id/{fileId}
```

`/api` 는 게이트웨이로 프록시되므로 브라우저가 302 를 그대로 따라가 파일을 받는다.
화면은 이 주소만 열면 되고, 세는 것과 넘기는 것은 서버가 한다.

**세는 데 실패해도 내려받기는 막지 않는다** — 숫자는 곁들이는 정보다.

### 2.4 화면 — [`views/funeral/help/archive/index.vue`](../../fronts/apps/jsini-portal/src/views/funeral/help/archive/index.vue)

자료명을 누르면 **설명과 파일 목록이 펼쳐진다**(F.A.Q 와 같은 모양이라 도움말 메뉴
안에서 조작이 일관된다). 조회 줄은 위에 고정하고 목록만 안에서 스크롤한다(준수사항 4).

펼치지 않아도 보이는 것: 분류 · 자료명 · 파일 개수 · 내려받기 횟수 · 비활성 표시.
펼치면: 설명(HTML) · 파일별 이름 · **크기** · 내려받기 횟수 · 등록/수정 시각.

파일은 확장자로 아이콘을 골라 종류를 한눈에 알 수 있게 했고, 크기는 KB·MB 로 바꿔
보여 준다 — 무엇을 얼마나 받는지 누르기 전에 알아야 한다.

관리자에게만 등록·수정·삭제가 보인다. 판정은 목록 응답의 `canManage` 를 쓴다 —
권한 스토어만 보면 권한이 늦게 도착했을 때 서버와 어긋난 버튼이 보인다.

업로드는 게이트웨이의 파일 서비스로 바로 보낸다(`/api/file/upload?bizType=help-archive`,
공지 첨부와 같은 흐름).

## 3. 판단한 것

### 3.1 읽기만이 아니라 등록까지 만들었다

지시는 "설명을 확인하고 다운로드" 였다. 그런데 **자료를 넣을 길이 없으면 화면이 늘 비어
있어 쓸 수가 없다.** F.A.Q 가 이미 "관리자가 쓰고 모두가 읽는다" 로 되어 있으므로
같은 범위로 맞췄다. 읽기 쪽이 지시한 것이고, 등록 쪽은 그것을 쓸 수 있게 하는 최소한이다.

### 3.2 수정할 때 남긴 파일은 지우고 다시 넣지 않는다

첨부를 맞출 때 "보낸 목록으로 통째로 교체" 가 쓰기 쉽지만, 그러면 **파일별 다운로드 수가
초기화된다.** 빠진 것만 지우고 새로 온 것만 넣는다. 실제로 확인했다 — 수정 후에도
남긴 파일의 다운로드 수 3회가 그대로 유지된다.

### 3.3 자료를 지워도 FileServer 의 파일은 지우지 않는다

같은 파일을 다른 곳(공지 등)에서 참조하고 있을 수 있다. 자료실에서 뗀 것과
파일을 없애는 것은 다른 일이다.

### 3.4 파일명도 검색 대상에 넣었다

자료실에서는 "그 파일 어디 있지" 로 찾는 일이 많다. 자료명·설명만 훑으면
파일명을 아는데도 못 찾는다.

### 3.5 파트너는 읽기만 — 권한을 **끄는** 스크립트다

`role_menu_backfill.sql` 이 "메뉴가 쓴다고 지정한 항목은 모두 허용" 으로 채워 둔 탓에
네 역할 모두 자료실에 등록·수정·삭제까지 할 수 있었다. 그러면 파트너 39명이 전사 자료를
올리고 지울 수 있어 지시와 반대가 된다. 그래서 스크립트가 권한을 끄기도 한다.

관리자 역할은 F.A.Q 와 **똑같은 목록**으로 잡았다(ADMINISTRATOR · SYSTEM_ADMINISTRATOR).
PARTNER_ADMINISTRATOR 를 넣지 않은 이유도 같다 → 21-help-faq-qna.md 의 D-H1 과 같은 건이다.

실행 후 상태:

| 역할 | 열람 | 검색 | 등록 | 수정 | 삭제 |
|---|---|---|---|---|---|
| 관리자 | O | O | O | O | O |
| 시스템관리자 | O | O | O | O | O |
| 파트너 관리자 | O | O | — | — | — |
| 파트너 | O | O | — | — | — |

## 4. 확인한 것

격리된 AuthServer(:15266)를 따로 띄워 실제 요청으로 확인했다.
개발자가 띄워 둔 :5264 · :5265 는 건드리지 않았다.

| 확인 | 결과 |
|---|---|
| 관리자(vben) `canManage` | true |
| 파트너(uspuni) `canManage` | false |
| 자료 등록 (한글 · 첨부 2개) | 설명·분류·파일 모두 정상 저장 |
| 파트너가 등록 시도 | 403 FORBIDDEN |
| 내려받기 | 302 → `/api/file/download/id/{fileId}` |
| 다운로드 수 | 3번 누르면 파일 3 · 항목 합계 3 |
| 파트너 내려받기 | 302 (읽기 권한으로 가능) |
| 검색 | '플레이어'(자료명) 1건 · 'setup.exe'(파일명) 1건 · 없는 말 0건 |
| 수정 — 첨부 교체 | 뗀 파일 사라지고 새 파일 추가, **남긴 파일 다운로드 수 3회 유지** |
| 비활성으로 내림 | 관리자 1건 / 파트너 0건, 파트너 내려받기 404 |
| 파트너 삭제 시도 | 403 |
| 관리자 삭제 | 200, 목록에서 사라짐 |

화면(:5555)에서 렌더링·조회 줄·빈 상태를 확인했다.
검증용으로 만든 자료와 첨부 행은 모두 지웠다(남은 자료 0건).

`dotnet build` · `pnpm vite build` 통과.

## 5. 고쳐 둔 것

목록을 못 불러왔을 때도 "등록된 자료가 없습니다" 라고 나왔다. **거짓말이다** —
자료가 없는 것과 못 불러온 것은 다르다. 그대로 두면 사용자가 관리자에게
"자료실이 비었다" 고 말하게 된다. 실패를 구분해 "불러오지 못했습니다 + 다시 조회" 로
바꿨다. 백엔드를 아직 다시 띄우지 않은 지금 상태에서 실제로 그 문구가 나오는 것을 확인했다.

## 6. 남은 것

- **백엔드를 다시 띄워야 동작한다.** 실행 중인 AuthServer(:5264)는 이 변경 전 빌드다
  (`dotnet watch` 가 아니다). 그전까지 화면은 "불러오지 못했습니다" 를 보여 준다.
- `archive-custom/index.vue` 는 여전히 없는 API 를 import 하는 고아 파일이다.
  이번에 만든 화면이 그 의도를 대체하므로 지울 수 있지만, 지시 범위를 넘어 손대지 않았다.
- 역할이 하나도 없는 계정은 **관리자로 취급된다.** `MenuService.GetEffectivePermissionAsync`
  가 "권한 정보가 아예 없으면 전부 허용" 으로 열어 두기 때문이다(프론트 가드와 같은 방침).
  자료실만의 문제가 아니라 F.A.Q · Q&A 도 같다 — 별건이라 손대지 않았다.
  실제로 `administrator` 계정이 역할 배정이 없어 이 경로로 관리자가 된다.
- 자료 하나에 붙는 첨부 개수·용량 상한은 두지 않았다. FileServer 의 업로드 상한
  (게이트웨이 500MB)만 적용된다.
