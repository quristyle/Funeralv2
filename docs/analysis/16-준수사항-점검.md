## 1. 규칙 3 — 팝업 이동 ✅ 전부 처리

### 무엇을 했나

화면마다 손대지 않고 **두 곳에서 한 번에** 걸었다.

| 대상 | 처리 | 파일 |
|---|---|---|
| vben 모달 (31개 화면) | 기본값 `draggable: true` | `packages/@core/ui-kit/popup-ui/src/modal/modal-api.ts` |
| ant 모달 (30개 화면 이상) | 앱 시작 시 DOM 을 지켜보다 헤더를 손잡이로 만든다 | `apps/jsini-portal/src/plugins/draggable-modal.ts` (신규) |

ant 쪽을 화면마다 `:modal-render` 로 처리하는 방법이 흔하지만, 30곳을 고치고 앞으로도
새 팝업마다 잊지 않아야 한다. **한 곳에서 걸어 두는 편이 지켜지기 쉽다**고 보고 그렇게 했다.

- 움직임은 `transform` 으로만 준다. ant 가 계산한 `top`·`margin` 을 건드리지 않아야
  닫았다 다시 열 때 제자리로 돌아온다.
- 헤더 안의 버튼(닫기 등)을 누른 것은 드래그로 보지 않는다.
- 창 밖으로 완전히 나가지 않도록 가장자리를 남긴다.
- 모달이 닫히면 위치를 초기화한다.

### 곁들여 고친 것 — 헤더가 없던 팝업

**공지 팝업이 `:title="null"` 이라 헤더가 없었다.** 잡을 곳이 없으니 규칙을 지킬 수 없다.
제목을 본문 안에 그리던 것을 모달 헤더로 옮겼다(`components/notice/notice-popup.vue`).

전체 화면을 훑어 헤더 없는 모달을 찾았고, 예제·데모를 뺀 운영 화면에서는 이 하나뿐이었다.

### 확인

```
공지 팝업      헤더 생성 · cursor: move · 끌어서 (+200, -120) 이동
공지 등록 모달  끌어서 (-220, +140) 이동 · 닫았다 열면 제자리
콘솔 오류      없음
```

## 2. 규칙 4 — 세로 스크롤

### 먼저 알아야 할 것 — 재는 곳이 다르다

이 시스템은 **문서 전체가 스크롤되지 않는다.** 레이아웃이 내용 영역만 스크롤한다.
그래서 `document.documentElement` 로 재면 128개 화면 전부 0 이 나온다.
**내용 영역(`.h-full.p-4`)을 재야 한다.**

또 하나. 자료가 늦게 들어오는 화면이 많아 **연 직후에 재면 0 이 나온다.**
처음 측정에서 이 함정에 걸려 "고쳤다"고 잘못 판단한 화면이 8개 있었다.
지금은 3초 기다린 뒤 2회 측정해 큰 값을 쓴다.

### 원인 — 조회 조건 줄 높이만큼 넘친다

화면 대부분이 이 구조다.

```
<Page auto-content-height>     내용 영역 높이 = 712px 로 고정
  <SearchBar />                 40px
  <Grid class="h-full" />       712px  ← 남은 높이가 아니라 전체 높이를 차지
</Page>
```

`h-full`(=`height:100%`)이 **남은 높이가 아니라 영역 전체 높이**로 풀린다.
그래서 조회 조건 줄 높이(+여백)만큼 넘쳐 47~95px 짜리 스크롤이 생긴다.

### 처음 시도한 방법과 그 실패 — 기록해 둔다

`Page` 부품에서 전역으로 고치려 했다. 내용 영역을 세로 flex 로 두고
직계 자식의 `h-full` 을 '남은 높이를 채운다'로 재해석하는 CSS 한 덩어리다.

**20개가 고쳐지고 8개가 망가졌다.** 안쪽에서 높이를 다시 계산하는 화면들이
백분율 사슬이 끊겨 늘어났다 — 내 댓글 화면은 24,000px 이 되었다.

되돌리고 **화면마다 켜는 방식**으로 바꿨다.

```vue
<Page auto-content-height content-class="page-fill-last">
```

`page-fill-last` 는 `apps/jsini-portal/src/styles/index.css` 에 있다.
마지막 자식만 '남은 높이를 채우는' 것으로 바꾼다. 화면 코드의 `h-full` 은 그대로 둬도 된다.

> **교훈:** `h-full` 은 화면마다 뜻이 다르다. 전역으로 재해석하면 안 된다.

### 적용한 화면 33곳 — 24곳 완전 해소, 9곳은 잔여

| 결과 | 수 | 화면 |
|---|---|---|
| **넘침 0** | 24 | 건물·층·호실·고인·빈소 사용내역 / 부서 관리 / 원인 분석 / 프로젝트 참여자·소스 정보·유즈케이스·공통코드·화면 메뉴·일정표·ERD·업무 흐름·DB 등록·코드 정보·쿼리 테스터·테이블 설명·DB 로직·소스 추적·Glue 추적·서버 모니터 2종 |
| **8px 남음** | 7 | 화면 스캐너(95→8) · Fast 호출 테스트(55→8) · 프로젝트 WBS(55→8) · 부품 테스트(55→8) · 프로젝트 목록(55→8) · DB 로직 항목(55→8) · 할일 관리(8→8) |
| **일부만** | 2 | 헬스체크(50→36) · 다국어 관리(10→10) |

47~95px 짜리 스크롤은 사라졌고, 남은 것은 8~36px 이다.
자식 높이 합은 영역과 정확히 맞는데도 몇 픽셀이 남는 화면이 있다 —
안쪽 부품(그리드 하단 등)이 몇 픽셀 삐져나오는 것으로 보인다.
**실사용에 지장이 없는 크기라 더 파고들지 않았다.** 필요하면 화면별로 잡으면 된다.

되돌리려면 해당 화면의 `<Page>` 에서 `content-class="page-fill-last"` 만 지우면 된다.

### 대시보드에는 쓰지 않았다

`고객사 현황`에 적용했다가 **179px → 640px 로 더 나빠져** 되돌렸다.
카드를 위아래로 쌓는 화면은 마지막 카드만 늘어나기 때문이다.

## 3. 🟠 판단이 필요한 것 — 아직 넘치는 화면

아래는 **손대지 않았다.** 고치려면 화면을 다시 설계해야 하고,
"한 화면에 담기"와 "읽을 수 있게 보이기" 중 무엇을 우선할지 정해야 한다.

### R1. 원래 길게 보는 화면 — 예외로 둘까 🟡

| 화면 | 넘침 | 성격 |
|---|---|---|
| 운영 모니터링 | 701px | 지표 카드 + 차트 여러 개 |
| SM 모니터링 | 661px | 같음 |
| IO 정밀 분석 | 645px | 분석 리포트 |
| 가용성 분석 | 532px | 분석 리포트 |
| 월간 리포트 | 431px | 리포트 |
| 주간 리포트 | 250px | 리포트 |
| 유지보수 보고 | 702px | 보고서 |
| 고객사 현황 | 654px | 대시보드 |
| 헬프데스크 현황 | 170px | 대시보드 |
| 푸시 현황 | 372px | 대시보드 |

**의견: 예외로 두는 편이 낫습니다.** 억지로 한 화면에 넣으면 차트와 숫자가
읽을 수 없게 작아집니다. 다만 규칙에 "리포트·대시보드는 예외" 를 명시해 두면
다음에 판단이 흔들리지 않습니다.

선택지

| | 방법 | 비고 |
|---|---|---|
| **A** | 예외로 인정하고 규칙에 적는다 | 지금 상태 유지 |
| B | 탭으로 나눈다 (요약 / 상세 / 추이) | 한 화면에 담기지만 클릭이 늘어난다 |
| C | 카드를 접을 수 있게 한다 | 처음 보이는 것만 줄어든다 |

### R2. 목록이 길어 넘치는 화면 — 안쪽 스크롤로 바꿀까 🟠

| 화면 | 넘침 | 원인 |
|---|---|---|
| 내 댓글 | 25,883px | 댓글 전부를 한 번에 그린다 |
| 할일 정산 현황 | 15,649px | 같음 |
| DB 개체 탐색 | 15,309px | 같음 |
| 체크리스트 | 2,108px | 항목 전부를 한 번에 그린다 |
| 설비 상태 로그 · FMS 상태 로그 | 각 1,421px | 로그 전부 |
| 요청 처리 | 494px | 카드 목록 |
| 수집 현황 | 679px | 표 |
| MC 모델 관리 | 231px | 목록 |
| 발송 이력 | 265px | 목록 |
| 빈소현황 | 477px | 카드 배치 |

**의견: 고치는 편이 맞습니다.** 특히 앞의 셋은 2만 픽셀이 넘어 브라우저도 느려집니다.
다만 화면마다 목록 부품이 달라(카드·표·직접 그린 목록) 일괄 처리가 안 되고,
페이지 나누기를 넣을지 무한 스크롤로 갈지 결정이 필요합니다.

선택지

| | 방법 | 비고 |
|---|---|---|
| **A** | 목록 영역에만 스크롤을 준다 | 가장 작게 끝난다. 자료가 많으면 여전히 무겁다 |
| B | 페이지 나누기를 넣는다 | 서버 쪽 조회도 함께 바꿔야 한다 |
| C | 가상 스크롤 | 가장 빠르지만 부품을 바꿔야 한다 |

**A 로 시작해 무거운 셋만 B 로 가는 것**을 제안합니다.

### R3. 일정 화면 115px 🟡

전체 일정 · 내 일정. 달력 부품 높이가 고정이라 조금씩 넘친다.
달력 높이를 남은 높이에 맞추면 되는데, 주 수에 따라 칸 높이가 달라져
어색해 보일 수 있습니다. **눈으로 보고 정하는 편이 낫습니다.**

### R4. 요청 등록 129px 🟡

편집기(`min-height: 280`) + 첨부 + 버튼이 쌓여 조금 넘칩니다.
편집기 최소 높이를 줄이면 해결되지만 글 쓰는 자리가 좁아집니다.
**얼마까지 줄일지 정해 주시면 맞추겠습니다.**
