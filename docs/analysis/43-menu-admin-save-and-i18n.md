# 메뉴 관리 — 저장되지 않던 항목들과 늦게 뜨던 목록

## 1. 배지를 한 번 누르면 그 뒤로는 죽어 있었다

`/system/menu` 의 휴대폰사이즈사용 · 테블릿사이즈사용 배지는 **첫 클릭만 저장되고,
그 뒤로는 눌러도 요청이 나가지 않았다.** 배지가 "저장 중" 모습
(`opacity: 0.45` · `pointer-events: none` · 클릭 핸들러 없음)에 영구히 굳었다.

백엔드는 처음부터 정상이었다 — `PUT /auth/system/menu/{id}` 로 직접 넣어 보면
양방향으로 저장되고, `scom.system_menus.use_mobile · use_tablet` 칸도 있었다.

원인은 **반응성 프록시를 우회한 한 줄**이다.

```ts
// list.vue — 고치기 전
const saving = ((row as any).__sizeSaving ??= {}) as Record<string, boolean>;
saving[field] = true;   // ← 프록시를 거치지 않는다
```

`__sizeSaving` 이 없는 상태에서 `??=` 는 **프록시가 아니라 원본 객체**를 돌려준다.
그래서 `saving[field] = …` 는 화면을 다시 그리게 하지 못한다.

- **켤 때는** 같은 함수의 `meta[field] = next`(이쪽은 프록시라 반응성이 있다)가
  재렌더를 일으키고, 그때 읽힌 `saving` 이 `true` 라 배지가 잠긴다.
- **끌 때는**(`finally` 의 `false`) 재렌더를 일으킬 것이 없어 잠금이 풀리지 않는다.

상태 배지(`__statusSaving`)는 **행 프로퍼티를 바로** 세우기 때문에 이 문제가 없었다.
그래서 "상태는 잘 되는데 화면 크기만 안 된다" 로 보였다.

고친 방법 — 저장 표시를 행 프로퍼티에 **새 객체로 넣어** 프록시를 거치게 한다.

```ts
const setSaving = (value: boolean) => {
  target.__sizeSaving = { ...target.__sizeSaving, [field]: value };
};
```

> 교훈: `reactiveObj.foo ??= {}` 로 받은 객체를 그대로 고치면 반응성이 끊긴다.
> 중첩 객체를 상태로 쓸 때는 **매번 새 객체를 프록시에 넣는다.**

## 2. 수정 창에 있는데 저장되지 않던 항목 셋

숨김 체크는 넷이었지만 저장되는 것은 `hideInMenu` 하나뿐이었다.
나머지 셋은 표에 칸도 DTO 도 없어서 **요청 본문에 실려 나가지도 않았다.**

| 항목 | 칸 |
|---|---|
| 하위 메뉴 숨기기 | `hide_children_in_menu` |
| 브레드크럼에서 숨김 | `hide_in_breadcrumb` |
| 탭 바에서 숨김 | `hide_in_tab` |

셋 다 vben 라우트 메타가 그대로 알아듣는 이름이라, 칸을 만들고 DTO 에 실어 보내는 것으로
끝난다. `docs/sql/menu_hide_flags.sql` 로 칸을 넣었고(기본값 false — 기존 동작 그대로),
`/auth/menu/all` 이 함께 내려보내므로 라우트에 실제로 적용된다.

**목록 · 브레드크럼 · 탭 바에서만 감춘다.** 라우트는 그대로 만들어지므로 주소로 들어가면
화면은 열린다 — `status = 0`(비활성)과 다른 뜻이고 `use_mobile` · `use_tablet` 과 같은 성격이다.

## 3. 수정 창으로 저장하면 폼에 없는 메타가 초기화됐다

서버는 `meta` 를 통째로 받아 덮는다. 그런데 폼이 내놓는 `meta` 에는
**화면에 그려진 항목만** 들어 있었다. 그래서 제목 하나만 고쳐 저장해도
`domCached` · `authority` · `menuVisibleWithForbidden`, 그리고 유형이 달라 숨어 있던
`link` · `iframeSrc` 가 조용히 서버 기본값으로 되돌아갔다.

고친 방법 — **받아 온 메타 위에 폼 값을 얹는다.**

```ts
const { titleText: _titleText, ...keptMeta } = formData.value?.meta ?? {};
data.meta = { ...keptMeta, ...data.meta };

// 유형을 바꿔 입력칸이 사라졌으면 옛 주소는 남기지 않는다
data.meta.link = data.type === 'LINK' ? data.linkSrc : null;
data.meta.iframeSrc = data.type === 'EMBEDDED' ? data.linkSrc : null;
```

## 4. 목록이 늦게 뜬 진짜 이유 — 번역이 아니라 콘솔이었다

제목 칸이 그릴 때마다 `$t(row.meta.title)` 를 불렀다. 그런데 저장된 제목은 대부분
**번역 키가 아니라 이미 완성된 글자**다.

```
전체 메뉴 180건
  ├ 번역해야 하는 제목(키)     16건   ← scom.i18n_resources 에 있다
  └ 이미 완성된 글자          164건   ← 옮길 것이 없다
```

키가 아닌 제목마다 vue-i18n 이 "대체 언어로 넘어간다" 는 경고를 냈다.
**한 번 새로 그릴 때마다 492줄이었다.** 옮길 것은 열여섯뿐인데
경고를 콘솔에 찍는 값이 메인 스레드를 붙잡고 있었다.
[18번 문서 3절](18-i18n-fallback-warning.md)에서 이미 재어 둔 그대로다 —
**느린 것은 찾는 일이 아니라 찍는 일이고 23배 차이다.** 개발자 도구를 열어 두면 더 느리다.

### 4.1 서버가 옮겨서 내려보낸다

`GET /auth/system/menu/list?locale=ko` 가 제목의 번역을 함께 붙인다.

- 언어 하나에 해당하는 `scom.i18n_resources` 를 **왕복 한 번에 사전으로** 읽는다.
  실제로 쓰이는 제목만 `IN` 으로 좁히고, `(locale, key)` 인덱스를 새로 뒀다.
- **찾았을 때만** `meta.titleText` 에 담는다. 못 찾으면 `null` 이다 —
  프론트의 언어 파일에만 있는 키가 아직 있어서, 그때는 화면이 알던 방식으로 처리하게 남긴다.
- 요청한 언어에 없으면 `ko` 로 한 번 더 본다. 화면에 키가 그대로 뜨는 것보다 낫다.

키를 **문자열 그대로** 맞추므로 점이 없는 키(`role_management`)도 걸린다 —
"점이 있으면 키" 같은 어림짐작보다 정확하다(그래서 14건이 아니라 16건이다).

### 4.2 화면은 이름을 한 번만 정한다

목록을 받을 때 행마다 `displayTitle` 을 정해 얹어 둔다.

```ts
meta?.titleText || $tIfKey(meta?.title) || row.name
```

`$tIfKey` 는 `te()` 로 먼저 확인하므로 **없는 키에 경고를 내지 않는다**(18번 문서의 권장안 B).
템플릿은 문자열 하나를 찍기만 하므로, 다시 그릴 때도 정렬·필터를 걸 때도 옮기는 일이 없다.

같은 잘못이 **수정 창의 상위메뉴 선택기**에도 있었다(`afterFetch` 가 노드마다 `$t`,
`filterTreeNode` 가 한 글자마다 노드 수만큼 `$t`). 같은 규칙으로 바꿨다.

### 4.3 관리는 그대로 올바르게

- **번역 편집**: 다국어 번역 수정 창에서 값을 고치면 목록을 다시 받아 `titleText` 가 갱신된다.
- **키 편집**: 수정 창은 여전히 저장된 값(`meta.title`)을 고친다. `titleText` 는 읽기용이라
  되돌려 보내지 않는다.
- **언어 전환**: 제목은 **받아 온 시점의 언어**다. 그래서 언어가 바뀌면 목록을 다시 받는다.
- **찾기**: 필터는 보이는 이름 · 저장된 값(키) · 메뉴명을 모두 훑는다.
  키가 제목인 메뉴도 눈에 보이는 한국어로 찾힌다.
- **정렬**: 이제 **보이는 이름**으로 선다(`sortBy`). 전에는 키인 메뉴만 키 순서로 끼어들어
  화면과 어긋났다.

### 4.4 재어 본 결과

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 목록 한 번 새로 그릴 때 `[intlify]` 경고 | **492줄** | **0줄** |
| 제목 칸 정렬 한 번 | 492줄 | 0줄 |
| 제목 칸 필터 한 번 | 492줄 | 0줄 |
| 수정 창 한 번 열 때 | 180줄 + | 1줄 (vben 내부의 상위메뉴 라벨) |

## 5. 같은 목록을 여러 번 받던 것

같은 목록을 필요로 하는 곳이 둘이었고, 각자 따로 받았다.

1. 그리드 — 화면에 그리는 목록
2. 수정 창의 **상위메뉴 선택기**(`ApiTreeSelect`)

세어 보니 "화면 들어갈 때 두 번" 이 아니라 **수정 단추를 누르는 횟수만큼** 이었다.
창이 `destroyOnClose` 라 열 때마다 새로 만들어지고, 그때마다 선택기가 자기 요청을 냈다.

| 동작 | 전 | 후 |
|---|---|---|
| 화면 진입(SPA) | 1건 | 1건 |
| 수정 · 하위 추가 창 열기 | **매번 1건** | **0건** |
| 전체 새로고침(F5) | 2건 | **1건** |
| 저장한 뒤 | 1건(+ 다음 창 열기마다 1건) | 1건 |

받아 둔 것을 [`use-menu-tree.ts`](../../fronts/apps/jsini-portal/src/views/portal/system/menu/use-menu-tree.ts)
한 곳에 두고 둘이 나눠 쓴다.

- `reloadMenuTree()` — **그리드가** 쓴다. 언제나 서버에 묻고 받은 것을 여기 둔다.
  (첫 진입 · 새로고침 단추 · 저장한 뒤) 새로고침이 캐시를 보고 마는 일이 없다.
- `loadMenuTree()` — **선택기가** 쓴다. 받아 둔 것이 있으면 그것을 쓴다.
  같은 순간에 둘이 부르면(F5) 진행 중인 요청에 함께 붙어 한 번만 나간다.
- 화면을 떠나면 비운다(`clearMenuTree`) — 다시 들어왔을 때 옛 트리를 쓰지 않게.

곁들여 **일관성도 좋아졌다.** 전에는 선택기가 그리드보다 새 목록을 볼 수 있었다
(그리드를 그린 뒤 다른 사람이 메뉴를 바꾸고, 그 뒤에 창을 열면). 이제 선택기가 보는 것은
**그리드가 보고 있는 것과 항상 같다.** 저장에 성공하면 화면이 다시 받으므로 함께 새로워진다.

> 다른 화면 셋(역할 수정 창 · 메뉴롤 · 사람롤)도 `getMenuList` 를 부르지만
> 각자 한 번씩이고 화면이 달라 이번 범위에 넣지 않았다.

## 6. 남은 것

- **수정 창의 `activeIcon` · `activePath` · `affixTabOrder` · `maxNumOfOpenTab` ·
  `openInNewWindow` · `noBasicLayout` · `badgeVariants`** 는 프론트 타입에는 있는데
  표에 칸이 없다. 지금 화면에 입력칸이 없어 문제가 드러나지 않지만,
  넣으려면 2절과 같은 방식으로 칸부터 만들어야 한다.
- 18번 문서의 사이드바 쪽(`layout.vue` 의 `wrapperMenus`) 은 이 작업 범위가 아니었다.
  같은 원인이 남아 있는지 따로 확인이 필요하다.
