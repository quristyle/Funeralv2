# 부서 관리 화면 개선 · 메뉴롤 화면 신설

> 지시: "`/system/dept` 는 제안한 방향으로 진행하고, `/auth/menu-role` 도 만들어줘"

작업일: 2026-08-26

---

## 1. `/system/dept` — 좌측 회사 목록 + 우측 부서 트리

### 1.1 무엇이 불편했나

회사가 14개인데 화면 위쪽 드롭다운 하나로 골랐다. 여러 회사의 부서를 훑으려면
**고르고 → 펼치고 → 다시 고르고** 를 반복해야 하고, 지금 어느 회사를 보고 있는지도
드롭다운을 확인해야 알 수 있었다.

### 1.2 바꾼 것

왼쪽에 회사 목록, 오른쪽에 그 회사의 부서 트리를 둔다. 한 번 눌러 바로 옮겨 가고
무엇을 보고 있는지 늘 보인다. `/company/user` · `/system/role-map` 이 이미 쓰는 모양이라
관리 화면들 사이에서 조작이 일관된다.

회사 목록에는 **부서 수와 사용자 수**를 함께 보여 준다(직전 작업에서 만든 값).
어느 회사를 봐야 하는지 고르기 전에 규모를 알 수 있고, "부서는 있는데 사람이 없는 회사"
(GHUB: 부서 2 · 사용자 0)가 바로 드러난다. 회사명 검색칸도 두었다.

부서 트리에는 **사용자 열**을 더했다. 하위 부서가 있으면 `직접 / 전체` 로 보여 준다 —
접어 둔 상태에서 상위 부서만 보면 그 아래 인원이 안 보여 사람 없는 조직으로 착각한다.

회사명 열은 **'전체' 일 때만** 보여 준다. 한 회사를 보고 있으면 모든 행에 같은 값이
들어가 자리만 차지한다.

### 1.3 '전체' 가 실제로는 전체가 아니었다 🔴

새 화면을 확인하다 발견했다. **예전 화면의 '전체' 는 자기 회사만 보여 주고 있었다.**

```csharp
var targetCompanyId = companyId ?? userContext?.CompanyId;   // 비우면 '내 회사' 로 좁혀진다
```

회사 인자를 비우는 것으로 '전체' 를 표현할 수 없었던 것이다. BizSelect 의 `show-all` 로
'전체' 를 고르면 `undefined` 가 넘어가 → 서버가 로그인한 사람의 회사로 좁혔다.
`administrator`(미르포토) 로 보면 부서 2개만 나왔다.

`allCompanies` 파라미터를 새로 두어 뜻을 분명히 했다. 기존 호출은 그대로 동작한다.

| 호출 | 결과 |
|---|---|
| 인자 없음 | 요청한 사람의 회사 (기존 동작 유지) |
| `companyId=…` | 지정한 회사 |
| `allCompanies=true` | 전 회사 |

### 1.4 응답 타입이 실제와 달랐다

`company.ts` 의 `getCompanyList()` 반환 타입은 `{ items, total }` 로 적혀 있는데
**실제 응답은 `{ result, page }`** 다(AuthServer 응답 필터). 타입만 믿고 `res.items` 를
꺼내면 undefined 가 되고, 통째로 쓰면 배열이 아니라 객체가 들어와 `reduce` 에서 터진다.
실제로 그렇게 터졌다.

이 화면에서는 모양을 가리지 않고 꺼낸 뒤 **배열인지 확인하고** 쓴다. 타입 선언을 고치는
것이 맞지만 다른 화면들이 그 타입을 함께 쓰고 있어 건드리지 않았다 → 아래 5절.

## 2. `/auth/menu-role` — 메뉴 기준 권한 현황

### 2.1 무엇을 만들었나

`/system/role-map` 은 **역할**에서 출발한다 — "이 역할은 어떤 메뉴를 쓰나".
이 화면은 반대다 — **"이 메뉴는 누가 쓸 수 있나"**.

지금까지 그 방향으로 볼 방법이 없었다. "이 메뉴에 파트너도 들어오나?" 를 알려면
역할을 하나씩 열어 메뉴 목록을 훑어야 했고, 역할이 넷이면 네 번 확인해야 했다.

```
왼쪽   메뉴 트리 (검색 · 93개)
오른쪽 이 메뉴를 쓸 수 있는 역할 × 권한   ← 여기서 바로 고친다
       그 역할을 통해 닿는 회사 · 부서 · 사용자 (어느 역할 때문인지 함께)
       실제 열람 가능 사용자 수
```

### 2.2 만든 것

```
DTOs/MenuRoleDto.cs             메뉴 기준 현황
Services/MenuRoleService.cs     role_menus · role_companies · role_departments
                                · role_accounts 를 거꾸로 훑는다
Endpoints/MenuRoleEndpoints.cs  GET /system/menu-role/{menuId}
api/portal/system/menu-role.ts  프론트 API
views/portal/auth/menu-role/    화면
```

### 2.3 저장 경로를 새로 만들지 않았다

이 서비스는 **읽기 전용**이다. 저장은 이미 있는 것을 그대로 쓴다.

| 무엇 | 어디로 |
|---|---|
| 역할↔메뉴 권한 | `POST /system/role-permission/roles/{roleId}/menus/save` |
| 역할↔회사·부서·사람 해제 | `POST /system/role-scope/remove` |

같은 일을 하는 저장 경로를 두 개 만들면 한쪽에만 규칙이 붙어 갈라진다.

**주의 하나**: `saveRoleMenus` 는 그 역할의 메뉴 권한 목록을 **통째로** 받는다.
이 화면은 메뉴 하나만 보고 있으므로, 저장할 때 그 역할의 현재 목록을 먼저 받아
이 메뉴 한 줄만 갈아 끼워 보낸다. 그러지 않으면 다른 메뉴의 권한이 전부 지워진다.

### 2.4 메뉴가 쓰지 않는 권한 항목은 보여 주지 않는다

메뉴가 "쓰지 않는다" 고 지정한 항목(`system_menus.use_*`)은 역할에 켜 두어도 효과가 없다
(서버가 AND 로 묶는다). 켜도 아무 일이 없는 체크박스를 보여 주면
"켰는데 왜 안 되지" 로 헤매게 되므로, 쓰는 항목만 보여 준다.

같은 규칙을 '닿는 대상' 계산에도 적용했다 — `can_view` 가 켜져 있어도 메뉴가 열람을
쓰지 않으면 그 역할은 대상에서 뺀다. 화면이 "닿는다" 고 말한 대상이 실제로는
못 들어오는 일이 없어야 한다.

### 2.5 이 화면이 스스로 권한 구멍이 될 수 있었다 🔴

손대기 전 상태를 재어 보니 **네 역할 모두 `can_view`·`can_update` 가 켜져 있었다**
(`role_menu_backfill.sql` 이 채워 둔 탓). 그대로 두면 파트너 계정 39개가 이 화면에서

- 자기 역할에 아무 메뉴나 열람 권한을 켤 수 있고
- 남의 회사·부서에 걸린 역할을 해제할 수 있다

즉 **권한을 스스로 올리는 문**이 된다. 화면을 만들면서 그 문을 열어 둘 수는 없어
[`docs/sql/menu_role_screen.sql`](../sql/menu_role_screen.sql) 로 좁혔다(실행 완료).

| 역할 | 열람 | 조회 | 수정 |
|---|---|---|---|
| 관리자 | O | O | O |
| 시스템관리자 | O | O | O |
| 파트너 관리자 | — | — | — |
| 파트너 | — | — | — |

**읽기까지 막은 이유**: 이 화면은 어느 회사·부서·사람이 어떤 메뉴에 닿는지를 통째로
보여 준다. 조직 구조가 그대로 드러나므로 열람도 관리자만 둔다.
관리자 역할 목록은 F.A.Q · 자료실과 같게 잡았다(D-H1 과 같은 건).

메뉴가 쓰는 항목도 `열람·조회·수정` 만으로 좁혔다 — 새로 만들거나 지우는 화면이 아니다.

## 4. 실패를 '없음' 으로 보여 주지 않게 했다

두 화면 모두 못 불러왔을 때를 구분한다.

- `/system/dept` — 회사 목록 실패 시 메시지

  뜻하지는 않습니다.**"

권한 화면에서 이 오해가 가장 나쁘다 — 열려 있는데 닫힌 줄 알게 된다.
백엔드가 아직 반영되지 않은 지금 상태에서 실제로 그 문구가 나오는 것을 확인했다.

## 6. 왼쪽 메뉴 목록을 실제 메뉴처럼 보이게 (2026-08-28)

> 지시: "왼쪽에 보여지는 메뉴목록에 아이콘 표시와 다국어 표현이
> **실제 사용하는 아이콘과 다국어가 적용되어** 보여지도록 개선해 줘."

이 화면은 "그 메뉴가 어디 있더라" 를 찾는 화면이다. 그런데 목록이
**사이드바와 다르게 생겨서** 눈으로 짚을 수가 없었다. 두 군데가 어긋나 있었다.

### 6.1 이름 — 번역 키가 그대로 보였다

목록은 `(m as any).title` 을 읽었는데 API 는 그 값을 **`meta.title`** 에 담아 준다.
그래서 늘 `undefined` 였고 `m.name`(원래 이름)으로 떨어졌다 —
사이드바에 `분석` 으로 뜨는 메뉴가 여기서는 `Analytics` 로 보였다.

`meta.title` 을 읽도록 고치는 것만으로는 부족하다. `system_menus.title` 에는
**번역 키와 완성된 글자가 섞여 있다.**

| 예 | 무엇 |
|---|---|
| `page.dashboard.analytics` · `menu.account_management` | 번역 키 |
| `상태관리` · `Github` · `F.A.Q` | 완성된 글자 |

그래서 사이드바와 **같은 규칙**을 쓴다 — `$tIfKey()`. 키면 번역하고 아니면 그대로 둔다.
`$t()` 를 그냥 쓰면 완성된 글자마다 vue-i18n 이 대체 언어를 훑으며 경고를 두 줄씩
찍는다([18번 문서](18-i18n-fallback-warning.md)). 이 화면은 메뉴를 263개 그리므로
특히 그렇다. (`/system/menu` 는 아직 `$t()` 를 쓴다 — 그쪽은 이번 지시 밖이라 두었다.)

번역도 원래 이름도 없으면 `name` → `path` 순으로 떨어진다.
**빈 줄만은 만들지 않는다** — 고를 수 없는 항목이 되기 때문이다.

### 6.2 아이콘 — 폴더/문서 둘뿐이었다

`meta.icon`(`lucide:*` · `mdi:*` · `logos:*` …)을 아예 보지 않고
`isDir` 로 폴더·문서만 그렸다. 활성 메뉴 263개 중 **262개에 아이콘이 있는데**
전부 같은 그림 두 개로 뭉개진 셈이다.

이제 그 값을 그대로 그린다. 없는 한 개는 폴더/문서로 떨어지고,
버튼 권한은 메뉴가 아니므로 자물쇠(`carbon:security`)로 구분한다
(메뉴 관리 화면과 같은 규칙).

### 6.3 곁따라 고친 것 둘

**오른쪽 제목도 같은 규칙을 태웠다.** 서버가 주는 `menuName` 은 DB 의 `title`
그대로라 번역 키일 수 있다. 왼쪽만 고치면 **한 화면에서 같은 메뉴가 두 이름**으로 보인다.

**검색이 원래 이름·번역 키로도 걸리게 했다.** 화면에는 `분석` 이라고 떠도 사람은
`analytics` 나 `Analytics` 로 기억하고 있을 수 있다. 보이는 이름·원래 이름·번역 키·경로
넷 중 하나만 걸리면 찾힌다.

그리고 **검색하면 펼친다.** 검색은 걸린 것과 부모만 남기는데, 부모가 접혀 있으면
antd 트리는 자식을 그리지 않는다. 그래서 찾았는데도 **부모 이름만 보이고 정작 찾던
메뉴가 안 보였다**(메뉴가 263개라 접힌 상태가 기본이므로 거의 항상). 검색어를 지울
때는 접지 않는다 — 사람이 직접 펼쳐 둔 것까지 닫으면 자리를 잃는다.

### 6.4 확인한 것

개발 서버에서 실제로 눌러 확인했다.

| | 결과 |
|---|---|
