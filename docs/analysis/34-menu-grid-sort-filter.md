# `/system/menu` 그리드에 정렬·필터 넣기 (드래그와 충돌하지 않게)

> 지시: "메뉴관리 화면은 메뉴를 이동하여 순서나 부모메뉴를 변경할 수 있다.
> 해당 그리드 컬럼에 정렬, 필터를 사용할 수 있나? 있다면 추가해 줘."

작업일: 2026-08-28

---

## 1. 쓸 수 있다. 다만 그냥 켜면 순서가 망가진다

이 화면의 저장 방식이 문제의 핵심이다. 자리 이동은
**"화면에 보이는 그대로가 진짜 순서"** 로 저장된다 —
`collectOrderChanges()` 가 트리를 훑으며 **배열에서의 자리(index)를 `orderNo` 로**
삼아 서버에 보낸다.

정렬을 걸면 화면의 배치는 `order_no` 가 아니라 **정렬 기준**을 따른다.
그 상태에서 한 줄이라도 끌면 정렬된 자리 번호가 그대로 새 `order_no` 로 저장돼
**메뉴 263개의 순번이 통째로 정렬 결과로 덮인다.** 되돌릴 방법은 손으로 다시 옮기는 것뿐이다.
필터도 같다 — 걸러진 뒤에는 형제 일부가 화면에서 빠져 있어 자리 번호가 실제와 다르다.

그래서 정렬·필터를 넣되 **둘 중 하나라도 걸려 있으면 자리 이동을 저장하지 않는다.**
막지 않고 저장하는 쪽이 훨씬 나쁘다 — 사용자는 한 줄을 옮겼다고 생각하는데
실제로는 전체 순번이 바뀐다.

| | 하는 일 |
|---|---|
| 정렬·필터가 걸리면 | 손잡이를 흐리게(회색 · `cursor-not-allowed`) 하고 이유를 툴팁으로 |
| 그래도 끌면 | `rowDragend` 가 **저장하지 않고** 안내를 띄운 뒤 서버 값으로 되돌린다 |
| 정렬·필터를 풀면 | 손잡이가 원래대로 돌아온다 |

상태는 vxe 의 `sortChange` · `filterChange` 로 따라간다.

## 2. 어느 칸에 무엇을 넣었나

| 칸 | 정렬 | 필터 | 메모 |
|---|---|---|---|
| 제목 | ○ | 입력 | 보이는 이름 · 번역 키 · 원래 이름 중 아무거나로 걸린다 |
| 유형 | ○ | 목록 | 디렉토리 · 메뉴 · 버튼 · 내장 페이지 · 링크 |
| 정렬 순서 | ○ | — | 숫자라 입력 필터가 쓸모없다 |
| 메뉴명 · 권한 코드 · 라우트 경로 | ○ | 입력 | |
| 컴포넌트 | ○ | 입력 | 이 칸은 종류에 따라 컴포넌트 · iframe 주소 · 링크를 보여 준다. **셋을 함께 훑는다** |
| 상태 | ○ | 목록 | 활성 · 비활성 |

**제목 필터가 세 가지를 훑는 이유** — `meta.title` 에는 번역 키
(`page.dashboard.analytics`)와 완성된 글자(`상태관리`)가 섞여 있다. 사이드바와 같은
규칙(`$tIfKey`)으로 옮긴 글자로도, 원래 키로도, 원래 이름(`name`)으로도 찾히게 했다.
화면에는 '분석' 으로 떠도 사람은 'Analytics' 로 기억하고 있을 수 있다.

## 3. 필터는 **머리글 아래 칸**으로 (팝업이 아니라)

> 추가 지시: "그리드 컬럼 헤드 아래에 제공하면 필터에 입력값을 넣고 사용 시
> 사용자의 행동이 줄고 더 빠르게 필터링할 수 있어 편리하다."

깔때기를 눌러 팝업을 열고 → 값을 넣고 → '적용' 을 누르는 **세 동작**을,
머리글 아래에 **바로 치는 한 동작**으로 줄였다. 확인 버튼이 없다 — 치면 걸린다.

- 글자 칸: 입력창. **글자마다 다시 거르지는 않는다**(263행 트리를 매 글자마다
  다시 세우면 입력이 끊긴다). 250ms 쉬면 건다.
- 정해진 값 칸(유형·상태): 고르는 칸. 고르는 즉시 걸린다.

**조건과 판정은 vxe 의 것을 그대로 쓴다**(`filters` · `filterMethod`). 아래 칸은
`setFilter()` 로 그 조건에 값을 넣어 줄 뿐이다 — 걸러내는 규칙을 두 벌로 만들면
언젠가 둘이 어긋난다.

그래서 두 가지를 함께 정리했다.

- `filterRender` 를 두지 않는다. 두면 팝업에도 입력칸이 생겨 **같은 조건을 넣는
  자리가 두 곳**이 된다.
- 깔때기 아이콘을 감춘다(CSS). 남겨 두면 눌렀을 때 '적용 · 초기화' 버튼만 있는
  **빈 팝업**이 열린다. 정렬 화살표는 그대로 둔다.

머리글이 두 줄이 되므로 위아래 여백을 줄였다(머리글 높이 103px).

**손대야 했던 것 하나** — 머리글 슬롯은 `column.slots.header` 다. 제목·상태 칸은
본문도 슬롯으로 그리므로 **둘을 합쳐 적어야 한다.** 하나만 적으면 다른 하나가 사라진다.

또 머리글 안의 입력에는 `@keydown.stop` 과 `@click.stop` 이 필요하다 —
이 그리드는 셀 편집을 켜 두어서 머리글에서 친 글쇠가 표로 새면 엉뚱한 셀이
편집으로 들어가고, 머리글 클릭은 정렬 토글이라 같이 눌린다.

## 4. `params.filterList` 는 쓰지 않았다 (덮어쓴다)

유형·상태처럼 값이 정해진 칸에 원래 `params: { filterList: true }` 가 붙어 있었다.
그 옵션은 프레임워크가 필터를 열 때마다 **화면 데이터에서 값을 긁어 목록을 새로 만들어
덮어쓴다**(`use-vxe-grid.vue` 의 `onFilterVisible`). 실제로 그래서 —

- 이름표가 **저장된 값 그대로** 나왔다: `디렉토리` 가 아니라 `CATALOG`, 상태는 `1` · `0`.
- 트리 그리드에서는 긁어 오는 범위가 일부라 **다섯 종류 중 둘만** 목록에 떴다.

종류를 이미 알고 있는 칸이므로 `filterList` 를 떼고 옵션을 직접 적었다.
떼자마자 다섯 개가 한국어 이름표로 모두 나왔다.

---

## 5. 트리는 걱정한 것보다 잘 버틴다

필터를 걸면 **걸린 것의 부모가 함께 남는다**(vxe 가 알아서 한다). 그래서 트리가
끊기지 않고, 찾은 메뉴가 어디 밑에 있는지도 같이 보인다.
정렬도 **형제끼리만** 다시 서므로 부모·자식 관계는 그대로다.

(같은 트리라도 `/auth/menu-role` 은 직접 만든 트리라 검색 시 펼치는 것을 손으로
넣어야 했다. 이쪽은 vxe 가 해 준다.)

## 6. 확인한 것

개발 서버에서 실제로 눌러 확인했다.

| | 결과 |
|---|---|
| 컬럼 | 값 칸 8개 전부 정렬, 7개 필터(정렬 순서만 제외) |
| 필터 (메뉴명 `Analytics`) | 798행 → **대시보드(부모) + 분석** 만 남음 |
| 필터 (유형 `내장 페이지`) | 798행 → 60행. 유형 칸에 **디렉토리(부모)·내장 페이지만** |
| 유형 필터 목록 | `디렉토리 · 메뉴 · 버튼 · 내장 페이지 · 링크` (전부 한국어) |
| 정렬 (라우트 경로 · 제목) | 형제 안에서 다시 서고 트리 유지 |
| 정렬 걸었을 때 손잡이 | `cursor-not-allowed` · 흐림 · 툴팁에 이유 |
| 필터 걸었을 때 손잡이 | 같음 |
| 둘 다 풀었을 때 | `cursor: move` 로 복귀, 첫 행이 원래대로(`시스템`) |

**머리글 아래 필터 칸** (추가 지시분)

| | 결과 |
|---|---|
| 렌더 | 입력칸 5개 · 고르는 칸 2개, 정렬 화살표 유지, **깔때기는 안 보임** |
| 치는 즉시 (`Analytics`) | **버튼 한 번도 안 누르고** 798행 → 대시보드(부모) + 분석 |
| 지우면 | 798행으로 복귀, 자리 이동 다시 가능 |
| 고르는 칸 (유형 `내장 페이지`) | 60행, 유형 칸에 디렉토리(부모)·내장 페이지만 |
| 두 칸 함께 (유형 `메뉴` + 경로 `system`) | 22행. 조건이 **AND** 로 걸린다 |
| 그때 남은 `권한`(`/auth`) | 자식 `역할 관리`(`/system/role-map`)가 걸려 **부모로 남은 것** — 정상 |
| 필터 칸에 값이 있는 동안 | 자리 이동 손잡이 비활성 (`setFilter` 는 `filterChange` 를 쏘지 않아 직접 세운다) |

콘솔 오류 없음 · `pnpm vite build` 통과 · eslint 새 오류 없음.

### 확인하지 못한 것 🟡

**"정렬 중에 실제로 끌었을 때 저장되지 않는다" 를 몸소 끌어서는 확인하지 못했다.**
vxe 의 행 드래그는 native `draggable` 이 아니라 마우스 이벤트로 동작해서 흉내 내기가
까다롭고, **성공하는 쪽(정상 드래그)을 시험하면 실제 메뉴 순서가 DB 에서 바뀐다.**
개발자가 쓰는 실데이터라 그 시험은 하지 않았다.

대신 그 판단에 쓰이는 상태(`viewReordered`)가 정렬·필터에 따라 **정확히 켜지고 꺼지는 것**을
손잡이 모양으로 확인했다. `rowDragend` 는 같은 값을 읽어 앞에서 되돌린다.
