## 1. 🔴 게이트웨이 우회 인증 우회 — **조치 완료**

### 무슨 문제였나

내부 서비스들이 **모든 네트워크 인터페이스(`http://+:포트`)에 열려** 있었다.
그런데 이 서비스들은 신원을 **게이트웨이가 붙여 주는 `X-User-Id` 헤더로 판단**한다
(`UserContext.BindAsync`).

게이트웨이는 이 헤더를 제대로 다루고 있었다 — 외부에서 들어온 `X-User-*` 를 지우고,
JWT 를 검증한 뒤에만 다시 붙인다(`ApiGateway/Program.cs:71`). 설계는 옳았다.
문제는 **그 게이트웨이를 건너뛸 수 있었다**는 점이다.

실제로 확인한 결과다.

```
게이트웨이 경유, 토큰 없음
  GET http://localhost:5265/api/funeral/building/room/list      → 401

서비스 직접 호출 + 헤더 위조
  GET http://192.168.55.9:5320/building/room/list
      X-User-Id: jsini-boss-quristyle
      X-User-Role: SYSTEM_ADMINISTRATOR                          → 200 + 실데이터
```

같은 네트워크에 있으면 누구나 아무 계정으로 위장할 수 있었다.
비밀번호도 토큰도 필요 없었다.

### 어떻게 고쳤나

내부 서비스를 **루프백에만 바인딩**했다. AuthServer 는 원래 그렇게 되어 있었고,
나머지가 어긋나 있었다.

| 서비스 | 전 | 후 |
|---|---|---|
| AuthServer | `127.0.0.1:5264` | 그대로 |
| funeralv2Api | `*:5320` | `127.0.0.1:5320` |
| FileServer | `*:5350` | `127.0.0.1:5350` |
| HelpDeskServer | `*:5400` | `127.0.0.1:5400` |
| **ApiGateway** | `0.0.0.0:5265` | 그대로 (유일한 외부 창구) |

`appsettings.json` 뿐 아니라 **`appsettings.Development.json` / `.Production.json` 이
같은 키를 다시 `+:포트` 로 덮고 있어서** 그쪽까지 고쳐야 반영됐다.

검증: 외부 IP 로 4개 포트 모두 연결 거부(000), 게이트웨이 경유 경로는 전부 정상.

### 남은 조건

서비스를 **다른 장비로 분리하려면 이 포트를 다시 열어야 하는데, 그때는 반드시
서비스 간 인증을 먼저 붙여야 한다.** 헤더를 그대로 믿는 구조는 그대로이기 때문이다.
선택지는 §2 에 적었다. 각 `appsettings.json` 의 `//kestrel` 주석에도 같은 내용을 남겼다.

## 2. 🔴 JWT 서명 키가 저장소에 평문 — **결정 필요**

### 현황

**토큰을 서명·검증하는 바로 그 키**가 git 에 추적되는 파일에 그대로 들어 있다.

| 파일 | 값 |
|---|---|
| `ApiGateway/appsettings.json` | `a-very-secret-key-that-is-long-enough-for-security` |
| `microservices/FileServer/appsettings.json` | 〃 |
| `microservices/funeralv2Api/appsettings.json` | 〃 |
| `microservices/HelpDeskServer/appsettings.json` | 〃 + `quristyle_blabbbbbla_secret_key_1234567890!@#$` |
| `funeralv2Api`, `HelpDeskServer` | VAPID `PrivateKey: [REVOKED-VAPID-PRIVATE-KEY]-...` (웹푸시 발송 권한) |

저장소를 열람할 수 있는 사람은 **누구나 관리자 토큰을 직접 만들 수 있다.**
§1 을 막았어도 이건 그대로 남아 있다 — 게이트웨이를 정상 통과하는 위조 토큰이기 때문이다.

### 왜 자율 진행에서 바꾸지 않았나

키를 교체하면 **모든 서비스가 같은 새 키를 동시에 알아야 하고, 기존 토큰이 전부 무효**가 된다.
이 장비 밖에 다른 배포 환경이 있는지 확인할 수 없는 상태에서 키를 돌리면,
그 환경은 자리를 비우신 동안 로그인 자체가 막힌다. 그래서 손대지 않았다.

### 선택지

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 환경변수** (권장 1단계) | `Jwt__Key` 환경변수로 주입. ASP.NET 이 기본 지원하므로 코드 변경 없음 | 즉시 가능, 저장소에서 값 제거 | 장비마다 환경변수 관리 필요 |
| **B. appsettings.Local.json** | 이미 쓰는 방식(gitignore 됨). 추적 파일에는 자리표시자만 | 기존 관행과 동일 | 배포 시 파일 배치 절차 필요 |
| **C. 시크릿 저장소** | Vault / AWS Secrets Manager / Azure Key Vault | 회전·감사 가능 | 인프라 도입 필요 |

### 권장 순서

1. **새 키 생성** — `openssl rand -base64 48`
2. 모든 서비스에 `Jwt__Key` 환경변수로 주입 (A안)
3. 추적 파일의 값을 `"__SET_VIA_ENV__"` 같은 자리표시자로 교체
4. 서비스 일괄 재기동 → **전 사용자 재로그인 발생**
5. VAPID 키도 같은 방식으로 분리 (`Vapid__PrivateKey`)

### 저장소 이력

값이 이미 커밋 이력에 남아 있다. 완전히 지우려면 `git filter-repo` 로 이력을 다시 써야 하고,
**협업자 전원이 다시 clone** 해야 한다. 이건 확실히 결정이 필요한 사안이라 손대지 않았다.
실무적으로는 **이력 정리보다 키 교체가 먼저**다 — 교체하면 옛 값은 무의미해진다.

## 3. 🟠 헬프데스크만 다른 DB·계정 — **결정 필요**

### 현황

| 서비스 | DB | 스키마 | 계정 |
|---|---|---|---|
| AuthServer | `funeralv2` | `scom` | `funeralv2` |
| FileServer | `funeralv2` | `scom` | `funeralv2` |
| funeralv2Api | `funeralv2` | `smfr` | `funeralv2` |
| **HelpDeskServer** | **`jinrecept`** | **`jsini`** | **`jsini`** |

세 서비스는 한 DB 를 스키마로 나눠 쓰고, 헬프데스크만 별도 DB 에 별도 계정이다.
독자 시스템이던 시절의 흔적이다.

### 지금 생기는 불편

- **트랜잭션이 걸치지 못한다.** 계정 연결(`jsini.auth_user_links`)처럼 두 세계를 잇는
  데이터가 한쪽에만 있어, 포털에서 계정을 지워도 헬프데스크 연결은 남는다.
- **백업·복구 단위가 둘**이다.
- 헬프데스크 계정 비밀번호가 별도로 관리된다.

### 선택지

| 안 | 내용 | 평가 |
|---|---|---|
| **A. 현행 유지** | 스키마만 문서화 | MSA 관점에서는 오히려 정석(서비스별 DB). 단 계정 연결 정합성은 애플리케이션이 책임져야 함 |
| **B. 같은 DB 로 통합** | `jinrecept.jsini` → `funeralv2.jsini` 스키마로 이전 | 백업·계정 관리 단순. 마이그레이션 작업 필요(테이블 30여 개 + 데이터) |
| **C. 완전 분리 강화** | 서비스별로 DB 계정·권한 분리 | 가장 MSA 다움. 지금 세 서비스가 한 계정을 공유하는 것부터 정리해야 함 |

**의견:** MSA 원칙만 보면 C 가 맞지만, 실제 운영 인원과 규모를 보면 **B 가 실용적**이다.
지금은 "서비스별 DB" 의 이점(독립 배포·장애 격리)을 누리지 못하면서 불편만 지고 있다.
다만 이전 작업이 가볍지 않아 결정이 필요하다.

## 4. 🟠 응답 봉투 불일치

### 현황

표준은 `JSini.Shared.DTOs.ApiResponse<T>` 다.

```json
{ "success": true, "code": "S000", "message": "...", "data": { "result": [...], "page": { "total": n } } }
```

`ApiResponseFilter` 가 자동으로 감싸므로 **단건도 `result` 배열**로 나온다. 이건 일관성 있다.

어긋나는 곳이 둘 있다.

**(1) 헬프데스크 전반** — `{ success, message, data, meta }` + 총건수를 봉투 최상위에
`totalcount` / `totalpagecount`(전부 소문자)로 싣는다. JinRestApi 를 그대로 이식한 결과다.
→ **프론트의 `api/helpdesk/request.ts` 가 흡수**하고 있다. 서버를 바꾸면 아직 살아 있는
JinReception 과 어긋나므로 현행 유지가 맞다.

**(2) 헬프데스크 일정 API** — `ScheduleEndpoints` 만 `{ data: [...] }` 로 `success` 조차 없다.
헬프데스크 안에서도 **혼자 다른** 경우다.
→ 프론트 `unwrapSchedule()` 로 흡수했다. 서버를 고치는 게 맞지만 JinReception 영향 확인이 필요하다.

### 권장

`ScheduleEndpoints` 를 `ApiResponseBuilder` 로 맞추고 프론트의 예외 처리를 걷어낸다.
JinReception 이 이 API 를 쓰는지 확인한 뒤 진행 — **결정 필요**.

## 5. 🟡 서비스별 미들웨어 제각각 — **조치 완료**

점검 당시 상태다.

| 서비스 | 헬스체크 | 전역예외 | Serilog | CORS |
|---|---|---|---|---|
| AuthServer | O | O | **X → O** | X |
| funeralv2Api | O | O | O | O |
| FileServer | O | O | O | O |
| AIAgentServer | O | O | **X → O** | O |
| HelpDeskServer | O | O | O | O |

- **Serilog**: AuthServer·AIAgentServer 에 추가했다. 이제 다섯 서비스가 같은 형식으로 로그를 남기고,
  요청 한 줄 로그(`UseSerilogRequestLogging`)도 공통이다. 장애를 쫓을 때 모양이 제각각이면 시간이 배로 든다.
  AuthServer 는 `Microsoft.Extensions.Configuration.Binder` 를 직접 참조하면서 실제로 쓰지는 않아
  Serilog 와 버전이 충돌했다. 쓰지 않는 참조라 걷어냈다.
- **CORS**: 게이트웨이가 전담한다(`AllowFrontend`, `http://localhost:5555` 허용).
  내부 서비스의 `AllowAll` 은 이제 루프백 전용이라 실효가 없다.
  **일부러 남겨 두었다** — CORS 는 브라우저에만 적용되므로 지워도 보안이 나아지지 않는 반면,
  건드리면 예상 못 한 곳이 깨질 수 있다. 실제 위험은 §1 의 바인딩으로 이미 막았다.

## 5-1. 🔴 비밀번호 평문 저장 — **조치 완료**

### 무슨 문제였나

`scom.accounts.password` 에 비밀번호가 **평문 그대로** 들어 있었다.
로그인도 `account.Password != request.Password` 로 문자열을 그냥 비교했다.
DB 를 읽을 수 있는 사람은 전 사용자의 비밀번호를 그대로 볼 수 있었다.

### 어떻게 고쳤나

PBKDF2(HMAC-SHA256, 600,000회) 해시를 넣었다 — `Services/PasswordHasher.cs`.
외부 패키지 없이 .NET 표준만 쓴다.

핵심은 **기존 평문 값과 함께 쓸 수 있게** 만든 점이다.

- 저장값이 해시 형식(`pbkdf2$sha256$...`)이 아니면 평문으로 보고 비교한다.
- **로그인에 성공한 그 순간** 다시 해시해서 저장한다. 평문 비밀번호를 아는 유일한 시점이다.
- 저장에 실패해도 로그인은 막지 않는다.

그래서 **도입 시점에 잠기는 계정이 하나도 없고**, 사용자는 아무것도 하지 않아도
다음 로그인 때 조용히 해시로 바뀐다. 사전 마이그레이션이 필요 없다.

로그인 경로가 둘(`AuthEndpoints.cs` 의 인라인 구현과 `AuthService.LoginAsync`)이라
**양쪽 모두** 적용했다. 비밀번호 변경(`UserService`)도 해시로 저장한다.

### 검증

임시 계정으로 네 경로를 모두 확인한 뒤 계정을 지웠다.

| 확인 | 결과 |
|---|---|
| 평문 저장 상태로 로그인 | 200 (기존 사용자와 동일 조건) |
| 로그인 직후 DB 값 | `pbkdf2$sha256$600000$...` 로 승격됨 |
| 승격 후 같은 비밀번호로 재로그인 | 200 |
| 틀린 비밀번호 | 401 |

### 남은 것

현재 실계정 4개는 아직 평문이다. **각자 다음 로그인 때 자동으로 바뀐다.**
오래 로그인하지 않는 계정이 신경 쓰이면 비밀번호 재설정을 안내하면 된다.

## 8. ⚪ API 버저닝 미도입

모든 엔드포인트가 `/api/{서비스}/...` 로 버전이 없다.
지금은 프론트와 백엔드를 같이 배포하므로 문제가 드러나지 않지만,
**플레이어(Flutter)** 처럼 별도 배포 주기를 갖는 클라이언트가 있어 위험이 있다.
플레이어가 쓰는 익명 엔드포인트(장비·고인 조회)를 바꾸면 구버전 앱이 깨진다.

→ 권장: 최소한 플레이어가 쓰는 익명 경로만이라도 `/api/funeral/v1/...` 로 고정.

---

## 9. ⚪ 컨테이너화·CI 미도입

- `Dockerfile` / `docker-compose.yml` 없음. 기동은 `backend_run_ubuntu.sh` 가 터미널 6개를 띄우는 방식.
- `.github/workflows/release.yml` 은 있으나 이 백엔드와 무관하다(플레이어 릴리즈용으로 보임).
- 서비스 간 기동 순서·의존성이 스크립트에 암묵적이다.

→ compose 도입이 가장 효과가 크다. 다만 DB 가 외부(jin114.co.kr)라 부분 도입이 된다.

## 10. 추가 MSA 분리 검토

지시하신 "추가 분리가 필요하면 MSA 를 만들어도 좋다"에 대한 검토다.

### 규모

| 서비스 | 파일 | 줄 수 |
|---|---|---|
| HelpDeskServer | 153 | **63,079** |
| AuthServer | 96 | 12,896 |
| funeralv2Api | 78 | 9,687 |
| FileServer | 9 | 2,704 |
| AIAgentServer | 4 | 543 |
| ApiGateway | 1 | 309 |

HelpDeskServer 가 압도적으로 크다. 엔드포인트 그룹이 25개다.

### 분리 후보

**(1) 알림/푸시 → `NotificationServer`** — 추천도 높음
`/api/push` + VAPID + 이메일(`EMailUtil`) + 워커. 지금 헬프데스크에만 있는데
**포털·장례식장도 알림이 필요하다.** 공통으로 빼면 세 시스템이 함께 쓴다.
VAPID 키를 한 곳에서만 관리하게 되는 이점도 크다.

**(2) 외부 연동(한주/OADR) → `IntegrationServer`** — 추천도 중간
지금 게이트웨이가 `nums.hanjucorp.co.kr` 로 직접 프록시한다(`oadr-route`).
게이트웨이가 외부 시스템을 아는 건 역할을 넘는다. 연동·캐싱·장애 격리를 맡을 서비스가 맞다.
리포트 화면 13개가 여기에 의존한다.

**(3) WBS/프로젝트 → `ProjectServer`** — 추천도 낮음
`/api/wbs`, `/api/wbs-diagram`, `/api/wbslink`, `/api/project`.
헬프데스크 요청과 얽혀 있어 지금 떼면 서비스 간 호출만 늘어난다.

### 먼저 할 일

분리보다 **§3(DB 정리)과 §2(시크릿)** 가 먼저다.
지금 나누면 DB 를 공유하는 서비스가 하나 더 느는 것뿐이다.

## 11. 이번에 실제로 조치한 것

| 항목 | 내용 |
|---|---|
| 인증 우회 차단 | 내부 서비스 4개 루프백 바인딩 (`appsettings` 3종 전부) |
| 비밀번호 해시 | PBKDF2 600k회 도입. 기존 평문과 호환되어 잠기는 계정 없이 로그인 시 자동 승격 |
| 시크릿 주입 준비 | `scripts/secrets.env` 가 있으면 환경변수로 실어 주는 구조. 없으면 종전과 동일 동작 |
| 레이트 리미팅 | 게이트웨이에서 로그인·비밀번호 초기화를 IP 당 1분 10회로 제한 |
| 배포 도구 이전 | 헬프데스크 → 포털. 대상을 설정(`Release:Targets`)으로 일반화 |
| 공지 기능 | 포털 공통 공지 + 팝업 + 첨부. 헬프데스크 공지 제거 |
| FileServer 복구 | 저장 경로·DB 연결 문자열이 없어 업로드가 아예 실패하던 상태를 고침 |
| 스모크 테스트 | `scripts/smoke-test.sh` 추가 |
