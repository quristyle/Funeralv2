# 안드로이드 앱 기본설계

## 1. 목적과 설계 기준

현재 업무 포털은 `https://portal.jsini.co.kr` 에서 설치형 PWA로 제공된다. 안드로이드 앱은 기존 포털의 로그인·업무 화면·권한·알림을 다시 만드는 대신, 우선 포털을 Play 스토어에서 설치할 수 있는 Android 패키지로 제공하는 것을 목표로 한다.

**권고안은 Trusted Web Activity(TWA)** 다. TWA는 검증된 웹 도메인을 Chrome 기반 전체 화면 앱으로 연다. 포털은 기존 Blazor 셸과 서버 인증을 그대로 쓰고, 앱은 Android 설치·실행 진입점과 스토어 배포를 맡는다. 첫 버전에서 오프라인 기능이나 네이티브 화면을 새로 만들지 않는다.

이 문서는 구현 전 기본설계다. 앱 식별자, 배포 채널, 네이티브 기능 범위 등은 확정하지 않았으며, 운영 설정·DB는 변경하지 않는다.

## 2. 현재 시스템과 그대로 쓸 부분

| 현재 구성 | Android 앱에서의 역할 |
|---|---|
| `web/src/Shell/JSini.Web.Shell` (:5557) | 기존 로그인·화면·업무 모듈을 그대로 제공 |
| `portal.jsini.co.kr` 과 Nginx | HTTPS 웹 진입점. Blazor SignalR 회로와 `/api/` 경로를 기존처럼 중계 |
| `manifest.webmanifest` | 앱 이름·아이콘·시작 주소·범위의 PWA 정본 |
| `push-sw.js` | 웹푸시 수신, 알림 표시 및 알림을 눌렀을 때 포털 경로 열기 |
| NotificationServer | 현재 웹푸시 구독·발송·도달 확인과 알림 설정을 담당 |
| 포털 BFF 인증 | 브라우저에는 인증 쿠키만 두고 게이트웨이용 토큰은 서버가 보관 |

매니페스트는 이미 `start_url: "/"`, `scope: "/"`, `display: "standalone"` 을 선언한다. 서비스워커는 포털 오리진의 `/push-sw.js` 에 있고 캐시로 화면을 제공하지 않는다. Blazor Server 회로는 앱이 온라인 상태로 열려 있을 때 연결되어야 하며, PWA 설치만으로 오프라인 업무나 백그라운드 실행이 생기지는 않는다.

## 3. 앱 제공 방식 비교

| 방식 | 장점 | 제약·비용 | 판단 |
|---|---|---|---|
| **TWA** | 기존 HTTPS 포털·PWA·웹푸시·BFF를 재사용하고 Android 앱으로 스토어 배포 가능 | Chrome 기반 런타임과 온라인 연결에 의존. 도메인 소유 검증과 기기별 동작 확인 필요 | **첫 단계 권고** |
| 일반 WebView 앱 | 앱 껍데기 구현은 가능 | 서비스워커·웹푸시·패스키·쿠키·파일 선택 등 브라우저 기능의 동작 차이를 별도로 풀어야 함 | 우선안으로 삼지 않음 |
| 네이티브 앱(예: Kotlin/Compose) | OS 기능과 네이티브 UI를 온전히 제어 | 화면 재구현, 앱 전용 인증/API, 푸시 파이프라인, 배포·유지보수 비용 발생 | 네이티브 요구가 확정되면 별도 검토 |

TWA도 네이티브 기능을 자동으로 제공하는 것은 아니다. 오프라인 업무, Android 백그라운드 위치 수집, 네이티브 화면, 자체 FCM 토큰 관리가 필수 요구가 되면 TWA 범위를 넘어선다.

## 4. 권고 대상 구조

```text
Android 사용자
  └─ Play 스토어에서 JSini 앱 설치
       └─ Android TWA (앱 ID·아이콘·시작 진입점)
            └─ Chrome이 https://portal.jsini.co.kr/ 표시
                 ├─ Nginx → Blazor 포털 셸 :5557
                 ├─ 포털 셸 → API Gateway :5265 → 업무 서비스
                 └─ /push-sw.js → 웹푸시 수신·알림 클릭 처리

NotificationServer → 웹푸시 서비스(Chrome/FCM) → 기기 서비스워커
```

Android 패키지는 UI나 업무 데이터를 담지 않는다. 포털의 주소가 앱의 콘텐츠 정본이고, 앱에서 시작하거나 웹에서 직접 접속해도 같은 계정·권한 체계를 거친다. 업무 요청은 기존 포털 BFF를 유지하며 Android 앱 전용 JWT를 만들거나 브라우저로 게이트웨이 토큰을 노출하지 않는다.

### 앱 식별·웹 도메인 연결

- 앱의 `applicationId`(예: `kr.co.jsini.portal`)와 표시 이름은 구현 전에 확정한다. 예시는 제안값이며 현재 확정된 식별자가 아니다.
- TWA 생성 도구와 Android Gradle 프로젝트로 스토어용 패키지를 만든다. 생성 도구·Gradle·Android SDK 버전은 구현 시점의 지원 버전과 Google Play 정책에 맞춰 고정한다.
- 포털 오리진 `https://portal.jsini.co.kr/.well-known/assetlinks.json` 에 Android 앱의 패키지 ID와 **릴리스 서명 인증서 SHA-256 지문**을 공개한다. 이 파일은 도메인과 앱의 연결을 검증하는 공개 메타데이터이며 비밀키를 포함하지 않는다.
- 로컬·개발 서명본 검증이 필요하면 개발 지문을 별도로 추가하되, 운영 릴리스 지문과 혼동되지 않게 관리한다. 서명 키는 저장소에 넣지 않고 CI/스토어의 비밀 보관 기능으로 관리한다.
- `manifest.webmanifest` 의 HTTPS 주소, `start_url`, `scope` 와 Android 쪽 시작 주소가 일치하는지 확인한다. 소개 사이트(`jsini.co.kr`)가 아니라 업무 포털 도메인을 사용한다.
- `assetlinks.json` 은 기존 Nginx 정본(`deploy/nginx/portal.jsini.co.kr.conf`) 또는 포털 정적 파일 경로 중 한 곳에서 HTTPS로 제공한다. URL이 인증 화면으로 리다이렉트되지 않고 JSON을 직접 돌려주는지 확인한다.

### 인증 및 계정 보안

- 로그인은 기존 포털 로그인 화면에서 처리한다. 현재 포털의 BFF 인증 쿠키(`jsini.portal`)는 HttpOnly이며 운영 HTTPS에서 Secure, SameSite=Lax로 설정되어 있고 경로는 `/` 이다.
- TWA가 사용하는 Chrome 프로필에서 로그인·로그아웃·세션 만료·비밀번호 변경·패스키 및 외부 로그인 흐름을 실기기로 확인한다. 앱 설치와 일반 Chrome 접속 사이의 쿠키·서비스워커 공유 여부를 가정하지 말고 검증한다.
- 앱을 닫거나 장시간 백그라운드에 두어 SignalR 회로가 끊기는 것은 정상적인 네트워크 상황이다. 재연결 후 기존 화면 동작을 확인하며, 회로가 끊긴 동안 저장 요청이 성공한 것처럼 보이지 않는지도 점검한다.
- 로그아웃은 기존 포털 절차를 사용한다. 공용 기기에서는 앱을 종료하는 것만으로 로그아웃되었다고 안내하지 않는다.

### 알림과 기기 등록

- 1차 권고는 **현재 Web Push를 유지**하는 것이다. NotificationServer는 이미 VAPID 기반 웹푸시 구독을 받고, `push-sw.js` 가 도착·클릭을 처리한다. 이 경로를 유지한다면 별도의 Android Firebase 프로젝트, FCM 서버 키 또는 native push 토큰 경로는 우선 필요하지 않다.
- Android 앱에서 알림 권한은 사용자가 이해할 수 있는 순간에 요청하고, 거부·시스템 차단·구독 해제 상태를 기존 알림 설정 화면에서 확인할 수 있게 한다.
- 구독 API는 로그인한 사용자 신원으로 구독 주인을 정한다. Android 앱도 기존 API 경로를 사용하되, 기존 클라이언트가 `Source="portal"` 로 보내는 값을 Android 진입점에서 어떻게 구별할지는 구현 전에 정한다. 필요한 경우 구독의 출처·기기 표시만 보완하고, 중복 구독이나 동일 사용자 여러 기기의 알림 동작을 확인한다.
- 웹푸시의 수신, 서비스워커 도달 보고, 알림 클릭으로 앱/포털의 올바른 내부 화면으로 이동하는 동작을 Android 실기기에서 검증한다. TWA·Chrome·PWA 설치 간 구독 공유 및 알림 클릭 시 어느 화면 컨텍스트가 열리는지는 사전 확인 항목이다.
- 네이티브 FCM으로 전환할 경우에는 현재 웹푸시 구독과 다른 토큰·발송 경로가 생긴다. 이때는 NotificationServer의 대상 모델, 사용자별 기기 관리, 수신·도달 확인, 알림 클릭 딥링크를 함께 설계하며 웹푸시 구독과 병행하는 기간도 정한다.

## 5. 화면 이동, 네트워크 및 OS 기능

- 업무 화면 주소는 기존 포털 라우팅을 따른다. 알림 클릭과 외부 링크의 내부·외부 URL 판별을 점검하고, 인증이 필요한 상세 주소는 기존 화면 권한 검사를 그대로 거친다.
- 포털은 오프라인 HTML 캐시를 하지 않는다. 네트워크가 없으면 로그인·업무 조회가 불가능하다는 점을 1차 범위로 명확히 하고, 연결 복구 때 재연결 안내를 확인한다.
- 파일 내려받기·업로드, 카메라/사진 선택, 공유, 전화·메일 링크, 키보드 표시, 화면 회전과 뒤로 가기를 Android Chrome/TWA에서 확인한다. TWA가 다루지 못하는 기능은 임의의 WebView 브리지로 우회하지 말고 요구사항을 분리한다.
- 현재 위치 기능은 열린 화면에서 사용자 허용을 받아 수집한다. 서비스워커에는 위치 API가 없으므로 앱 종료 후 백그라운드 위치 수집을 약속하지 않는다. 그런 요구가 생기면 별도 사용자 동의·OS 권한·수집 중 표시·중지·보관 기간을 포함한 네이티브 설계가 필요하다.

## 6. 빌드·배포·운영 구성

| 산출물/설정 | 관리 위치·책임 |
|---|---|
| 포털 웹 화면·서비스워커·PWA 매니페스트 | 기존 `web/` 빌드 및 포털 컨테이너 배포 |
| Android 프로젝트·앱 ID·버전·화면 아이콘 | 별도 Android 프로젝트(저장소 내 위치는 구현 때 결정) |
| 앱-도메인 검증 파일 | `/.well-known/assetlinks.json`, 릴리스 인증서 지문 포함 |
| 앱 서명 | 안전한 CI/스토어 비밀 관리. 서명 개인키는 저장소에 커밋하지 않음 |
| 스토어 등록 | 앱 설명·스크린샷·개인정보/데이터 안전성 고지·심사 및 출시 단계 관리 |

Android 앱 업데이트와 포털 업데이트는 독립적이다. 웹 화면 수정은 기존 포털 배포를 따르고, 앱 ID·앱 아이콘·TWA 설정·서명·앱 기능 변경은 Android 패키지를 다시 빌드해 스토어에 배포한다. CI를 붙일 때는 Android 빌드/서명/스토어 업로드를 기존 웹 컨테이너 배포와 분리한다. 초기 출시 전에는 내부 테스트 트랙으로 제한된 계정·기기에서 확인하고, 단계적 공개와 이전 앱 버전으로의 대응 방안을 정한다.

운영 모니터링은 기존 포털·게이트웨이·NotificationServer 지표를 우선 사용한다. Android 배포 상태는 스토어 트랙과 앱 버전으로 확인하고, TWA/Chrome 문제와 포털 서버 문제를 구분할 수 있도록 앱 버전·웹 주소·회로 연결 실패를 함께 살핀다. 클라이언트 로그에 인증 토큰, 쿠키, 푸시 구독 비밀값을 남기지 않는다.

## 7. 단계별 진행안

1. **요구사항 확정** — Play 스토어 공개/비공개 여부, 앱 이름·아이콘, 앱 ID, 대상 계정, 필수 네이티브 기능과 오프라인 필요 여부를 결정한다.
2. **TWA 기술 검증** — 테스트 서명 앱과 `assetlinks.json` 을 구성해 로그인, 패스키/외부 로그인, 웹푸시 등록·수신·클릭, 업로드·다운로드, 뒤로 가기를 실기기로 확인한다.
3. **출시 패키지 준비** — 릴리스 서명·CI 비밀 관리, 스토어 메타데이터·개인정보/데이터 안전성 자료, 내부 테스트 트랙을 준비한다.
4. **단계적 배포** — 제한된 사용자로 시작해 크래시·로그인 실패·푸시 미수신·회로 재연결을 확인한 뒤 공개 범위를 넓힌다.
5. **네이티브 확장 판단** — TWA 검증에서 드러난 실제 요구만 기준으로 네이티브 기능 추가 또는 전용 앱 전환을 별도 결정한다.

## 8. 출시 전 수용 기준

- Play 테스트 트랙 앱이 검증된 포털 도메인을 전체 화면으로 열고, 연결 검증 실패 시에도 원인을 재현·진단할 수 있다.
- 신규 로그인, 로그아웃, 만료 세션, 패스키/외부 로그인과 권한 차단이 기존 포털과 동일하게 동작한다.
- Android에서 알림 권한을 선택적으로 허용·거부할 수 있고, 등록 기기·수신·알림 클릭이 기존 알림 정책과 맞는다.
- 회선 끊김·앱 재개·기기 재시작·웹 앱 업데이트 뒤에도 재연결과 서비스워커 갱신이 정상이다.
- 첨부 선택/업로드/다운로드, 키보드·뒤로 가기 및 핵심 휴대폰 화면이 지원 대상 Android 버전과 Chrome에서 확인된다.
- 서명 개인키와 인증 정보가 앱 패키지·로그·저장소에 노출되지 않고, 스토어 고지와 실제 데이터 처리 내용이 일치한다.

## 9. 구현 지시 전에 확정할 결정

1. **TWA 기반 앱을 1차로 허용할지**, 아니면 네이티브 UI나 네이티브 기능이 출시 필수인지.
2. 앱 배포 채널이 Google Play 공개 등록인지, 조직 내부/비공개 배포인지.
3. 최종 앱 이름·아이콘·`applicationId` 와 테스트 대상 Android 기기/최소 지원 버전.
4. TWA에서 재사용할 기존 웹 로그인·웹푸시만으로 충분한지, 네이티브 FCM 푸시가 필요한지.
5. 앱에서도 오프라인 조회, 백그라운드 위치, 파일/카메라 제어 등 웹 범위를 넘는 기능이 필요한지.

**권고 결론:** 별도의 네이티브 요구가 없다면 TWA로 Android 배포를 먼저 검증한다. 기존 PWA와 BFF 보안 경계를 유지하고 웹푸시를 재사용해 출시 범위와 중복 구현을 줄인다. 인증·푸시·딥링크의 TWA 실기기 검증에서 제한이 확인되거나 네이티브 요구가 확정될 때만 네이티브 앱 전환을 설계한다.
