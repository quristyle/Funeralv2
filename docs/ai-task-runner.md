## 1. 만들려는 것

편집기(Monaco)에 **AI 에게 시킬 일**을 글로 적어 저장한다. 저장된 글은 제목이 붙어
목록에 쌓이고, 「작업요청」을 켜면 서버가 그것을 알아채서 상태를 **준비중**으로
바꾼 뒤, `claude` · `antigravity` · `copilot` CLI 가 깔린 장비에서 실제로 실행시킨다.
진행 중 출력과 끝난 결과를 같은 화면에서 본다.

한 문장으로: **웹 화면이 곧 AI 작업 대기열의 입구**다.

> 이 문장을 뒤집으면 이 기능의 본질이 보인다 — **웹에 글을 쓰면 어느 장비에서
> 명령이 돈다.** 설계상 원격 코드 실행이고, 그래서 9장(보안)이 이 문서에서
> 제일 긴 장이다. 편의 기능 하나를 붙이는 일이 아니다.

## 2. 누가 CLI 를 띄우나 — **B안 확정** (2026-09-17)

**서버는 대기열만 갖고, CLI 가 깔린 장비의 실행기가 따로 돈다.**

### 2.1 그렇게 정한 이유는 그대로다

운영의 `ai` 서비스는 GHCR 이미지 한 장으로 뜨는 컨테이너다
(`deploy/docker/docker-compose.prod.yml:114`). 그 안에는 CLI 도, 소스도,
CLI 로그인 자격도 없고 재배포하면 사라진다. **서버 프로세스가 직접
`Process.Start` 하는 그림은 운영에서 성립하지 않는다.**

### 2.2 실행 장비 — 운영 서버(jin114.co.kr), `/home/lee/Funeralv2`

이제 「실행기를 어디서 돌리나」의 답이 정해졌다. **운영 서버 그 자체다.**
소스는 이미 거기 clone 되어 있다.

이것으로 좋아지는 것이 있다. 실행기가 게이트웨이도 RabbitMQ 도 **localhost 로**
부른다. 방화벽에 구멍이 필요 없고, 장비가 꺼져 있을 걱정도 없다.

### 2.3 그런데 **가장 위험한 자리**가 되기도 했다

실행 장비가 개발 PC 였다면 사고의 크기는 「내 PC 가 이상해졌다」였다.
운영 서버가 되면서 사고의 크기가 **「서비스가 내려간다」**로 올라갔다.
확인한 것(2.4)을 근거로, 무엇을 막아야 하는지는 **9장에 전부 다시 적었다.**

### 2.5 백엔드는 `ProjMngServer` 다 — `AIAgentServer` 가 아니다

처음 초안은 `AIAgentServer`(:5029)를 권했다. **`ProjMngServer`(:5450)로 정해졌고,
옮기고 보니 얻는 것이 잃는 것보다 크다.**

#### 얻는 것 — 문제 둘이 통째로 사라진다

1. **게이트웨이 인증 문제가 없어졌다.** `ai-route` 는 `AuthorizationPolicy:
   "Anonymous"` 라서 그 밑에 대기열을 붙이면 로그인 없이 운영 서버에서 AI 를
   돌릴 수 있게 되는 자리였다(옛 9.8). `projmng-route` 는 정반대다 —
   게이트웨이 설정에 이렇게 적혀 있다:

   > 이 서비스는 저장 프로시저를 이름으로 호출하는 범용 통로다. **익명으로 열
   > 경로가 없으므로** `AuthorizationPolicy` 를 지정하지 않고 `Program.cs` 의
   > `FallbackPolicy`(= 인증 필요)를 따른다.

   **게이트웨이를 고칠 일이 없어졌다.**

2. **모듈 접두사와 경로가 일치한다.** 화면이 `ProjMng` 인데 `/api/ai/…` 를 부르는
   어긋남이 있었다(옛 11.1). 이제 `projmng/ai-tasks` 로 다른 열한 개 클라이언트와
   같은 모양이다.

#### 값을 치르는 곳

| | 무엇 | 어떻게 |
|---|---|---|
| ORM | **EF Core 가 없다.** Dapper + Npgsql 이고 컨트롤러 기반(MVC)이다 | 스키마는 SQL 파일로, 읽기는 Dapper 로 — 4.6 |
| 큐 | RabbitMQ 클라이언트가 이 서비스에 없다 | `AuthServer.ReleaseService` 의 발행 코드를 그대로 옮긴다(6장) |
| LLM | 제목 자동 생성이 **서비스 간 호출**이 된다 | `ProjMngServer` → `/api/ai/chat` (8장) |

셋 다 작은 값이다. 특히 첫째는 **그 서비스의 결을 따르는 것**이지 우회가 아니다 —
`ProjMngServer` 에만 EF 를 새로 들이면 이 저장소에서 유일하게 둘을 섞는 서비스가 된다.

#### `AIAgentServer` 는 무엇을 하나

**LLM 중계 그대로다.** 모델 목록·대화 스트리밍·공급자 전환. 우리는 제목 생성
한 가지로 그것을 쓴다. AI 작업 대기열은 「AI 를 부르는 일」이 아니라
**「일을 맡기고 결과를 기다리는 일」**이라 성격이 다르다 — 그쪽에 두면 무상태
중계기에 DB·큐·배포 권한이 한꺼번에 붙는다.

## 4. 자료 모형

DB 는 **프로젝트관리 DB**(`jsini`), 스키마 **`projmng`** — `ProjMngServer` 가 쓰는 곳
그대로다. 표 넷을 더한다(`ai_task` · `ai_task_run` · `ai_task_log` · `ai_target` ·
`ai_runner`).

### 4.1 `ai_task` — 사람이 쓰는 글 한 건

| 칸 | 뜻 |
|---|---|
| `id` | bigint / identity |
| `title` | 제목. 비우면 규칙으로 만든다(8장) |
| `content` | 본문 — AI 에게 줄 지시문 |
| `content_format` | `markdown` 기본 |
| `request_flag` | **작업요청여부** — `none` · `requested` · `cancel_requested` |
| `status` | **작업상태** — `idle` · `queued` · `preparing` · `running` · `succeeded` · `failed` · `timeout` · `canceled` · `interrupted` |
| `runner_kind` | `claude` · `antigravity` · `copilot` (어느 CLI 로 돌릴지) |
| `target_id` | **작업 대상**(`ai_target` 의 열쇠). 화면에서 고른다 — 4.5 |
| `target_ref` | 저장소 대상일 때 기준 브랜치. 비우면 대상의 기본값 |
| `priority` | 같은 시각에 여럿이면 순서 |
| `timeout_minutes` | 건별 상한(기본 30) |
| `attempt_count` · `attempt_max` | 재실행 횟수·상한(기본 1 — 6.4 참고) |
| `requested_at` · `started_at` · `finished_at` · `duration_ms` | **시간** |
| `notify_email` · `notify_to` · `notify_when` | **끝나면 메일로 받기.** 받는 이(기본 요청자), 시점(`always` · `on_success` · `on_failure`) — 8장 |
| `auto_push` | 이 건을 **push 까지** 할 것인가. 대상이 허용할 때만 켤 수 있다(4.4) |
| `pushed_commit` | push 한 커밋 SHA. **비어 있지 않으면 운영 배포가 일어났다는 뜻** |
| `previous_tag` | push 직전의 운영 `TAG`. **되돌릴 때 필요한 값이다**(9.3) |
| `last_run_id` · `last_exit_code` · `last_error` | 최근 실행 요약(목록 조회용 비정규화) |
| `created_by` · `created_at` · `updated_by` · `updated_at` | 감사 |
| `row_version` | 동시 편집 방지(낙관적 잠금) |

### 4.2 `ai_task_run` — 실행 한 번

`task_id` · `seq` · `runner_id` · `status` · `lease_expires_at` · `started_at` ·
`finished_at` · `exit_code` · `error_summary` · `workspace_path` · `git_branch` ·
`base_sha` · `diff_stat` · `log_line_count` · **`result_text`**

**`result_text` 를 로그와 따로 둔다.** AI 의 **마지막 답**이다 — 「무엇을 고쳤다」
일 수도, 물은 것에 대한 답일 수도, 시킨 보고서 자체일 수도 있다. 로그 수천 줄에서
그것만 가려내는 일을 화면과 메일이 각각 하게 두면 둘이 갈린다. **한 번 가려서
여기 적어 두고 둘 다 이것을 읽는다.** `claude` 는 `--output-format stream-json`
의 마지막 `result` 가 그 값이다(7.5).

**왜 글과 실행을 나누나.** 같은 글을 여러 번 돌린다. 한 줄에 상태를 다 담으면
「지난번엔 됐는데 이번엔 왜 실패했나」를 볼 방법이 없고, 두 번째 실행이 첫 번째
기록을 조용히 덮는다.

### 4.3 `ai_task_log` — 출력 줄

`run_id` · `seq` · `at` · `stream`(`stdout`/`stderr`/`system`) · `text`

**왜 별도 표인가.** 로그를 `ai_task` 의 text 칸에 이어 붙이면 목록 한 번 조회할
때마다 수 MB 를 읽는다. 그리고 실행 중에 계속 커지는 값이라 매번 행 전체를
다시 쓰게 된다(Postgres 는 UPDATE 마다 새 행 버전을 만든다).
보존 기간을 정하고(예: 90일) 넘은 것은 지운다 — 안 정하면 반드시 이 표가 제일 커진다.

### 4.4 `ai_target` — **작업 대상** (화면에서 고르는 것)

| 칸 | 뜻 |
|---|---|
| `id` · `name` | 열쇠와 사람이 읽는 이름(「Funeralv2 저장소」 · 「빈소 이미지 폴더」) |
| `kind` | **`repo`** (git 저장소) · **`folder`** (그냥 폴더) |
| `path` | 운영 서버의 **절대 경로**. 등록할 때 검사한다(9.5) |
| `repo_url` · `default_ref` | `repo` 일 때. `folder` 면 비운다 |
| `credential_ref` | 비공개 저장소일 때 쓸 **읽기 전용 키**의 이름(7.3) |
| `isolation` | **`worktree`**(repo) · **`copy`**(폴더 복사본) · **`inplace`**(원본 직접) |
| `max_size_mb` | `copy` 일 때 복사 상한. 넘으면 실행을 거절한다 |
| `allow_push` · `push_ref` | **push 를 허용하는 대상인가**, 어느 ref 로(기본 `main`) |
| `gate` | push 전에 돌릴 검사 — `build` · `test` · `none` (9.3) |
| `enabled` | 끄면 화면 목록에서 사라진다 |
| `running_run_id` | **대상별 동시 1건 잠금**. 비어 있어야 새로 집는다 |
| `created_by` · `created_at` · `updated_*` | 감사 |

**왜 표로 두나 — 사람이 경로를 타이핑하면 안 되기 때문이다.** 화면이 대상을
고르게 하면서 그 값을 자유 입력으로 두면 `../../srv/jsini/config` 가 들어온다.
**등록은 관리자가, 선택은 사용자가** 하는 구도라야 그 길이 막힌다(9.5).

`running_run_id` 를 대상 쪽에 두는 이유: 폴더 대상은 worktree 가 없어 **둘이 동시에
돌면 서로의 파일을 덮는다.** 잠금을 작업이 아니라 **대상**에 걸어야 맞다.

### 4.5 `ai_runner` — 등록된 실행 장비

`id` · `name` · `host` · `kinds`(`claude,antigravity,copilot`) · `token_hash` · `enabled` ·
`max_parallel` · `last_seen_at` · `version`

토큰은 **해시로만** 둔다. 장비를 빼앗겼을 때 `enabled=false` 한 줄로 끊는다.

큐를 붙이면서 이 표의 역할이 「어디로 배달할까」에서 **「살아 있나」**로 줄었다 —
6.12 참고. 장비가 하나뿐인 지금은 행도 하나다.

## 5. 상태 — 요청여부와 작업상태를 왜 둘로 두나

사용자가 요구한 대로 둘을 나눈다. 나누는 이유가 있다.

- `request_flag` 는 **사람의 의사**다. 「이거 돌려 주세요」 · 「취소해 주세요」
- `status` 는 **기계의 현재 위치**다. 「지금 준비중」 · 「지금 실행중」

합치면 표현할 수 없는 상태가 생긴다 — *사람이 취소를 눌렀는데 이미 실행 중*이
대표적이다. 합친 설계에서는 이때 상태를 `canceled` 로 덮게 되고, 그러면
**실제로는 아직 돌고 있는 CLI 가 화면에서 사라진다.**

```
 request_flag :  none ──(사람: 요청)──▶ requested ──(사람: 취소)──▶ cancel_requested
                   ▲                                                      │
                   └──────────────(끝나면 되돌린다)───────────────────────┘

 status :  idle ──▶ queued ──▶ preparing ──▶ running ──┬──▶ succeeded
                                                        ├──▶ failed
                                                        ├──▶ timeout
                                                        ├──▶ canceled
                                                        └──▶ interrupted   (실행기가 사라짐)
```

`interrupted` 를 따로 두는 이유: 「실패」와 「모르겠음」은 다르다. 실패는 CLI 가
답을 준 것이고, 중단은 **아무것도 모르는 것**이다 — 파일이 반쯤 고쳐져 있을 수도
있다. 같은 칸에 넣으면 사람이 안심하고 다시 누른다.

## 6. RabbitMQ 를 쓰는가 — **쓴다. 단, 별도 큐로**

### 6.1 이미 **똑같은 모양의 것**이 돌고 있다

새로 발명할 것이 거의 없다. 이 저장소에는 「화면에서 누른 것을 다른 장비에서
실행하고 진행 상황을 되돌려 보고하는」 물건이 이미 있다 —
**배포 도구**(`/portal/release`)다.

```
포털 화면 ─POST─▶ AuthServer ─RabbitMQ─▶ 배포 장비 소비자 ─▶ release-run.sh ─▶ 배포 스크립트
   ▲                    ▲                                        │
   └──── 폴링 ──────────┴────────── HTTP 콜백(run별 토큰) ────────┘
```

- 큐에 넣는 쪽: `microservices/AuthServer/Services/ReleaseService.cs`
  — **우리는 이 코드를 `ProjMngServer` 로 옮겨 온다**(그 서비스에는 RabbitMQ
  클라이언트가 아직 없다. 2.5)
- 집어가는 쪽: `deploy/release-consumer/consumer.py` (참고 구현)
- 감싸고 보고하는 쪽: `deploy/release-consumer/release-run.sh`
- 약속: `deploy/release-consumer/README.md`

**우리가 만들려는 것은 이것의 사촌이다.** 다른 것은 셋뿐이다 —
① 시키는 내용이 스크립트 이름이 아니라 **사람이 쓴 글**이고,
② 실행하는 것이 배포 스크립트가 아니라 **AI CLI** 이고,
③ 요청이 화면에서 만들어져 **DB 에 남는다**(배포는 남길 것이 요청뿐이다).

그래서 이 장의 대부분은 **그 구현의 어느 부분을 베끼고 어느 부분을 바꾸나**다.

### 6.2 `run_script` 큐에 **얹지 않는다**

가장 쉬워 보이는 길은 이미 있는 `run_script` 큐에 메시지를 하나 더 넣는 것이다.
**하지 않는다.** 이유가 저장소에 이미 적혀 있다:

> 이 큐(`run_script`)는 헬프데스크의 메일 발송과 공유하고 있어서, 큐에 메시지를
> 넣을 수 있는 쪽이면 **무엇이든 실행시킬 수 있는 상태**다.
> — `deploy/release-consumer/consumer.py`

이미 둘(배포 · 메일)이 한 큐를 쓰고 있고 그것이 알려진 약점이다. 거기에 셋째를
얹으면 약점이 커진다. 그리고 실무적으로도 섞이면 안 된다 —
**AI 작업은 30분씩 걸리고 배포는 몇 분이다.** 한 큐에 두면 `prefetch=1` 인
소비자가 AI 작업 하나를 잡고 있는 동안 **배포가 줄을 선다.**

새 큐 `ai_task` 를 쓰고, 소비자도 별개로 띄운다.

### 6.3 큐가 주는 것과 **주지 않는 것**

| | 큐가 준다 | 큐로는 안 된다 |
|---|---|---|
| 지연 | 넣는 즉시 간다(폴링 3초가 사라진다) | |
| 동시 실행 제한 | `basic_qos(prefetch=5)` 한 줄 — 정해진 상한 그대로 | |
| 장비 늘리기 | 소비자를 하나 더 띄우면 끝 | |
| **지금 이 건이 어디 있나** | | 큐는 **조회할 수 없다** |
| **목록·검색·기간 조회** | | 메시지는 집어가면 사라진다 |
| **내용 수정·취소** | | 넣은 메시지는 고칠 수 없다 |
| **이력** | | 남지 않는다 |

화면이 요구하는 것(작업요청여부 · 작업상태 · 완료여부 · 시간)은 **전부 오른쪽
칸이다.** 그러니 큐가 DB 를 대신할 수 없다. 큐는 **빠르게 깨우는 역할**만 한다.

### 6.4 **정본은 DB, 큐는 종** — 이중 쓰기를 피하는 방법

둘을 같이 쓰면 반드시 만나는 함정이 있다. DB 에 쓰고 큐에 넣는 두 번의 쓰기가
**둘 다 성공한다는 보장이 없다.**

- DB 는 `queued` 인데 메시지가 안 갔다 → **영영 안 돈다**
- 메시지는 갔는데 DB 커밋이 굴렀다 → 소비자가 **없는 작업**을 집는다

보통은 여기서 outbox 패턴을 꺼낸다. **그러지 않아도 되게 설계한다.**

```
메시지 본문 = { "taskId": 123 }        ← 그것뿐이다. 지시문도 상태도 싣지 않는다
```

메시지는 **「123번을 봐라」는 종소리일 뿐**이고, 소비자는 종을 듣고 서버에
`claim` 을 부른다. 실제 상태 변경은 5장·6.5 의 **원자적 UPDATE 한 문장**이다.
그러면 이렇게 된다.

| 어긋남 | 무슨 일이 나나 |
|---|---|
| 메시지를 잃었다 | 안전망 폴링(6.6)이 **최대 60초 뒤** 집는다. 손실이 아니라 지연이다 |
| 메시지가 두 번 왔다 | `claim` 이 두 번째엔 **빈손**을 돌려준다. 그냥 ack 한다 |
| DB 는 안 됐는데 메시지만 갔다 | `claim` 이 빈손. 소비자는 아무것도 안 한다 |
| 지시문을 고친 뒤 돈다 | 소비자가 **집는 시점에** 본문을 읽으므로 항상 최신이다 |

메시지에 지시문 전문을 싣고 싶은 유혹이 있는데(호출 한 번이 줄어든다),
싣는 순간 **큐에 든 내용과 DB 의 내용이 갈릴 수 있고**, 큐를 볼 수 있는 쪽에
지시문이 통째로 남는다. 싣지 않는다.

### 6.5 집는 것은 여전히 한 문장 UPDATE 다

종이 울렸든 폴링이든, 실제로 집는 방법은 하나다.

```sql
UPDATE projmng.ai_task t
   SET status = 'preparing',
       started_at = now(),
       attempt_count = attempt_count + 1
 WHERE t.id IN (
       SELECT id FROM projmng.ai_task
        WHERE request_flag = 'requested'
          AND status IN ('idle', 'queued')
          AND runner_kind = ANY(@kinds)
        ORDER BY priority DESC, requested_at
        FOR UPDATE SKIP LOCKED
        LIMIT @capacity)
RETURNING t.*;
```

읽고 → 판단하고 → 쓰는 세 걸음으로 나누면, 소비자가 둘이거나 종과 폴링이
겹치는 순간에 **같은 건을 둘이 집는다.** `FOR UPDATE SKIP LOCKED` 는 둘이 동시에
들어와도 서로 다른 건을 집게 하고 기다리지도 않는다.

### 6.6 안전망 폴링을 **없애지 않는다**

소비자는 종을 기다리는 것과 별개로 **60초마다 한 번 `claim` 을 부른다.**
빈손이면 그냥 끝난다.

> **그래서 브로커가 아예 없어도 돈다.** 로컬 개발 장비에는 RabbitMQ 가 없는데,
> 실행기의 `Queue:Enabled` 를 끄고 `PollSeconds` 를 3초로 두니 그대로
> 끝까지 동작했다(2026-09-18 확인). 큐는 **지연을 줄이는 종**일 뿐이고
> 일을 찾는 것은 이 조회다 — 설계가 그렇게 갈라져 있는 값을 실제로 받은 셈이다.

큐를 붙였으니 폴링을 뺄 수 있다고 생각하기 쉬운데, 이 기능에서 가장 나쁜 실패는
**「요청」인 채로 아무도 모르게 남는 것**이다. 메시지는 잃을 수 있다 —
브로커 재시작(지금 큐는 `durable: false` 다), 소비자 재배포, 넣기 실패.
60초에 한 번 도는 조회 하나로 그 실패가 전부 「조금 늦게 돌았다」가 된다.

### 6.7 ack 는 **받자마자** 한다 — 되돌리지 않는다

배포 소비자가 이렇게 하고 있고, 이유가 우리에게 더 강하게 적용된다.

> 무엇이 있어도 ack 한다. 실패한 요청을 큐에 되돌리면 같은 배포를 무한히
> 재시도한다 — **배포는 재시도해도 좋은 일이 아니다.**
> — `consumer.py`

AI 작업은 **파일을 고친다.** 되돌린 메시지가 다시 배달되면 반쯤 고쳐진 저장소
위에서 같은 지시가 다시 돈다. 그래서 받자마자 ack 하고, 진행과 결과는 **DB 가**
말한다. 큐가 신뢰성을 책임지지 않는 대신 6.6 이 책임진다.

### 6.8 소비자가 안 떠 있는 것을 **빨리 안다**

배포 도구가 이미 같은 문제를 풀어 두었다 — `Release:PickupTimeoutSeconds: 60`:

> 큐에 넣고 이 시간 안에 아무도 집어가지 않으면 중단으로 본다.
> 소비자가 안 떠 있다는 뜻이라 빨리 알려 주는 편이 낫다.

그대로 가져온다. `queued` 인 채로 N초가 지나면 화면이 **「실행기가 응답하지
않습니다」**라고 말한다. 이것이 없으면 「준비중」에서 영원히 멈춘 것처럼 보이고,
그게 이 기능의 가장 흔한 고장이다(12장).

#### 서버는 상태를 안 바꾸고, **화면이 갈라 적는다** (2026-09-19)

감시자는 제한 시간이 지난 건에 사유(`last_error`)만 적고 상태는 `queued` 로
둔다 — 늦게 뜬 실행기가 집어 갈 수 있어 여기서 「실패」로 못 박으면 그 뒤의
보고가 갈 곳을 잃기 때문이다. **그래서 한동안 아무 화면도 그 사실을 말하지
않았다.** 실패해 놓고 「대기」로 앉아 있는 건이 두 가지였다.

| 겉보기 | 실제 | 화면이 적는 글자 |
|---|---|---|
| 대기 | 방금 보냈고 기다리는 중 | 대기 (주황) |
| 대기 | 지난 실행이 실패해 다시 넣었다(6.11) | **실패·재시도** (빨강) |
| 대기 | 제한 시간이 지나도록 안 집혀 갔다 | **계속대기중** (빨강) |

가르는 값은 **끝난 시각**이다(`AiTaskDto.IsRetrying` · `IsUnclaimed`). 보낼 때
(`RequestAsync`) 서버가 `finished_at` 을 지우므로, 대기인데 그 시각이 남아
있으면 한 번은 돌았다는 뜻이다. 상태값(`task_status`)은 그대로 둔다.

재시도로 다시 넣을 때 `requested_at` 도 다시 찍는다. 안 찍으면 처음 보낸
시각이 남아 감시자가 곧바로 「집어 가지 않았습니다」를 덮어써 **왜 실패했는지가
지워진다.**

### 6.9 실행기 → 서버 보고는 **배포 콜백 규약을 그대로 베낀다**

`release-run.sh` 가 이미 다음을 해결해 두었고, 전부 우리에게도 필요하다.

| 이미 풀린 것 | 우리도 같다 |
|---|---|
| 줄을 모아 보낸다(20줄 또는 2초) | 로그가 본 작업보다 느려지지 않게 |
| ANSI 색 코드를 지운다 | 안 지우면 화면이 `[32m` 범벅 |
| UTF-8 을 바이트로 다룬다(`LC_ALL=C awk`) | 한글이 깨지지 않게. **sed 로 하면 구현마다 다르다** |
| 잘린 UTF-8 문자를 버린다 | 반 토막이 섞이면 **그 묶음 전체를 잃는다** |
| run 별 1회용 토큰 (`X-Release-Token`) | 장비에 계정을 두지 않는 인증 |
| 403/404 면 보고만 멈추고 **작업은 계속** | 포털이 내려가도 작업이 멈추지 않게 |
| 연속 5회 실패하면 보고 포기 | 포기 안 하면 **작업 자체가 느려진다** |
| `MaxEventsPerRun: 5000` · `MaxEventLength: 4000` | 로그 폭주 방어 |

**우리 쪽 헤더 이름만 `X-AiTask-Token` 으로 바꾼다.** 규약을 새로 만들지 않는다.

### 6.10 실행 중인 것이 살아 있는지 — 임대와 하트비트

집은 건에는 `lease_expires_at = now() + 30초` 를 단다. 실행기는 15초마다
하트비트로 연장한다. 서버의 `StaleSweeper`(BackgroundService)가 만료된 것을 찾는다.

**큐가 이것을 대신해 주지 않는다.** ack 를 받자마자 했기 때문에(6.7) 브로커는
그 뒤로 아무것도 모른다. 「지금 도는 중인가」는 DB 만 안다.

### 6.11 만료된 것을 **자동으로 다시 돌리지 않는다**

여기가 보통의 작업 큐와 갈리는 자리다. 보통은 「만료 → 다시 대기열로」가 정답인데,
이 작업은 **파일을 고친다.** 실행기가 CLI 를 띄운 뒤 네트워크만 끊긴 경우, 서버가
보기엔 죽은 것이지만 CLI 는 계속 돌고 있다. 거기서 같은 일을 또 주면
**둘이 같은 저장소를 동시에 고친다.**

그래서 만료된 것(`interrupted`)은 **지금도 자동으로 다시 돌리지 않는다.**
사람이 보고 다시 누른다.

#### 그 전제가 채워져서, 실패·시간초과는 다시 돈다 (2026-09-18)

위 문단이 자동 재시도의 전제로 적어 둔 것이 **작업공간이 실행마다 완전히
갈리는 것**(7.3)이었다. worktree · 복사본 대상은 그 조건을 만족하므로
`attempt_max` 기본값을 **3** 으로 올리고 자동 재시도를 켰다.

켜는 범위를 좁게 잡는다 — 판정은 `AiRunService.CompleteAsync` 에 있다.

| 끝난 상태 | 다시 도나 | 까닭 |
|---|---|---|
| `failed` · `timeout` | **돈다** (상한까지) | CLI 가 답을 주고 끝났다. 다시 돌 자리가 깨끗하다 |
| `interrupted` | 안 돈다 | 위 문단 그대로. CLI 가 아직 돌고 있을 수 있다 |
| `canceled` | 안 돈다 | 사람이 그만두라고 한 것이다 |

대상이 **원본 직접(`inplace`)이면 어느 경우에도 안 돈다.** 지난 시도가 고쳐
놓은 파일 위에서 다시 도는 셈이라, 두 번째 시도가 무엇을 보고 있는지 아무도
모른다. 이것이 위 전제의 뒤집은 표현이다.

#### 다시 돌 때는 **지난 실패를 들려준다**

재시도가 같은 지시문을 같은 자리에서 다시 읽는 것뿐이면 대개 같은 이유로 또
실패한다. 그래서 집어 갈 때(`ClaimAsync`) 지시문 **앞에** 지난 실행의 오류
요약과 결과 꼬리를 얹는다(`RetryPrompt`).

- **본문은 손대지 않는다.** 실패 이야기를 위에 얹을 뿐이다 — 본문을 고쳐 넣으면
  사람이 화면에서 읽는 글과 실제로 돈 글이 달라진다.
- 실행 줄의 `instruction` 스냅샷에는 **얹은 뒤의 글**이 들어간다. 그 실행이
  실제로 무엇을 받았는지가 남아야 하기 때문이다.
- 길이를 자른다. 결과문은 수십 KB 가 되기도 하고, antigravity 처럼 인자로
  넘기는 어댑터는 길이 제한이 있다. 오류는 앞에서, 결과는 **뒤에서** 남긴다 —
  오류는 대개 마지막 줄에 찍힌다.

중간 실패는 **메일로 알리지 않는다.** 세 번 시도해 두 번 실패하면 「실패」가
두 통 먼저 가고 마지막에 「성공」이 온다 — 받는 사람은 그 순서를 못 읽는다.

#### 실패 시 지연 재시도와 상한 기본값 (2026-09-19)

1. **`attempt_max` 기본값 일원화**:
   - `AiAsk.razor`(빠른지시), `AiTaskList.razor`, `AiTaskClient.cs`(DTO)에서 1로 고정되던 값을 모두 **3**으로 맞추고, DB 기본값도 3으로 유지한다.
   - `AiTaskService.NormalizeAsync`에서도 `AttemptMax <= 0`이면 기본 3으로 보정한다.

2. **수동 재요청 시 시도 횟수 초기화**:
   - `AiTaskService.RequestAsync`에서 `attempt_count = 0`으로 초기화하여, 사람이 다시 요청한 작업이 이전 실패 횟수에 가로막히지 않고 온전한 재시도 기회를 갖도록 한다.

3. **재시도 지연 대기 시간 (`AiTasks:RetryDelaySeconds`, 기본 15초)**:
   - 실패 즉시 다시 돌면 일시적 자원 경합이나 네트워크 오류 시 같은 오류를 반복하기 쉽다.
   - 실패 후 재시도 시 `requested_at = now() + make_interval(secs => @retryDelay)`로 지연 시각을 찍고, 지연 시간 경과 후 큐 알림(`queue.Ring`)을 전달한다.
   - `ClaimAsync`의 집어가기 조건에 `AND (a.requested_at IS NULL OR a.requested_at <= now())`를 추가하여 지연 시간이 지나기 전에는 실행기가 집어가지 않도록 제어한다.

### 6.12 그래서 4.5 의 `ai_runner` 표는 어떻게 되나

큐가 배달을 맡으므로 「어느 장비에 줄까」를 서버가 고를 일이 없다.
그래도 표는 **남긴다** — 다만 역할이 배달이 아니라 **살아 있는지 보기**다
(`last_seen_at`, `enabled`). 13장의 헬스 항목이 이 표를 읽는다.
장비가 하나뿐인 지금은 행도 하나다.

## 7. 실행기(Runner)

### 7.1 무엇으로 만드나 — 소비자 겸 실행기 하나

**RabbitMQ 를 듣고, `claim` 을 부르고, CLI 를 띄우고, 보고하는** 상주 프로그램
하나다. 받는 포트가 없다 — 큐와 게이트웨이로 나가기만 한다.

무엇으로 쓰나. 운영 서버에 `dotnet` 이 이미 있고(`/usr/bin/dotnet`), 우리 코드가
전부 .NET 이므로 **.NET 콘솔**로 만든다(`tools/AiTaskRunner`). 참고 구현인
`consumer.py` 는 python 인데, 그쪽을 따라가면 `pika` 를 얹어야 하고
(그 장비에 python 패키지를 하나 더 심는 일이다) 무엇보다 **우리가 필요로 하는 것이
`consumer.py` 보다 훨씬 많다** — 작업공간 만들기, 어댑터, 로그 배치, 하트비트,
취소 받기. 한 언어로 두는 편이 낫다.

**별도 프로세스인 이유는 배포 편의가 아니다.** 셸을 여는 권한이 웹 요청을 받는
프로세스와 같은 자리에 있으면 안 된다. 그리고 지금은 **운영 서버**이므로 그
원칙이 훨씬 더 중요하다(9장).

systemd 유닛으로 상주시킨다. 죽으면 다시 뜨고, 로그는 journald 로 간다.

### 7.2 프로세스를 띄우는 규칙 — 여기서 틀리면 크게 틀린다

- `UseShellExecute = false`, 인자는 **`ArgumentList` 로 하나씩 넣는다.**
  문자열 하나로 만들어 셸에 넘기지 않는다 — 본문에 `; rm -rf ~` 가 들어 있어도
  인자 한 개로 전달되게 하는 것이 유일하게 믿을 수 있는 방어다.
- **프롬프트는 인자가 아니라 stdin 또는 임시 파일로 준다.** 이유 셋:
  리눅스 argv 는 ~2MB, 윈도우 명령줄은 8191자라 **편집기에 긴 글을 쓰는 화면에서
  금방 넘는다**. 그리고 인자로 주면 `ps` 에 지시문이 그대로 보인다.
  마지막으로 따옴표 이스케이프 문제가 아예 사라진다.
- 출력은 줄 단위로 읽어 모았다가 **200줄 또는 2초 중 먼저 오는 쪽**에 서버로 민다.
  줄마다 HTTP 를 때리면 로그가 본 작업보다 느려진다.
- ANSI 색 코드는 적재 전에 벗긴다. 안 벗기면 화면이 `[32m` 로 도배된다.
- 타임아웃이면 **`Process.Kill(entireProcessTree: true)`.** CLI 는 자식(node·git·
  ripgrep)을 띄우므로 부모만 죽이면 자식이 남아 장비에 쌓인다.
- 실행기가 죽을 때(Ctrl+C·재부팅) 자기가 띄운 자식을 정리하고, 서버에 `interrupted`
  를 보고하고 나간다.

### 7.3 작업공간 — **대상 종류에 따라 갈린다**

대상을 화면에서 고르게 되면서(4.4) 작업공간이 한 가지가 아니게 됐다.
**공통 원칙은 하나다 — 원본에서 직접 돌리지 않는다.** 다만 「원본을 어떻게
비껴가나」가 종류마다 다르다.

| 대상 | 격리 방법 | 병렬 | 되돌리기 |
|---|---|---|---|
| `repo` | `git worktree add` | **된다** | 브랜치를 버리면 끝 |
| `folder` + `copy` | `rsync -a` 로 복사본 | 된다 | 복사본을 버리면 끝 |
| `folder` + `inplace` | **격리 없음** | **안 된다** | 실행 전 tar 백업뿐 |

**격리 방법과 「올릴 수 있나」는 다른 이야기다.** 한동안 push 게이트가 그 둘을
붙여 놓아 `worktree` 가 아니면 무조건 돌아섰는데, `inplace` 는 정본 그 자체라
git 이 멀쩡히 있다 — 올릴 수 있고, 올리기를 켜 두었으면 **올려야 한다**
(밟은 것 18번).

| 격리 | 올릴 수 있나 | 어디에서 커밋하나 |
|---|---|---|
| `worktree` | 된다 | 사본 그 자리 — 이 실행만의 가지 `ai/<task>-<run>` |
| `inplace` | 된다 | 정본 그 자리 — **지금 가지가 올릴 가지와 같아야 한다** |
| `copy` | 된다 | **정본으로 되돌린 뒤 정본에서** |

> **`inplace` 는 저장소 대상에 쓰지 않는다 (2026-09-19).**
>
> 빠른지시 대상(`portal-jsini`)이 `/home/lee/Funeralv2` 를 「그냥 폴더」로
> 등록하는 바람에 격리가 `inplace` 로 잡혀 있었고, 보낸 건이 전부 **운영
> 정본을 직접** 고쳤다. 게이트가 금지 경로(`deploy/`)에 걸려 커밋을 못 한
> 실행 하나가 정본을 더럽힌 채 끝나자 **그 뒤로 집혀 간 여덟 건이 모두**
> 「정본이 깨끗하지 않습니다」로 죽었다.
>
> 동시 실행 때문이 아니다 — 같은 대상에 둘이 겹치는 것은 서버의
> `running_run_key`(4.4) · 실행기의 `TargetGate`(9.5) · 끝낼 때의
> `ParkAsync` 로 이미 막혀 있다. 한 건이 남긴 것이 **그 뒤 전부를 막는**
> 구조였던 것이 문제다.
>
> 고친 것이 둘이다.
>
>   1. 그 대상을 `repo` + `worktree` 로 되돌렸다
>      (`deploy/sql/projmng-ai-target-inplace-2026-09-19.sql`).
>      **worktree 도 push 는 그대로 된다** — `inplace` 로 둘 이유가 없었다.
>   2. `PrepareAsync` 가 원본 직접인데 정본이 더러우면 **막지 않고 stash 로
>      옮기고 지나간다.** 끝낼 때 치우는 `ParkAsync` 가 한 번 거르는 경우
>      (실행기가 CLI 가 도는 중에 죽으면 그 자리가 아예 안 돈다)를 받는
>      그물이다. 치우지도 못하면 그때는 막는다 — 더러운 자리에서 고치면
>      게이트의 `git add -A` 가 남의 변경까지 집어 커밋한다.

마지막 줄이 이 표에서 유일하게 「자리를 옮기는」 경우다. 사본에는 `.git` 이
없어 그 자리에서는 커밋할 곳이 없다 — 그렇다고 「올릴 수 없는 대상」으로
끝내면 **올리기를 켜 둔 사람의 결과가 아무 데도 안 간다.**

```
① 사본에서 AI 가 일한다              /home/lee/ai-workspaces/run-N
② 올리기가 켜져 있으면 되돌린다      rsync -a --delete --exclude .git  사본/ → 정본/
③ 정본에서 커밋·검사·push 한다       (worktree 와 같은 길)
```

되돌릴 때 **복사할 때 쓴 규칙을 그대로 뒤집는다.** 사본은 정본을 그대로 뜬 것에
AI 의 손이 얹힌 것이라 AI 가 지운 파일은 정본에서도 지워지는 것이 맞다
(`--delete`). `.git` 만은 건드리지 않는다 — 그것까지 덮으면 이력이 통째로 날아간다.

**올리기가 꺼져 있으면 되돌리지 않는다.** 원본을 안 건드리는 것이 `copy` 의
요점이므로, 올릴 생각이 없는 실행이 정본을 바꿔서는 안 된다.

정본마저 git 이 아니면 그때는 정직하게 막는다 — 올릴 원격이 없는데 push 할
방법은 없다.

#### `repo` 대상 — 한 실행의 처음부터 끝까지

기본 대상인 `/home/lee/Funeralv2` 가 이쪽이다. 순서가 정해져 있다.

```
① 정본 clone 이 깨끗한지 본다      git status --porcelain  → 더러우면 원본 직접만 거절(21)
② **반드시 최신으로 당긴다**        git fetch origin && git merge --ff-only origin/<가지>
③ worktree 를 판다                  git worktree add …/<run_id> -b ai/<task>-<run> origin/main
④ CLI 가 거기서 돈다                (커밋까지. push 는 안 한다 — 9.3)
⑤ push 게이트 여섯               빌드·테스트·바뀐 것·금지 경로·잠금 (9.3)
⑥ 통과하면 실행기가 민다            git fetch origin main && git rebase origin/main && git push origin HEAD:main
⑦ 정리                              브랜치·worktree 를 남길지 치울지
```

②가 **결정된 요구사항이다** — 「시작 전 반드시 `pull`」.
정본이 뒤처져 있으면 뒤에 오는 것이 전부 어긋난다(아래).

**정본에서 직접 돌리지 않는 이유 넷:**

1. **`main` 체크아웃 상태다**(2.4). 거기서 AI 가 커밋하면 게이트를 거치지 않고
   `main` 이 움직인다 — 그리고 그것이 곧 배포다(9.3).
2. 실패한 실행의 찌꺼기가 정본에 남지 않는다. 다음 실행의 기준이 깨끗하다.
3. 병렬 실행이 서로의 파일을 밟지 않는다.
4. 무엇이 바뀌었는지가 worktree 하나로 깔끔히 남는다(diff·브랜치).

⑥에서 **정본을 거치지 않고 worktree 에서 바로 민다**(`HEAD:main`).
정본에 merge 했다가 미는 길도 있지만 걸음이 하나 더 늘 뿐이고, 정본은 다음
실행의 ②에서 어차피 따라온다.

저장소가 61MB 이고 817GB 가 남아 있으니(2.4) worktree 는 싸다.
**끝난 것을 치우는 규칙은 둔다**(성공 후 N일). 안 두면 반드시 쌓인다.

##### 왜 ②가 그냥 좋은 습관이 아니라 **필수**인가

배포는 GHCR 이미지를 받지 소스를 pull 하지 않는다. `/home/lee/Funeralv2` 는
**아무도 갱신하지 않으면 조용히 뒤처진다.** 지금은 마침 최신이지만(2.4) 보장은 아니다.

push 까지 하기로 한 지금은 결과가 더 나쁘다 — 뒤처진 기준에서 만든 커밋을
`main` 에 밀면 **그 사이 다른 사람이 올린 것을 되돌리는 커밋**이 될 수 있다.
그리고 그것이 곧 배포다.

뒤처진 기준에서 돌면 **없는 파일과 깨진 빌드가 「기능이 없는 것」으로 보인다.**
AI 가 그것을 보고 「그 기능을 새로 만들겠다」 하면 결과물이 통째로 헛것이 된다.
그래서 worktree 를 만들기 전에 `git fetch` 하고, **갈라져 나온 커밋 SHA 를
`ai_task_run` 에 남긴다.**

##### 비공개 저장소를 대상으로 등록하면 — **자격 문제가 생긴다**

우리 저장소는 공개라 `fetch` 에 자격이 필요 없고, 그래서 `~/.git-credentials` 를
통째로 막을 수 있었다(9.3). **비공개 저장소를 대상으로 등록하는 순간 그 전제가
깨진다** — 막아 놓은 자격이 없으니 `fetch` 부터 실패한다.

풀 때 **막아 둔 것을 도로 여는 쪽으로 가지 않는다.** 대상마다 **읽기 전용
배포 키**를 따로 두고 실행기가 그 키만 쓰게 한다.

```
GIT_SSH_COMMAND="ssh -i /etc/ai-runner/keys/<credential_ref> -o IdentitiesOnly=yes"
```

- 키는 **읽기 전용**으로 발급한다(GitHub 배포 키의 write 권한을 끈다).
  그러면 push 를 코드로 막을 필요조차 없다 — **키가 못 한다.**
- 키 파일은 실행기만 읽게 두고, 대상 표에는 **이름만** 담는다(`credential_ref`).
  DB 에 키를 넣지 않는다.

#### `folder` 대상 — 복사본이 기본이다

**그 폴더가 git 저장소이면 시작 전에 `pull` 한다** — 종류가 `folder` 라도 마찬가지다.
git 이 아니면 해당 없다.

git 이 아닌 폴더는 worktree 가 없다. 기본은 **`copy`** 다 — `rsync -a` 로
작업공간에 떠 놓고 거기서 돌린다. `max_size_mb` 를 넘으면 **실행을 거절한다**
(복사에 몇 분을 쓰다 타임아웃으로 죽는 것보다 낫다).

**`inplace` 는 예외로만 연다.** 원본을 직접 고치는 것이라 되돌릴 방법이
실행 전 tar 백업뿐이고, 같은 대상에 두 건이 겹치면 서로를 덮는다
(그래서 4.4 의 `running_run_id` 잠금이 필요하다).

**복사본은 끝나도 지우지 않는다.** worktree 는 브랜치에 결과가 남지만 복사본은
그 폴더가 결과의 전부다 — 치우면 AI 가 한 일이 통째로 사라진다(실제로 한 번
날렸다). 실행기가 끝낼 때 그 경로를 로그에 적는다. 대신 쌓이므로 **치우는
규칙이 따로 필요하다**(성공 후 N일).

`copy` 의 한계도 정직하게 적어 둔다 — **고친 결과가 복사본에 남는다.**
폴더 작업의 목적이 대개 그 폴더를 실제로 고치는 것이라면, 사람이 결과를 보고
반영하는 절차가 따로 필요하다. 그 절차(diff 보여 주고 「반영」 누르기)는
**4단계 이후**다. 그전까지 `folder` 대상은 「봐 주고 알려 주는」 일에 쓴다.

#### 브랜치는 남긴다

실행기는 언제나 새 브랜치를 판다(`ai/<task_id>-<run_id>`). 게이트를 통과해
`main` 으로 나갔더라도 **그 브랜치를 바로 지우지 않는다** — 무엇이 나갔는지
되짚을 자리이고, 게이트에 걸려 안 나간 건은 사람이 이어받을 자리다.

`auto_push` 가 꺼져 있으면 ⑤·⑥을 건너뛴다. 커밋과 브랜치만 남고 화면이
「밀 준비가 됐습니다」로 말한다.

### 7.4 **DB 의 본문을 CLI 에게 어떻게 주나** (실제로 확인함, 2026-09-17)

이 기능의 한가운데다. 화면에서 쓴 글은 DB 에 있고, CLI 는 명령줄 프로그램이다.
그 사이를 잇는 방법이 **CLI 마다 다르다** — 운영 서버에서 직접 확인했다.

| | `claude` | `agy` (안티그래비티) | `copilot` |
|---|---|---|---|
| 비대화형 | `-p` | `-p=<프롬프트>` · `--print` | `-p/--prompt=<프롬프트>` |
| **stdin 으로 본문** | **된다** — `claude -p < task.md` ✅ | **안 된다.** `-p` 가 값을 요구한다 | **쓰지 않는다.** 인자로 전달한다 |
| 인자로 본문 | 된다 | **된다** — `agy -p="…"` ✅ | **된다** — `copilot --prompt="…"` ✅ |
| stream-json 입력 | Claude 형식 | **자체 형식** — `event` 필드를 요구한다 | 지원하지 않음 — 일반 출력의 마지막 40줄을 결과로 사용 |
| 기본 제한 시간 | 없음 | **5분** (`--print-timeout`) ⚠️ | 없음 |

확인한 것 그대로:

```
$ claude -p < /tmp/agtest.md
5

$ agy --print-timeout 60s -p="2 더하기 3은? 숫자만 답하라."
5
```

#### 밟은 것 둘 — 둘 다 조용히 틀린다

**① `agy -p` 뒤에 플래그를 두면 그 플래그를 프롬프트로 먹는다.**

```
$ agy -p --print-timeout 60s < task.md
Error: -p took "--print-timeout" as its prompt, so the intended prompt was
       left as an argument and ignored.
```

다행히 이 경우는 말을 해 준다. **`-p=값` 으로 붙여 쓴다.**

**② `agy` 의 제한 시간 기본값이 5분이다.**

30분짜리 작업을 시키면 **5분에 잘린다.** 그리고 잘린 것은 「실패」로 보이지
「시간이 모자랐다」로 보이지 않는다. 어댑터에 반드시 적는다.

#### 그래서 어떻게 주나 — **본문은 언제나 파일로 남기고, 전달은 길이로 가른다**

실행기가 DB 에서 읽어 작업공간에 `task.md` 로 떨어뜨린다. **이것은 전달 수단과
무관하게 늘 한다** — 나중에 「그때 무슨 지시였나」를 손으로 재현할 수 있어야 하고,
그 파일 하나면 사람이 같은 명령을 그대로 다시 칠 수 있다.

```csharp
var promptPath = Path.Combine(workspace, ".ai-task", "task.md");
await File.WriteAllTextAsync(promptPath, task.Contents, new UTF8Encoding(false));
```

> **BOM 을 붙이지 않는다.** `new UTF8Encoding(false)` 가 그 뜻이다.
> 기본 `File.WriteAllText` 는 BOM 을 붙이고, 그러면 프롬프트 첫 글자가
> 보이지 않는 문자로 시작한다.

그다음 전달은 셋 중 하나다.

| 본문 길이 | 방법 |
|---|---|
| `claude`, 아무 길이 | **stdin** — `claude -p < task.md`. 가장 깔끔하다 |
| `agy`, 짧다(기본 60KB 미만) | **인자** — `-p=<본문>`. `ArgumentList` 로 넣는다 |
| `agy`, 길다 | **파일 참조** — `-p="<경로> 를 읽고 그대로 수행하라"` |

60KB 로 가르는 이유: 리눅스는 **인자 하나의 길이 상한이 128KB**(`MAX_ARG_STRLEN`)다.
전체 argv 2MB 와는 다른 값이고, 긴 지시문 하나면 **이쪽에 먼저 걸린다.**
절반에서 갈라 두면 여유가 있다.

#### `"$(cat task.md)"` 를 쓰지 않는 이유

손으로 칠 때는 그것이 제일 편하다. **실행기는 그렇게 하지 않는다.**

1. **셸을 거치지 않는다.** `UseShellExecute = false` + `ArgumentList` 로 인자를
   하나씩 넣는다. 셸 문자열을 만들면 본문 안의 `"` · `` ` `` · `$(…)` 가
   **명령으로 해석된다** — 사람이 쓴 글이 그대로 명령이 되는 자리다.
2. **`ps` 에 본문이 그대로 보인다.** 같은 장비의 다른 프로세스에서 읽힌다.
3. 128KB 상한(위).

### 7.5 어댑터는 코드가 아니라 설정이다

확인한 값을 그대로 적는다.

```json
"Runners": {
  "claude": {
    "Executable": "/home/lee/.local/bin/claude",
    "Args": ["-p", "--dangerously-skip-permissions",
             "--output-format", "stream-json", "--verbose"],
    "PromptVia": "stdin",
    "TimeoutMinutes": 30
  },
  "antigravity": {
    "Executable": "/home/lee/.local/bin/agy",
    "Args": ["--print-timeout", "30m", "--dangerously-skip-permissions",
             "--output-format", "stream-json"],
    "PromptVia": "arg",
    "PromptArgPrefix": "-p=",
    "PromptMaxBytes": 61440,
    "PromptFileFallback": "{path} 를 읽고 그대로 수행하라.",
    "TimeoutMinutes": 30
  },
  "copilot": {
    "Executable": "/home/lee/.local/bin/copilot",
    "Args": ["--allow-all-tools", "--allow-all-paths", "--silent"],
    "PromptVia": "arg",
    "PromptArgPrefix": "--prompt=",
    "PromptMaxBytes": 61440,
    "PromptFileFallback": "{path} 를 읽고 그대로 수행하라.",
    "TimeoutMinutes": 30,
    "ResultFrom": "tail"
  }
}
```

**경로를 절대 경로로 박는다.** 실행기는 systemd 로 도는데 그 환경의 `PATH` 에는
`~/.local/bin` 이 없을 수 있다 — 로그인 셸에서만 보이던 자리다(실제로
`command -v` 가 한 번 빈손이었다).

CLI 의 플래그는 자주 바뀐다. 코드에 박으면 플래그 한 글자 때문에 배포한다.

#### 여기 적힌 것이 **돌릴 수 있는 것의 전부다** (2026-09-20)

한동안 `Runner:Kinds` 라는 배열이 따로 있어서, 어댑터를 넣을 때 **두 곳을
고쳐야** 했다. 그 둘이 어긋나는 방향에 따라 증상이 갈렸다.

| 어긋난 방향 | 무슨 일이 나나 |
|---|---|
| `Kinds` 에 있는데 어댑터가 없다 | 집어 가서 **「이 장비에는 'x' 어댑터가 없습니다」로 시끄럽게 실패한다.** 사람이 바로 안다 |
| 어댑터가 있는데 `Kinds` 에 없다 | 집어가기 질의가 `runner_kind = ANY(kinds)` 로 거른다 → **아무도 집지 않는다.** 오류도 로그도 없이 「대기」로만 앉아 있다 |

**뒤엣것을 실제로 밟았다.** `copilot` 어댑터를 넣은 뒤 운영 장비의
`appsettings.json` 을 옛것으로 둬서, 코파일럿으로 시킨 건이 전부 「대기」에
남았다. 화면·서버·DB·실행기 모두 멀쩡했고 — **실행기는 떠 있었다** — 고장은
장비 설정 파일 한 줄이었다. 그동안 화면이 한 말은
「실행기가 떠 있는지 확인하십시오」였고, 그래서 엉뚱한 곳을 한참 봤다.

그래서 **적는 자리를 하나로 줄였다.** `Kinds` 를 없애고 `Adapters` 의 열쇠를
그대로 쓴다(`RunnerOptions.RunnableKinds`). 어긋날 두 곳이 없으면 어긋나지 않는다.

- **이 장비에서만 하나를 끄려면** 그 어댑터의 `Executable` 을 빈 문자열로 덮는다.
  `appsettings.Local.json` 에 `"Adapters": { "copilot": { "Executable": "" } }` 다 —
  **사전은 열쇠로 겹치므로** 배열처럼 칸 번호로 뒤섞이지 않는다.
  옛 `Kinds` 배열이 바로 그 함정이었다(Local 에 둘을 적으면 기본 파일의 셋째가
  남아 시작 로그에 중복으로 찍혔다).
- 시작할 때 어댑터를 한 번 훑는다 — **어댑터가 하나도 없거나**(설정이 통째로
  안 읽힌 것이다) **적힌 실행 파일이 없으면** 그 자리에서 말한다. 시켜 보기
  전에 알아야 하는 것들이다.
- 감시자가 적는 사유에도 **고른 AI 이름이 박힌다**(`AiStaleSweeper`) —
  「`copilot` 를 돌릴 실행기가 집어 가지 않았습니다」. 봐야 할 변수를
  그 자리에서 가리킨다.

#### 어댑터를 고쳤으면 **장비를 다시 만다**

이 파일은 실행기 폴더로 **함께 말려 올라간다**(`deploy/ai-runner/README.md` ②
— `dotnet publish` 한 산출물을 통째로 `rsync` 한다). 그래서 「코드는 안
바뀌었으니 배포는 안 해도 된다」가 **틀린 자리**다. `copilot` 이 딱 그렇게
어긋났다 — 저장소에는 어댑터가 있고 장비에는 없었다.

장비에서 확인하는 방법은 **기동 로그 한 줄**이다.

```
실행기 jsini-prod 시작 · 서버 http://127.0.0.1:5450 · CLI [antigravity,claude,copilot] · 동시 5 · 조회 60초
```

거기 없는 종류로 시킨 건은 집어가기 질의에서 걸러져 **아무도 집지 않는다** —
오류도, 로그도, 실패한 실행 한 줄도 없다.

> **덧 — 담장은 생각보다 헐겁다.** 유닛의 `ProtectSystem=strict` 는 `/` 를
> 읽기전용으로 만들지만, 이 장비의 `/home` 은 **별도 마운트라 그대로
> 읽기·쓰기**다. `ReadWritePaths` 에 `~/.claude` 만 적혀 있고 `~/.copilot` 은
> 없는데도 코파일럿이 자기 세션을 쓸 수 있는 것이 그 때문이다 —
> **우연히 되는 것이지 뜻이 아니다.** 담장을 조일 때(9.9 권한 분리) 같이 본다.

### 7.6 `--dangerously-skip-permissions` 를 쓴다 — 그러면 **담장이 유일한 경계다**

비대화형에서는 물어볼 사람이 없다. 안 켜면 `claude` 도 `agy` 도
(기본 `permission_mode` 가 `request-review` 다) **첫 파일 쓰기에서 멈춘 채로
제한 시간을 채운다.** 그래서 켠다.

대신 이것만은 분명히 해 둔다 — **켜는 순간 CLI 쪽 안전장치가 0 이 된다.**
남는 경계는 9.2 의 systemd 담장 하나뿐이다. 그 유닛이 「있으면 좋은 것」에서
**「이것 하나가 전부인 것」**으로 바뀐다.

| | 안 켰을 때 | **켰을 때(지금)** |
|---|---|---|
| CLI 가 파일을 쓸 때 | 물어본다 → 비대화형에선 멈춘다 | 그냥 쓴다 |
| 막는 것 | CLI + 담장 | **담장뿐** |
| 유닛을 빠뜨리면 | 그래도 멈춘다 | **아무것도 안 막는다** |

그래서 0단계(장비 준비)가 1단계보다 먼저다(16장).

### 7.7 두 CLI 의 공통점과 차이

`agy --help` 에서 확인한 것 중 쓸 만한 것:

- `--add-dir` 로 작업 폴더를 더 붙일 수 있다 — `folder` 대상을 함께 물릴 때 쓴다.
- `--mode accept-edits` 가 있다. `--dangerously-skip-permissions` 보다 좁은 선택지다.
- `--output-format stream-json` 이 둘 다 있다 — **로그와 결과를 같은 방식으로
  다룰 수 있다**(4.2 의 `result_text`).
- `agy` 는 `run_command` · `write_to_file` · 브라우저 조작까지 도구로 갖고 있다.
  담장 안에서 돈다는 전제가 여기서도 그대로다.

`claude` 는 로그인 자격이 `~/.claude` 에, `agy` 도 같은 계정 홈에 있다.
둘 다 **구독 인증이 이미 끝나 있다**(2.4).

## 8. 제목을 「적당히」 붙이는 규칙

순서대로 시도하고, **저장을 막지 않는다.**

1. 사람이 적었으면 그것.
2. 본문 첫 `#` 제목 줄. 없으면 첫 비어 있지 않은 줄 40자.
3. 그래도 비면 저장 응답 안에서 LLM 에게 한 줄 요약을 시킨다 —
   `ProjMngServer` 가 `AIAgentServer`(`/api/ai/chat`)를 **서비스 간 호출**로 부른다.
   새로 만들 것이 없다. **타임아웃 3초, 한 번만, 실패하면 2번 값.**

   > 이 한 번이 `ProjMngServer` → `AIAgentServer` 의 유일한 연결이다.
   > 그 호출이 안 돼도 저장은 된다 — **곁들이 기능이 본 기능을 막지 않는다.**

비동기로 나중에 채우는 방식은 쓰지 않는다. 목록이 잠깐 「제목 없음」으로 보이고,
그 사이 사용자가 제목을 고치면 뒤늦게 온 AI 제목이 사람이 쓴 것을 덮는다.

## 8-2. 끝나면 **이메일로 받는다** (옵션)

만드는 화면에 「완료되면 메일로 받기」를 둔다. 켜면 작업이 끝났을 때 결과가
메일로 간다.

### 8-2.1 **처리 요약은 알림의 일부가 아니다** (2026-09-20)

`ai_task_run.summary_text` 를 적는 일은 메일·앱푸시 설정과 **무관하다.**
끝난 실행이면 언제나 만든다.

한동안 그렇지 않았다. 요약은 메일 본문에 실을 값이었으니 메일을 만드는 쪽
(`AiTaskNotifier`)에서 만들었고, 그러면 **요약의 수명이 알림 관문에 매달린다** —
「메일로 받기」가 꺼져 있으면 그 앞에서 돌아가므로 요약도 없다. 그런데 알림을
끈 사람이야말로 **화면의 「처리 요약」 칸이 결과를 읽는 유일한 자리**다
(8-4.4). 하필 그 사람에게만 요약이 없었다.

2026-09-19 에 관문 순서를 바꿔 한 번 고쳤지만 그것은 **주석으로 지킨 약속**
이었다 — 알림 쪽을 손대는 다음 사람이 관문을 하나 더 얹으면 조용히 되돌아간다.
지금은 구조로 갈라 두었다.

| | 누가 | 언제 |
|---|---|---|
| 요약을 만들어 적는다 | `AiRunSummaryWriter` | 완료 처리가 부른다. **알림 설정을 보지 않는다** |
| 알린다 | `AiTaskNotifier` | 그다음. 적혀 있는 요약을 **읽기만** 한다 |

순서가 있다 — 메일의 「무엇을 했다나」 칸이 그 요약을 싣는다. 나란히 돌리면
메일이 요약을 못 받고 나간다(`AiRunService.SummarizeThenNotifyAsync`).

**한 번 실패했다고 포기하지 않는다.** AI 호출은 30초에서 끊기고, 바쁘거나
한도에 걸리면 빈손으로 돌아온다. 예전에는 그 한 번이 전부여서 `summary_text`
가 영영 비었다 — 메일을 켠 사람은 옛 방식(결과문 앞 몇 줄)으로라도 답을
받으니 눈치채지 못했고, **알림을 끈 사람만 빈칸을 봤다.**

| 손잡이 | 기본 | 무엇 |
|---|---|---|
| `AiTasks:SummarizeResult` | `true` | 아예 끈다 (AI 가 안 떠 있는 장비) |
| `AiTasks:SummaryAttempts` | `2` | 몇 번까지 불러 보나 |
| `AiTasks:SummaryRetryDelaySeconds` | `3` | 다시 부르기 전에 쉬는 시간 |
| `AiTasks:SummaryTimeoutSeconds` | `30` | 한 번에 거는 시간 |

**넉넉히 잡으면 안 된다** — 메일이 이 결과를 기다리므로, 시도를 늘린 만큼
AI 가 죽어 있는 동안 결과 메일이 늦게 나간다. 화면이 요약을 기다리는 바퀴 수
(8-4.4)도 이 값들의 합보다 길어야 한다.

**작업 제목도 이때 다시 짓는다.** 요약의 첫 문장(`headline`)으로 `ai_task.title`
을 덮는다 — 「빠른 지시」로 들어온 건은 제목이 지시문 앞부분이라, 끝난 뒤 한
일로 고쳐 주면 목록에서 찾기 쉽다. 이것도 알림 설정과 무관해야 하는 값이었고,
갈라 두기 전에는 **메일을 끄면 제목도 안 바뀌었다.**

**중간 실패는 요약하지 않는다.** 다시 시도할 건은 여기까지 오지 않는다 —
세 번 시도하는 작업이 시도마다 요약을 만들면 모델을 세 번 부르고, 그 요약이
작업 제목을 두 번 갈아 치운다. 마지막 판정만 남긴다(알림과 같은 규칙).

### 무엇을 보내나 — 세 가지가 같은 자리에 온다

시킨 일이 무엇이었느냐에 따라 본문이 다르다. **셋을 구분하려 들지 않는다.**

| 시킨 것 | 메일에 오는 것 |
|---|---|
| 「이것을 고쳐라」 | 무엇을 고쳤는지 · 바뀐 파일 · 배포됐는지 |
| 「이게 왜 이런지 알려 달라」 | **답** |
| 「이것을 조사해 보고서로 써라」 | **보고서 본문** |

셋 다 `ai_task_run.result_text` 하나에 담긴다(4.2). 그래서 메일을 만드는 쪽은
「무엇을 시켰나」를 몰라도 된다 — **AI 가 마지막에 한 말을 그대로 싣는다.**
이것이 갈래를 나누지 않는 이유고, 나누려 들면 분류가 틀렸을 때 답이 통째로 사라진다.

### 메일 한 통의 모양 — **요약이 먼저, 전문이 뒤**

이 메일은 대개 휴대폰에서 열린다. 「빠른 지시」(11.4)로 보낸 건은 답을
**오직 메일로만** 보고, 그 사람은 이미 그 화면을 떠났다. 그런데 아래로
스크롤해야 알 수 있는 메일은 사실상 안 읽힌다 — **첫 화면에서 끝나야 한다.**

그래서 맨 위에 요약 다섯 줄을 둔다.

```
══════════════════════════════════════════════
  완료 · 운영에 올라감 — url /projmng/ai/task/{번호} 는 …
══════════════════════════════════════════════

■ 결과    완료 · 3차 · 0:19:40
■ 대상    portal-jsini
■ 시킨 것 작성 중인 내용이 탭을 옮기면 사라진다. 임시저장하도록 고쳐라.
■ AI 의 답 작성 중인 지시문을 localStorage 에 적어 두도록 고쳤습니다.
            돌아오면 되살리고, 되살렸다고 화면이 말합니다.
■ 바뀐 것 4 files changed, 813 insertions(+), 37 deletions(-)
■ 할 일   없습니다. 이미 올라갔고 배포가 돕니다.
```

| 칸 | 답하는 물음 |
|---|---|
| 첫 줄 | **무엇이 어떻게 됐나** — 제목 하나로 끝난다 |
| 결과·대상 | 언제 어디에서 |
| 시킨 것 | **무엇을 물었나** |
| AI 의 답 | 무엇을 했다나 |
| 바뀐 것 | 파일이 움직였나 |
| 할 일 | **내가 뭘 해야 하나** |

**「시킨 것」이 한동안 빠져 있었다.** 답만 있고 물음이 없으면, 며칠 뒤에
열어 본 사람은 이 메일이 무엇에 대한 것인지 알 수 없다. 여러 건을 던져 두고
답을 받는 화면을 만든 이상 이 칸이 없으면 메일이 서로 구분되지 않는다.

**「할 일」이 요약에서 제일 쓸모 있는 칸이다.** 「읽고 끝」인지 「가서 봐야
하는지」가 여기서 갈린다 — 올라갔으면 할 일이 없고, 커밋만 있으면 사람이
확인해 올려야 하고, 실패했으면 로그를 봐야 한다.

#### 「AI 의 답」은 **AI 가 다시 쓴다** (2026-09-18)

처음에는 결과문의 앞 몇 줄을 그대로 떴다. 「앞부분은 대개 이미 결론」이라고
본 것인데, **실제 결과문은 그렇지 않았다.** 실행기의 답은

```
먼저 관련 파일을 찾아보겠습니다.

## 작업 내용
...
```

처럼 서론으로 시작하고 결론은 글 끝에 있다. 메일은 첫 화면에서 끝나야 하는데
**가장 잘 보여야 할 칸에 「찾아보겠습니다」가 앉았다.** 표로 시작하는 답이면
`| 파일 | 내용 |` 이 요약 칸에 들어갔다.

그래서 끝난 뒤 AI 에게 한 번 더 정리시킨다(`AiResultSummarizer` →
AIAgentServer `/chat`). 받는 것은 **한 문장 + 항목 서넛 + 확인할 것**이고,
메일은 그것을 점 찍힌 줄로 그린다.

> **처음에 이것을 하지 않은 이유는 그대로 옳다** — 「메일 한 통마다 모델을 한 번
> 더 부르고, 그 호출이 실패하면 메일이 안 나간다」. 세 가지로 막는다.
>
> 1. **메일이 실제로 나갈 건에만 부른다.** 받기가 꺼졌거나 받는 사람이 없어
>    어차피 안 나갈 건은 거기까지 오지 않는다.
> 2. **실패하면 옛 방식으로 돌아간다.** 정리에 실패해도 메일은 나간다 —
>    앞 몇 줄 뜨기(`Gist`)가 그대로 남아 있는 것이 그 장치다. 표 구분선이나
>    밑줄 같은 꾸밈 줄을 건너뛰는 것도 그쪽이 계속 한다.
> 3. **시간을 짧게 건다.** 결과 메일은 빨리 와야 뜻이 있다.
>
> 끄는 손잡이는 `AiTasks:SummarizeResult` 다. 끄면 예전 모양으로 돌아간다.

### 전문의 모양

```
제목: [AI 작업] <작업 제목> — 완료 / 실패 / 중단

· 대상 · 걸린 시간 · 종료 코드
· 운영 배포됨 : abc1234  (push 한 건만. 안 나갔으면 왜 안 나갔는지)   ← 9.3
· ────────────────────────────────
· result_text 전문
· ────────────────────────────────
· 바뀐 파일 요약 (diff_stat)
· 화면에서 보기: https://portal.jsini.co.kr/projmng/ai/task/{번호}   ← 8-4.2
```

- **로그 전문을 첨부하지 않는다.** 수천 줄이 메일함에 쌓이고, 9.6 의 마스킹을
  통과한 것이라도 메일은 한 번 나가면 회수할 수 없다. 링크로 보낸다.
- `result_text` 가 비어 있으면(CLI 가 아무 말 없이 끝났으면) **그 사실을 적는다.**
  빈 메일을 보내면 받는 사람이 메일 사고로 읽는다.

### 누가 보내나 — **실행기가 아니라 서버가**

실행기는 `complete` 를 보내는 것으로 자기 일을 끝낸다. 메일은 **`ProjMngServer`**
가 그 뒤에 보낸다.

그렇게 가르는 이유: 실행기가 보내면 **작업은 끝났는데 메일 때문에 실행 슬롯이
묶인다.** 그리고 메일 실패로 실행이 실패한 것처럼 보이게 된다 — 이 둘은 다른 일이다.

### 보내는 길 — 이미 있는 것을 쓴다

`NotificationServer`(:5460)에 둘이 있다.

| 길 | 성질 | 우리 선택 |
|---|---|---|
| `POST /api/notification/email` | **큐**로 넣는다(`run_script`). 결과는 「넣었다」까지만 안다 | 안 쓴다 |
| `POST /api/notification/emails/send` | **SMTP 직발송.** 성공·실패를 안다 | **이쪽** |

큐 쪽은 6.2 에서 피하기로 한 바로 그 `run_script` 를 다시 타고, 무엇보다
**보내졌는지 알 수 없다.** 「결과를 메일로 받겠다」는 기능에서 그것을 모르면
기능이 절반만 있는 것이다.

`/emails/send` 는 `X-User-Id` 를 요구한다 — 서비스 간 직접 호출이므로
`AI_TASK` 같은 자기 이름을 적어 보낸다(`SiteServer` 가 `SITE_INQUIRY` 로 하는 것과 같다).

#### 받는 사람을 **아이디로** 넘긴다

「받는 사람」을 비우면 요청한 사람에게 보낸다. 그런데 **`projmng` DB 에는
사람의 메일 주소가 없다** — 계정은 `scom` 에 있고 그쪽은 알림 서비스의 DB 다.
그래서 이쪽이 아는 것은 로그인 아이디(`cre_id`)뿐이다.

| 칸 | 무엇을 넣나 | 누가 푸나 |
|---|---|---|
| `to` | 주소 그대로 (사람이 적은 값) | 안 푼다 |
| `toUser` | **로그인 아이디** | 알림 서비스가 `scom` 에서 |
| `toRole` | 역할 키 | 알림 서비스가 `scom` 에서 |

아이디를 `to` 에 실으면 **주소 꼴이 아니라서 걸러진다.** 실제로 그렇게
`NO_RECIPIENT` 400 만 쌓이고 한 통도 안 나갔다(밟은 것 20번).

> `toRole` 은 받는 사람이 이메일 알림을 껐으면 뺀다 — 「그 역할인 사람 아무나」
> 에게 가는 알림이라 본인의 뜻을 지킬 수 있다. **`toUser` 는 빼지 않는다.**
> 이쪽은 그 건마다 본인이 직접 켠 업무 메일이고, 알림 설정으로 막으면 켠
> 사람이 왜 안 오는지 알 길이 없다.

### 실패해도 작업은 완료다

메일이 안 나가도 **작업 상태를 바꾸지 않는다.** 대신 `notify_error` 를 남기고
화면에 「결과 메일: …」 줄을 띄운다. 배포 도구가 같은 규칙을 쓴다 —
보고에 실패해도 배포는 계속한다(6.9).

**그 줄을 그리는 것까지가 이 기능이다.** 사유를 DB 에만 적고 화면에 안 띄웠더니
증상이 「메일이 안 온다」 하나로만 보였고, 이유는 DB 를 열어야 알 수 있었다.
남길 때도 상태 번호만 적지 않고 **실패 응답의 본문까지** 읽어 붙인다 —
「HTTP 400」은 무엇이 틀렸는지 한 글자도 말해 주지 않는다.

재시도는 두세 번까지만. 받는 주소가 틀린 것은 재시도로 고쳐지지 않는다.
그래서 **주소가 아닌 값은 보내기 전에 여기서 막고** 그렇게 적는다.

### 보내기 전에 **한 번 더 가린다**

메일은 우리 담장 **밖으로** 나간다. 9.6 의 마스킹을 이미 거친 값이라도
`result_text` 에 한 번 더 건다. 화면은 로그인한 사람만 보지만 메일은 전달되고
보관되고 검색된다 — **되돌릴 수 없는 유일한 출구**다.

## 8-4. 「빠른 지시」 — **길에서 한 줄 던지는 자리** (11.4)

화면: `web/src/Apps/JSini.Web.ProjMng/Components/Pages/AiAsk.razor`
(`/projmng/ai/ask` · 메뉴 SQL 은 `deploy/sql/portal-menu-ai-ask-2026-09-18.sql`)

「AI 작업」 화면(11장)은 **책상에서 짓는 자리**다. 좌우 분할에 편집기와 실행
로그가 있고 한 건을 오래 붙들고 고친다. 그게 맞는 화면이다.

이 화면은 다른 일을 한다. 엘리베이터에서, 회의 들어가기 전에 떠오른 것을
적어 보내고 답은 나중에 메일로 받는다. 그 상황에서는

- 좌우 분할이 설 자리가 없다(세로 화면이다)
- 로그를 실시간으로 볼 이유가 없다(어차피 그 자리를 뜬다)
- 고를 것이 많으면 안 된다(한 손이고, 흔들린다)

**세로 한 줄 · 큰 글상자 · 단추 하나.**

| 정한 것 | 왜 |
|---|---|
| **자료는 `ai_task` 를 그대로 쓴다** | 표를 나누면 두 화면이 서로의 건을 못 본다. 같은 일이다 |
| **Monaco 를 안 쓴다** | 3MB 를 받고 터치 편집이 형편없다 — 「빠르게」가 무색해진다 |
| **저장과 요청을 합친다** | 저쪽은 일부러 나눴지만(쓰다 만 글이 가면 안 된다), 여기에 적는 일 자체가 「보내겠다」는 뜻이다 |
| **올리기는 켤 수 있되 세 겹으로 막는다** | 아래 8-4.1 — 처음에는 아예 못 켜게 두었다가 2026-09-18 에 돌렸다 |
| **메일은 끌 수 없다** | 이 화면의 존재 이유다. 끄면 답이 아무 데도 안 가는 건이 생긴다 |
| **로그를 안 보여 준다** | 수천 줄은 휴대폰에서 못 읽고, 회로가 그것을 전부 실어 나른다 |

올리기를 끄고 보내도 결과가 사라지지는 않는다 — 고친 것은 커밋과 브랜치로 남고
**그 사실이 메일의 「할 일」 칸에 적혀 온다**(8-2).

### 8-4.1 올리기 — **못 켜게 두었다가 돌렸다** (2026-09-18)

처음 판단은 「언제나 꺼짐」이었다. `main` push 는 곧 운영 배포고(이미지 열둘)
흔들리는 자리에서 손가락 하나로 그것이 나가면 안 된다고 보았다.

**그 판단이 일을 반으로 잘랐다.** 여기서 시키는 건은 거의 다 「고쳐서 올려
달라」인데, 올리기가 없으면 AI 가 다 고쳐 놓은 뒤에 사람이 자리에 돌아와
「AI 작업」 화면을 열고 같은 건을 다시 올려야 한다. 그때까지 고친 것은
브랜치에 앉아 있고 **그 사이를 기억하는 것은 사람뿐이다** — 잊으면 아무 일도
안 일어나고, 안 일어났다는 사실이 어디에도 안 남는다.

지금은 켤 수 있다. 대신 **한 번에 못 켜진다.**

| 겹 | 무엇이 막나 | 어디 |
|---|---|---|
| 1 | 기본이 꺼짐이다. 그냥 보내면 커밋까지만 한다 | `_push = false` (보낼 때마다 되돌린다) |
| 2 | 대상이 허용한 것만 켜진다. 아니면 칸이 회색이고 **왜 회색인지 그 자리에 적는다** | `ai_target.allow_push` |
| 3 | 켠 채로 보내면 묻는 창이 뜬다 | `ConfirmDialog` — 「보내고 올리기」 |

서버도 저장할 때 2번을 한 번 더 본다(`AiTaskService.Normalize`). 이 값 하나가
운영 배포를 일으키므로 화면만 믿지 않는다 — 「AI 작업」 화면과 같은 규칙이다.

**보내고 나면 칸이 다시 꺼진다.** 글상자를 비우는 것과 같은 이유다. 남겨 두면
이어서 적은 다음 한 줄이 묻지도 않고 올라간다.

보낸 뒤에는 최근 몇 건의 **상태만** 둔다. 「갔나?」와 「끝났나?」에 답하면
이 화면의 일은 끝이고, 그 다음은 메일이다. 끝난 건을 누르면 결과문이
펼쳐진다 — 메일을 못 본 채 다시 들어온 경우를 위한 자리다.

**빠르게 닿는 길이 셋이다.** 휴대폰은 홈 화면에 추가하고 데스크탑은
북마크한다. 메뉴에서는 `AI 작업` 묶음의 **맨 앞**에 둔다(`order_no = 0`) —
이 화면의 요점이 「빠르게 닿는 것」이라 세 번째에 있으면 요점이 반쯤 사라진다.

그리고 **헤더 오른쪽 도구 묶음에 번개 단추**가 있다(`HeaderTools`). 어느
화면에서 일하다가도 한 번에 온다 — 메뉴를 두 단계 펼치는 것이 「빠르게」와
어울리지 않는다. 볼 권한이 있는 사람에게만 보이고(걸러진 메뉴에서 찾는다),
주소는 박아 두지 않고 그 메뉴가 들고 있는 링크로 간다.

### 8-4.2 지시 한 건에 **주소가 생겼다** (2026-09-20)

화면: `web/src/Apps/JSini.Web.ProjMng/Components/Pages/AiTaskViewPage.razor`
(`/projmng/ai/task/{번호}` — **메뉴에 없는 화면이다**)

카드를 누르면 뜨던 창(`AiTaskPeek`)에는 주소가 없었다. 그래서 세 가지가
같은 곳에서 막혔다.

- **앱알림**과 **메일**이 실을 주소가 목록(`/projmng/ai/tasks`)뿐이었다.
  누른 사람은 편집기 3MB 를 받은 뒤 **그 건을 목록에서 눈으로 다시 찾았다.**
- 책상에서도 창이 떠서 **한 번에 한 건만** 볼 수 있었다. 아침에 보낸 것과
  방금 끝난 것을 나란히 놓고 견주는 일이 안 된다.
- 남에게 「이거 봐 달라」고 보낼 것이 없었다.

그래서 보여 주는 코드를 창에서 떼어 **부품 둘**로 만들고, 그 둘을 창과
화면이 함께 쓴다.

| 부품 | 무엇 | 쓰는 곳 |
|---|---|---|
| `AiTaskView` | 머리띠 + 「지시와 결과」·「로그」 탭 | 창 · 화면 |
| `AiTaskActions` | 이어서 지시 · 재시도 · 확인 · 자세히 | 창(바닥 띠) · 화면(본문 끝) |
| `AiTaskPeek` | **창 껍데기뿐** — 열고 닫고 제목 달기 | 휴대폰 |
| `AiTaskViewPage` | 한 건을 스스로 받아 오고 따라간다 | 넓은 화면 · 알림 · 메일 |

누르면 어디로 가나 —

| 어디서 | 무엇이 열리나 |
|---|---|
| 휴대폰(≤767px)에서 카드 | 창. 화면을 꽉 채운다 |
| 넓은 화면에서 카드 | **탭.** 주소가 건마다 다르니 여러 건을 누르면 탭이 여러 개 선다 |
| 앱알림 · 메일의 「화면에서 보기」 | 같은 주소 (`AiTaskNotifier.TaskUrl` 한 줄이 정본) |

**질의 문자열이 아니라 경로에 번호를 싣는다.** 포털의 탭 줄은 질의 문자열을
뗀 경로로 탭을 가르므로(`PortalTabs`), `?task=` 로 실으면 몇 건을 열어도
탭이 하나만 선다.

#### 메뉴가 없는 화면이라 **메뉴에 딸린 것들을 끈다**

주소에 자료 번호가 들어가므로 `scom.system_menus` 가 가리킬 수 있는 값이
아니다. 그래서

- 사이드바가 이 화면을 고르지 않고 브레드크럼도 비어 있다 —
  `MainLayout.Track` 이 메뉴 줄기를 못 찾으면 저절로 그렇게 된다.
- **탭은 화면이 직접 연다.** 레이아웃은 메뉴에 있는 화면만 탭으로 만든다.
- 탭 줄의 **즐겨찾기 항목이 안 나온다**(`PortalTab.Standalone`).
  즐겨찾기는 DB 메뉴 경로를 열쇠로 쌓이는데 그 표에 없는 주소를 담으면
  **사이드바에서 영영 못 푸는 줄**이 하나 남는다.
- 고정은 그대로 둔다 — 그건 메뉴가 아니라 탭의 성질이다.

열쇠(`RouteKey`)는 `projmng.ai.task-view` 로 하나 붙인다. 아키텍처 테스트가
화면마다 하나를 요구하기 때문이고(`RouteKeyTests`), 헬프데스크의
`/helpdesk/request/detail/{id}` 가 이미 같은 모양이다.

### 8-4.3 앱알림 아이콘이 **지시한 사람의 얼굴**이 됐다 (2026-09-20)

빠른 지시로 보낸 일이 끝나면 앱알림이 온다. 그 아이콘이 회사 로고였다 —
포털이 보내는 알림은 무엇이든 같은 그림이라, 잠금 화면에 두어 개 쌓이면
**어느 것이 내가 시킨 일인지 그림으로는 알 수 없었다.**

이제 아이콘이 그것을 답한다. 사진이 있으면 지시한 사람의 프로필 사진이,
없으면 사람 얼굴 형상 그림자가 뜬다.

| 어디 | 무엇을 하나 |
|---|---|
| `AiTaskNotifier` | `iconOwnerKey` 에 **`cre_id`** 를 싣는다. 사진은 모른다 |
| `AvatarIconResolver` (알림 서비스) | 그 아이디로 `scom` 에서 사진을 찾아 주소를 만든다 |
| `FileDownload` 의 `/files/avatar/{파일}` (셸) | 사진을 내준다. **못 내주면 그림자로 갈아 준다** |
| `push-sw.js` | 받은 `icon` 을 그대로 띄운다 (고칠 것이 없었다) |

**왜 알림 서비스가 사진을 푸는가.** `projmng` DB 에는 사람의 사진이 없다 —
계정은 `scom` 에 있고 그쪽은 알림 서비스의 DB 다. 메일 주소를 `toUser` 로
넘겨 저쪽에서 풀게 한 것과 같은 이유이고, 같은 표(`account_profile_details`)를
`detail_type` 만 바꿔 읽는다.

**왜 `toUser` 가 아니라 `cre_id` 인가.** 지금은 둘이 같다(결과는 지시한
본인에게 간다). 「받는 사람」 칸을 적어 남에게 보내게 되면 갈리는데, 그때
아이콘이 답해야 하는 것은 **「누가 시킨 일인가」** 쪽이다.

**왜 그림자 갈아 주기를 셸에 두는가.** 서비스워커에는 「그림을 못 받았다」를
되받을 자리가 없다. 화면이라면 `onerror` 로 이름 첫 글자를 대신 그리지만
(`CurrentUser.MarkAvatarUnavailable`), 알림 아이콘은 브라우저가 혼자 받아
가고 실패하면 **아이콘 없이 뜰 뿐 아무도 알지 못한다.** 그래서 `/files/avatar`
갈래만 404 를 주지 않고 그림자로 302 한다 — 사진을 못 받는 길이 여럿이다
(신원이 안 실려 왔거나, 개발 장비에서 올려 운영에 바이트가 없거나, 지워졌거나).

그림자는 구워서 넣는다(`scripts/build-avatar-fallback.py` →
`JSini.Web.Shell/wwwroot/avatar-fallback.png`). **크롬은 알림 아이콘으로 SVG 를
받지 않는다.** 두 서비스에 나뉘어 적힌 경로 글자는 아키텍처 테스트가 맞춰
본다(`AvatarIconTests`) — 어긋나도 빌드는 통과하고 아이콘만 조용히 빈다.

#### 그런데 **다른 기기에서는 늘 그림자였다** (2026-09-20 같은 날 고침)

지시한 본인의 얼굴이 떠야 하는 알림이 다른 장비에서는 그림자로 왔다.
사진이 없어서가 아니다 — **그 기기가 사진을 받을 자격을 못 보였다.**

길을 따라가면 이렇다.

1. 알림 서비스가 아이콘 주소를 `/files/avatar/{파일}` 로 보낸다.
2. 그 주소를 부르는 것은 화면이 아니라 **브라우저 자신**이다. 알림을 띄우는
   그 순간 브라우저가 직접 받아 가고, **서비스워커의 `fetch` 처리기도 거치지
   않는다**(w3c/ServiceWorker#1161). 그래서 실을 수 있는 신원이 쿠키뿐이다.
3. 그런데 **알림은 포털에 로그인해 있지 않은 기기에도 도착한다.** 구독은
   서비스워커 등록에 붙어 오래 살아남고, 포털의 인증 쿠키(`jsini.portal`)는
   `IsPersistent` 를 주지 않은 **세션 쿠키**라 브라우저를 닫으면 사라진다.
   둘의 수명이 다르다.
4. 신원 없이 올라간 중계는 게이트웨이에서 익명이 되고, 프로필 사진은 익명에게
   열리지 않는다 — `profile/` 은 `Files:AnonymousReadablePaths` 에 없다
   (`PublicFileAccessFilter`). 404 가 오고 중계는 약속대로 **그림자로 302** 한다.

**증상이 조용한 것이 이 길의 성질이다.** 오류가 아니라 「그림자로 갈아 준다」는
정상 동작이라, 지시를 내린 그 장비(로그인해 있다)에서는 얼굴이 뜨고 다른
장비에서만 그림자다. 두 기기를 나란히 놓고 보기 전에는 알 수 없다.

##### 고친 방법 — **사진 한 장만 여는 열쇠를 주소에 싣는다**

`profile/` 을 익명에 열지 않는다. 그 판정을 만든 이유가 「남의 얼굴 사진이
아이디만 알면 열리는 일이 없게」이고, 알림 아이콘 하나 때문에 되돌릴 값이
아니다. 대신 **그 알림에만** 통하는 열쇠를 함께 보낸다.

| 어디 | 무엇을 하나 |
|---|---|
| `AvatarIconTokenFactory` (알림 서비스) | 주인 이름이 `push-icon:{파일아이디}` 인 토큰을 만든다. 우리 `Jwt:Key` 로 서명하고 **한 시간**이다 |
| `AvatarIconResolver` | 주소에 싣는다 — `/files/avatar/{파일}?t={열쇠}` |
| `FileDownload` (셸) | `t` 를 게이트웨이로 **그대로 넘긴다.** 풀어 보지 않는다 — 셸에는 키가 없다 |
| `ApiGateway` | 서명을 보고 `X-User-Id` 를 붙인다. **`push-icon:` 으로 시작하면 파일 읽기 경로 밖에서는 아예 거절한다** |
| `PublicFileAccessFilter` (FileServer) | 그 이름에 적힌 **그 파일만** 내준다 |

**두 겹이 함께 있어야 한다.** 게이트웨이만 있으면 한 시간 동안 아무 파일이나
읽는 열쇠가 되고, FileServer 만 있으면 파일 읽기 밖의 API 에 **한 시간짜리
로그인**으로 쓰인다. 어느 한 줄이 사라져도 **아이콘은 멀쩡히 뜨므로**
아무도 알아채지 못한다 — 그래서 둘 다 `AvatarIconTests` 가 지킨다.

수명을 한 시간으로 둔 것은 꺼져 있다 나중에 받는 알림 때문이다(푸시 서비스가
들고 있다가 배달한다). 그보다 늦게 온 알림은 그림자로 뜬다 — 고치기 전과 같다.
`Push:IconTokenMinutes` 로 조절한다.

**열쇠를 못 만들면 `?t=` 없이 보낸다.** 그때는 로그인해 있는 기기에서만
얼굴이 뜬다 — 고치기 전과 같고, 알림 자체는 그대로 나간다.

### 8-4.4 탭을 둘로 줄이고 **가운데에 처리 요약**을 놓았다 (2026-09-20)

앱알림을 누르면 그 건 하나가 열린다(`AiTaskView`). 탭이 셋이었다 —
**지시 · 결과 · 로그**. 이제 둘이다 — **지시와 결과 · 로그**.

#### 왜 지시와 결과를 갈라 두면 안 되나

로그를 떼 둔 것은 지금도 옳다. 기계가 찍은 수백 줄 밑에 결과를 깔면 아무도
거기까지 내려가지 않고, 탭이면 보는 것만 회로를 탄다(모바일 회선이다).

그런데 **지시와 결과는 성격이 다른 글이 아니라 물음과 답 한 쌍이다.**
알림을 누르고 들어온 사람이 「결과」를 펴면 답만 있고 물음이 없다 —
며칠 전에 보낸 건이면 **무엇에 대한 답인지부터** 모른다. 그래서 탭을 오가며
둘을 맞춰 봐야 했다. 결과 메일은 같은 이유로 이미 지시문을 답 위에 싣고
있었다(8-2 의 「요약 다섯」 중 둘째).

그래서 한 판에 이 차례로 깐다.

| 차례 | 무엇 | 어디서 오나 |
|---|---|---|
| 처리 요약 | AI 가 결과문을 다시 정리한 것 | `ai_task_run.summary_text` |
| 지시 | **사람이 적어 보낸 그대로** | `ai_task.contents` |
| 결과 | AI 의 답 원문 | `ai_task_run.result_text` |

#### 요약이 **맨 위다** (2026-09-20 고침)

처음에는 가운데였다 — 지시 → 요약 → 결과. 물음 다음에 답이 오는 것이
글의 차례이기는 하다.

그런데 **이 판을 여는 사람은 글을 읽으러 오는 것이 아니다.** 알림을 누르고
「됐나 안 됐나, 내가 볼 것이 있나」를 보러 온다. 그 답은 요약에만 있고,
요약은 셋 중 가장 짧다. 지시가 위에 있으면 그 짧은 답이 **내가 이미 아는
글**(내가 적어 보낸 지시문이다) 뒤에 숨는다.

그래서 결론을 먼저 놓고, 그것을 믿을지 가릴 원문 둘을 아래에 잇는다.

#### 지시도 결과도 **상자 안에서 구르지 않는다** (2026-09-20 고침)

한동안 글 상자마다 높이 상한이 있었다 — 지시 11rem(휴대폰 30dvh) ·
결과 22rem(휴대폰 62dvh). 판이 짧아지기는 하는데, 대신 **한 판 안에 구르는
자리가 셋**이 된다. 바깥 판 · 지시 상자 · 결과 상자.

거기서 두 가지가 깨졌다.

- 휴대폰에서 손가락이 상자 위에 있으면 판이 안 움직인다. 상자 안이 먼저
  끝까지 굴러야 판이 따라 구른다(스크롤 체이닝).
- 긴 결과문을 훑다가 **끝까지 읽었는지 알 수 없다.** 22rem 짜리 구멍으로
  보는 글에는 바닥이 안 보인다.

그래서 지시와 결과는 **통째로 편다.** 길면 판이 길어지고, 판은 창이든
화면이든 이미 구르는 자리가 하나씩 있다 — 창은 `CommPopup` 의 `Scrollable`
(`MaxHeight` 86vh), 화면은 페이지 그대로.

**로그만 상한을 그대로 둔다**(22rem · 휴대폰 62dvh). 수백 줄이 통째로
펴지면 그 아래에 아무것도 없는데 판만 수십 화면 길이가 되고, 새 줄을 바닥에
붙여 두는 일(`js/log-tail.js`)도 구르는 상자가 있어야 할 수 있다.

#### 요약은 **이미 있는 값이다** — 화면이 다시 만들지 않는다

`summary_text` 는 결과 메일의 「무엇을 했다나」 칸이 쓰던 값이고, 서버가
실행이 끝날 때마다 적어 둔다(`AiResultSummarizer`). 화면은 그것을 **읽기만**
한다 — 여기서 모델을 다시 부르면 메일에 적힌 요약과 화면의 요약이 다른 말을
하게 되고, 그때 어느 쪽이 그 실행의 요약인지 가릴 방법이 없다.

담긴 꼴은 **사람이 읽는 평문**이다(이어가기 지시문이 이 칸을 그대로 다음
실행의 문맥으로 올려보내기 때문 — 8-3). 그래서 되읽는 짝이 둘 있고
**같은 머리말(`확인할 것`)을 약속**한다.

| 어디 | 무엇 |
|---|---|
| `AiResultSummary.ToText` / `.Parse` (서버) | 적고 되읽는다 |
| `AiRunSummary.Parse` (화면) | 되읽기만 한다 |

**요약이 없는 건은 요약 칸 없이** 지시와 결과만 보인다 — 그 칸이 생기기
전의 건, AI 가 안 떠 있던 때, 정리에 실패한 건이 그렇다. 빈 상자를 그려
두면 「요약이 고장났다」로 읽힌다.

#### 끝난 뒤에도 **요약을 조금 더 기다린다**

요약은 실행이 끝난 **뒤에** 적힌다. 서버는 완료 보고를 그 시간만큼 붙들지
않으려고 요약·알림을 뒤로 떼어 돌리고(`_ = SummarizeThenNotifyAsync(runKey)`),
그 안에서 AI 를 한 번 더 부른다 — 한 번에 길면 30초고, 빈손으로 오면 한 번 더
부른다(8-2.1).

그사이 화면은 「끝났다」를 보고 따라가기를 멈춘다. 그러면 **끝나는 것을
지켜보고 있던 사람에게만 요약이 영영 안 보인다** — 나중에 다시 연 사람에게는
보이는데. 그래서 답이 왔는데 요약이 비어 있으면 3초 간격으로 **스물다섯 바퀴**
(≈75초) 더 보고 포기한다. 답 자체가 없는 건은 요약할 원문이 없으니 기다리지
않는다.

> **그 바퀴 수는 서버가 요약에 거는 시간보다 길어야 한다.** 짧으면 화면이
> 먼저 포기하고, 증상은 「어떤 건은 요약이 보이고 어떤 건은 안 보인다」로만
> 나온다.

#### 처음 열리는 탭

- 돌고 있으면 **로그** — 「어디까지 갔나」
- 그 밖에는 **지시와 결과** — 물음과 답이 한 판에 있다

대기 중인 건과 끝난 건을 가를 이유가 없어졌다. 셋일 때는 「끝났으면 결과,
대기면 지시」로 갈랐는데 이제 둘이 같은 판이다.

## 8-3. 끝난 작업에 **이어서 지시하기**

「고쳐 놓은 것에 이어서 이것도 해 달라」를 할 수 있어야 한다.
요약을 보관하자는 것이 출발점이었는데, **요약만으로는 절반이다.**

### 8-3.1 절반이 빠지는 이유 — 요약은 있는데 **코드가 되돌아가 있다**

이어가기의 값은 「지난번 결과 위에서 계속」이다. 그런데 실행마다 worktree 를
새로 파면(7.3) 두 번째 실행은 **지난번 변경이 하나도 없는 자리**에서 시작한다.

요약에는 「A 파일을 고쳤다」고 적혀 있는데 그 파일에는 그 변경이 없다.
AI 는 둘 중 하나를 한다 — 없는 것을 있다고 믿고 그 위에 쌓거나(엉뚱한 결과),
「다시 고치겠다」며 처음부터 한다(했던 일 반복). **둘 다 나쁘고, 둘 다 조용하다.**

그래서 이어가기는 **요약 + 작업공간**이 한 벌이다.

### 8-3.2 규칙 — **`push` 했느냐가 가른다**

깔끔하게 둘로 갈린다.

| 지난 실행이 | 작업공간 | 프롬프트에 넣을 것 | CLI 세션 |
|---|---|---|---|
| **push 안 했다** (브랜치에만 있다) | **그 worktree 를 그대로 다시 쓴다** | 새 지시만 | `--continue` 가 그대로 먹는다 |
| **push 했다** (`main` 에 갔다) | 최신에서 **새로 판다** | **요약 + 새 지시** | 새 세션 |

push 했으면 지난 변경이 이미 `main` 에 있으므로 새 worktree 에도 들어 있다.
그때는 작업공간을 이을 필요가 없고 **요약만 있으면 된다.**
안 했으면 그 변경이 그 worktree 에만 있으므로 **그것을 버리면 안 된다.**

그래서 `ai_task` 가 **자기 작업공간과 브랜치를 기억한다**(8-3.5).

### 8-3.3 CLI 가 이미 이어가기를 갖고 있다 — 쓰되, 기대지는 않는다

확인한 것:

| | 이어가기 | 지목해서 이어가기 |
|---|---|---|
| `claude` | `--continue` | `--resume <세션 id>` |
| `agy` | `-c` · `--continue` | `--conversation <대화 id>` |

`agy` 는 실행하자마자 첫 줄로 대화 id 를 알려 준다 — 우리가 직접 봤다:

```json
{"event":"init","conversation_id":"8dcc4e18-8c25-43cc-b4fb-02d1969c348f", …}
```

**이것이 가장 충실한 이어가기다.** 요약은 「무엇을 했나」만 남지만 세션에는
**무엇을 읽었고 무엇을 시도했다 실패했는지**가 남는다. 요약에 「B 안으로 했다」
라고만 적히면 다음 실행이 **이미 버린 A 안을 다시 시도한다.**

그런데 여기에만 기댈 수 없다.

1. **세션은 작업 폴더에 묶인다.** worktree 를 새로 파면 못 찾는다 —
   8-3.2 의 왼쪽 줄(같은 worktree 재사용)에서만 성립한다.
2. **CLI 를 갈아타면 못 잇는다.** `claude` 로 한 것을 `agy` 로 이을 수 없다.
3. 세션 파일은 우리 것이 아니다. 지워지거나 형식이 바뀔 수 있다.

**그래서 둘 다 한다** — 세션 id 를 적어 두고 쓸 수 있으면 쓰되,
요약은 **언제나** 남긴다. 요약은 보험이자 **사람이 읽는 유일한 것**이다.

### 8-3.4 요약을 누가 만드나 — **끝난 뒤 LLM 이 줄인다**

셋 중에 골랐다.

| 방법 | 값 | 판단 |
|---|---|---|
| 결과문(`result_text`)을 그대로 | 공짜. 이미 있다 | **되돌아가는 자리** |
| 프롬프트에 「끝나면 요약을 남겨라」를 넣는다 | 모양을 정할 수 있다 | 안 쓴다 |
| **끝난 뒤 LLM 에게 줄이게 한다** | 모양과 길이를 맞출 수 있다 | **기본** |

가운데를 안 쓰는 이유: 지시문마다 그 문장이 붙어 **사람이 쓴 글과 우리가 붙인
글이 섞인다.** 그리고 AI 가 그 지시를 잊으면 요약이 통째로 빈다 —
그때 실패하는 방식이 「요약이 없다」라서 다음 이어가기가 맨땅이 된다.

처음에는 첫째를 기본으로 뒀다(「결과문은 대개 그 자체가 요약이다」). 메일에서
그것이 틀렸음이 드러났고(8장), 지금은 **실행이 끝날 때마다 정리시킨 것을
`summary_text` 에 적어 둔다.** 그래서 이어가기가 읽는 요약도 같은 것이 된다 —
여태 이 칸은 비어 있었고 `COALESCE(summary_text, result_text)` 가 늘
결과문 쪽으로 떨어졌다.

**첫째는 사라지지 않는다.** 정리에 실패한 건은 `summary_text` 가 비어 있고,
그때는 예전처럼 결과문이 올라간다.

### 8-3.5 **요약을 믿지 않는다** — 기계가 아는 사실을 함께 싣는다

여기가 제일 중요하다. 요약은 **AI 의 주장**이지 사실이 아니다.
「다 고쳤습니다」로 끝났는데 실제로는 한 줄도 안 바뀐 경우가 있고,
그 요약을 다음 실행에 그대로 물리면 **거짓말이 누적된다.**

그래서 이어가기 프롬프트에는 요약과 **기계가 아는 것**을 나란히 싣는다.

```markdown
## 이전까지의 진행

### 1차 (2026-09-17 14:20, 성공)
지시: 첨부 내려받기에서 한글 파일 이름이 깨지는 것을 고쳐라
AI 요약: FileDownload 의 Content-Disposition 을 RFC 5987 로 바꿨다.

기록된 사실:          ← **우리가 잰 값이다. AI 가 쓴 것이 아니다**
  · 종료 코드 0
  · 바뀐 파일 2개 (+31 −8): FileDownload.cs · FileDownloadTests.cs
  · 커밋 a1b2c3d (아직 push 안 함)

## 이번에 할 일
<새 지시>
```

「바뀐 파일 2개」는 `git diff --stat` 에서 온다. **요약과 어긋나면 그 어긋남이
프롬프트 안에서 바로 보인다** — 「고쳤다」는데 바뀐 파일이 0개면 다음 실행의
AI 가 그것을 알아본다.

### 8-3.6 길이가 터지는 것을 막는다

요약을 계속 앞에 붙이면 다섯 턴째에 프롬프트가 지시문보다 커진다.
그러면 AI 가 **새 지시보다 지난 이야기에 더 무게를 둔다.**

- 최근 **3턴**은 전문, 그 이전은 **한 줄**(지시 첫 줄 + 성공 여부)로 접는다.
- 전체 상한(예: 20KB)을 넘으면 오래된 것부터 더 접는다.
- **접었다는 것을 프롬프트에 적는다** — 「이전 4건은 줄여서 적었다」.
  조용히 자르면 AI 가 그것이 전부인 줄 안다.

### 8-3.7 자료 모형에 더할 것

| 어디 | 칸 | 왜 |
|---|---|---|
| `ai_task_run` | `instruction` | **그때 실제로 준 지시문.** 본문을 고쳐도 지난 실행이 무엇이었는지 남아야 한다 |
| `ai_task_run` | `summary_text` | 요약. 없으면 `result_text` 를 쓴다 |
| `ai_task_run` | `session_id` · `session_kind` | CLI 의 대화 id 와 어느 CLI 것인지 |
| `ai_task` | `workspace_path` · `git_branch` | **이어가기가 재사용할 자리**(8-3.2) |
| `ai_task` | `turn_no` | 몇 번째 왕복인가. 화면이 「3차」로 보여 준다 |

**작업(`ai_task`)이 스레드, 실행(`ai_task_run`)이 왕복**이다. 이어서 지시하면
새 작업을 만들지 않고 **같은 작업에 실행이 하나 더 붙는다** — 「해당 요청건에
이어서」라는 말 그대로이고, 이력이 한 줄에 모인다.

### 8-3.8 화면에서는 어떻게 보이나

끝난 작업을 열면 **「이어서 지시」** 단추가 생긴다.

- 누르면 편집기가 **비워지고**(지난 지시가 아니라 새 지시를 쓰는 자리다)
  그 위에 지난 진행이 접힌 채로 보인다.
- 지난 지시를 그대로 두면 **AI 가 같은 일을 또 한다** — 편집기를 비우는 것이
  이 단추의 핵심이다.
- 실행 이력 탭에 1차·2차가 쌓이고, 각 줄에 지시·요약·바뀐 파일이 붙는다.

### 8-3.9 언제 만드나

**3단계다.** 1단계(지금)는 한 번 시키는 것까지고, 이어가기는 실행과 결과가
실제로 돌아온 뒤에 얹는다 — 이을 결과가 없는데 이어가기를 먼저 만들 수 없다.

## 9. 보안 — 실행 장비가 **운영 서버**라서 다시 쓴다

### 9.1 무엇을 만드는지 정확히

**웹 화면에 글을 쓰면 운영 서버에서 명령이 돈다.** AI CLI 는 파일을 고치고 셸을
연다. 즉 이 화면의 쓰기 권한은 **운영 서버의 셸 권한과 같다.**

실행 장비가 개발 PC 였다면 최악이 「내 PC 가 이상해졌다」였다. 지금은
**「서비스가 내려간다」·「DB 비밀번호가 샌다」**다. 아래 셋이 확인된 사실이고,
그것 때문에 대책도 달라진다.

### 9.2 실행 계정은 `lee` 다 — 담장은 **계정이 아니라 systemd** 가 친다

결정됐다(2026-09-17). 전용 계정을 만들지 않는다.

그러면 이것을 그대로 안고 간다는 뜻이다:

```
uid=1000(lee) groups=…,27(sudo),…,128(docker)
```

`docker` 그룹이면 `docker run -v /:/host` 한 줄로 호스트 전체를 root 로 읽고 쓸 수
있다. **sudo 비밀번호를 몰라도 그렇다.** 그리고 `lee` 는 `~/.git-credentials` 와
`/srv/jsini/config`(그 계정만 읽을 수 있게 돼 있다)도 들고 있다.

**계정을 안 나누는 대신, 프로세스에 담장을 친다.** systemd 255 다(2.4) —
아래 지시어가 전부 먹는다. 그리고 **자식 프로세스가 그 담장을 물려받는다** —
실행기가 띄운 `claude` 도, `claude` 가 띄운 `git` 도 같은 우리 안에 있다.

```ini
# /etc/systemd/system/ai-task-runner.service   (발췌)
[Service]
User=lee
ExecStart=/usr/bin/dotnet /opt/ai-task-runner/AiTaskRunner.dll
Restart=always

# ① 권한 상승을 막는다 — sudo 가 무력해진다
NoNewPrivileges=yes

# ② docker 소켓을 끊는다 — docker 그룹이 무력해진다
InaccessiblePaths=/var/run/docker.sock

# ③ 운영 비밀값을 끊는다 — 9.6
#    .env 는 막지 않는다. 안에 TAG 한 줄뿐이고(2.4) 되돌리기에 그 값이 필요하다(9.3)
InaccessiblePaths=/srv/jsini/config

# ④ 쓰는 곳을 정해 둔다
ProtectSystem=strict
ReadWritePaths=/home/lee/Funeralv2 /home/lee/ai-workspaces /srv/ai-targets
PrivateTmp=yes

# ⑤ 자원 (9.4)
CPUQuota=200%
MemoryMax=8G
```

`~/.claude` 는 **막지 않는다.** 로그인 자격이 거기 있고 CLI 가 세션 파일을 쓴다.

> **정본 clone 을 읽기 전용으로 둘 수 없다.** `git fetch` 도 `git worktree add` 도
> `.git` 에 쓴다. 그 대신 매 실행 전 `git status --porcelain` 으로 정본이
> 깨끗한지 보고, 더러우면 **원본 직접 실행을 거절한다**(7.3). 조용히 얹고 가면
> 다음 실행의 기준이 오염된다. 그 거절이 기능 전체를 멈춰 세우지 않도록
> **원본 직접으로 돈 실행은 끝날 때 자기가 남긴 변경을 `git stash` 로 치운다**(21).
>
> **`~/.git-credentials` 도 막지 않는다** — push 를 하기로 했기 때문이다(9.3).

#### 무엇이 막히고 무엇이 안 막히나 — 정직하게

| | 전용 계정이었다면 | **`lee` + systemd 담장** |
|---|---|---|
| `sudo` | 그룹에 없다 | `NoNewPrivileges` 로 무력 ✅ |
| `docker` 탈출 | 그룹에 없다 | 소켓 경로 차단 ✅ |
| `git push` | 자격이 없다 | **막지 않는다 — 기능이다**(9.3). 대신 게이트를 통과한 것만 실행기가 민다 |
| `/srv/jsini/config` | 권한 없음 | 경로 차단 ✅ |
| 정본 clone 훼손 | 쓰기 권한 없음 | 막을 수 없다(fetch 가 쓴다). **실행 전 깨끗한지 검사** ⚠️ |
| **유닛 밖에서 손으로 `claude` 를 띄우면** | 그래도 막힌다 | **하나도 안 막힌다** ⚠️ |
| **유닛 파일을 고치면** | 계정은 그대로 남는다 | 담장이 통째로 사라진다 ⚠️ |

마지막 둘이 이 선택의 값이다. 담장이 **설정 파일 한 장에 얹혀 있다.**
전용 계정은 누가 무엇을 하든 남는 벽인데, 이쪽은 유닛을 고치면 없어진다.

그래서 **유닛 파일을 배포 산출물로 관리한다** — `deploy/` 에 넣어 저장소가
정본을 들고, 장비의 것과 다르면 그 자체가 신호가 되게 한다.

#### 사고의 두 종류를 구분한다

| | 막히나 |
|---|---|
| **실수** — AI 가 좋은 뜻으로 push 하거나 컨테이너를 만진다 | **막힌다.** 위 담장이 겨냥하는 것이 이것이고, 실제로 일어나는 것도 대부분 이것이다 |
| **작정한 우회** — 담장을 알아보고 돌아 나간다 | 완전히는 못 막는다. 계정을 나눠야 막히는 영역이다 |

지금 상대는 앞엣것이다. 담장은 그 값을 한다. **뒤엣것까지 막아야 할 상황이
되면(예: 여러 사람이 지시문을 쓰게 되면) 전용 계정을 다시 꺼낸다.**

### 9.3 `main` 에 push 한다 — **막는 대신 관문을 둔다** (2026-09-17 결정)

`main` 에 commit·push 까지 자동으로 한다. 이전 판에서 이것을 막자고 적었고,
그 우려는 아래에 사실로만 남긴다 — **결정됐으므로 그 전제 위에서 설계한다.**

한 줄로 옮기면 이렇다:

> **AI 작업 한 건이 곧 운영 배포 한 번이다.**
> push → `deploy.yml` → 이미지 열둘 → self-hosted 러너가 `pull` · `up -d`.

그러니 이제 할 일은 push 를 막는 것이 아니라 **어떤 상태의 코드만 나가게 하느냐**다.

#### 먼저 알아야 할 것 — **GitHub 의 CI 는 배포를 막지 않는다**

`ci.yml` 과 `deploy.yml` 은 `main` push 에서 **나란히** 돈다. deploy 는 ci 를
기다리지 않는다. 게다가 deploy 는 컨테이너 안에서 `dotnet publish` 만 하므로
**아키텍처 테스트가 거기서는 한 번도 돌지 않는다**(루트 CLAUDE.md).

| | 언제 도나 | 배포를 막나 |
|---|---|---|
| `ci.yml` (빌드 + 아키텍처 테스트 208건) | main push · PR | **안 막는다** |
| `deploy.yml` (이미지 열둘 → 러너) | main push | — |

즉 **테스트가 빨간불이어도 배포는 그냥 나간다.** 그래서 관문을 GitHub 에 맡길 수
없고, **push 하기 전에 실행기 쪽에** 둬야 한다.

#### push 게이트 — 여섯 개를 다 통과해야 나간다

1. CLI 가 **성공 종료**(exit 0)
2. **바뀐 것이 있다** — 없으면 push 하지 않는다(빈 배포를 일으키지 않는다)
3. **빌드가 통과한다** — 바뀐 영역에 따라 백엔드 / `web`
4. **아키텍처 테스트가 통과한다**(`web` 이 바뀌었으면). 이것이 막는 것들은
   하나같이 *빌드는 통과하고 런타임에 조용히 틀리는* 종류다
5. **금지 경로가 안 바뀌었다** — `.github/workflows/**` · `deploy/**` ·
   `scripts/secrets*` · `Directory.*.props`. 배포 방식 자체를 AI 가 고치는 것을 막는다
6. **대상 잠금을 쥐고 있다**(4.4) — 두 건이 동시에 배포를 일으키지 않게

하나라도 어긋나면 **커밋은 남기고 push 는 하지 않는다.** 브랜치가 남으므로
사람이 화면에서 보고 직접 올릴 수 있다. 「아무것도 안 됨」이 아니라
「여기까지 됐고 왜 안 나갔는지」가 남는 것이 중요하다.

> 이 게이트 때문에 **「AI 가 운영 서버에서 빌드·테스트를 돌려도 되나」는 답이
> 정해졌다 — 돌려야 한다.** 그러지 않으면 게이트가 검사할 것이 없다.
> 자원은 9.4 에서 조인다.

#### push 는 **AI 가 아니라 실행기가** 한다

AI 는 **커밋까지만** 한다. push 는 게이트를 통과시킨 뒤 **실행기가** 한다.

- CLI 거부 목록에 `git push` 를 넣는다(7.6 — 권한을 다 열어 두므로 이 한 줄이 더 중요해졌다).
- AI 가 스스로 push 하면 그것은 **게이트를 통째로 건너뛴 것**이다.
  맡겨 두면 게이트는 장식이 된다.

#### systemd 담장에서 ③ 을 뺀다

9.2 의 `InaccessiblePaths=/home/lee/.git-credentials` 는 **더 못 쓴다** —
push 하려면 자격이 있어야 한다. ① ② ④ ⑤ ⑥ 은 그대로 둔다(push 와 무관하다).

잃는 것은 「실수로 push 하는 것」을 막던 벽인데, push 가 이제 기능이므로
그 벽은 뜻이 없다. 대신 위의 **누가 push 하느냐**가 그 자리를 대신한다.

#### 배포가 겹치지 않게

`deploy.yml` 이 워크플로를 하나로 합쳐 둔 이유가 그대로 우리에게 온다 —
둘이 겹치면 `/srv/jsini/.env` 의 `TAG` 를 서로 덮고, **그런데도 배포가 성공한
것처럼 끝난다.** 그래서:

- 대상 잠금으로 동시 1건(4.4·9.5)
- push 직전 `git fetch origin main` + `git rebase origin/main` (7.3·22)
- push 가 거절되면 1회만 다시 시도하고, 또 막히면 **사람에게 넘긴다**

#### 화면은 「완료」로 끝나면 안 된다

push 한 건은 **「운영에 배포됨」**이 따로 보여야 한다. 같은 「완료」로 뭉개면
*코드만 고친 건*과 *운영이 바뀐 건*을 구분할 수 없다.

- `pushed_commit` 을 남긴다(4.1).
- **`previous_tag` 를 반드시 함께 남긴다.** 되돌리기는 `/srv/jsini/.env` 의
  `TAG` 를 이전 SHA 로 돌리고 `up` 하는 것인데(루트 CLAUDE.md),
  **그 이전 값을 아무도 안 적어 두면 되돌릴 수가 없다.**
  실행기가 push 직전에 그 파일에서 읽어 기록한다.
- `deploy.yml` 실행 링크를 걸어 두면 배포 결과까지 한 화면에서 본다(선택).

### 9.4 운영 서버의 자원을 나눠 쓴다 — **이제 빌드가 필수다**

8코어 · 31GB 를 운영 컨테이너 열둘과 나눠 쓴다(2.4). 그리고 push 게이트가
빌드와 테스트를 요구하므로(9.3) **「빌드를 안 돌리면 된다」는 선택지가 없어졌다.**

그래서 조이는 자리를 옮긴다 — 돌리느냐 마느냐가 아니라 **얼마나 먹게 두느냐**다.

```ini
CPUQuota=300%      # 8코어 중 셋까지 (다섯이 겹칠 수 있으므로 1건일 때보다 넉넉히)
MemoryMax=12G      # 31GB 중 12GB 까지
IOWeight=50        # 디스크도 양보한다
```

유닛 하나에 거는 값이므로 **다섯 건이 이 안에서 나눠 쓴다.** 한 건이 폭주해도
전체가 이 선을 못 넘는다 — 건별로 거는 것보다 이쪽이 운영을 지킨다.

#### 동시 5건 — 단 **게이트는 직렬로 돈다**

동시 최대 5건으로 정해졌다. 그대로 간다. 다만 **5건을 그냥 5건으로 두면 안 되는
자리가 하나 있다.**

CLI 가 도는 동안은 대부분 네트워크를 기다린다(API 응답). 다섯이 겹쳐도 CPU 를
크게 다투지 않는다. **문제는 push 게이트다** — `dotnet build` 와 아키텍처 테스트
208건은 CPU 를 실제로 먹는다. 다섯이 동시에 그 단계에 들어가면 8코어를 운영
컨테이너와 함께 나눠 쓰는 장비에서 **포털 응답이 눈에 띄게 느려진다.**

| 단계 | 동시 | 왜 |
|---|---|---|
| CLI 실행 | **5** | 대개 기다리는 시간이다 |
| **push 게이트(빌드·테스트)** | **1** | CPU 를 실제로 먹는 유일한 구간 |
| push 그 자체 | **1** | 배포가 겹치면 `TAG` 가 엎치락뒤치락한다(9.3) |

게이트 앞에 줄을 세운다. 다섯째 작업이 게이트를 기다리는 동안 「검사 대기 중」
으로 보이면 되고, 그것은 멈춘 것이 아니다 — **화면이 그 상태를 말할 수 있어야
한다**(그러지 않으면 「완료인데 왜 배포가 안 되나」로 읽힌다).

- 같은 대상에는 여전히 1건이다(4.4). 5는 **서로 다른 대상까지 합친 전체 상한**이다.
- `dotnet build` 는 기본이 병렬이다. `-m:2` 로 묶어 둔다.
- 그래도 배포가 나가는 순간에는 러너가 이미지 열둘을 만든다 — **그때가 이
  장비에서 가장 바쁜 시각**이다. 게이트 빌드와 겹치면 둘 다 느려진다.
  급하면 `deploy.yml` 이 도는 동안 새 작업을 집지 않게 막는 것을 검토한다(선택).

### 9.5 **대상 경로**는 등록할 때 검사한다 — 화면은 고르기만 한다

대상을 화면에서 고르게 되면서 「사용자가 경로를 정한다」가 설계에 들어왔다.
여기서 틀리면 `../../srv/jsini/config` 한 줄로 9.2 의 담장 안쪽이 열린다.

가르는 선은 하나다.

| | 누가 | 무엇을 |
|---|---|---|
| **등록** | 관리자 | 경로를 **적는다**. 검사를 받는다 |
| **선택** | 작성자 | 등록된 목록에서 **고른다**. 경로를 못 적는다 |

작업 저장 API 는 `target_id` 만 받는다. **경로 문자열을 받는 자리를 두지 않는다.**

#### 등록할 때 하는 검사

1. 절대 경로여야 한다.
2. **`realpath` 로 풀고 나서 다시 검사한다.** 심볼릭 링크로 허용 뿌리 밖을
   가리키는 것이 가장 흔한 우회다.
3. 허용 뿌리 밑이어야 한다 — `AiTasks:AllowedRoots`
   (지금 셋: `/home/lee/Funeralv2` · `/home/lee/nums` · `/srv/ai-targets`).

   > **새 폴더를 대상으로 쓰려면 여기부터 늘린다.** 안 늘리면 화면이
   > 「허용된 뿌리 아래여야 합니다」로 거절하는데, 그 문구만 보면 폴더가
   > 없는 것처럼 읽힌다 — 실제로는 **폴더는 멀쩡하고 목록에 없을 뿐**이다.
   > 설정이라 코드를 안 고쳐도 되지만 **서비스는 다시 띄워야 한다**
   > (`appsettings` 변경만으로는 재기동되지 않는다 — 루트 CLAUDE.md).
   >
   > 뿌리를 넓게 잡지 않는다. `/home/lee` 를 통째로 열면 `~/.local/bin`
   > (CLI 자신) · `~/.config` 까지 대상이 될 수 있다. 4번의 거부 목록이
   > 대표적인 것들을 막지만, **거부 목록은 뒷단속이지 울타리가 아니다.**
4. 거부 목록에 걸리면 안 된다 — `/srv/jsini/config` · `/srv/jsini/.env` ·
   `/srv/jsini/runner` · `/home/lee/.ssh` · `~/.claude` · `/etc` · `/`.
5. 존재해야 하고 디렉터리여야 한다.

#### **담장이 최종 관문이다** — 그리고 그게 운영상 불편을 만든다

DB 에 등록해도 systemd 유닛의 `ReadWritePaths` 에 없으면 **그 경로는 쓸 수 없다**
(9.2 ⑤). 좋은 성질이다 — 화면에서 대상을 추가하는 것만으로는 담장이 안 열린다.

값을 치른다. **대상을 추가할 때마다 유닛을 고치고 재시작해야 한다.**
그게 싫으면 대상을 **한 뿌리 아래로 모은다**:

```ini
ReadWritePaths=/home/lee/ai-workspaces /srv/ai-targets
```

`/srv/ai-targets` 밑에만 폴더 대상을 두기로 하면(심볼릭 링크가 아니라 실제로),
유닛을 다시 고칠 일이 없다. **이 방식을 권한다.**

#### 대상마다 동시 1건

`ai_target.running_run_id` 로 잠근다(4.4). 저장소 대상은 worktree 라 병렬이
가능하지만, **처음에는 종류를 가리지 않고 1건으로 시작한다** — 8코어를 운영
컨테이너와 나눠 쓰는 장비다(9.4).

### 9.6 비밀값이 **그 장비에 있다**

`/srv/jsini/config/` 밑에 서비스 열 곳의 `appsettings.Local.json` 이 있다 —
DB 비밀번호와 JWT 키가 평문으로 들어 있고, 권한이 `drwx------ lee:lee` 라
**`lee` 로 도는 AI 에게는 그냥 읽힌다**(2.4). 저장소 안에도 `scripts/secrets.env` 가 있다.

- **`InaccessiblePaths` 로 끊는다**(9.2 ③). 계정을 안 나누는 대신 이것이 그 역할을 한다.
  `/srv/jsini/.env` 는 대상이 아니다 — `TAG` 한 줄뿐이고 되돌리기에 필요하다.
- 작업공간에 `secrets.env` 를 복사하지 않는다.
- **로그를 적재하기 전에 마스킹 한 벌을 거친다.** 담장을 우회한 경로로든,
  대상 폴더 안에 있던 것이든, 출력에 섞이면 그대로 DB 에 남고 화면에 뜬다.
  알려진 이름부터 막는다 — `Jwt__Key` · `*_KEY` · `*_SECRET` · `Password=` ·
  `ConnectionStrings`.

### 9.7 큐

- **`ai_task` 를 새로 만든다.** `run_script` 에 얹지 않는다(6.2).
- 5672 는 바깥에서 막혀 있다(확인함 — 2.4). **그 상태를 유지한다.**
- 그래도 큐에 넣을 수 있는 쪽은 실행을 일으킬 수 있다. 다만 우리 메시지는
  `{taskId}` 뿐이라(6.4) **큐를 쥐어도 임의 실행은 못 한다** — 이미 DB 에 있는
  건을 깨울 수 있을 뿐이다. `run_script` 와 결정적으로 다른 점이고, 의도한 것이다.

### 9.8 게이트웨이 — **고칠 것이 없어졌다**

초안에서 가장 위험한 자리로 꼽았던 것이 `ai-route` 의
`AuthorizationPolicy: "Anonymous"` 였다. 백엔드가 `ProjMngServer` 로 옮겨지면서
그 문제가 **통째로 사라졌다**(2.5) — `projmng-route` 는 정책을 따로 적지 않고
`Program.cs` 의 `FallbackPolicy`(인증 필요)를 따른다.

| | 옛 계획(`/api/ai/tasks/**`) | **지금(`/api/projmng/ai-tasks/**`)** |
|---|---|---|
| 게이트웨이 | 새 라우트 + 정책을 **반드시 추가** | 손댈 것 없다 |
| 빠뜨리면 | 익명으로 운영 서버에서 AI 실행 | — |

`ai-route` 는 그대로 둔다 — 소개 사이트의 대화창이 그 익명 경로를 쓴다.
**우리가 그 밑으로 들어가지 않는 것**이 핵심이었다.

남는 것은 하나다. **실행기가 보고하는 경로**는 사람의 로그인이 아니라
run 별 1회용 토큰으로 인증한다(6.9). `/api/projmng/**` 가 인증을 요구하므로,
실행기는 게이트웨이를 거치지 않고 **내부망에서 :5450 을 직접 부른다** —
같은 장비 안이라 localhost 다(3장).

### 9.9 누가 요청할 수 있나

메뉴 권한만으로 부족하다. 메뉴는 보이는 것을 정할 뿐이고 API 는 주소만 알면
부른다. **요청 API 에서 서버가 역할을 다시 본다.**

배포 도구가 쓰는 방식을 그대로 베낀다 — `ReleaseService` 는 메뉴 경로
(`/portal/release`)의 `can_cust1` 권한을 읽는다. 「보기」와 「실행」이 갈려 있다.
우리도 **작성은 여럿, 요청(실행)은 소수**로 나눈다.

### 9.10 킬 스위치

설정 한 줄(`AiTasks:Enabled=false`)로 새로 집는 것을 멈춘다. 그리고 실행 중인
건을 **화면에서** 취소할 수 있어야 한다. 끄는 방법이 재배포뿐이면 그건 끌 수
없는 것이고, 운영 서버에서 도는 물건에는 반드시 있어야 한다.

### 9.11 과금과 상한

CLI 가 구독을 태운다. **하루 실행 수 상한**과 건별 타임아웃을 둔다.
무한 루프에 빠진 에이전트가 30분씩 열 번 도는 것이 가장 흔한 사고다.

### 9.12 감사

누가·언제·무엇을 요청했고 무엇이 돌았는지 남긴다. 본문은 판(version)을 남겨
「그때 무슨 지시였나」를 나중에 볼 수 있게 한다. 운영 서버에서 돈 일이므로
이력이 없으면 사고가 났을 때 **무엇이 원인인지 영영 모른다.**

### 9.13 여러 사람이 쓴다면

다른 사람이 쓴 글을 AI 가 **운영 서버에서** 실행한다. 프롬프트가 신뢰 경계라는
뜻이다. 9.9 의 권한 분리가 특히 중요하다.

## 10. API 표면

### 포털용 (게이트웨이 경유 · 인증)

게이트웨이가 `/api/projmng` 를 떼고 `/api` 를 다시 붙인다
(`/api/projmng/ai-tasks` → `ProjMngServer` 의 `/api/ai-tasks`).
컨트롤러 이름은 그 서비스의 관례대로 kebab 이다(`[Route("api/ai-tasks")]`).

```
GET    /api/projmng/ai-tasks?status=&flag=&q=&from=&to=&page=
GET    /api/projmng/ai-tasks/{id}
POST   /api/projmng/ai-tasks                 생성
PUT    /api/projmng/ai-tasks/{id}            수정 (row_version 으로 낙관적 잠금)
POST   /api/projmng/ai-tasks/{id}/request    요청 켜기  → flag=requested, status=queued
POST   /api/projmng/ai-tasks/{id}/cancel     취소 요청  → flag=cancel_requested
GET    /api/projmng/ai-tasks/{id}/runs
GET    /api/projmng/ai-runs/{runId}/logs?fromSeq=   꼬리 읽기 (증분)

GET    /api/projmng/ai-targets               대상 목록 (고르기용)
POST   /api/projmng/ai-targets               대상 등록 (관리자. 경로 검사 — 9.5)
PUT    /api/projmng/ai-targets/{id}

GET    /api/projmng/ai-dashboard?from=&to=   현황 한 판 (11.5)
```

`ai-dashboard` 는 **주소가 하나다.** 조각마다 주소를 두면 화면이 열릴 때
여덟 번 왕복하고, 그중 하나가 늦으면 대시보드가 조각조각 채워진다 —
그것이 사람에게는 「자료가 없다」로 읽힌다. 전부 같은 기간·같은 표를 훑는
집계라 한 연결에서 끝내는 편이 서버에도 싸다.

등록·수정자는 **게이트웨이가 붙여 주는 `X-User-Id`** 로 채운다. 본문으로 받지
않는다 — `ProjMngServer` 의 다른 컨트롤러가 전부 그렇게 한다.

### 실행기용 (run 별 1회용 토큰 · `X-AiTask-Token`)

```
POST   /runner/claim        {runnerId, kinds[], capacity}  → 집은 작업 0~N + run 토큰
POST   /runner/runs/{id}/heartbeat
POST   /runner/runs/{id}/logs      {events[], final:false}
POST   /runner/runs/{id}/complete  {events[], final:true, exitCode, branch, diffStat}
POST   /runner/usage        {runnerName, kinds[], items[]}  ← 장비 토큰 (11.6)
```

`logs` · `complete` 의 몸통은 **배포 콜백 규약과 같은 모양**이다(6.9) —
`{ "events": [{"level":"stdout","message":"…"}], "final": false }`.
응답 코드의 뜻도 같다: `403`/`404` 면 보고만 멈추고 **작업은 계속**,
`409` 면 잠시 뒤 다시 보낸다.

`claim` 만 장비 토큰이 필요하고(그 한 번으로 run 토큰을 받는다), 나머지는
run 토큰으로 인증한다. **장비에 계정 정보를 두지 않는다.**

## 11. 화면

### 11.1 모듈은 **`ProjMng`** 다 (2026-09-17 확정)

`/projmng` 아래에 둔다(`ProjMngModule.cs:17,21` — `Key = "projmng"`,
`RoutePrefix = "/projmng"`). **새 모듈을 만들지 않는다.**

정한 이유는 셋이다.

1. Monaco 가 이미 그 모듈에 있다 — 감싸개 `Components/Shared/CodeEditor.razor`,
   지연 로더 `wwwroot/js/monaco-loader.js`, 그리고 `BlazorMonaco` 패키지 참조
   (`JSini.Web.ProjMng.csproj:15`). **새로 붙일 패키지도, 새로 쓸 JS 도 없다.**
2. 모듈 간 참조가 금지라(의존 규칙 2) 다른 모듈에 두면 그 셋을 **복제**해야 한다.
3. 새 `Ai` 모듈은 셸 csproj 참조 · `PortalApps` 설정 · `_Pending.razor` ·
   아키텍처 테스트(`ShellCompositionTests`)가 전부 따라온다. 화면 한둘에 무겁다.

> 나중에 세 번째 모듈이 편집기를 쓰게 되면 그때 `CodeEditor` 를
> `JSini.Web.Components` 로 승격한다(web/CLAUDE.md 의 「두 모듈이 쓰면 복제,
> 세 번째부터 승격」). **지금은 승격하지 않는다** — 쓰는 곳이 둘이면 복제가 규칙이다.

#### 이 결정에서 따라 나오는 것

| 자리 | 무엇을 한다 |
|---|---|
| `Components/Pages/AiTaskList.razor` | 목록 + 편집 화면. `@page "/projmng/ai/tasks"` |
| `Components/Pages/AiTargetList.razor` | **대상 관리** — `@page "/projmng/ai/targets"` |
| `Components/Pages/AiTaskRunView.razor` | 실행 이력·로그 (4단계에서) |
| `Api/AiTaskClient.cs` | `GatewayClient` 를 받는 업무 클라이언트. DTO 도 같은 파일 |
| `ProjMngModule.ConfigureServices` | `services.AddScoped<AiTaskClient>();` 한 줄 |
| `wwwroot/projmng.css` | `pm-*` 접두사로 스타일. `StyleSheet` 선언은 **이미 있다** |
| `Components/Pages/_Pending.razor` | 손댈 것 없다. 리터럴 라우트가 언제나 이긴다 |

#### 접두사가 **일치한다**

초안에서는 화면이 `ProjMng` 인데 게이트웨이 경로가 `ai/…` 라 이 파일만 어긋나는
문제가 있었다. 백엔드가 `ProjMngServer` 로 정해지면서(2.5) 사라졌다.

```csharp
public sealed class AiTaskClient(GatewayClient gateway)
{
    private const string Url = "projmng/ai-tasks";   // ← 다른 열한 개와 같은 모양
}
```

#### 응답은 **봉투에 싸서** 내려야 한다

`GatewayClient` 는 공통 봉투(`result` 배열)를 벗기는 클라이언트다.
새 컨트롤러도 `ApiResponse<T>.Ok(...)` 로 싸야 한다 — `ProjMngServer` 의 다른
컨트롤러가 전부 그렇게 한다(`HomeTodosController` 의 `Ok(ApiResponse<List<HomeTodo>>.Ok(rows))`).

안 싸면 **오류가 나지 않는다.** `GetListAsync` 는 빈 배열, `GetOneAsync` 는
`null` 을 돌려주고 화면은 「자료가 없습니다」를 띄운다 — 서버 로그에는 200 만
남아서 어디가 틀렸는지 보이지 않는다.

#### 메뉴에 꽂기

DB 는 URL 을 모른다. 화면의 열쇠(`RouteKey`)를 `scom.system_menus.route_key` 에
넣는 것이 연결의 전부고, 그것도 **메뉴 관리 화면(`/admin/system/menu`)의
「화면」 칸에서 골라서** 한다 — 실려 있는 화면 목록에서만 고를 수 있으므로
없는 화면을 가리킬 방법이 없다. SQL 을 직접 쓰지 않는다.

#### 이름 규칙 — 화면이 자료 타입을 가리면 안 된다

Razor 가 만드는 클래스는 `JSini.Web.ProjMng.Components.Pages` 에 들어가고
DTO 는 `JSini.Web.ProjMng.Api` 에 있다. 이름이 같으면 화면 안에서는 **화면
자신이 이긴다.** 그래서 화면은 `AiTaskList`, 자료는 `AiTaskDto` 로 가른다 —
둘 다 `AiTask` 로 지으면 `'AiTask' 에는 'Status' 에 대한 정의가 없습니다` 라는,
**DTO 를 잘못 만든 것처럼 읽히는** 오류가 난다. `ComponentNamingTests` 가 막는다.

### 11.2 뼈대

```razor
@page "/projmng/ai/tasks"
@attribute [RouteKey("projmng.ai-tasks")]
@inherits DataPage
```

- **제목 줄을 두지 않는다.** 사이드바·브레드크럼이 이미 말한다.
- 조회 영역은 `CommSch`(상태 · 요청여부 · 기간 · 검색어), 조회 단추는 판이 그린다.
- 좌우는 **`ad-vsplit`**(끌어서 폭 조절) — 왼쪽 목록(`CommGrd`), 오른쪽 편집.
  긴 글을 쓰는 화면이라 팝업(`CommPopup`)보다 분할이 맞다.
  분할 양쪽 판은 **반드시 `CommCont`** 여야 높이 규칙이 걸린다.
- 저장·요청·취소 결과는 **토스트**다(`DataPage` 가 띄운다). 화면이 그릴 것이 없다.
- 「왼쪽에서 건을 고르십시오」처럼 **사라지면 안 되는 안내**만 `PageNotice`.
- 표 안에서 높이를 값으로 주지 않는다 — `flex: 1; min-height: 0`.
- 모듈 전용 스타일은 `wwwroot/projmng.css`.

### 11.3 편집기

`CodeEditor` 를 그대로 쓴다. 이미 해결돼 있는 것들:

- `editor.main.js` 가 3MB 라 **이 화면에서만** 받는다(`<head>` 에 적지 않는다).
- `window.monaco` 가 준비되기 전에 그리면 **회로가 끊긴다** — 로더가 막아 둔다.
- 변경 콜백은 debounce 를 거친다. Blazor Server 에서 키 입력마다 회로 왕복 두 번이다.

언어는 `markdown`. 편집기 안에 Ctrl+S 단축키를 붙이려면 **눌린 순간 값을 읽어
오는 왕복**이 한 번 더 든다는 것을 감안한다.

### 11.4 진행 중 보기

실행 중인 건을 열어 두면 **2~3초마다 `fromSeq` 로 새 줄만** 가져와 붙인다.
새 SignalR 허브를 만들 필요가 없다 — 이미 Blazor Server 회로 위다.

**SSE 로 흘리지 않는 이유가 있다.** `GatewayClient` 는 봉투를 통째로 받아
벗기는 클라이언트라 `text/event-stream` 을 흘려 읽을 수 없다. AI 대화창이
그래서 클라이언트를 따로 두고 있다(`JSini.Web.Http/AiChatClient.cs`).
로그까지 그 길로 가면 **공유 자리에 스트리밍 클라이언트가 하나 더** 생기는데,
얻는 것은 지연 2초뿐이다. 증분 폴링이 맞다.

빠뜨리면 반드시 사고가 나는 둘:

1. **화면을 떠날 때 타이머를 끈다**(`IAsyncDisposable`). 안 끄면 회로마다 타이머가
   쌓이고, 사람이 화면을 열었다 닫을수록 서버가 느려진다.
2. **꼬리 500줄만 그린다.** 수만 줄을 DOM 에 그리면 회로가 그것을 전부 실어 나른다.
   전체는 내려받기로.

## 11.5 「AI 작업 현황」 — **처리한 것을 세어 보는 자리** (2026-09-21)

화면: `web/src/Apps/JSini.Web.ProjMng/Components/Pages/AiDashboard.razor`
집계: `microservices/ProjMngServer/Services/AiDashboardService.cs`
주소: `/projmng/ai/dashboard` · 열쇠 `projmng.ai.dashboard`
메뉴: `deploy/sql/portal-menu-ai-dashboard-2026-09-21.sql`

### 세는 단위는 **「실행」**이다 — 「지시」가 아니다

한 지시를 세 번 돌리면 **처리한 일은 셋**이고, 그 셋의 처리시간과 성패가
서로 다르다. 지시로 세면 재시도가 통째로 안 보이는데, 이 기능에서 사람이
가장 알고 싶어 하는 것 중 하나가 **「얼마나 다시 돌리고 있나」**다
(6.11 의 자동 재시도가 얼마나 도는지를 여기서만 볼 수 있다).

그래서 타일도 차트도 `ai_task_run` 을 센다. 「지시 건수」는 따로 한 칸을 준다.

### 기간을 타는 것과 「지금」을 **갈라 둔다**

대기·실행 중·미확인·실행기 소식은 **언제로 조회하든 지금 값**이다. 기간에
섞으면 지난달로 조회한 화면이 「실행 중 0건」이라고 말하면서 실제로는 지금
돌고 있는 일이 생긴다. 화면에서도 띠를 갈라 놓고 「지금」이라고 적는다.

### 빈 칸을 지우지 않는다

일별·시간대별은 자료가 없는 칸도 0 으로 채워 돌려준다(`generate_series`).
있는 것만 주면 가로축이 들쭉날쭉해져 **「아무 일 없던 사흘」이 아예 없던
일**처럼 보인다 — 추세를 보는 화면에서 가장 나쁜 거짓말이다.

### 차트를 두 축으로 겹치지 않는다

일별 건수와 일별 평균 처리시간은 단위가 다르다. 한 차트에 축 둘을 세우면
두 선이 만나는 자리가 아무 뜻도 없는데 사람은 거기서 뜻을 읽는다.
**차트를 둘로 나눈다.**

### 예상 사용 건수는 예언이 아니다

최근 28일의 일평균을 그대로 늘려 잡은 것뿐이다. **근거를 같이 적는다**
(며칠 · 몇 건 · 일평균 얼마) — 안 적으면 화면의 숫자가 예언처럼 읽힌다.

오늘치는 「오늘 실적 + 일평균 × 남은 시간의 몫」이다. 오늘 실적을 지난
비율로 나누는 방식은 **새벽 한 건이 하루 백 건으로 부풀어** 쓸모가 없다.

### 실행기가 붙어 있는지를 화면이 말한다

`ai_runner.last_seen_at` 을 쓴다. **그 표에는 지금껏 아무도 쓰지 않았다** —
만들어 두고 쓰는 곳이 없었다. 아래 11.6 의 사용량 보고가 그것을 찍는다.
「대기가 쌓였는데 실행기가 죽어 있다」가 이 기능의 가장 흔한 고장인데(13장)
화면 어디에도 그 말이 없었다.

## 11.6 AI 모델 한도 — **실행기가 `/usage` 를 읽어 올린다** (2026-09-21)

표: `projmng.ai_usage_snapshot` — `deploy/sql/projmng-ai-usage-2026-09-20.sql`
올리는 쪽: `tools/AiTaskRunner/UsageReporter.cs` · `UsageText.cs`
받는 쪽: `AiRunnerController.UsageAsync` → `AiUsageService`

### 왜 서버가 직접 묻지 않나

`/usage` 를 아는 것은 **CLI** 이고, 그 CLI 와 그 계정의 로그인 상태는
실행기 장비에만 있다. 서버가 읽으려면 웹 요청을 받는 프로세스에 셸을 여는
권한을 줘야 하는데, **이 기능 전체가 그러지 않으려고 갈라져 있다**(2장 · 9.8).

### 명령을 코드에 박지 않는다

어댑터마다 `UsageArgs` 로 적는다(7.4 의 실행 인자와 같은 자리다). 이 출력은
사람이 보라고 만든 화면이지 API 가 아니라 문구도 플래그도 예고 없이 바뀐다.
**비워 두면 그 CLI 에는 아예 안 묻는다** — 지금 `antigravity` · `copilot` 이
비어 있다(묻는 길을 아직 확인하지 못했다).

### 가려낸 숫자가 전부가 아니다 — **원문을 늘 함께 올린다**

형식이 바뀌었을 때 가장 나쁜 결과는 *파싱이 실패했다고 보고를 통째로
버리는 것*이다. 화면이 「값 없음」으로 굳고 왜 그런지 아무도 모른다. 그래서

1. 원문(`raw_text`)을 늘 함께 올리고 화면이 접어서 보여 준다.
2. 줄의 뜻은 **머리글 낱말**로 정한다(session · week · opus). 순서에 기대면
   줄이 하나 끼는 순간 전부 어긋난다.
3. 못 읽은 칸은 **비운다.** 0 으로 채우면 「다 썼다」와 「모른다」가 같은
   숫자가 되는데, 그 둘은 사람이 할 일이 정반대다.
4. 숫자를 하나도 못 읽었으면 `ok = false` 다. 명령은 돌았는데 형식이
   바뀐 경우가 그것이고, 화면이 빈 칸을 「0% 썼다」로 읽지 않게 한다.

시각 해석은 **형식을 먼저 대 본다**(`UsageText.Formats`). `DateTime.TryParse`
에만 맡기면 `Nov 5 at 12:00am` 을 **조용히 「오늘 05:12」로** 읽는다 —
오류가 아니라 그럴듯한 값이 나오는 실패라, 화면에는 「갱신 시각이 이미
지났다」로만 보인다(실제로 밟아서 형식 목록이 생겼다).

### 운영 장비에서 실제로 본 출력 (2026-09-21)

```
Current session: 1% used · resets Sep 21, 12:10pm (Asia/Seoul)
Current week (all models): 36% used · resets Sep 24, 11pm (Asia/Seoul)
Current week (Fable): 0% used · resets Sep 24, 11pm (Asia/Seoul)
```

**퍼센트는 처음부터 맞았는데 갱신 시각만 셋 다 비어 있었다.** 꼬리의
`(Asia/Seoul)` 과 날짜 뒤 쉼표 때문에 어느 형식에도 걸리지 않았다. 괄호와
쉼표를 먼저 걷어내고 `MMM d htt`(분 없는 시각)를 형식에 넣어 고쳤다.
**퍼센트가 멀쩡해서 더 안 보이는 고장**이었다 — 화면은 채워지는데 「언제
기준의 값인가」만 비어 있었고, 그 칸이야말로 숫자를 믿게 하는 칸이다.

`Current week (…)` 둘째 줄은 **이제 Opus 가 아니다.** `week_opus_pct` 는
낱말 `opus` 로 찾으므로 이 장비에서는 비어 있다 — 비어 있는 것이 맞다.
낱말만 넓혀 주워 담으면 화면의 「Opus 주간」 칸에 **다른 모델 숫자**가
앉는데, 빈 칸보다 그쪽이 나쁘다.

### 사용량 보고 하나가 실행기를 통째로 죽일 뻔했다

`catch (Exception ex) when (ex is not OperationCanceledException)` 이
저장소 곳곳의 모양인데, **`HttpClient.Timeout`(30초)도
`TaskCanceledException` 으로 온다.** 종류만 보고 흘려보내면 제한 시간까지
함께 빠져나가고, `UsageReporter` 는 `BackgroundService` 라
기본값 `BackgroundServiceExceptionBehavior.StopHost` 가 **돌던 작업까지
통째로 내린다.** 곁들이는 칸 하나 때문에 본업이 죽는 자리다.

그래서 취소를 둘로 가른다 — **멈추라는 신호로 온 것만** 밖으로 내보내고
(`ct` 가 취소됐을 때), 제한 시간은 여느 실패처럼 적고 넘어간다.
`ServerClient` 의 다섯 자리가 같은 모양이었고 같이 고쳤다. 집어가기·
하트비트 쪽은 죽지는 않았지만 **`RunnerWorker` 가 「멈추라는 신호가 왔다」로
읽고 조용히 고리를 빠져나가** 실행기가 살아 있는 채로 아무 일도 안 집는,
더 찾기 나쁜 모양이었다.

확인은 **일부러 매다는 프록시**로 했다. `/api/ai-runner/usage` 만
통과시키고 나머지는 503 으로 막아(확인용 실행기가 실제 작업을 집어가지
못하게) 한 번만 40초를 매단다. 고치기 전에는 그 자리에서 `FTL ... StopHost`
로 내려갔고, 고친 뒤에는 경고 한 줄만 남기고 다음 주기에 정상 보고했다.

### 퍼센트는 「쓴 비율」이다

남은 비율이 아니다. CLI 가 그렇게 말하기 때문이고, 뒤집어 적으면 원문과
화면이 어긋나는 순간을 아무도 못 잡는다.

### 보고가 곧 「살아 있다」는 신호다

같은 요청으로 `ai_runner.last_seen_at` 을 찍는다. **한도를 하나도 못
읽었어도 보고는 간다** — 「실행기는 붙어 있는데 사용량만 못 읽는 중」이
실제로 있는 상태이고, 화면은 그 둘을 다르게 보여 줘야 한다.

주기는 15분(`Runner:UsageIntervalMinutes`)이다. **짧게 두지 않는다** —
물어보는 것 자체가 CLI 호출이라, 그것이 한도를 깎는 형태라면 *사용량을
보려고 사용량을 쓰는* 꼴이 된다. `AIAgentServer` 가 공급자에게 따로 묻지
않고 응답 헤더를 줍는 것과 같은 생각이다(`AiUsageTracker`).

### 한도는 두 군데에서 온다 — 한 칸에 뭉개지 않는다

| | 무엇의 한도 | 어디서 | 화면 |
|---|---|---|---|
| 작업지시 CLI | `claude` · `agy` · `copilot` | 실행기가 `/usage` 로 읽음 | 계량기 |
| AI 공급자 | 포털 AI 도우미가 쓰는 모델 | `ai/providers` (응답 헤더에서 주움) | 표 |

**다른 계정의 다른 한도**다. 둘 다 「언제 기준의 값인가」를 반드시 함께
보여 준다 — 그것을 모르면 숫자를 믿을 수 없다.

## 13. 운영에서 보이게 하기

- **헬스체크에 항목을 더한다.** `AIAgentServer` 가 `LlmHealthCheck` 로
  「LLM 이 꺼져 있으면 초록이 아니다」를 해 둔 것과 같은 방식으로,
  `ProjMngServer` 의 헬스에
  *최근 1분 안에 하트비트한 실행기 수* 와 *RabbitMQ 연결*을 더한다.
  **프로세스는 멀쩡한데 일할 장비가 없는 상태**가 이 기능의 가장 흔한 고장이고,
  그게 안 보이면 초록이다.
- 대기열 길이·최장 대기 시간을 주기 로그로.
- 실행기 자신의 로그는 journald 로 간다(`journalctl -u ai-task-runner`).
- 완료·실패 알림은 `NotificationServer`(:5460)가 이미 있다. **선택** —
  1단계에서는 넣지 않는다.

## 14. 배포·설정

### 14.1 서버 쪽 (컨테이너)

- **표는 SQL 파일로 만든다**(4.6) — `deploy/sql/projmng-ai-tasks-2026-09-17.sql`.
  EF 마이그레이션이 아니다. 운영 반영은 손으로 한 번 돌리는 일이고,
  **돌렸는지 반드시 확인한다**(루트 CLAUDE.md).
- 현황 화면(11.5 · 11.6)은 SQL 둘을 더 돌려야 한다 —
  `projmng-ai-usage-2026-09-20.sql`(한도 표 · 집계 인덱스)와
  `portal-menu-ai-dashboard-2026-09-21.sql`(메뉴 · 권한).
  **메뉴 SQL 만 돌리면** 화면은 열리는데 한도 칸이 비고 로그에 경고가 남는다.
  **한도 SQL 만 돌리면** 화면은 있는데 메뉴에서 닿을 길이 없다.
- 설정은 `/srv/jsini/config/ProjMngServer/appsettings.Local.json` — 이미 마운트돼 있다.
- RabbitMQ 설정은 배포 도구의 모양을 따른다:

```json
"AiTasks": {
  "Enabled": true,
  "QueueName": "ai_task",
  "Durable": true,
  "PickupTimeoutSeconds": 60,
  "MaxEventsPerRun": 5000,
  "MaxEventLength": 4000,
  "MaxParallel": 5,
  "GateParallel": 1
}
```

> **`Durable` 은 `true` 로 시작한다.** `run_script` 가 `false` 인 것은 이미 그렇게
> 존재하는 큐라 바꿀 수 없어서지 그게 나아서가 아니다(`ReleaseService` 주석:
> durable 로 다시 선언하면 브로커가 `PRECONDITION_FAILED` 를 낸다).
> `ai_task` 는 새 큐라 그 제약이 없다.
>
> **넣는 쪽과 집는 쪽이 같은 값을 선언해야 한다.** 다르면 같은 오류를 우리가 낸다.

- 컨테이너에서 브로커 주소는 `localhost` 가 아니다. 호스트 서비스로 도는
  RabbitMQ 를 부르려면 `host.docker.internal` 또는 호스트 IP 를 써야 한다.
  **컨테이너 안의 `localhost` 는 자기 자신이다.**

### 14.2 장비 쪽 (실행기)

- systemd 유닛으로 상주. `Restart=always`, `CPUQuota`, `MemoryMax`(9.4).
- 전용 계정 `ai-runner` 로 돌린다(9.2). 그 계정으로 `claude` 로그인을 한 번 한다.
- 작업공간 뿌리를 그 계정 소유로 만든다(`/home/ai-runner/workspaces`).
- **이미지가 아니다.** 배포 이미지 열둘은 그대로 열둘이다.
- 실행기 소스는 저장소 안에 둔다(`tools/AiTaskRunner`) — 장비와 서버 사이의
  약속이 저장소 밖에 있으면 반쪽만 버전 관리된다. `deploy/release-consumer` 가
  같은 이유로 저장소 안에 있다.

> **실행기 바이너리는 `main` 푸시로 안 바뀐다.** GHCR 이미지 열둘과 **전혀
> 다른 길**이다 — 사람이 publish 해서 `/home/lee/ai-task-runner` 에 올려야
> 한다. 그래서 **설정만 올리고 재기동하면 조용히 망가진다**: 새 설정 칸을
> 모르는 옛 바이너리가 기본값으로 떨어지고, 오류 없이 그 기능만 사라진다
> (2026-09-20 에 `Runner:Kinds` 로 실제로 그 자리에 섰다).
>
> 11.6 의 사용량 보고도 **바이너리 기능**이다. `UsageArgs` 만 올리고 옛
> 바이너리를 그대로 두면 아무 일도 일어나지 않고, 화면은 「올라온 한도가
> 없습니다」만 보여 준다.
>
> ```
> DOTNET_ROOT=/home/lee/.dotnet /home/lee/.dotnet/dotnet publish -c Release \
>   -r linux-x64 --self-contained true -o <스테이지>
> rsync -a --delete --exclude=appsettings.Local.json <스테이지>/ /home/lee/ai-task-runner/
> ```
>
> `--exclude=appsettings.Local.json` 을 꼭 넣는다 — 장비 토큰이 거기 있고
> `--delete` 가 지운다. 재기동은 `sudo systemctl restart` 가 안 된다
> (유닛의 `NoNewPrivileges=yes`). 주 프로세스에 `kill -TERM` 을 보내
> `Restart=always` 로 되살린다. **재기동은 그때 돌던 작업도 같이 죽인다.**
>
> **언제 내리나 — 「실행 중」이 0 일 때다.** 대개 이 배포를 하는 것이
> 실행기 안에서 도는 AI 자신이라, 그냥 내리면 *자기 작업을 자기가 죽인다.*
> cgroup 에 CLI 가 보이나로 세면 안 된다 — CLI 가 끝난 뒤에도 실행기는
> 게이트(빌드·테스트)를 돌리고 `push` 하고 완료를 보고한다. 그 사이에
> 내리면 **다 해 놓고 보고만 못 한 채 죽는다.** 서버에
> `GET /api/ai-dashboard` 의 `summary.runningNow` 를 물어 0 이 될 때까지
> 기다렸다가 내리는 감시 하나를 떼어 두면 된다.
>
> 그 감시를 유닛 안에서 돌리면 **재기동과 함께 같이 죽어** 뒤처리를 못 한다.
> `systemd-run --user` 로 띄우면 `user@1000.service` 밑으로 빠져 살아남지만,
> 세션이 닫히면 사용자 관리자도 같이 내려간다(`Linger=no`). 둘 다 띄워 두고
> `mkdir` 로 자리를 하나만 잡게 하는 것이 지금의 답이다.

## 15. 아직 안 정해진 것

답을 받은 것은 머리말의 「정해진 것」으로 옮겼다 — 모듈 · B안 · 실행 장비 ·
실행 계정 · 대상 지정 방식 · `main` push · 동시 5건 · 이메일 옵션 · 백엔드.

남은 것은 둘뿐이고, **둘 다 1단계를 막지 않는다.**

1. **쓰는 사람이 나 혼자인가, 여럿인가?** (9.9·9.13 의 크기가 달라진다)
   이것 하나가 5단계의 마지막 조각(권한 분리)을 막고 있다 — 혼자면 할 일이 없고,
   여럿이면 「작성은 여럿, 요청은 소수」를 실제로 나눠야 한다.
   여럿이 되면 「작성은 여럿, 요청은 소수」 권한 분리를 실제로 나눠야 하고,
   9.2 에서 접어 둔 **전용 계정**이 다시 안건이 된다.
   권한을 다 열어 두기로 했으므로(7.6) 그 무게가 더 크다.

    그 다음 실행은 ①에서 「정본이 깨끗하지 않습니다」로 죽고, 그 다음도,
    그 다음도 — **사람이 손으로 치울 때까지 기능 전체가 멈춘다.** 실제로
    `deploy/docker-compose.prod.yml` 을 건드린 작업 하나가 그렇게 멈춰 세웠다.

      예전에는 거기서도 막아 **한 대상의 찌꺼기가 다른 대상의 실행까지
      죽였다.** 지금은 경고 한 줄을 적고 간다(당기지 못했을 때와 같은 규칙 —
      19번).

      올라가지 않은 커밋이 `main` 에 얹혀 있다. 그것은 지우지 않는다 —
      사람이 이어받을 결과물이라 판단이 필요하다.

22. **지시 둘을 잇달아 넣으면 뒤엣것이 `fatal: Cannot rebase onto multiple
    branches.` 로 죽었다.** 게이트의 `git pull --rebase origin main` 이 낸
    말인데, 가지가 여럿인 적은 한 번도 없었다 — **`FETCH_HEAD` 가 섞인 것**이다.
    - `git pull` 은 「방금 받은 것」을 자기 자신에게 `FETCH_HEAD` **파일**로
      넘긴다. 그 파일은 저장소마다(작업분기마다) 하나뿐이고 **자물쇠 없이
      덮어쓴다.** 그래서 한 실행이 그것을 쓰는 동안 다른 실행의
      `git fetch origin`(준비 구간)이 같은 파일을 쓰면 두 글이 섞여
      「merge 대상」 줄이 둘이 된다. pull 은 그것을 「가지 둘에 얹으라는 뜻」
      으로 읽고 죽는다.
    - 재현했다. 같은 저장소에서 `git fetch origin` 과
      `git pull --rebase origin main` 을 겹쳐 돌리니 **60번 중 60번** 났다.
    - 고침: **pull 을 쓰지 않는다.** 받는 것과 얹는 것을 갈라
      `git fetch origin +refs/heads/<가지>:refs/remotes/origin/<가지>` 로 받고
      `git rebase origin/<가지>` 로 얹는다. 원격 추적 가지는 git 이 잠금 파일로
      갱신하므로 겹쳐도 섞이지 않는다. 같은 시험에서 **60번 중 0번**.
    - 준비 구간의 `git pull --ff-only origin <가지>` 도 같은 이유로
      `git merge --ff-only origin/<가지>` 로 바꿨다(바로 앞에서 fetch 를 하므로
      받을 것은 이미 다 받아 둔 상태다).
    - **남은 것:** 복사본(`copy`) 격리는 준비가 끝나면 대상 잠금을 놓는데,
      게이트에서 다시 정본으로 돌아와 커밋·push 한다. 그 사이 다른 실행이
      정본에서 준비를 돌면 `index.lock` 을 두고 다툴 수 있다. `FETCH_HEAD`
      쪽은 이 고침으로 사라졌지만 잠금 범위 자체는 그대로다.
23. **빠른지시에서 실패 시 자동 재시도가 돌지 않았다.**
    - 원인 ①: `AiAsk.razor` 및 화면 DTO(`AiTaskClient.cs`, `AiTaskList.razor`)에서 `AttemptMax`가 `1`로 고정되어 생성되어 재시도 조건(`counters.Count < counters.Max`)을 만족하지 못했다.
    - 원인 ②: `AiTaskService.RequestAsync`(수동 재요청)에서 `attempt_count`를 초기화하지 않아 재요청 후 실패 시 즉시 상한에 걸렸다.
    - 원인 ③: 재시도 지연 대기 시간이 없어 실패 시 0초 만에 즉시 재실행되었다.
    - 고침:
      - `AiAsk.razor`, `AiTaskList.razor`, `AiTaskClient.cs`의 `AttemptMax` 기본값을 3으로 수정하고 `NormalizeAsync`에서 `<= 0`일 때 3으로 보정.
      - `RequestAsync`에서 `attempt_count = 0`으로 초기화.
      - `AiTasks:RetryDelaySeconds`(기본 15초)를 도입하여 `requested_at`을 지연 시간 뒤로 설정하고, `ClaimAsync`에 `requested_at <= now()` 조건을 추가하여 지연 시간 경과 후 큐 알림과 함께 재실행되도록 개선.

#### push 게이트를 **실제 push 까지** 확인했다

운영을 건드리지 않고 확인하려고 **로컬 bare 저장소를 `origin` 으로** 두었다.
그러면 push 가 실제로 일어나되 바깥으로 나가지 않는다.

```
[준비] git fetch → git pull --ff-only → worktree (ai/14-9 ← origin/main)
[시작] claude …
[게이트] 검사 차례를 받았습니다.          ← 게이트는 직렬(9.4)
[게이트] 바뀐 파일 1개를 커밋합니다.
[게이트] git pull --rebase
[게이트] 통과. main 으로 올립니다 — 배포가 일어납니다.
```

origin 의 `main` 에 커밋이 실제로 올라갔고, 화면의 `pushed_commit` 이 그 SHA 다.

#### 이어가기도 한 바퀴 돌았다

같은 작업에 **2차 실행**이 붙고, 조립된 프롬프트가 이렇게 나왔다:

```markdown
### 1차 (2026-09-18 00:18, succeeded)
지시: # README 에 한 줄 더해라
AI 요약: README.md 맨 아래에 "두 번째 줄" 을 추가했다. …
         커밋은 하지 않았다. 필요하면 말해 달라.        ← **AI 의 주장**

기록된 사실:                                            ← **우리가 잰 값**
  · 종료 코드 0
  · 1 file changed, 2 insertions(+)
  · 브랜치 ai/14-9

> 지난 결과는 이미 올라갔습니다(13bc237e).
```

**여기서 8-3.5 가 그대로 증명됐다.** AI 는 「커밋은 하지 않았다」고 썼는데
기록은 커밋도 push 도 됐다고 말한다 — 요약만 물렸으면 다음 실행이 그
거짓말 위에서 시작했을 것이다. 두 값을 나란히 실었더니 어긋남이 프롬프트
안에서 그대로 보인다.

#### 여기서도 밟았다

7. **지시문 파일이 커밋에 섞였다.** 작업공간 안(`.ai-task/`)에 두었더니
   `git add -A` 가 그것까지 집어 `main` 에 올라갔다. worktree 의
   `info/exclude` 는 정본과 공유되는 파일이라 거기 적는 것은 정본을 건드리는
   일이 된다 — **작업공간 밖**으로 옮겼다.
8. **실행기가 서버에 닿지 못했다 — 그 포트가 호스트에 안 열려 있었다.**
   설계 3장에 「같은 장비 안이라 localhost 다」라고 그려 놓았는데, 정작
   백엔드 컨테이너들은 호스트에 포트를 하나도 열지 않는다(게이트웨이만 연다).

   바깥에 열면 헤더만 위조하면 아무나 남의 권한으로 부를 수 있다.
9. **없는 경로 하나 때문에 유닛이 아예 안 떴다.** `ReadWritePaths` 에

   한 번에 안 읽힌다.** 나중에 만들 수 있는 경로에는 `-` 를 붙인다 —
   다만 **막는 쪽(`InaccessiblePaths`)에는 붙이지 않는다.** 막을 것이 없어서

   담장이 조용히 사라진 채로 AI 가 돈다.
10. **`Jwt__Key` 가 안 가려졌다.** 마스킹 규칙이 `jwt[_-]?key` 라 밑줄 하나만
   허용했는데, 이 저장소의 환경변수는 **이중 밑줄**을 쓴다. `[_-]*` 로 고쳤다.
