# 업무 비서 — RAG 자료 + 포털 업무 데이터를 가로질러 묻는 화면

**슈퍼관리자와 임원만 연다.** `/admin/ai/assistant`, 메뉴 `SYS_AI_ASSISTANT`.
다른 사람에게는 메뉴가 안 보이고 주소로도 안 열린다(기본 차단,
[docs/screen-access.md](screen-access.md)).

설계 원본은 [docs/superpowers/specs/2026-10-24-portal-ai-assistant-design.md](superpowers/specs/2026-10-24-portal-ai-assistant-design.md).
이 문서는 그중 **실제로 돌려 잰 결과**와 **아직 안 끝난 것**을 담는다.

## 왜 묻는 사람의 평소 권한을 넘어서는가

헬프데스크 요청글을 뒤지고, 프로젝트관리 일정을 열어 보고, 메일을 찾아보는
일을 한 번 물어서 끝내는 것이 이 화면의 목표다. 그런데 그 세 자료는 원래
각자의 권한으로 나뉘어 있다 — 홍길동의 글을 볼 권한이 없는 임원도 이 화면에서는
내용을 받는다.

그 대가로 **모든 질문과 답이 통째로 기록된다.** 권한을 넘는 자리에 기록이
없으면 나중에 되짚을 방법이 없다. 아래 「기록」절 참고.

## 왜 포털 데이터를 RAG 색인에 넣지 않았나 — 검색이 아니라 도구다

사내 문서(규정·매뉴얼)는 RAG 색인으로 충분하다. 하지만 포털 업무 데이터는
두 가지가 RAG 와 맞지 않는다.

1. **"10월 17일 이후", "오늘 이후" 는 범위 질의다.** 벡터 검색은 뜻이 가까운
   것을 찾지 날짜로 자르지 못한다. 10월 17일과 10월 18일의 임베딩은 거의 같다.
2. **업무 데이터는 매분 바뀐다.** 색인을 다시 만드는 데 CPU 임베딩으로
   780토막에 4분 40초가 걸리는데, 그 사이 들어온 새 요청글은 안 보인다.

그래서 모델에게 **도구**를 쥐어 준다. `AssistantAgent.RunAsync` 가
OpenAI 규격 `tool_calls` 루프를 최대 `Assistant:MaxToolRounds`(기본 6, 1~10 으로
자름)회 돌리고, 마지막 답만 SSE 로 흘린다. 기존 AI쳇(`AiChatPanel`·
`RagAugmenter`·`WebChatAgent`)은 전혀 건드리지 않았다 — 이 화면은 완전히
별도의 길(`/assistant/*`)로 돈다.

## 도구 일곱

| 도구 | 받는 것 | 닿는 곳 | 비고 |
|---|---|---|---|
| `find_user` | 이름 | AuthServer(`scom.accounts`) | 동명이인이면 후보를 전부 돌려준다 — 하나를 임의로 고르지 않는다 |
| `search_requests` | userId?·from?·to?·status?·keyword?·take | HelpDeskServer | userId 는 글쓴이·담당자·댓글 단 사람 **셋 중 아무거나**로 걸린다 |
| `get_request` | id | HelpDeskServer | 본문 + 댓글 전부 |
| `search_schedules` | userId?·name?·from?·to?·keyword?·take | HelpDeskServer + ProjMngServer(`dev_wbs`) | 두 자료원을 한 목록으로 합친다. userId 만 와도 이름을 자동으로 되찾아 WBS 매칭에 쓴다 |
| `search_todos` | userId?·from?·to?·done?·take | ProjMngServer(`home_todo`) | |
| `search_mails` | userId?·from?·to?·keyword?·take | NotificationServer | 보낸 메일함과 알림 직발송 메일을 함께 본다. 받은 메일함은 포털에 없다 |
| `search_documents` | query·category? | AIAgentServer(`RagStore`) | 이 화면에서만 RAG 도 도구다 — 첫 검색이 빗나가면 모델이 낱말을 바꿔 다시 찾을 수 있다 |

**회사 경계를 넘는다.** RAG 카테고리도 회사별로 갈리지만(`company_id`), 이
화면은 권한을 넘기로 한 것의 자연스러운 연장으로 보고 전체를 본다.

**일정·일 칸의 담당자는 손으로 적은 글이다.** 프로젝트관리 WBS(`dev_wbs`)의
담당자 칸(`dev_user`·`build_user`·`qc_user`)은 로그인 아이디와 사람 이름이
섞여 있고 `박경수/완료`처럼 뒤에 글자가 붙기도 한다 — 계정과 자동으로
안 이어진다. 시스템 프롬프트가 이 사정을 모델에게 그대로 알리고, 동명이인이면
단정하지 말라고 못박는다.

## 권한을 넘는 호출 — 내부 토큰

사내 서비스(HelpDesk·ProjMng·Notification)는 보통 토큰 주인의 범위로 좁혀
답한다(`UserContext`). 이 화면은 그것을 넘어야 하므로 **공유 비밀**
`Assistant:InternalToken` 을 쓴다 — `DeployNotify:Token` 과 같은 방식이다.
세 서비스에 조회 전용 내부 엔드포인트(`/internal/*`)를 새로 열었을 뿐,
기존 사용자 엔드포인트에는 우회로를 뚫지 않았다.

**값이 없으면 도구가 조용히 꺼진다.** `PortalToolSet.Tools(internalEnabled: false)`
는 `search_documents` 하나만 돌려준다 — 나머지 여섯은 터지는 대신 아예
모델에게 안 보인다. 개발 장비처럼 토큰이 없는 곳에서도 비서가 통째로 죽는
대신 문서 질문만은 답한다. **지금 이 저장소의 `scripts/secrets.env`·
`scripts/secrets.env.example` 에는 이 값이 없다** — 운영에 올리려면 두 곳
(AIAgentServer 와, 이 토큰을 받는 세 서비스)에 같은 값을 넣어야 한다.

## 기록 — 왜 답을 통째로 남기는가

새 표 `scom.ai_assistant_audit`(EF 마이그레이션이 아니라
`deploy/sql/ai-assistant-audit-2026-10-25.sql`, RAG 표들과 같은 길).

| 칸 | 담는 것 |
|---|---|
| `asked_by`·`asked_at` | 누가·언제(UTC) |
| `question` | 물은 글 그대로 |
| `scope_category` | 고른 RAG 카테고리 |
| `tool_calls` | 어떤 도구를 어떤 조건으로 불렀나(jsonb 배열) |
| `sources` | 지금은 **늘 빈 배열**(아래 「아직 안 된 것」) |
| `answer` | **답 전문** |
| `elapsed_ms`·`error` | 걸린 시간·실패 까닭 |

권한 밖 자료가 나간 자리라 "무엇이 나갔나"를 뒤에서 되짚을 유일한 길은
질문이나 도구 조건이 아니라 **답 그 자체**다. 그래서 자르지 않고 통째로
담는다. 저장이 실패해도(지금처럼 표가 없을 때도) 이미 사용자에게 흘려 보낸
답은 해치지 않는다 — 로그만 남기고 삼킨다(`AssistantAgent.SaveAuditAsync`).
사람이 창을 닫아 연결이 끊겨도 기록은 남는다 — 저장을 요청 자체의
취소 토큰이 아니라 `CancellationToken.None` 으로 부르기 때문이다.

## 실측 (2026-10-25, 개발 장비)

### 가를 수 없었던 절반

이 측정 시점에 두 가지가 막혀 있었다.

1. **`Assistant:InternalToken` 이 설정되어 있지 않다.** 설계대로 포털 도구
   여섯(요청글·일정·할 일·메일·사람 찾기)이 전부 꺼지고 `search_documents`
   하나만 남는다. "홍길동의 10/17일 이후", "오늘 이후 할일목록" 류의
   질문은 **오늘은 잴 수 없다** — 답이 틀렸는지가 아니라 도구 자체가 없다.
2. **감사 표(`scom.ai_assistant_audit`)가 아직 운영 DB에 없다.** `GET
   /assistant/audit` 는 500 을 돌려준다(`42P01: relation ... does not exist`).

그래서 사양의 「재는 것」 네 갈래(일정 5·과거 5·문서 5·섞인 것 5·자료에 없는
것 5, 총 25개) 중 **문서 질문 5개와 「자료에 없는 것」질문 5개, 열 개만
실제로 돌렸다.** 일정·과거·섞인 것 세 갈래(15개)는 포털 도구가 꺼져 있어
오늘은 측정 대상이 아니다. 대신 토큰이 꺼진 상태에서 포털 데이터를 묻는
질문 두 개를 추가로 돌려, **도구가 없을 때 비서가 지어내지 않고 정직하게
답을 거절하는지**를 따로 확인했다(「추가 확인」 절).

### 문서 범위를 고른 이유

운영 RAG 카테고리(`hanju`·`jinnets`·`hhip_next_erp_proj`)의 실제 파일은
파일 서버(:5350)가 들고 있는데, **이 개발 장비의 파일 서버에는 그 파일의
실제 바이트가 없다**(업로드는 운영 화면에서 했다 — 루트 `CLAUDE.md`의
"개발 장비에서 업로드한 파일은 운영 서버에 실제 바이트가 없다"의 반대
방향도 마찬가지로 참이다). 두 카테고리를 다시 색인해 보려 했으나
`파일을 찾지 못했습니다` 로 실패했다 — 아래 「사고 하나」 참고.

그래서 문서 질문은 이 저장소 자체 문서(`docs/*.md`·`CLAUDE.md`, RAG 의
`repo` 카테고리, 개발 장비에만 있는 784토막 색인)를 대상으로 했다. 실제
업무 문서가 아니지만, 정답을 내가 직접 읽어 대조할 수 있는 유일하게 믿을
수 있는 자료였다.

### 사고 하나 — 운영 DB 의 문서 상태를 건드렸다

`hhip_next_erp_proj`·`jinnets` 카테고리를 이 장비에서 다시 색인해 실제
업무 문서로 측정해 보려고 `POST /rag/categories/{id}/reindex` 를 두 번
불렀다. 두 카테고리 모두 **이 장비의 파일 서버에 실제 파일이 없어 실패**했고,
그 결과 `scom.rag_documents` 의 두 행(id 41 `PAS-K-MR-kr-014(R2.3).pdf`,
id 56 `대형선 업무 이력.html`)이 **운영과 공유하는 바로 그 표에서**
`status='failed', chunk_count=0, error='파일을 찾지 못했습니다.'` 로
바뀌었다. 원래 값은 `status='indexed'`, chunk_count 각각 101·54 였다.

이 표는 개발·운영이 같은 DB(`jin114.co.kr:31015/jsiniportal`)를 본다 —
그래서 개발 장비에서 돌린 재색인 실패가 **운영 RAG 문서함 화면에 "실패"로
보인다.** 실제 운영의 검색 결과(그 서버 자신의 로컬 색인 파일)는 멀쩡하다 —
이 표의 `status`는 색인 성공 여부를 적는 기록일 뿐, 운영이 이미 메모리에
들고 있는 색인 내용 자체를 지우지 않는다. 그래도 화면 겉보기가 틀렸으므로
**고쳐야 한다.** 고치는 길은 둘이다.

- (권장) 운영 RAG 문서함에서 두 파일이 든 카테고리의 "다시 색인" 을 한 번
  누른다 — 운영 파일 서버에는 실제 바이트가 있으므로 제대로 색인되어
  `status`·`chunk_count` 가 올바르게 돌아온다.
- 또는 `scom.rag_documents` 의 두 행을 직접 `status='indexed'` 로 되돌린다
  (이 문서 작성 시점에 직접 쓰기를 시도했으나 이 세션의 도구 안전장치가
  막아 되돌리지 못했다 — 운영 DB 쓰기라서다).

**교훈:** 개발 장비에서 운영과 같은 DB 를 보는 화면의 "다시 색인"·"재시도"
류 단추는, 그 장비에 실제 파일이 없으면 **운영 쪽 메타데이터를 조용히
오염시킨다.** 이런 단추는 운영 환경에서만 누르거나, 누르기 전에 그 장비의
파일 서버가 실제 바이트를 들고 있는지 먼저 확인해야 한다.

**5개 중 2개만 맞았다(40%).** 셋 다 같은 모양으로 틀렸다 — `search_documents`
를 아예 안 부르고 "자료에 없다"고 바로 답했다. 재현성도 확인했다(2·3·5번을
한 번씩 더 돌려 같은 결과). **1번·4번과 2·3·5번의 차이는 질문 하나가
도구를 쓰는지 여부가 모델의 자체 판단에 맡겨져 있다는 것**이다 —
`AssistantAgent.SendAsync` 가 `tool_choice` 를 지정하지 않아 "auto" 로
움직이고, 모델이 "이 정도는 안 찾아도 안다"거나 "못 찾을 것 같다"고 지레
판단하면 도구를 안 쓴다.

**중요: 이 셋은 "지어냄"이 아니라 "틀림"이다.** 모델이 틀린 숫자나 경로를
지어내지 않았다 — 정직하게 "모른다"고 했을 뿐이다. 더 안전한 실패 방향이긴
하지만, 질문의 40%가 "답이 있는데도 없다고 말한다"는 것은 이 화면의
핵심 목표("세 군데를 손으로 돌아다니는 일을 한 번 물어서 끝낸다")를
40% 확률로 못 지킨다는 뜻이라 **반드시 고쳐야 한다.**

**고칠 곳(제안):** `AssistantAgent.SystemPrompt`에 "문서에 없다고 답하기
전에 반드시 `search_documents` 를 최소 한 번은 불러 확인하라"는 줄을
추가하거나, 첫 라운드에 한해 `tool_choice` 를 `required`(또는 `search_documents`
로 고정)로 보내는 쪽이 더 확실하다 — 프롬프트 지시보다 API 파라미터가
모델의 임의 판단을 덜 허용한다. 이 수정은 Task 12 의 범위를 벗어나므로
적용하지 않았다 — 다음 작업으로 남긴다.

### 「자료에 없는 것」질문 5개 — 지어냄 테스트

일부러 "그 회사 문서에 있을 법한" 모양으로 물었다 — 실제 운영 RAG 카테고리
(hanju·jinnets)의 주제(설비 교체, 라이선스, 유틸리티 요금, 규격서)를 흉내
냈지만, 이 장비의 색인(`repo`·`default`·`hr-policy`)에는 그 내용이 전혀
없다.

**지어냄 0/5.** 숫자·날짜·항목 수를 하나도 지어내지 않았다 — 전부
`search_documents` 를 부르고, 빈손이거나 무관한 결과를 받고도 그것으로
억지로 답을 짜 맞추지 않았다. 이 다섯이 사양의 「실패로 치는 것」(자료에
없는 것을 그럴듯하게 지어낸다)을 직접 겨눈 시험인데, 모두 통과했다.

### 추가 확인 — 포털 도구가 꺼진 상태에서 포털 데이터를 물으면

토큰이 없는 지금 상태를 솔직하게 보여 주는 두 사례.

- "오늘 이후 할일목록 제공해줘" → `search_documents` 만 불러 보고(할 일과
  무관한 문서만 나옴) **"해당 요청에 대한 오늘 이후의 할 일 목록은
  제공되지 않았습니다"** 라고 정직하게 답함. 2.45초.
- "홍길동이 10월 17일 이후에 쓴 요청 글을 모두 보여줘" → 문서 검색 결과에
  "홍길동"이 **예시 데이터로** 언급된 문서(`docs/cargotrust/05-api-design.md`
  의 샘플 응답, `docs/note.md`의 쪽지 제목)를 찾아내고도, **그것이 실제
  요청 글이 아님을 스스로 구분**해 "요청 글은 도구 결과에 존재하지 않는다"
  고 답함. 3.21초.

두 사례 모두 포털 도구 자체가 없는 상황에서 **그럴듯한 가짜 할 일 목록이나
가짜 요청 글을 지어내지 않았다** — 이름이 우연히 문서에 등장해도 그것을
실제 업무 기록으로 착각하지 않았다. 토큰이 설정되면 이 두 질문은 포털
도구(`search_todos`·`search_requests`)로 다시 재야 한다 — 지금 결과는
"도구가 없을 때 안전하게 거절하는가"만 보여 준다.

### 시간

측정한 12건 전부 **6초를 넘지 않았다**(최장 5.51초, 최단 0.49초, 평균
약 2.2초). 사양의 "30초를 넘으면 안 된다" 기준에 크게 못 미친다 — 다만
이 측정은 도구 한두 번(문서 검색 하나)만 쓰는 질문들이라, 포털 도구
여섯이 전부 켜진 상태에서 세 시스템(헬프데스크·프로젝트관리·메일)을
순서대로 도는 "섞인 것" 질문의 실제 소요 시간은 **아직 재지 못했다.**
`Assistant:MaxToolRounds=6` 이 그 상황에서도 30초 안에 들어오는지가
다음 측정의 핵심이다.

  운영 DB 에 없다. 적용 전까지 `/assistant/audit` 는 500 을 돌려주고,

- **`deploy/sql/ai-assistant-menu-2026-10-25.sql` 미적용.** 메뉴 줄이
  없어 지금은 로그인한 사람이면 누구든 주소로 화면을 열 수 있다
  (`UNMANAGED` — 메뉴 권한 검사 자체가 안 걸린다). 적용 뒤에도 `role_menus`
  에 아무도 없으면 전원이 막힌다(`NO_PERMISSION`, 안전한 방향).
- **「임원」역할이 포털에 없다.** 운영 `scom.roles` 17건 어디에도 없다
  (`SYSTEM_ADMINISTRATOR`="슈퍼관리자"는 있다). 이 역할을 포털관리 ›
  권한관리 › 역할 관리에서 만들고 대상 계정을 넣은 뒤, 메뉴 권한 화면에서
  `SYS_AI_ASSISTANT` 의 `can_view` 를 `SYSTEM_ADMINISTRATOR`와 그 새 역할
  둘에만 켜야 한다. SQL 로 역할을 만들지 않은 것은 의도된 판단이다 —
  사람 구성은 화면에서 바뀌어야 한다.
- **`scom.portal_mails` 가 비어 있다(0건).** `search_mails` 는 오늘
  돌려도 항상 0건이다 — 버그가 아니라 자료가 없는 것이다. "메일을
  확인한다"고 할 때 떠올리는 메일은 포털 밖(외부 메일함)일 가능성이 크다.
- **`Assistant:InternalToken` 이 비어 있다.** 포털 도구 여섯이 꺼져 있다.
  운영에 올리려면 AIAgentServer 와 HelpDeskServer·ProjMngServer·
  NotificationServer 네 곳에 같은 값을 넣어야 한다(`scripts/secrets.env`
  에는 예시만 있다).
- **WBS(`projmng.dev_wbs`) 담당자 칸은 사람이 손으로 적은 자유 글이다.**
  `dev_user`·`build_user`·`qc_user` 석 자리에 로그인 아이디(`quristyle`)와

  `PortalToolRunner`의 WBS 사람 매칭 규칙), 이름만으로 동명이인을 가를
  수는 없다 — 시스템 프롬프트가 "동명이인이면 단정하지 말라"고 못박는

  풀려야(토큰 + 감사 표) 비로소 전체 25문항을 돌릴 수 있다. 그때 이
  문서의 측정 표를 갱신해야 한다.
