# 권한관리 밖의 화면 — 기본 차단과 차단 접근기록

**포털관리 › 상태관리 › 「차단 접근기록」**(`/admin/status/blocked-access`)에서 본다.
메뉴 권한은 **시스템관리자(`SYSTEM_ADMINISTRATOR`)에게만** 주어져 있다.

## 무엇이 뚫려 있었나 (2026-10-13)

계정 관리 권한이 **없는** 사람이 주소창에

```
/admin/system/account/jupark/app
```

을 치면 **열렸다.** 그 화면은 「계정 앱 현황」이고, 남의 기기·구독·발송 기록을
보여 준다.

까닭은 단순하다. **판정의 열쇠가 DB 메뉴의 `path` 였다.** 메뉴에 줄이 없는 화면은
따질 열쇠가 없었고, 레이아웃은 그런 화면을 막지 않고 지나쳤다 —

> 메뉴에 없는 화면(탭으로 여는 상세 화면 · 진단 화면)은 권한표에 줄이 없으므로
> 여기서 막지 않는다. 그런 화면은 `[Authorize]` 와 서버가 지킨다.
> — `MainLayout.Track` 의 옛 머리말

`[Authorize]` 는 **로그인했는가**만 본다. 그래서 로그인한 사람이면 누구나 열렸다.
상세 화면은 대개 목록에서 줄을 골라야 들어가지므로 그 길이 오래 안 보였는데,
**주소를 직접 치면 목록을 안 거친다.**

이런 화면이 코드에 **열한 개** 있었다(상세 화면 셋 · 가입신청 · 계정 앱 현황 ·
뉴스속보 · 길잡이 넷 · 부품 확인 하나).

## 권장하는 방법 — **화면이 자기 부모를 가리킨다**

고치는 길이 둘인데 하나만 옳다.

| | 방법 | 왜 아닌가 / 왜 이것인가 |
|---|---|---|
| | 그런 화면마다 **DB 메뉴를 만든다** | 사이드바에 세울 수 없는 것을 메뉴 표에 억지로 넣는 일이다. 「`/admin/system/account/{누구}/app`」 은 **사람을 고르기 전에는 누구의 것인지 없는 주소**라 메뉴가 될 수 없다. 메뉴가 늘수록 권한 화면이 읽기 어려워지고, 상세 화면마다 권한을 따로 켜야 해서 **목록은 보이는데 상세는 안 열리는** 새 어긋남이 생긴다 |
| ✅ | 화면이 **부모 메뉴를 가리킨다** | 「목록을 열 수 있는 사람만 그 목록의 상세를 연다」는 뜻이고, 권한 화면에서는 줄 하나가 그대로 유지된다. 코드가 선언하므로 **DB 를 안 고치고** 배포 한 번으로 끝난다 |

```razor
@page "/admin/system/account/{LoginId}/app"
@attribute [RouteKey("admin.system.account.app")]
@attribute [ScreenAccess("admin.system.account")]   @* 계정 관리의 권한을 따른다 *@
```

메뉴에 올릴 수 **없는** 자리(로그인·오류·첫 화면)는 까닭을 적어 열어 둔다.

```razor
@attribute [ScreenAccess(ScreenAccessKind.Open, Reason = "첫 화면이다. 로그인하면 반드시 여기로 떨어진다.")]
```

## 기본이 차단이다

판정하는 자리는 하나다(`JSini.Web.Components/Security/ScreenAccess.cs`).
가리킬 메뉴를 **셋까지 찾아보고**, 못 찾으면 막는다.

```
 ① 지금 주소로 메뉴를 찾는다        사이드바가 건 링크와 같은 값이면 그 메뉴다
 ② 화면이 선언한 RouteKey 로 찾는다  주소가 메뉴의 path 와 어긋나 있어도 열쇠는 맞는다
 ③ [ScreenAccess] 가 가리킨 부모로   메뉴에 올릴 수 없는 상세 화면
 ───────────────────────────────────────────────────────────────
 셋 다 빈손 → 막는다 (UNMANAGED)
 찾았는데 CanView 가 거짓 → 막는다 (NO_PERMISSION)
```

**틀리는 방향을 「안 열리는」 쪽으로 두었다.** 반대로 두면 새로 만든 화면이
아무에게나 열리는데, 그 사실이 아무 데도 안 남아 영영 안 드러난다.

### 아직 모르는 동안에는 막지 않는다

권한표와 메뉴는 부트스트랩이 늦게 채운다. 그 사이를 「권한 없음」으로 다루면
새로고침할 때마다 차단 안내가 한 번 스치고, **그 한 번이 기록에도 쌓여 진짜 막힌
줄이 묻힌다.** 실제 통제는 서버가 계속 하므로 안전 범위 안이다
(`IPermissionContext.IsLoaded` 와 같은 판단이다).

> 그래서 **권한표가 도착한 뒤 다시 따져야 한다.** `ScreenAccess` 가
> `MenuProvider.MenusChanged` 를 구독하고 있고, 그 줄이 없으면 첫 통과가 그대로
> 굳어 **기본 차단이 사실상 안 돈다.**

### 막는 자리 — 라우터 바로 앞

`Routes.razor` 의 `ScreenGate` 가 `AuthorizeRouteView` 를 감싼다. 여기여야 하는
까닭이 둘이다.

- 라우터가 고른 **화면 클래스**(`RouteData.PageType`)를 아는 자리가 여기뿐이다.
  주소에는 매개변수가 들어 있어 주소만으로는 어느 화면인지 다시 맞춰 봐야 하는데,
  그 짝맞추기는 라우터가 이미 한 일이다.
- **레이아웃보다 위**다. `BareLayout` 을 쓰는 화면도 이 문을 지난다.

막혔을 때 업무 레이아웃을 그대로 씌운다 — 맨 화면으로 떨어뜨리면 사이드바가 사라져
돌아갈 길이 없고, 그 모양이 「로그아웃됐다」로 읽힌다.

### 포괄 라우트는 열어 둔다

`_Pending.razor`(`@page "/admin/{*rest}"`)는 화면이 아니라 **「아직 화면이 없다」는
안내**다. 보여 줄 자료가 없으므로 막을 것도 없고, 막으면 **오타 주소가 전부 차단
기록으로 쌓여 진짜 막힌 줄이 묻힌다.** 포괄이라도 자료를 보여 주는 화면(셸의
`Embedded` — `EMBEDDED` 메뉴의 바깥 화면을 띄운다)은 스스로
`[ScreenAccess(ScreenAccessKind.Menu)]` 를 적어 이 기본값을 덮는다.

### 묶음(CATALOG)과 외부 링크는 따지지 않는다

묶음에는 자기 화면이 없다. 길잡이 화면(`GroupLinks`)이 그리는 것은 링크뿐이고
**그 링크들은 각자 다시 이 문을 지난다.** 외부 링크는 앱 라우트가 아니라 권한표에
줄이 없다 — 막으면 틀리는 방향이 「멀쩡한 메뉴가 안 열리는」 쪽이다.

## 기록 — 누가 어떤 주소를 열려 했나

```
 브라우저            포털 셸(:5557)           게이트웨이        AuthServer
    │                     │                       │                │
    │ 주소를 친다         │                       │                │
    ├────────────────────▶│                       │                │
    │              ① ScreenGate 가 막고           │                │
    │              ② BlockedAccessRecorder.Record │                │
    │                 (기다리지 않는다)            │                │
    │                     ├──────────────────────▶│───────────────▶│
    │                     │  POST /api/auth/blocked-access  ③ 한 줄 INSERT
    │  차단 안내가 뜬다 ◀─┤                       │      scom.blocked_access_logs
```

**막는 일과 적는 일은 갈라져 있다.** 적는 쪽이 통째로 죽어도 막는 쪽은 돈다 —
기록을 못 적어서 차단이 풀리면 본말이 뒤집힌다.

### 왜 서버 로그로는 안 되나

포털은 **한 회로 안에서 라우팅만 바뀐다.** 주소를 쳐서 들어와도 HTTP 요청이 한
건도 나가지 않으므로 nginx 접근 로그에는 로그인 한 번과 WebSocket 하나뿐이다.
`menu_usage_logs` 가 있는 까닭과 같다([menu-usage.md](menu-usage.md)).

### 프리렌더에서는 적지 않는다 — 막기는 한다

첫 그림은 정적 SSR 요청에서 한 번, 회로가 붙은 뒤 또 한 번 그려진다. 그 둘은
**범위가 달라 각자 제 기록기를 갖고**, 시각으로 가려내는 규칙이 서로를 못 봐서 한
번 막힌 것이 두 줄로 남는다. **막는 것은 프리렌더에서도 한다** — 적는 것만 미룬다.

### 같은 차단을 두 번 적지 않는다

문은 한 번 들어올 때 여러 번 다시 그려진다(늦게 도착한 권한표·메뉴가 판정을 다시
돌린다). 그렇다고 「같은 주소면 안 적는다」로 두면 **같은 주소를 다시 두드린 것**이
영영 안 적히는데, 그것이야말로 보고 싶은 줄이다. 가르는 기준은 **시간**이고
2초다(`BlockedAccessRecorder.DedupeWindow` — 메뉴 사용기록과 같은 값).

### 넣는 길에는 권한을 묻지 않는다

**적히는 일이 권한이 없다는 사실 그 자체다.** 여기서 또 메뉴 권한을 따지면 권한이
가장 적은 사람의 줄이 먼저 빠지는데, 그 줄이야말로 이 표가 보고 싶은 것이다.
적히는 이름은 몸체가 아니라 게이트웨이가 붙여 준 `X-User-Id` 라 남의 이름으로
쌓을 수는 없다.

`scom.blocked_access_logs` — DDL 과 까닭은
[deploy/sql/blocked-access-2026-10-13.sql](../deploy/sql/blocked-access-2026-10-13.sql).
EF 마이그레이션 `20261012170121_AddBlockedAccessLogs` 를 그대로 뽑은 것이다.

| 칸 | 무엇 |
|---|---|
| `occurred_at` | 막힌 때. **UTC 다** |
| `user_id` | 로그인 아이디 |
| `href` | **실제로 연 주소.** 매개변수가 들어 있다 — 「누구의 것을 보려 했나」가 이 칸에만 남는다 |
| `route_key` · `screen_type` | 화면의 열쇠와 클래스 이름. 「어느 파일이냐」의 답 |
| `menu_path` | 권한을 따진 메뉴 경로. 메뉴를 못 찾았으면 비어 있다 |
| `reason` | `NO_PERMISSION` · `UNMANAGED` (아래) |
| `from_path` | 직전에 보던 화면 |
| `client_ip` | 접속 주소. **위조할 수 있어 보여 주기 전용이다** |

한 해만 들고 있다(`BlockedAccessService.RetentionDays` = 365). `menu_usage_logs` 와
**같은 값**이어야 한다 — 나란히 놓고 보는 표라 보관 기간이 다르면 어느 날부터
한쪽만 남아 대조가 조용히 깨진다.

### `menu_usage_logs` 와 한 표로 섞지 않는다

저쪽은 **열린** 화면을 적는다. 섞으면 「누가 포털을 많이 쓰나」를 묻는 조회 넷이
**막힌 줄까지 함께 세게** 되고, 그러면 열람 수가 실제보다 많아진다. 보는 사람도
다르다 — 저쪽은 운영 자료고 이쪽은 **점검 자료**다.

## 화면 — 보기 셋

| 보기 | 답하는 물음 | API |
|---|---|---|
| 화면별 | **어떤 화면이 권한관리 밖인가** — 이 표가 있는 까닭 그 자체다 | `GET /api/auth/blocked-access/by-screen` |
| 사용자별 | 누가 자꾸 막히나 | `.../by-user` |
| 기록 | 누가 **어떤 주소**를 언제 열려 했나 | `GET /api/auth/blocked-access` |

화면별 표에서 줄을 오른쪽 클릭하면 「이 화면의 기록」으로 간다.

### 까닭 둘을 가르는 것이 요점이다 — **할 일이 다르다**

| 까닭 | 무슨 일인가 | 할 일 |
|---|---|---|
| **권한 없음**(`NO_PERMISSION`) | 메뉴는 있는데 그 역할에 열람이 꺼져 있다 | 메뉴 권한 화면(`/admin/auth/menu-role`)에서 체크 하나 |
| **관리 밖**(`UNMANAGED`) | 가리킬 메뉴가 아예 없다 | 메뉴로 등록하거나, 화면이 `[ScreenAccess]` 로 부모를 가리켜야 한다 |

뒤엣것은 **권한을 아무리 줘도 안 열린다.** 한 칸에 뭉뚱그리면 관리자가 권한을 주고
나서 「줬는데 왜 안 되지」로 되돌아온다. 그래서 타일 하나가 「관리 밖 화면」의 수를
따로 세고, 표에서도 그쪽만 눈에 띄게 칠한다 — **사람이 손봐야 하는 수**다.

### 권한 — 판정이 한 곳이다

게이트웨이의 `auth-route` 는 `/api/auth/**` 를 통째로 **익명**으로 열어 둔다
(로그인이 그 길로 간다). 그래서 **보는 길은 서버가 스스로 막는다**
(`AuthServer/Services/MenuViewAccess.cs`) — 이 표에서는 「어느 화면이 어떻게
뚫려 있나」가 사실상 공격 지도다. 막는 판정은 역할 이름을 코드에 적는 것이 아니라
사이드바와 같은 표(`scom.role_menus`)에 묻는다. 메뉴 권한 화면에서 역할을 더하면
조회도 그 순간부터 따라간다.

## 빌드가 막는 것

`web/tests/JSini.Web.Architecture.Tests/ScreenAccessTests.cs` 다섯.

1. 모든 화면이 권한의 출처를 갖는다
2. `[ScreenAccess("부모")]` 의 부모가 **저장소에 실제로 있다** (오타 하나면 영영 막힌다)
3. 자기 자신을 가리키지 않는다
4. `Open` 으로 열어 두었으면 **까닭을 적는다**
5. **셸의 화면은 반드시 신고한다** — `RouteKey` 가 없어 신고가 빠지면 로그인한
   사람에게 전부 막힌다(「로그아웃하면 로그인 화면이 뜨는데 로그인하면 안 뜬다」)

**DB 를 볼 수 없으므로 「이 열쇠의 메뉴가 실제로 있나」는 못 따진다.** 그건 운영에서
이 화면의 `UNMANAGED` 줄이 말해 준다.

## 메뉴에 없는 화면의 권한을 주려면

**사용자에게 메뉴를 바로 매는 표는 없다.** 권한은 언제나 역할 × 메뉴
(`scom.role_menus`)이고, 사람은 역할에 들어가서 받는다(`role_accounts` ·
`role_departments` · `role_companies` — 역할 관리의 「지정 사용자」 탭).
그러니 「이 사람에게」는 「이 사람이 든 역할에」이거나 「이 사람만 든 역할을
하나 만들어서」다.

메뉴에 없는 화면은 `[ScreenAccess]` 가 가리킨 **부모 메뉴의 열람 권한**을 따른다.
그래서 길이 셋이다.

| | 방법 | 고치는 곳 | 따라오는 것 |
|---|---|---|---|
| ① | 부모 메뉴의 열람을 역할에 켠다 | 메뉴 권한(`/admin/auth/menu-role`)에서 체크 하나 | 그 역할의 사이드바에 **부모 메뉴(목록)도 함께 선다** |
| ② | 상세 화면만 따로 숨은 메뉴로 올린다 | 메뉴 관리에서 메뉴 하나(`hide_in_menu` 켬, `route_key` = 화면의 `RouteKey`) + 메뉴 권한 | 그 열쇠의 메뉴가 생기는 순간 **부모 대신 그것이 판정한다**(`Resolve` 의 ② 가 ③ 보다 먼저다). 지금 부모로 열던 역할에도 같이 켜 두지 않으면 **그 사람들이 막힌다** |
| ③ | 화면이 가리키는 부모를 바꾼다 | 코드의 `[ScreenAccess("…")]` 와 배포 | 부모는 지금 **하나만** 적을 수 있다 |

`menu_path` 칸이 비어 있지 않은 `NO_PERMISSION` 줄은 ① 이나 ② 로 풀리고,
`UNMANAGED` 는 ② 나 ③ 이어야 풀린다.

### 보기 — `/projmng/ai/task/{번호}` (AI 지시 상세)

`[ScreenAccess("projmng.ai.tasks")]` 라 **지시 목록(`PM_AI_TASKS`)을 열 수 있는
역할**만 연다 — 지금은 `SYSTEM_ADMINISTRATOR` · `ADMINISTRATOR` · `PROJMNG_ADMIN`.

받은 역할(`DEVELOPMENT_TEST1`)의 사람은 카드를 누를 때마다 막힌다 — 차단 기록의
`from_path` 가 `/projmng/ai/ask` 인 줄이 그것이다. 서버(`GET /api/ai-tasks/{번호}`)는
로그인만 보므로 막는 것은 이 문 하나다.

- 지시 목록까지 보여 줘도 되면 ① — `DEVELOPMENT_TEST1` 에 `PM_AI_TASKS` 열람.
- 상세만 주려면 ② — 숨은 메뉴의 `route_key` 를 `projmng.ai.task-view` 로 두고,
  위 세 역할과 `DEVELOPMENT_TEST1` 에 열람을 켠다.
