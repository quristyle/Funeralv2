# 푸시가 한꺼번에 몰려 오거나 늦게 오는 까닭과 막는 법

> **증상 1** — PWA 로 알림을 받고 있는데, 브라우저를 오래 안 쓰다가 켜면
> 그동안의 알림이 **한꺼번에** 쏟아진다. → 이 문서 앞쪽(수명·겹침)
>
> **증상 2** — 알림이 **예전보다 늦게** 온다. → [보내는 쪽이 늦었다](#보내는-쪽이-늦었다--알림이-ai-요약을-기다리고-서-있었다)

## 고장이 아니다 — 웹푸시가 원래 그렇게 생겼다

서버가 브라우저로 알림을 바로 꽂는 길은 없다. 우리가 보내는 곳은 **브라우저
제조사의 푸시 서비스**이고(크롬·엣지·삼성인터넷이면 FCM, 파이어폭스면 Mozilla
autopush), 그쪽이 **브라우저와의 연결이 살아날 때까지 들고 기다린다.**

```
NotificationServer ──▶ 푸시 서비스(FCM …) ──▶ 브라우저 ──▶ 서비스워커
                          └ 여기서 줄을 선다 ┘
```

그래서 사람이 보는 「알림이 온 시각」은 **우리가 보낸 시각이 아니라 배달된
시각**이다. 며칠 닫아 둔 브라우저를 여는 순간 그 줄이 통째로 흘러나온다.

절전도 같은 결과를 만든다. 안드로이드는 화면이 꺼진 기기를 Doze 에 넣고 그
안에서는 **긴급도가 낮은 푸시를 모아 두었다가** 기기가 깰 때 함께 내보낸다.

## 줄을 못 서게 하는 손잡이는 규격(RFC 8030)에 있다

| 헤더 | 하는 일 |
|---|---|
| `TTL` | 이 시간이 지나면 푸시 서비스가 **버린다**(배달하지 않는다) |
| `Topic` | 같은 값끼리 **줄 안에서 앞의 것을 밀어낸다**. 스무 건이 밀려 있어도 최신 하나만 남는다 |
| `Urgency` | `high` 면 절전 중에도 미루지 않는다 |

**우리가 이 셋을 하나도 안 보내고 있었다.** 그러면 `WebPushClient` 의 기본
`TTL` 인 **28일**이 나간다 — 사실상 「영원히 들고 있어라」다.

## 무엇을 고쳤나

### 1. 서버가 수명을 준다 (`PushDeliveryOptions`)

`appsettings.json` 의 `Push` 구역이고, 보내는 쪽이 따로 안 정하면 **6시간**이다.

```json
"Push": {
  "DefaultTtlSeconds": 21600,
  "MaxTtlSeconds": 86400,
  "Urgency": "high"
}
```

알림마다 더 짧게 줄 수 있다(`PushMessageDto.TtlSeconds`).

| 알림 | 수명 | 왜 |
|---|---|---|
| 시험 알림 | **5분** | 「눌렀는데 오나」를 보려고 보낸다. 30분 뒤에 오면 시험의 뜻이 없다 |
| 기상 실황·특보 | 1시간 | 지나면 알릴 값이 없다 |
| 배포 알림 | 1시간 | 지난 배포는 배포 현황 화면에 다 있다 |
| 새 기기 구독 | 1시간 | 알림함에서 봐도 되는 소식이다 |
| 내 위치 날씨 | 3시간 | 정해진 시각에 한 번 보내는 것이라 그 시간대를 넘기면 버린다 |
| AI 작업 끝남 (`[완료] 제목`) | 2시간 | **이 포털에서 가장 잦다**(아래 실측). 끝난 작업은 작업 화면에 그대로 있다 |
| 쪽지 · 그 밖 | 6시간(기본) | 아침 쪽지를 점심에 열어도 받아야 하지만 어제 것까지는 아니다 |

#### 실제로 얼마나 밀리나 (운영 DB, 2026-09-24)

`scom.push_send_logs` 를 세어 본 값이다.

| | |
|---|---|
| 구독한 기기 | 4대 — **전부 구글(FCM)** |
| 최근 7일 성공 발송 | **254건**(한 사람 기준) |
| 그중 「AI 작업 끝남」 | **241건** |

고치기 전에는 그 254건이 **28일짜리 수명**으로 나가고 있었다. 일주일 브라우저를
안 켠 사람이 다시 켜면 **그만큼이 한꺼번에 내려온다** — 신고된 증상 그대로다.

### 날씨 푸시는 날씨 종류에 맞는 아이콘을 쓴다

LifeEnvServer 가 날씨 상태를 `WeatherIconKinds` 로 분류해 푸시 요청에 싣고,
NotificationServer 는 허용된 분류만 `/weather-icons/{종류}.svg` 로 바꿔 전달한다.
기준 알림은 측정 항목, 특보는 특보 종류, 내 위치 날씨는 현재 상태를 기준으로
맑음·구름·비·눈·진눈깨비·천둥번개·바람·기온·습도·특보 아이콘을 고른다.
아이콘 파일은 포털 셸의 `wwwroot/weather-icons/` 에 있어 앱 푸시에서 같은 포털
오리진으로 불러온다. 분류를 알 수 없는 값은 구름 아이콘으로 처리한다.

**버려도 되는 까닭**은 포털에 「내 알림함」(`/admin/push/history`)이 있기
때문이다. 푸시는 **지금 알려 주는 길**일 뿐이고 기록은 알림함에 남는다.

### 2. 같은 종류는 줄에서 겹친다 (`Topic`)

`PushMessageDto.Topic` 이다. 비우면 `Tag` 를 대신 쓴다.

**`Tag` 와 하는 일이 다르다.**

| | 언제 | 무엇을 |
|---|---|---|
| `Tag` | 브라우저가 **이미 받은** 뒤 | 알림창을 겹쳐 그린다 |
| `Topic` | 브라우저가 **꺼져 있는 동안** | 푸시 서비스의 대기줄에서 하나로 줄인다 |

그래서 둘을 따로 둔다 — 배포 알림처럼 **켜져 있을 때는 각각 보이는 편이 낫고
밀려 있을 때는 마지막 하나면 되는** 알림이 있다.

규격이 글자를 가린다(base64url 32자 이내). 맞지 않는 값은 `PushSender` 가
SHA-256 으로 접는다. **글자만 걸러 내지 않는다** — 구분 기호를 떼면 서로 다른
태그가 같은 값이 되어 남의 알림을 밀어내는 사고가 난다.

### 3. 늦게 도착한 것은 서비스워커가 한 줄로 묶는다

`TTL` 은 **부탁이지 보장이 아니다.** 기기가 절전에서 깰 때 시효가 지난 것이
섞여 오는 일이 남는다. 그래서 페이로드에 `sentAt` · `expiresAt` 을 실어 보내고
(`PushSender.BuildPayload`), `push-sw.js` 가 시효 지난 것을 낱낱이 띄우지 않고
**「지난 알림 N건」 하나로 묶는다.** 누르면 알림함으로 간다.

**버리지 않고 묶는 까닭**: push 이벤트를 받고 알림을 하나도 안 띄우면 크롬이
대신 "이 사이트가 백그라운드에서 갱신되었습니다" 를 띄우고, 그것이 반복되면
구독 자체를 끊는다.

기기 시계가 서버보다 앞설 수 있어 2분 여유를 둔다. 그것이 없으면 **방금 온
알림이 시계 차이만큼 「지난 것」으로 접힌다.**

## 그래도 남는 것

- **푸시 서비스가 `Topic` 을 반드시 지킨다는 보장은 없다.** 규격상 지원이
  권장이라, 안 지키는 구현에서는 3번 그물이 받는다.
- **즉시 배달은 여전히 못 만든다.** 브라우저가 죽어 있으면 어떤 헤더로도 깨울
  수 없다. 고칠 수 있는 것은 **깨어난 뒤에 몇 개를 보느냐**뿐이다.
- iOS 는 **홈 화면에 설치한 앱에서만** 웹푸시를 준다. 사파리 탭으로 열어 둔
  것은 이 문서와 무관하게 아예 안 온다.

## 보내는 쪽이 늦었다 — 알림이 AI 요약을 기다리고 서 있었다

위의 것은 **푸시 서비스가 들고 있는 시간**이다. 그런데 2026-09-25 에 「예전보다
늦다」는 말을 듣고 재 보니, 늦는 자리가 하나 더 있었다 — **우리가 보내기까지가
늦었다.**

### 얼마나 늦었나 (운영 실측, 2026-09-25)

`scom.push_send_logs.sent_at`(보낸 시각)과 `projmng.ai_task_run.finished_at`
(작업이 끝난 시각)을 맞대어 본 값이다. 이 포털에서 가장 잦은 알림
(「AI 작업 끝남」) 128건.

| 날짜 | 건수 | 중앙 | 평균 | 최대 |
|---|---|---|---|---|
| 09-20 | 16 | 8.4초 | 9.8초 | 27.8초 |
| 09-21 | 32 | 13.2초 | 24.7초 | 115.6초 |
| 09-24 | 33 | 21.3초 | 35.7초 | **177.1초** |
| 09-25 | 39 | 11.1초 | 13.3초 | 47.5초 |

**기분 탓이 아니다.** 작업이 끝나고 알림이 나가기까지 보통 십수 초, 열에 하나는
45초 넘게 걸렸고 3분까지도 갔다.

### 까닭 — 순서가 뒤집혀 있었다

끝난 작업의 뒤처리가 이 순서였다(`ProjMngServer/Services/AiRunService.cs`).

```
완료 → 처리 요약(모델 호출) → 자동 제목(모델 호출) → 메일 · 앱푸시
                └─ 45초에서 끊고 두 번까지 ─┘   └ 한 번 더 ┘
```

**푸시가 모델 호출 뒤에 줄을 서 있었다.** 그런데 푸시에 실리는 것은
**상태와 제목뿐**이다 — 요약은 메일 본문에만 들어간다. 기다릴 까닭이 없었다.

> 이 문단의 전제는 2026-09-27 에 바뀌었다 — 이제는 푸시 본문에도 요약이
> 실린다. 아래 [알림 본문에 처리 요약을 싣는다](#알림-본문에-처리-요약을-싣는다-2026-09-27) 참고.

### 고친 것

```
완료 → 앱푸시 → 처리 요약 → 자동 제목 → 메일
```

- `AiTaskNotifier.SendAsync` 를 `SendPushAsync` · `SendMailAsync` 로 갈랐다.
  관문(받기 꺼짐·받는 사람 없음·`notify_when`)은 `LoadAsync` 하나로 모아 둔다 —
  갈래마다 따로 적으면 한쪽만 고쳐져 **「메일은 왔는데 푸시는 안 온다」**가 된다.
- `ai_task.notify_error` 는 걸음이 둘이 되었으므로 **첫 걸음만 비우고 나머지는
  잇는다**(`MarkAsync` 의 `reset`). 안 그러면 뒤엣것이 앞의 사유를 덮어
  「푸시는 실패했는데 메일은 성공」이 아무 데도 안 남는다.

**바뀌는 것 하나** — 푸시에 실리는 제목은 이제 **AI 가 다시 짓기 전의 것**이다.
사람이 적은 제목이거나 지시문 첫 제목 줄에서 뽑은 것이라
(`AiTaskService.NormalizeAsync`) 알림 한 줄로는 충분히 읽히고, 다시 지어진
제목은 누르고 들어간 화면과 목록에 있다.

## 알림 본문에 처리 요약을 싣는다 (2026-09-27)

위의 고침으로 푸시는 빨라졌는데, **무엇을 했는지는 알림에서 사라졌다.**
본문이 `[완료] 제목` 한 줄이라 받는 사람이 아는 것은 「끝났다」뿐이었고,
그것을 보려면 언제나 눌러 들어가야 했다. 「빠른 지시」로 시킨 건은 제목이
지시문 앞부분을 뜬 것이라 더했다 — **시킨 말이 그대로 되돌아올 뿐**이었다.

### 무엇이 어디에 실리나

| | 전 | 후 |
|---|---|---|
| 제목 줄 | `AI 작업 끝남` (붙박이) | `[완료] 작업 제목` |
| 본문 | `[완료] 작업 제목` | **처리 요약** — 한 문장 + 한 일 둘 + 확인할 것 하나 |

알림창에서 가장 크게 보이는 자리가 어느 건이든 똑같은 글자에 쓰이고 있었다.
그 자리를 「어느 건이 어떻게 됐나」에 내주고, 본문은 「무엇을 했나」에 쓴다.
본문에 들어가는 값은 **결과 메일의 「AI 의 답」 칸과 같은 것**이다
(`ai_task_run.summary_text`) — 두 곳에서 다르게 요약하면 어느 쪽이 맞는지
가릴 방법이 없다.

줄머리는 `·` 로 찍는다. 알림창은 줄바꿈을 살려 주지만 「내 알림함」의 카드는
본문을 `<p>` 하나에 담아 **줄바꿈이 공백으로 접히기** 때문이다.

### 요약을 기다리되 상한을 건다

```
완료 → 처리 요약(상한까지만 기다림) → 앱푸시 → 자동 제목 → 메일
```

요약은 모델 호출이라 기다리면 다시 느려진다. 그래서 **요약 하나만**,
`AiTasks:PushSummaryWaitSeconds`(기본 30초)까지만 기다린다.

- 상한 안에 오면 — 본문에 요약이 실리고, **제목 줄도 AI 가 다시 지은 것**이
  된다(`AiRunSummaryWriter` 가 요약 첫 문장으로 `ai_task.title` 을 고쳐 적는다).
- 상한을 넘기면 — 요약 없이 그냥 나간다. 그때 본문은 실패한 건이면 오류 한 줄,
  아니면 결과문 앞 두 줄(`Gist`)이 채운다. **제목만 있고 본문이 빈 알림은
  고장처럼 보인다.**
- 상한이 지나도 **요약 만들기를 끊지는 않는다.** 끊으면 푸시가 늦은 그 건의
  화면 요약 칸이 영영 빈다.
- `0` 을 주면 안 기다린다 — 옛 동작(상태·제목만 싣고 곧장)으로 돌리는 손잡이다.

**자동 제목 짓기(`AiTaskTitler`)는 여전히 안 기다린다.** 모델을 한 번 더 부르는
일인데 알림 한 줄에 보태는 것이 없다. 최악의 지연이 177초에서 상한값으로 내려온
것은 그래서다.

### 30초로 잡은 근거

요약은 모델 호출 한 번을 45초에서 끊고, 빈손이면 3초 쉬었다 한 번 더 부른다
(`AiTasks:SummaryAttempts`, 기본 2). 한 번에 오는 보통의 건은 십수 초면 적히므로
그 대부분이 30초 안에 들어오고, **다시 부르기까지 간 건은 기다려 봐야 한도에
걸린 건**이라 요약이 안 나올 공산이 크다 — 그 꼬리를 기다리는 값이 알림이
늦는 값보다 작다.

### 발송 자체도 연결을 물려 쓴다

`PushSender` 가 발송마다 `new WebPushClient()` 를 만들고 있었다. 인자 없이
만들면 **제 HttpClient 를 새로 만들어** 알림 한 통마다 푸시 서비스와 손잡기를
다시 한다. 이제 팩토리가 들고 있는 연결을 건넨다(`Program.cs` 의 `webpush`
클라이언트, 핸들러 수명 10분 — 기본 2분으로는 산발로 나가는 이 알림이 어차피
매번 새 연결로 시작한다).

**제한 시간 30초를 못 박은 것이 절반이다.** 기본값 100초는 발송이 기기마다
차례로 도는 자리라 너무 길다 — 한 대가 매달리면 그 뒤의 기기가 전부 그만큼
늦는다. 그렇다고 짧게 잡을 수도 없다: 이 값은 손잡기만이 아니라 **응답까지의
전체 왕복** 한도이고, 실측 왕복이 **기기당 중앙 0.62초 · 최대 7.97초**였다.
짧게 잡으면 잘 가던 발송이 「전달 실패」가 된다.

**끊겨도 기록은 남긴다.** 부르는 쪽이 제한 시간에 걸려 끊으면 예전에는
`SaveChangesAsync` 까지 함께 취소되어 **그 발송의 기록이 통째로 사라졌다** —
「몇 대까지 갔고 어디서 멈췄나」가 가장 알고 싶은 갈래인데 하필 그때 아무것도
안 남았다.

### 알림함에 남는 것은 「보낸 그대로」다

`push_send_logs.title` 에는 **발송 시점의 문자열**이 박힌다. 그래서 자동 제목인
건은 알림함에는 지시문에서 뽑은 제목이, 작업 화면에는 AI 가 지은 제목이 남아
서로 다르다. 고장이 아니라 **기록이 거짓말을 안 하는 것**이다 — 알림함은 「그때
무엇을 보냈나」를 답하는 자리다.
