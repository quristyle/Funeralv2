# 푸시가 한꺼번에 몰려 오는 까닭과 막는 법

> **증상** — PWA 로 알림을 받고 있는데, 브라우저를 오래 안 쓰다가 켜면
> 그동안의 알림이 **한꺼번에** 쏟아진다.

## 고장이 아니다 — 웹푸시가 원래 그렇게 생겼다

서버가 브라우저로 알림을 바로 꽂는 길은 없다. 우리가 보내는 곳은 **브라우저
제조사의 푸시 서비스**이고(크롬·엣지·삼성인터넷이면 FCM, 파이어폭스면 Mozilla
autopush), 그쪽이 **브라우저와의 연결이 살아날 때까지 들고 기다린다.**

```
NotificationServer ──▶ 푸시 서비스(FCM …) ──▶ 브라우저 ──▶ 서비스워커
                          └ 여기서 줄을 선다 ┘
```

그래서 사람이 보는 「알림이 온 시각」은 **우리가 보낸 시각이 아니라 배달된
시각**이다. 며칠 닫아 둔 브라우저를 여는 순간 그 줄이 통째로 흘러나온다.

절전도 같은 결과를 만든다. 안드로이드는 화면이 꺼진 기기를 Doze 에 넣고 그
안에서는 **긴급도가 낮은 푸시를 모아 두었다가** 기기가 깰 때 함께 내보낸다.

## 줄을 못 서게 하는 손잡이는 규격(RFC 8030)에 있다

| 헤더 | 하는 일 |
|---|---|
| `TTL` | 이 시간이 지나면 푸시 서비스가 **버린다**(배달하지 않는다) |
| `Topic` | 같은 값끼리 **줄 안에서 앞의 것을 밀어낸다**. 스무 건이 밀려 있어도 최신 하나만 남는다 |
| `Urgency` | `high` 면 절전 중에도 미루지 않는다 |

**우리가 이 셋을 하나도 안 보내고 있었다.** 그러면 `WebPushClient` 의 기본
`TTL` 인 **28일**이 나간다 — 사실상 「영원히 들고 있어라」다.

## 무엇을 고쳤나

### 1. 서버가 수명을 준다 (`PushDeliveryOptions`)

`appsettings.json` 의 `Push` 구역이고, 보내는 쪽이 따로 안 정하면 **6시간**이다.

```json
"Push": {
  "DefaultTtlSeconds": 21600,
  "MaxTtlSeconds": 86400,
  "Urgency": "high"
}
```

알림마다 더 짧게 줄 수 있다(`PushMessageDto.TtlSeconds`).

| 알림 | 수명 | 왜 |
|---|---|---|
| 시험 알림 | **5분** | 「눌렀는데 오나」를 보려고 보낸다. 30분 뒤에 오면 시험의 뜻이 없다 |
| 기상 실황·특보 | 1시간 | 지나면 알릴 값이 없다 |
| 배포 알림 | 1시간 | 지난 배포는 배포 현황 화면에 다 있다 |
| 새 기기 구독 | 1시간 | 알림함에서 봐도 되는 소식이다 |
| 내 위치 날씨 | 3시간 | 정해진 시각에 한 번 보내는 것이라 그 시간대를 넘기면 버린다 |
| AI 작업 끝남 | 2시간 | **이 포털에서 가장 잦다**(아래 실측). 끝난 작업은 작업 화면에 그대로 있다 |
| 쪽지 · 그 밖 | 6시간(기본) | 아침 쪽지를 점심에 열어도 받아야 하지만 어제 것까지는 아니다 |

#### 실제로 얼마나 밀리나 (운영 DB, 2026-09-24)

`scom.push_send_logs` 를 세어 본 값이다.

| | |
|---|---|
| 구독한 기기 | 4대 — **전부 구글(FCM)** |
| 최근 7일 성공 발송 | **254건**(한 사람 기준) |
| 그중 「AI 작업 끝남」 | **241건** |

고치기 전에는 그 254건이 **28일짜리 수명**으로 나가고 있었다. 일주일 브라우저를
안 켠 사람이 다시 켜면 **그만큼이 한꺼번에 내려온다** — 신고된 증상 그대로다.


**버려도 되는 까닭**은 포털에 「내 알림함」(`/admin/push/history`)이 있기
때문이다. 푸시는 **지금 알려 주는 길**일 뿐이고 기록은 알림함에 남는다.

### 2. 같은 종류는 줄에서 겹친다 (`Topic`)

`PushMessageDto.Topic` 이다. 비우면 `Tag` 를 대신 쓴다.

**`Tag` 와 하는 일이 다르다.**

| | 언제 | 무엇을 |
|---|---|---|
| `Tag` | 브라우저가 **이미 받은** 뒤 | 알림창을 겹쳐 그린다 |
| `Topic` | 브라우저가 **꺼져 있는 동안** | 푸시 서비스의 대기줄에서 하나로 줄인다 |

그래서 둘을 따로 둔다 — 배포 알림처럼 **켜져 있을 때는 각각 보이는 편이 낫고
밀려 있을 때는 마지막 하나면 되는** 알림이 있다.

규격이 글자를 가린다(base64url 32자 이내). 맞지 않는 값은 `PushSender` 가
SHA-256 으로 접는다. **글자만 걸러 내지 않는다** — 구분 기호를 떼면 서로 다른
태그가 같은 값이 되어 남의 알림을 밀어내는 사고가 난다.

### 3. 늦게 도착한 것은 서비스워커가 한 줄로 묶는다

`TTL` 은 **부탁이지 보장이 아니다.** 기기가 절전에서 깰 때 시효가 지난 것이
섞여 오는 일이 남는다. 그래서 페이로드에 `sentAt` · `expiresAt` 을 실어 보내고
(`PushSender.BuildPayload`), `push-sw.js` 가 시효 지난 것을 낱낱이 띄우지 않고
**「지난 알림 N건」 하나로 묶는다.** 누르면 알림함으로 간다.

**버리지 않고 묶는 까닭**: push 이벤트를 받고 알림을 하나도 안 띄우면 크롬이
대신 "이 사이트가 백그라운드에서 갱신되었습니다" 를 띄우고, 그것이 반복되면
구독 자체를 끊는다.

기기 시계가 서버보다 앞설 수 있어 2분 여유를 둔다. 그것이 없으면 **방금 온
알림이 시계 차이만큼 「지난 것」으로 접힌다.**

## 그래도 남는 것

- **푸시 서비스가 `Topic` 을 반드시 지킨다는 보장은 없다.** 규격상 지원이
  권장이라, 안 지키는 구현에서는 3번 그물이 받는다.
- **즉시 배달은 여전히 못 만든다.** 브라우저가 죽어 있으면 어떤 헤더로도 깨울
  수 없다. 고칠 수 있는 것은 **깨어난 뒤에 몇 개를 보느냐**뿐이다.
- iOS 는 **홈 화면에 설치한 앱에서만** 웹푸시를 준다. 사파리 탭으로 열어 둔
  것은 이 문서와 무관하게 아예 안 온다.

## 고치는 곳

| 무엇 | 어디 |
|---|---|
| 기본 수명·긴급도 | `microservices/NotificationServer/appsettings.json` 의 `Push` |
| 그 설정을 읽는 곳 | `Options/NotificationOptions.cs` 의 `PushDeliveryOptions` |
| 헤더를 싣는 곳 | `Services/PushSender.cs` (`SendAsync` · `BuildTopic`) |
| 알림별 수명 | 각 엔드포인트의 `PushMessageDto.TtlSeconds` |
| 다른 서비스가 보내는 알림 | 본문 `message.ttlSeconds` (예: `ProjMngServer/Services/AiTaskNotifier.cs`) |
| 늦게 온 것 묶기 | `web/src/Shell/JSini.Web.Shell/wwwroot/push-sw.js` |
| 헬프데스크(옛 경로) | `microservices/HelpDeskServer/Services/WebPushService.cs` |
