# `DynamicGrid` 를 `CommGrd` 로 합칠 수 있는가 — 조사

작성: 2026-09-12 · **코드는 손대지 않았다.** 무엇을 옮길 수 있고 무엇이
막히는지만 정리한다.

## 한 줄

**절반은 된다. 전부는 안 된다** — `DynamicGrid` 가 업무 모듈 타입 셋에 기대고
있고, `Components` 는 업무 모듈을 참조할 수 없다(의존 규칙 4).

권하는 모양은 **「`CommGrd` 를 넓히고 `DynamicGrid` 를 그 위에 얹는 것」** 이다.
지우는 것이 아니라 **얇게 만드는 것**이다.

## 지금 상태

| | `CommGrd` | `DynamicGrid` |
|---|---|---|
| 자리 | `Shared/JSini.Web.Components/Data/` | `Apps/JSini.Web.ProjMng/Components/Shared/` |
| 줄 수 | 786 | 420 (+ scoped CSS 46) |
| 쓰는 화면 | **60** | **24** (전부 프로젝트관리) |
| 딸린 것 | — | `ProjMngTable`(237) · `ProcGrid`(204) |

## 실제로 다른 것은 넷뿐이다

나머지는 이미 같거나, 한쪽에만 있는 **부가 기능**이라 합치는 데 걸림돌이
아니다.

### 1. 칸을 어디서 얻는가 — **걸림돌이 아니다**

`CommGrd` 는 화면이 `<Columns>` 로 적고, `DynamicGrid` 는 프로시저가 준 메타
(`cols: { cm_cd: "System.String", … }`)로 런타임에 만든다.

**그런데 옮길 것이 없다.** `CommGrd.Columns` 는 `RenderFragment` 라 부르는 쪽이
런타임에 만들어 넘기면 그만이다. `CommGrd.Data` 도 이미 `object` 라 `DataTable`
을 그대로 받는다 — 자료와 칸 둘 다 이미 통한다.

### 2. 편집 방식 — **여기가 진짜 차이다**

| | `CommGrd` | `DynamicGrid` |
|---|---|---|
| 모드 | `PopupEditForm` | `EditRow`(인라인) |
| 단위 | **한 행** | **여러 행** |
| 저장 시점 | 창의 「저장」을 누르면 **즉시 서버** | 도구줄의 「저장」을 누를 때 **모아서 한 번** |
| 변경 추적 | 필요 없다(행 하나다) | `DataTable.RowState` |
| 화면이 받는 것 | `OnSave((item, isNew))` | `OnSave()` — 무엇이 바뀌었는지는 표가 안다 |

이건 부품의 모양 차이가 아니라 **업무 규약의 차이**다. 한 부품이 둘 다
기본값으로 삼을 수 없고, 골라 쓸 수 있게 열어 두는 것이 맞다.

`CommGrd` 는 `EditMode` 가 `PopupEditForm` 으로 **박혀 있다**. splat 으로
넘기는 길도 없다 — enum 이라 `Coerce` 가 글자를 못 읽는다(`CommTree` 머리말에
같은 이유가 적혀 있다). **파라미터로 선언해야 한다.**

그리고 `DataTable` 을 편집하려면 `CustomizeEditModel` 이 **필수**다.
DevExpress 는 자료 원본에서 편집 모델을 리플렉션으로 만드는데 `DataTable` 에는
그럴 타입이 없어서, 없으면 편집을 여는 순간 죽는다 —
`Cannot create an edit model automatically.`
지금 `CommGrd` 의 그 처리는 `if (e.EditModel is not TItem item) return;` 이라
`DataTable` 이면 **조용히 빠진다.**

### 3. 조작 자리

| | `CommGrd` | `DynamicGrid` |
|---|---|---|
| 위 | `Toolbar` 슬롯(비어 있으면 안 그림) | 조회 · 행 추가 · 저장 · 삭제 · 엑셀 + 「저장하지 않은 변경이 있습니다」 |
| 아래 | `commgrd__footer` — 쪽 · 엑셀 · 검색줄 토글 · `FooterLeft`/`FooterRight` | 없음 |

`CommGrd` 에 `Toolbar` 슬롯이 **이미 있다.** 일괄 저장 도구줄은 그 슬롯에
들어갈 수 있다. 새로 만들 것은 「저장하지 않은 변경」 표시 하나뿐이다.

### 4. 공통코드 드롭다운 — **이것이 막는다**

`DynamicGrid` 는 `DropdownCols="cm_type|CODE_TYPE"` 한 줄로 셀에 이름을 보여
주고 코드로 저장한다. 그 목록을 `CommonCodes` 에서 읽는데 —

```
Apps/JSini.Web.ProjMng/Api/CommonCodes.cs      ← 모듈 안
Apps/JSini.Web.ProjMng/Api/ProjMngTable.cs     ← 모듈 안
CommonCodeItem                                  ← 모듈 안
```

셋 다 업무 모듈 타입이고, **`Components` 는 업무 모듈을 참조할 수 없다**
(web/CLAUDE.md 의존 규칙 4 · `ArchitectureTests` 가 빌드 때 막는다).

그래서 이 기능만은 통째로 옮길 수 없다. 옮기려면 **뒤집어야** 한다 —
`CommGrd` 는 「목록을 받는 칸」만 알고, 그 목록을 읽어 주는 것은 모듈이 한다.
그것이 아래 권장안이 `DynamicGrid` 를 남기는 이유다.

## 권장안 — `CommGrd` 를 넓히고 `DynamicGrid` 를 얹는다

### `CommGrd` 에 넣을 것 (업무와 무관한 것만)

| 넣을 것 | 왜 |
|---|---|
| `EditMode` 파라미터 | 지금 박혀 있다. enum 이라 splat 으로 못 넘긴다 |
| `DataTable` 편집 갈래 | `CustomizeEditModel`·`EditModelSaving` 에 `DataRow` 길을 낸다. 없으면 인라인 편집이 죽는다 |
| 「저장하지 않은 변경」 표시 | 여러 행을 고치고 한 번에 저장하는 화면에는 늘 필요하다 |

### `DynamicGrid` 에 남을 것 (모듈의 것)

- 프로시저 메타 → 칸 조각(`RenderFragment`) 만들기
- 공통코드 드롭다운 (`CommonCodes` 는 모듈에 있어야 한다)
- 일괄 저장 도구줄이 부르는 `ProcGrid`
- 타입별 폭·날짜 서식 (`WidthOf` · `FormatOf` — 옛 Blazor·Vue 의 값을 옮겨
  온 것이라 프로젝트관리의 밀도다)

### 그러면 무엇이 좋아지나

- **그리드 골격이 한 곳**이 된다 — 줄무늬·초점 행·칸 폭 저장·엑셀·검색줄
  토글·권한 가리개가 `CommGrd` 하나에서만 관리된다.
- 화면 24개의 마크업은 **그대로**다. `<DynamicGrid …>` 를 계속 쓴다.
- 되돌리기가 쉽다 — 되돌릴 파일이 `DynamicGrid` 하나다.

## 규모와 위험

| | |
|---|---|
| 고칠 파일 | `CommGrd.razor` · `DynamicGrid.razor` **둘** |
| 화면 마크업 | **안 고친다**(24개 그대로) |
| 위험한 곳 | `CommGrd` 를 60화면이 쓴다. `EditMode` 기본값을 바꾸지 않는 한 그 60은 영향이 없어야 하지만, **확인은 눈으로 해야 한다** |
| 확인 조건 | ProjMng DB 가 2026-09-12 에 살아났다(포트 31015). 24화면을 실제로 띄워 볼 수 있다 |

## 곁들여 찾은 것 — 죽은 파라미터 둘

`DynamicGrid` 의 파라미터 중 **쓰는 화면이 하나도 없는 것**이 둘이다.

| 파라미터 | 쓰는 화면 |
|---|---|
| `ReadonlyCols` | **0** |
| `Toolbar` | **0** |

나머지는 이렇게 쓰인다 — `ExportName` 37 · `OnRefresh` 23 · `OnSave` 17 ·
`HideAdd` 16 · `OnDelete` 14 · `PageSize` 10 · `HiddenCols` 10 ·
`OnRowClick` 9 · `OnAdd` 8 · `DropdownCols` **2**.

`DropdownCols` 를 쓰는 화면이 **둘뿐**이라는 것이 눈에 띈다. 위에서 「막는
것」이라고 적은 그 기능인데, 값을 치르는 화면이 둘이다. 합치는 일을 실제로
할 때는 **그 둘을 `CellEditTemplate` 로 직접 적게 하고 기능을 없애는 쪽**도
견줄 만하다 — 그러면 마지막 걸림돌이 사라지고 `DynamicGrid` 는 더 얇아진다.

## 결정 — 2026-09-12

**위 권장안(`CommGrd` 넓히기)으로 가지 않는다.** 더 멀리 가기로 했다 —
**프로시저를 걷어내고 백엔드에 구현한다.** 그러면 화면이 `DataTable` 이 아니라
타입 있는 목록을 받으므로 `DynamicGrid` 자체가 필요 없어진다.

즉 이 문서의 「합치기」 고민은 **없어지는 쪽으로** 해결된다.

### 프로시저를 읽어 고친 것 셋

옮기면서 확인한 결함이다. **프로시저를 지우면 다시 읽을 수 없으므로**
`ProjectService` 머리말에 그대로 적어 두었다.

1. **수정할 때 등록일(`cre_dt`)을 덮어썼다.** update 문에 `cre_dt = now()` 가
   있어 한 번이라도 고친 프로젝트는 등록일을 잃었다. 이제 등록할 때만 채운다.
2. **번호를 `max(prj_rid)+1` 로 만들었다.** 동시에 둘이 등록하면 같은 번호가
   나온다(유일 제약도 없다). `insert … select` 한 문장으로 좁혔다 —
   **진짜 해법은 시퀀스**이고 표를 고칠 수 있을 때 바꾼다.
3. **금액 형변환이 등록과 수정에서 달랐다**(`::bigint` ↔ `::int`). 칸이
   `integer` 라 등록에서 큰 값을 넣으면 그 자리에서 터졌다.

그리고 **정렬 순서(`prj_srt`)를 등록에서도 받는다.** 프로시저는 수정에서만
다뤄서 새 프로젝트가 늘 목록 끝(99999)으로 갔다.

### 밟은 것 — Dapper 와 `DateOnly`

`date` 칸을 `DateOnly` 로 **읽는 것**은 Npgsql 이 알아서 하는데 **쓰는 것**은
Dapper 가 막는다 — `The member PrjEdt of type System.DateOnly cannot be used as
a parameter value`. **조회는 멀쩡하고 저장만 죽어서** 화면을 열어 보는 것으로는
안 걸린다.

`Services/DapperDateOnlyHandlers.cs` 를 두고 `Program.cs` 에서 한 번 등록한다.
**널 허용(`DateOnly?`)도 따로 등록해야 한다** — 한쪽만 등록하면 「비어 있는
날짜」를 보낼 때만 같은 예외가 난다.

**바꾼 것 — 한 줄을 켜면 그 자리에서 저장한다.** 옛 화면은 모아 두었다가
「저장」을 눌렀는데, 프로시저 자체가 한 줄씩 처리하는 일이라 모아 둘 이유가
없고 「켰는데 저장을 안 눌러서 안 들어간」 상태만 생겼다.

**서버가 센다** — 화면에서 세면 방금 남이 넣은 것을 못 본다.

**바꾼 것 — 한 건씩 팝업으로 고친다.** 표 안 편집은 칸 이름이 `cm_val2` 처럼

### 5. DB 접속·속성 (`sp_projdblist` · `_save` · `_del` · `sp_dev_db_prop_exec`) — 화면 2개

**이 표가 망가지면 개발 도구 화면 전부가 접속을 못 찾는다** — 테이블 관리 ·
쿼리 테스터 · ERD 가 모두 여기를 읽는다.

#### 고친 것 다섯

1. **DB 비밀번호가 목록에 실려 나갔다.** `select a.*` 라 `db_pwd` 가 화면까지

   나가 있었다. 이제 보내지 않고, 저장할 때 비워 두면 기존 값을 지킨다 —
   비밀번호를 몰라도 포트나 스키마를 고칠 수 있어야 한다.
2. **저장이 다루지 않던 칸 셋** — 접속의 설명(`db_comm`), 속성의
   설명·구분(`db_pcomment` · `db_ptype`). 목록에는 나가는데 넣거나 고칠 길이
   없었다.
3. **속성 수정이 열쇠 셋을 모두 맞춰야 들었다**(`db_prid`·`db_rid`·`db_pkey`).
   키 이름을 바꾸면 **조용히 아무 줄도 안 고쳤다** — 오류도 안 났다.
   이제 번호 하나로 찾는다.
4. **수정할 때 커서를 안 열었다.** `sp_projdbsave` 가 insert 갈래에서만
   `open p_cur` 를 한다. 부르는 쪽은 늘 커서를 기대한다.
5. 번호가 `max+1` — 다른 표와 같다.

**그대로 옮긴 것** — 속성 값에서 빈 줄을 걷어 내는 것(`REGEXP_REPLACE`).
값이 여러 줄짜리 질의라 편집기를 오갈 때 빈 줄이 쌓인다.

### 12-c. 업무 흐름 — **열쇠가 달라 아무 자료도 못 열고 있었다** (2026-09-12)

옛 소스(`views/projmng/proj/flow.vue`, 그 앞의 `Pages/Proj/ProjFlow.razor`)를
다시 읽어 확인했다. 이 화면은 **ERD 와 같은 속성(`db_pkey='erd'`)** 을 읽는다.
두 화면이 한 배치를 나눠 쓰고, 다른 점은 하나뿐이다 — 흐름도는 **DB 에서
사라진 표**에 `(삭제됨)` 을 붙인다.

한동안 여기만 `db_pkey='flow'` 를 읽고 있었다. 운영에 그런 속성은 **딱 한 줄**
이고 그마저 옛 draw.io XML 이라(`db_rid=4`, 449자), **어느 DB 를 골라도 빈
그림**이었다. `erd` 로 저장된 JSON 은 12건이다.

| | 전 | 후 |
|---|---|---|
| 읽는 속성 | `flow` (운영 1건, draw.io XML) | `erd` (운영 12건, JSON) |
| 프로젝트관리 DB 에서 | 빈 그림 | 도형 **21개**, 그중 **7개가 사라진 표** |
| 사라진 표 | 글자만 `(삭제됨)` | 글자 + **흐린 점선 도형** |
| 그 표시가 저장본에 | 남았다 | **안 남는다**(저장 직전에 뗀다) |

**표시를 저장하지 않는 것이 요점이다.** 그것은 「지금 그 DB 에 있는가」라는
조회 결과이지 그림의 성질이 아니다. 남기면 ERD 화면이 같은 배치를 읽을 때
그 글자를 물려받고, 표를 되살려도 꼬리표가 남는다.

확인: 흐름도에서 불러오기 → 21개(7개 흐림) → 저장 → 저장본의 좌표·관계선이
**한 글자도 안 바뀌고** `(삭제됨)`·`gone` 이 하나도 안 남았다. 이어서 ERD 를
열어 21개가 모두 보통 도형으로 그려지는 것까지 봤다.

### 13-b. DB 개체 탐색 — **이름 거르기가 EDB 에서만 듣고 있었다** (2026-09-12)

옛 소스(`views/projmng/develop/db-tools.vue`)와 대조했다. 탭 구성·템플릿 처리·
`proclist` 한 번으로 프로시저와 함수를 가르는 규칙(`pgtype='sql'` 이면 함수)은
그대로 옮겨져 있었다. 남은 문제는 **거르기**였다.

거르는 값(`param1`)은 **등록된 질의**가 받아 쓰는 것인데, 그 질의가 DB 종류마다
따로 등록돼 있다. 훑어 보니 `param1` 을 쓰는 것은 EDB 의 `tablelist` ·
`proclist` 둘뿐이다.

| 질의 | EDB | POSTGRESQL | MSSQL | MYSQL |
|---|---|---|---|---|
| `tablelist` | 쓴다 | 안 쓴다 | 안 쓴다 | 안 쓴다 |
| `proclist` | 쓴다 | 안 쓴다 | 안 쓴다 | 안 쓴다 |

그래서 프로젝트관리 DB(PostgreSQL)에서 이름을 쳐도 **목록이 그대로**였다.
오류가 아니라서 「거르기가 안 듣는다」로만 보인다.

등록 질의를 종류마다 고치는 대신 **화면이 거른다**(테이블 관리가 이미 그렇게
한다). `param1` 은 계속 보낸다 — 서버가 먼저 좁혀 주면 오가는 양이 줄고, 그
위에 한 번 더 걸러도 결과는 같다.

**탭 이름에 건수를 붙였다.** 탐색하는 화면인데 어디에 무엇이 몇 개 있는지
보려면 탭을 하나씩 눌러 봐야 했다 — 지금은 「테이블 14 · 프로시저 1 · 함수 7」
이 그대로 보인다.

확인(프로젝트관리 DB): 테이블 14 · 프로시저 1 · 함수 7. 이름에 `proj` 를 넣으면
테이블이 **3건**(`dev_proj` · `dev_proj_prop` · `dev_proj_user_map`)으로 좁혀지고
프로시저·함수는 0 이 된다. 미리보기가 만드는 생 SQL 은 통로까지 따로 확인했다
(`select * from dev_proj limit 10` → 8줄).

> 프로시저 23개를 지운 뒤라 **프로시저 1 · 함수 7** 이 맞다 — 남은 것은
> 도우미 함수 `nvl` · `to_ymd` 다.

### 13-c. 테이블·컬럼 설명 관리 — **표를 자료로 주면 줄이 `DataRowView` 로 온다** (2026-09-12)

옛 소스(`views/projmng/develop/table-manage.vue`)와 대조했다. 보내는 값 이름과
거르기는 이미 고쳐져 있었고(그 경위는 화면 머리말), 이번에 드러난 것은
**`RuntimeColumns` 를 만들며 내가 넣은 결함**이다.

`DataTable` 을 자료로 주면 DevExpress 가 `DataView` 로 감싼다. 그래서 셀
템플릿과 선택 알림에 오는 것은 `DataRow` 가 아니라 **`DataRowView`** 다.
바로 캐스팅하면 줄을 그리다 던지고 **회로가 끊긴다** — 화면이 통째로 멎어
「조회를 눌러도 아무 일이 없다」로 보인다.

| | 전 | 후 |
|---|---|---|
| 표의 자료 형 | `TItem="DataRow"` | `TItem="DataRowView"` |
| 셀·선택에서 줄 꺼내기 | 바로 캐스팅 | `RuntimeCell.Row(...)` 가 둘 다 받는다 |
| 증상 | 목록이 안 뜨고 행 선택도 안 됨 | 정상 |

같은 캐스팅이 `DbTester` · `DbTools` · `SourceScanner` · `SourceTrace` 에도
있었다 — **다섯 화면을 함께 고쳤다.** 그래서 DB 개체 탐색의 「테이블을 고르면
앞 10건」과 소스 추적의 파일 고르기도 이제 듣는다.

#### 칸 안에서 고칠 때 **다시 그리면 안 된다**

설명 칸의 입력칸이 값을 돌려줄 때 Blazor 는 기본으로 `StateHasChanged` 를
부르는데, 그 자리가 DevExpress 의 칸 설정 렌더 중이라 거기서 던진다 —
`Async rendering is not allowed here`, 그리고 또 **회로가 끊긴다.**
`RuntimeColumns` 가 `IHandleEvent` 를 구현해 그 자동 렌더를 끈다. 다시 그릴
이유도 없다 — 친 글자는 이미 칸에 보이고, 하는 일은 값을 `DataRow` 에 옮겨
담는 것뿐이다.

#### 「반영했습니다」가 뜨자마자 지워지고 있었다

저장 뒤 목록을 다시 읽는데, 그 조회가 자기 안내를 써서 성공 문구를 덮었다.
다시 읽은 **뒤에** 한 번 더 말한다.

확인(운영 DB, 프로젝트관리 DB 자신): `dev_excel` 의 테이블 코멘트를 화면에서
고쳐 반영 → `obj_description` 으로 바뀐 것 확인 → 되돌림. 같은 방식으로
`dev_excel.xls_id` 의 컬럼 코멘트도 반영 → 확인 → 되돌림. 표 선택 →
컬럼 12건(`dev_proj`) 도 확인했다.

### 12-d. 다이어그램에 **도형 추가 · 이름 편집**을 넣었다 (2026-09-12)

12-b·12-c 로 그림이 그려지고 저장되게 됐지만 **도형을 새로 만들 길이 없었다.**
ERD·흐름도는 도형이 곧 대상 DB 의 표라 그래도 되는데, **유즈케이스는 끌어올
표가 없어서** 화면이 「새로 그려 저장하십시오」라고 안내하면서 그릴 수단을 주지
않고 있었다.

| | 넣은 것 |
|---|---|
| 도형 추가 | 조건줄의 「도형 추가」 — 보고 있는 화면 가운데에 만들고 **바로 이름 편집 상태**로 들어간다 |
| 이름 편집 | 도형을 더블클릭. **손으로 만든 도형만** — 표에서 온 것은 DB 가 정본이다 |
| 구분 | 손으로 만든 도형은 옅은 파랑(`#f0f7ff`), 표에서 온 것은 흰색, 사라진 표는 흐린 점선 |

**표에서 온 도형의 이름을 캔버스에서 못 고치게 한 이유.** 그 이름·설명의
정본은 대상 DB 의 테이블 이름과 코멘트다. 캔버스에서 고쳐 봐야 다음 불러오기에
DB 값으로 되돌아가므로, 고칠 수 있게 두면 **고쳤는데 사라지는** 일이 된다.
그쪽은 [테이블·컬럼 설명 관리]에서 코멘트를 고친다.

저장 형식에 칸 하나(`manual`)가 늘었다. `gone` 과 달리 **저장본에 남긴다** —
조회 결과가 아니라 그림의 성질이기 때문이다. 업무 흐름의 「사라진 표」 판정도
이 칸을 보고 **손으로 만든 도형은 건너뛴다**(표가 아닌 것을 사라졌다고 말하면
그 그림은 늘 절반이 흐리다).

확인(운영 DB): ERD 에서 도형을 만들어 저장 → 저장본에 `manual: true` 와 좌표가
남는 것 확인(`{id: 'm-…', name: '새 도형', x: 433, y: 284}`) → 업무 흐름에서
같은 그림을 열어 **흰색 14 · 흐림 7 · 파랑 1**, 손으로 만든 도형에는
`(삭제됨)` 이 안 붙는 것까지 확인 → 시험 도형을 지우고 저장본을 원래대로 되돌렸다.

### 12-e. ERD 에 **컬럼 목록과 외래키 관계**를 넣었다 (2026-09-12)

「불러오기」가 읽어 오던 것은 **테이블 이름과 코멘트뿐**이었다. 상자 안이 비어
있으니 컬럼을 보려면 다른 화면으로 가야 했고, 관계선은 사람이 일일이 끌어
그려야 했다(저장 형식의 `fields` 칸은 아무도 채우지 않고 있었다).

**등록 질의 둘을 새로 넣었다**(`projmng.devsqlresp` — DB 로직 관리 화면에서
보이고 고칠 수 있다).

| 이름 | 무엇을 | 등록한 DB 종류 |
|---|---|---|
| `erdColumns` | 스키마 전체의 칸 목록(표·칸·자료형·PK 여부) | POSTGRESQL · EDB · MSSQL · MYSQL |
| `erdRelations` | 외래키(어느 표의 어느 칸 → 어느 표의 어느 칸) | POSTGRESQL · EDB · MSSQL · MYSQL |

**표마다 부르지 않는다.** 표가 스물몇 개면 왕복도 그만큼이라, 스키마 전체를
한 번에 주는 질의를 새로 짰다. 불러오기는 이제 넷을 나란히 부른다 —
저장본 · 테이블 목록 · 칸 목록 · 외래키.

#### 저장본에는 **남기지 않는다** (셋 다)

칸 목록도, 외래키 선도, **그것 때문에 커진 상자 크기도** 저장하지 않는다.

- 칸·선은 대상 DB 의 지금 모습이다. 저장하면 표가 바뀐 뒤에도 옛 칸이
  그려지고, 제약을 뗀 뒤에도 선이 남는다. 지운 선이 다음 불러오기에
  되살아나는 것이 **맞는 동작**이라, 사람이 끈 선과 색으로 갈라 둔다
  (초록 점선).
- 크기는 **보여 주려고 우리가 늘린 것**이지 사람이 정한 값이 아니다. 저장하면
  「컬럼 보기」를 끄고 열었을 때 속이 빈 커다란 상자만 남는다. 사람이 직접
  끌어 바꾼 크기는 늘려 준 값과 다르므로 그때는 그대로 저장된다.

확인(운영 DB): 프로젝트관리 DB 에서 불러오면 상자 21개에 칸이 펼쳐지고
(`dev_proj` 는 12칸, 상자 높이 60 → 458), **컬럼을 펼친 채로 저장해도 저장본이
한 글자도 안 바뀐다**(좌표·크기 그대로, `fields`·`auto` 없음).

외래키는 이 DB 에 **제약이 하나도 없어** 0건이 맞다. 질의 자체는 제약이 있는
스키마(포털의 `scom`)에 직접 돌려 확인했다 — `accounts → companies`,
`common_codes → common_code_groups` 같은 줄이 제 모양으로 나온다.

### 12-f. ERD·흐름도가 **접속 실패를 「테이블이 없다」로 말하고 있었다** (2026-09-12)

「jsini통합포탈 / jsini-comm 을 골랐는데 표가 많은 DB 인데도 『그릴 테이블이
없습니다』가 뜬다」는 신고. 확인해 보니 **대상 DB 에 못 붙은 것**이었다.

    Failed to connect to 175.200.10.40:13015

화면은 `tablelist` 의 결과 코드를 보지 않고 행 수만 셌다. 그래서 접속 실패가
빈 목록이 되고, 빈 목록이 「없습니다」가 됐다. **저장소가 이미 한 번 겪고 적어
둔 것과 같은 함정이다**(「실패를 빈 표로 말하지 않는다」) — 자료가 없는 것과 못
읽은 것은 고쳐야 할 곳이 서로 다르다(표 만들기 ↔ 접속 정보·방화벽).

고친 뒤 동작:

| 저장본 | 목록 조회 | 화면 |
|---|---|---|
| 없다 | 실패 | **「ERD 를 읽지 못했습니다 — Failed to connect to …」** |
| 있다 | 실패 | 저장본만 그리고 **경고** — 새 표가 안 붙었다는 사실을 알린다 |
| — | 성공 | 여느 때처럼 합쳐서 그린다 |

저장본이 있을 때 실패해도 그림은 그린다 — 잠깐 못 읽었다고 사람이 배치해 둔
것까지 안 보이면 곤란하다는 옛 판단을 따랐다.

> 신고한 접속 자체는 **등록된 주소의 포트 문제**다. 같은 계정·같은 DB 가
> `jin114.co.kr:31015` 로는 붙고 `scom` 에 표가 33개 있다. 등록값은
> `jsini.co.kr:13015` 인데 개발 장비에서 그 포트가 막혀 있다 — 운영 서버에서는
> 열려 있을 수 있어 **등록값은 건드리지 않았다.**

### 12-g. 「주소를 바꿨는데 옛 포트로 간다」 — **서버가 접속 정보를 캐시하고 있었다** (2026-09-12)

`jsini-comm` 의 주소를 `jin114.co.kr:31015` 로 고쳤는데도 서버는 계속
`…:13015` 로 붙으러 갔다. `BaseService.GetDbInfo` 가 찾은 접속을 **프로세스
살아 있는 동안 정적 목록**(`AppData.DB_Infos`)에 담고, 아무도 비우지 않았다.
[프로젝트 DB 등록] 화면으로 고쳐도 **다시 띄우기 전까지** 옛 주소로 간다.

같은 표에 캐시가 하나 더 있었다 — `AppData.DsrInfos`(등록 질의 SQL). 그래서
[DB 로직 관리]에서 질의를 고쳐도 서버는 옛 SQL 로 돌았다.

**둘 다 걷어냈다**(`AppData` 자체를 지웠다). 값은 `projmng` 의 한 줄이고 그
DB 는 같은 요청이 이미 쓰고 있다 — 아껴서 얻는 것보다 **틀린 주소로 붙는 것**이
훨씬 비싸다. 덤으로, 예전에 「못 찾은 것까지 캐시에 넣어 그 뒤 모든 호출이
NullReferenceException 으로 죽던」 갈래도 함께 사라졌다.

확인(서버 재기동 없이): 포트를 19999 로 고친 **직후** 호출 →
`Failed to connect to …:19999`, 다시 31015 로 되돌린 직후 → 33건. 화면에서도
`jsini통합포탈 / jsini-comm` 이 **도형 33개**로 그려진다(scom 스키마의 표 수와 같다).

### 12-h. 「불러오는 중」이 한 번도 안 보이고 있었다 (2026-09-12)

ERD 는 대상 DB 에 네 번 물어본다(저장본·표 목록·칸·외래키). 그 사이 화면은
**옛 그림 그대로**라 눌린 것인지 알 수 없어 사람이 다시 누른다.

덮개(`.pm-diagram-loading`)와 조회 단추 잠금을 붙였는데 **그래도 안 보였다.**
`DataPage.LoadAsync` 가 `Loading = true` 를 켠 뒤 **한 번도 그리지 않고** 첫
`await` 로 들어갔기 때문이다 — Blazor 는 처리기가 끝난 뒤에 다시 그리고, 그때는
이미 `Loading` 이 꺼져 있다. 첫 `await` 앞에 `StateHasChanged()` 한 줄을 넣었다.

**이 한 줄은 포털 전체에 걸린다** — 표가 있는 화면의 「불러오는 중」도 같은
이유로 늦게 떴다.

### 12-i. 조회 영역을 `CommSch` 로 모았다 — `SearchBar` 삭제 (2026-09-12)

프로젝트관리에만 남아 있던 `SearchBar`(모듈 전용 부품)를 쓰는 화면 아홉을
`CommSch` 로 옮기고 **부품과 그 CSS 를 지웠다.** 이제 저장소에 `SearchBar` 는
한 곳도 없다.

| | 전(`SearchBar`) | 후(`CommSch`) |
|---|---|---|
| 조건 칸 | 라벨 없이 늘어놓음 | `CommSchItem Label="프로젝트"` 처럼 **라벨이 왼쪽에** |
| 조회 단추 | 화면마다 `Actions` 에 손으로 | 판이 그린다(`OnSearch`) — **자리가 늘 같다** |
| 조회 중 | — | `Busy` 로 그 단추를 잠근다(이번에 `CommSch` 에 넣었다) |

단추 이름은 화면의 말을 지켰다 — 「쿼리 실행」 · 「스캔」 · 「추적 실행」 ·
「불러오기」는 `SearchText` 로 넘긴다.

### 12-j. ERD 를 **ERD 처럼** 그리고, 도구상자와 정렬을 붙였다 (2026-09-12)

세 가지를 했다.

**① 상자를 HTML 라벨로 그린다.** maxgraph 가 그리는 것은 네모와 테두리뿐이고
속은 우리 HTML 이다(`.pm-erd-*`, `projmng.css`). 머리띠에 표 이름과 설명,
몸에 칸을 한 줄씩 — 왼쪽에 이름, 오른쪽에 자료형, 열쇠 칸은 굵게 점 표시.
모양이 CSS 에 있으니 테마의 글자 크기·색을 그대로 따라간다.

> 높이는 JS 가 잰다(`HEAD_H` · `FIELD_LINE_H`). **CSS 의 줄 높이를 고치면
> 그쪽도 같이 고친다** — 어긋나면 칸이 상자 밖으로 나가거나 아래가 휑해진다.

**② 도구상자.** maxgraph 가 기본으로 등록해 둔 모양을 그대로 고르게 했다 —
사각형 · 둥근상자 · 타원 · 원 · 이중원 · 마름모 · 삼각형 · 육각형 · 원통(DB) ·
구름 · 액터 · 메모 · 글자만 · 묶음(swimlane). 목록은 **JS 가 정본**이고 화면이
받아 단추를 그린다(`shapes()`), 그래서 모양을 하나 더 열 때 고칠 곳이 한 곳이다.

**그림 위에 겹치지 않는다** — 겹치면 그 자리에 도형을 놓을 수 없고 좁은
화면에서 그림을 덮는다. 조회 영역 아래 한 줄로 둔다.

**③ 정렬.** `HierarchicalLayout`(계층) · `FastOrganicLayout`(유기) ·
`CircleLayout`(원형) · 격자. **관계선이 하나도 없으면 계층·유기는 할 일이
없어서** 격자로 떨어뜨리고 그 사실을 말해 준다 — 안 그러면 「눌렀는데 아무 일도
없다」로 보인다. 격자는 **열 단위로 쌓는다**(줄 단위면 칸 많은 표가 그 줄의
높이를 정해 사이가 휑해진다).

#### 밟은 것 — `graph.fit()` 은 0.24 에 없다

「맞춤」이 **한 번도 동작한 적이 없었다.** 그 일이 플러그인으로 옮겨 갔고
(`FitPlugin`, 이름은 `fit`), 옛 이름으로 부르면 `graph.fit is not a function`
으로 던지며 **회로가 끊긴다.** 정렬을 붙이다 같은 자리에서 다시 밟아 드러났다.
`graph.getPlugin('fit').fitCenter()` 로 부른다.

확인(운영 DB): 프로젝트관리 DB 를 불러오면 상자 21개가 머리띠와 칸으로 그려지고
(칸 131줄, 열쇠 2줄), 도구상자에서 마름모를 넣으면 도형이 늘고, 원형·격자·계층이
각각 배치를 바꾼다. **시험한 것은 저장하지 않았다** — 저장본의 좌표 21개와
관계선 18개가 그대로인 것을 확인했다.

#### 모양 여덟 개는 **직접 그려 등록했다**

maxgraph 가 기본으로 주는 모양은 열넷뿐이라(사각형·타원·마름모·삼각형·육각형·

로 잔뜩 싣는데, 여기서는 **경로로 그리는 여덟 가지**를 파일 안에서 만들어
`ShapeRegistry` 에 등록했다 — 바깥에서 받아 오는 것이 없다.

평행사변형(입·출력) · 사다리꼴(수동 조작) · 문서 · 단계 · 카드 · 지연 ·
메모(노트) · 십자.

목록은 **`diagram-viewer.js` 가 정본**이고 화면은 `shapes()` 로 받아 단추를
그린다. 모양을 하나 더 열 때 고칠 곳이 한 곳이다.

확인: 도구상자가 묶음 여섯 · 도구 44개로 뜨고, 고정 ↔ 띄움 ↔ 숨김 ↔ 다시 열기가
모두 듣는다. 직접 그린 모양(문서 · 수동 조작 · 지연 · 단계 · 카드 · 십자)과
기본 모양(클라우드 · 액터)을 넣어 캔버스에 그려지는 것을 확인했다.

### 12-l. stencil 도형 묶음 135개 · 도구상자 다듬기 (2026-09-13)

**① stencil 을 실었다.** mxGraph 가 배포하는 도형 묶음 XML 넷을 저장소에 넣고
(`wwwroot/lib/stencils` — Apache 2.0, LICENSE·VERSION.txt 동봉) 다이어그램
화면을 처음 열 때 한 번 읽어 `StencilShapeRegistry` 에 등록한다.

| 파일 | 모양 | 도구상자 묶음 |
|---|---|---|
| `basic.xml` | 28 | 도형 묶음 |
| `flowchart.xml` | 34 | 순서도 묶음 |
| `arrows.xml` | 34 | 화살표 |
| `bpmn.xml` | 39 | BPMN |

이름은 draw.io 와 같은 규칙이다 — `mxgraph.flowchart.document`(묶음 이름 +
모양 이름, 소문자·밑줄). 그 글자가 그대로 `shape` 값이 되므로 저장본에도
그대로 남고, 다시 열 때 같은 그림이 나온다.

**등록은 그림보다 먼저** 해야 한다(`create` 가 기다린다). 나중에 하면 그 사이
그려진 도형이 빈 네모로 남는다. 묶음 하나를 못 읽어도 그 칸만 비고 화면은 뜬다.

이제 도구가 **179개**(우리 것 36 + stencil 135 + 선 8)라 **찾는 칸**을 뒀다.
이름과 묶음 이름을 함께 본다 — 「순서도」로 묶음째 좁히는 일이 흔하다.

**② 도구상자 다듬기.**

- 고정·숨기기를 **아이콘으로**(`jsini-icon-pin` · `jsini-icon-close`). 머리띠가
  좁아 글자 둘이면 제목이 밀린다. 꽂힌 상태는 색으로 알린다.
- 숨겼을 때 손잡이가 **자리를 차지하지 않는다.** 흐름에 두었더니 숨긴 뒤에도
  폭을 먹어 그림이 좁은 채였다 — 그림 위 맨 앞 층에 띄우고 캔버스가 폭을 다
  쓴다(재어 보니 **829 → 1047px**).

**③ 「고루 펼치기」.** 배치 넷(계층·유기·원형·격자)은 그림을 **새로 짠다.**
이것은 사람이 놓아 둔 자리를 그대로 두고 **겹친 것만 밀어낸다** — 표가 새로
붙었거나 저장본 좌표가 서로 겹칠 때 쓴다. 덜 밀어도 되는 쪽으로 밀고(좌우가
조금 겹쳤는데 위아래로 밀면 그림이 세로로만 길어진다) 겹침이 없어지면 멈춘다.

확인: 도구 179개가 묶음 열로 뜨고, 찾는 칸에 `gateway` 를 넣으면 BPMN 여섯만
남는다. stencil 도형(Annotation·Card …)이 캔버스에 그려진다. 한자리에 쌓은
도형 여섯을 「고루 펼치기」로 풀면 **여섯 자리로 고르게 흩어진다**(세로 108px
간격). 시험한 것은 저장하지 않았고 저장본이 그대로인 것을 확인했다.

### 12-m. 도구상자 — 아코디언과 **실제 모양** 미리보기 (2026-09-13)

**① 묶음을 접는다.** 묶음이 열이고 도형이 백일흔한 개라 다 펼쳐 두면 찾는
것이 늘 화면 밖에 있었다. `<details>` 를 쓴다 — 여닫는 일을 브라우저가 하므로
회로 왕복도, 상태도 없고 키보드로도 열린다. 우리가 만든 묶음(기본·순서도·
UML·ERD·구성도)은 펼쳐 두고 stencil 묶음 넷은 접어 둔다. 머리에 **개수**를
적어 접힌 채로도 어디에 몇 개가 있는지 보인다. **찾는 글자가 있으면 전부
펼친다** — 걸린 것이 접힌 묶음 안에 있으면 「없다」로 보인다.

**② 도구를 실제 모양으로 보여 준다.** 이름만 적으면 「Or」·「Card」 가 무슨
모양인지 알 수 없다. 그림은 **maxgraph 가 그린 것을 그대로** 쓴다 — 숨긴
그래프에 도형을 하나씩 넣었다 빼면서 그려진 `<g>` 를 가져온다. 우리가 아이콘을
따로 그리면 캔버스의 모양과 언젠가 어긋난다(특히 stencil 135개).

칸은 **모두 같은 크기**(38×38)이고 비율은 `viewBox` 가 지킨다 — 납작한
화살표도 정사각 칸 안에서 제 비율로 눕는다. 덧붙이는 말(hover)에 **큰 그림과
이름**을 띄운다. `title` 을 안 쓰는 이유는 그림을 담을 수 없어서다.

#### 밟은 것 — **마크업을 회로로 보내면 연결이 끊긴다**

처음에는 `shapes()` 가 SVG 조각까지 함께 돌려줬다. 도형이 백일흔한 개라 그
답이 수백 KB 가 되고 **Blazor 회로의 수신 한도(기본 32KB)를 넘겨 연결이
끊겼다.** 화면에는 「도구상자가 통째로 안 보인다」로만 나타난다 — 한도 이야기는
어디에도 안 뜬다.

지금은 **그림을 브라우저 안에서 만들어 브라우저 안에서 끼운다.** 화면은 빈
칸(`[data-shape]`)만 그리고, 렌더가 끝나면 `paintPreviews()` 가 채운다.
회로로는 이름만 오간다(약 7KB). 이미 그린 칸은 건너뛰므로 거르개를 칠 때
깜빡이지 않는다.

확인: 묶음 10개가 접힘·펼침으로 뜨고(BPMN 39 접힘 → 눌러서 펼침), 칸 171개가
**전부** 제 모양으로 그려지며, 덧붙이는 말에 큰 그림과 이름(`Ad Hoc`)이 함께 뜬다.

### 8. WBS · 일정표 (`sp_proj_wbs_exec` · `sp_proj_wbs_moniter`) — 화면 4개

| | |
|---|---|
| 서비스 | `Services/WbsService.cs` |
| 엔드포인트 | `/api/wbs` · `…/summary` |
| 클라이언트 | `Api/WbsClient.cs` |
| 화면 | `Wbs` · `ProjectScheduler` · `FastTest` · `ProjectMonitoring` |

WBS 와 일정표가 **같은 표**를 본다 — `schedule_type` 하나로 갈린다. 편집 창도
하나를 같이 쓴다(`Components/Shared/WbsEditForm.razor`).

#### 고친 것 다섯

1. **조회가 자료를 고쳤다.** `srch` 갈래가 목록을 내기 전에 `UPDATE dev_wbs` 를
   돌려 빈 계획 날짜를 개발 종료일로 메웠다. **보기만 하려는 사람이 표를
   바꾸는 셈**이고 되돌릴 수도 없다. 이제 쓰지 않고 읽을 때만 메운다
   (`COALESCE`) — 화면에 보이는 값과 거르는 기준은 그대로다.
2. **일정표의 기간 탭이 아무 일도 안 했다.** 화면은 `start_day` · `end_day` 를
   보내는데 프로시저의 `WHERE` 에 그 값을 보는 곳이 **없었다.** 주·월·분기를
   눌러도 목록이 같았고 오류가 아니라서 아무도 몰랐다. 이제 **계획 기간이 그
   구간과 겹치는 것**을 낸다(시작일만 보면 걸쳐 있는 긴 일감이 사라진다).
3. **수정이 고친 사람을 안 남겼다.** `mod_dt` 만 찍고 `mod_user` 는 그대로라,
   등록한 사람이 끝까지 고친 사람으로 남았다.
4. **수정으로 바꿀 수 없는 칸이 여섯이었다** — `gb1` · `gb2` · `proc_lvl` ·
   `build_user` · `build_status` · `qc_user`.
5. 번호가 `max+1` — 다른 표와 같다.

#### 곁들여 찾은 것

- **일정표는 옛날부터 늘 비어 있었다.** 운영 자료의 `schedule_type` 은 전부
  `WBS`(318) 와 `Public`(4) 이고 `SCHEDULE` 인 줄이 **하나도 없다.**
  화면에 그 사실을 적어 두었다.
- **진행 현황의 DB 목록만 열쇠 이름이 달랐다**(`proj_rid` vs `prj_rid`).
  틀리면 걸러지지 않고 전부 나오는데 숫자가 그럴듯해 드러나지 않는다.
  REST 로 오면서 그 함정 자체가 사라졌다.
- **조회를 두 번 걸면 늦게 온 쪽이 이긴다.** 화면을 열 때 `OnInitializedAsync`
  에서 한 번, 프로젝트 고르개가 첫 항목을 고르며 또 한 번 — **프로젝트를 안 건
  조회가 늦게 돌아와** 목록이 전체로 보였다(WBS 에서 318건). 고르개에 맡기고
  화면에서는 걸지 않는다.
- **고르개에 값을 미리 박아 두면 첫 조회가 안 나간다.** 고르개는 「이미 고른
  값이 목록에 있으면 다시 고르지 않는다」 — 그래서 `OnChanged` 가 안 불린다.
  `FastTest` 가 `"7"` 을 박아 두어 그랬다.

### 9. 시스템 질의 (`sp_devsqlresp_base_exec`) — 화면 2개

| | |
|---|---|
| 서비스 | `Services/DbLogicService.cs` |

**개발 도구 화면들의 바닥이다** — 테이블 관리 · 쿼리 테스터 · DB 도구가
「테이블 목록」을 물으면 서버가 여기 등록된 SQL 을 꺼내 쓴다.

1. **「삭제」가 아무 일도 안 했다.** 프로시저에 `delete` 갈래가 없어 목록만

   하나 늘리려면 DB 를 직접 만져야 했다. 이제 오른쪽 판에서 고친다.
3. 이름표를 지울 때 딸린 질의를 센다 — 외래키가 없어 DB 가 막아 주지 않는다.

> 두 화면이 **글자 하나까지 같았다**(같은 프로시저를 조건 없이 불렀다).
> 지금은 [DB 로직 관리]가 고치는 자리, [DB 로직 항목]이 훑어보는 자리다.

### 13. 남은 다섯 화면 — **칸이 실행 시점에 정해진다**

`DbTester` · `DbTools` · `TableManage` · `SourceTrace` · `SourceScanner` 다.
이들은 프로시저를 부르지 않는다 — 등록된 질의를 **대상 DB** 에서 돌리거나
(`/Dev`) 서버 장비의 디스크를 훑는다(`/Media`). 그래서 무엇이 올지 미리 알 수
없고, 그것이 `DynamicGrid` 가 마지막까지 남아 있던 이유다.

**표를 하나 더 두지 않고** `CommGrd` 의 `Columns` 안에 넣는 조각을 만들었다 —
`Components/Shared/RuntimeColumns.razor`. `DataTable` 을 받아 칸을 세우고,
`Hidden` 으로 본문처럼 긴 칸을 빼고, `Editable` 로 그 자리에서 고칠 칸을
정한다(테이블 관리의 설명 칸).

```razor
<CommGrd TItem="DataRow" Data="@_data.Table" …>
    <Columns>
        <RuntimeColumns Table="@_data.Table" Order="@_data.ColumnOrder" />
    </Columns>
</CommGrd>
```

> **`ASP0006`.** 순서 번호를 변수로 굴리면 분석기가 막는다. 그래서 `.cs` 로
> 짓다가 `.razor` 로 옮겼다 — Razor 컴파일러가 번호를 매겨 준다.

### 곁들여 고친 것 둘 — **회로를 끊던 버그**

프로시저와 무관한데 이 화면들을 확인하다 드러났다. 둘 다 증상이 같다 —
**그 화면만 깨지는 것이 아니라 그때부터 아무 단추도 안 눌린다.**

1. **코드 편집기가 뜰 때마다 회로가 끊겼다.** BlazorMonaco 는 스크립트 세 장이
   전역에 있기를 기대하는데 셸의 `<head>` 에 그것이 없었다. 「쿼리 테스터」·
   「Glue 추적」·「DB 도구」·「소스 추적」이 **열자마자 죽어 있었다.**
   `<head>` 에 적으면 `editor.main.js` 3MB 를 **편집기가 없는 화면까지** 받게
   되므로, 부품이 필요할 때 받고 **다 받은 뒤에야** 편집기를 그린다
   (`wwwroot/js/monaco-loader.js`). 자식이 먼저 렌더되므로 감싸개가 나중에
   넣어 주는 방식으로는 언제나 늦다.
   - `requestAnimationFrame` 으로 기다리면 **보이지 않는 탭에서 영영 멈춘다.**
     `setTimeout` 으로 기다린다.
2. **표의 편집 창 안에서 고르개가 던졌다.** `CodeSelect` · `BizSelect` ·
   `SourceSelect` 는 `Value`/`ValueChanged` 로 값을 주고받아 DevExpress 가
   기대하는 `ValueExpression` 이 없다. `EditForm` 안에 들어가면 그것을 필수로
   보고 던진다. 우리는 DevExpress 검증을 쓰지 않으므로 셋 다 껐다.

### 편집 성격이 다른 화면 둘

WBS 와 공통코드는 **여러 줄을 고쳐 한 번에 저장**하는 화면이다. 프로젝트
목록처럼 한 건씩 팝업으로 바꾸면 쓰는 사람의 손이 느려진다. 그 둘은
`CommGrd` 에 인라인 편집 갈래를 열어 주는 쪽이 맞고, 그때 이 문서 앞부분의
「`CommGrd` 에 넣을 것」(`EditMode` · `DataTable` 편집 갈래)이 필요해진다.
