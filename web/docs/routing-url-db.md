# 라우팅 · URL · DB 로 화면을 관리하는 방법

작성 2026-09-06. **아직 결정된 것은 없다** — 고르기 위한 자료다.

지금 화면은 `@page "/admin/notice"` 처럼 URL 을 파일에 적어 연결한다.
"URL 을 안 적을 수는 없나", 나아가 "화면을 DB 에서 관리할 수는 없나" 에 대한 정리다.

---

## 0. 지금 어떻게 도는가 (사실 확인)

고를 때 걸리는 것이 전부 여기 있으므로 먼저 못을 박아 둔다.

### `@page` 는 문법 설탕이다

Razor 컴파일러가 컴포넌트 클래스에 `[Route("...")]` 를 붙여 줄 뿐이다.
라우팅을 굴리는 것은 그 어트리뷰트고, **그것이 어디서 오느냐만 바꾸면 된다.**

### 라우트를 읽는 곳이 **둘**이다

| | 무엇을 정하나 | 어디에 적혀 있나 |
|---|---|---|
| 엔드포인트 라우팅 | **첫 요청이 404 냐 아니냐** | `Program.cs` 의 `AddAdditionalAssemblies` |
| 회로 안 라우팅(`Router`) | 회로가 붙은 뒤 화면 전환 | `Routes.razor` 의 `AdditionalAssemblies` |

둘 다 컴포넌트의 `RouteAttribute` 를 본다. **한쪽만 손보면 "직접 주소를 치면
404 인데 메뉴로는 열린다"** 가 난다(실제로 밟았다 — `web/CLAUDE.md` 참고).

### 아키텍처 테스트는 `@page` **글자를 읽지 않는다**

리플렉션으로 `RouteAttribute` 를 본다.

- `DependencyRuleTests.cs:85` — 접두사 규칙
- `ShellCompositionTests.cs:93` — DB 메뉴 경로 대조
- `ShellCompositionTests.cs:145` — 라우트 매개변수를 받는 속성이 있는지
- `ComponentNamingTests.cs:51` — 화면 이름 규칙

**어트리뷰트로만 남아 있으면 어떻게 적든 65건이 그대로 돈다.** 아래 1·2번이
싼 이유가 이것이다.

### 지금 DB 가 소유한 것

`scom.system_menus` 는 **메뉴 노출과 권한만** 소유한다. `component` 컬럼
(Vue 시절 라우트 생성원)은 더 이상 읽지 않는다. 연결 고리는 `path` 하나고,
Vue 시절 경로 69건은 `RouteAliases.cs` 가 새 경로로 옮겨 준다.

### 모듈마다 포괄 라우트가 이미 하나씩 있다

`Components/Pages/_Pending.razor` → `@page "/admin/{*rest}"`.
**아래 4번(디스패처)이 기술적으로 가능한 것은 이것 덕분이다** — 엔드포인트
라우팅이 이미 그 접두사 아래 아무 주소나 받아 준다.

## 1부 — URL 을 화면에 안 적는 방법

### 방법 1. `@attribute [Route(상수)]`

`@page` 는 디렉티브라 리터럴만 받지만, `[Route]` 는 평범한 어트리뷰트라
`const string` 을 받는다.

```razor
@attribute [Route(AdminRoutes.NoticeList)]
```
```csharp
public static class AdminRoutes
{
    public const string NoticeList = "/admin/notice";
}
```

2026-09-06 에 `JSini.Web.Admin` 에 시험 파일을 넣어 빌드해 확인했다 —
경고 0, 오류 0. (확인 뒤 지웠다.)

**장점**

- 라우팅 방식이 하나도 안 바뀐다. 엔드포인트 라우팅 · 첫 요청 404 ·
  화면별 렌더 모드 · `[Parameter]` 자동 바인딩이 전부 그대로다.
- 아키텍처 테스트 65건을 **한 줄도 안 고친다**.
- 오타로 인한 불일치가 컴파일 오류가 된다.
- 되돌리기 쉽다. 화면 하나씩 옮겨도 되고 섞여 있어도 된다.

**단점**

- URL 이 사라지는 게 아니라 **한곳으로 모일 뿐**이다.
- razor 파일 맨 위만 보고 그 화면 주소를 알 수 없다 — 한 번 타고 들어가야 한다.
- 화면 145개를 한 번 훑어야 한다(기계적인 일이라 위험하진 않다).

### 방법 2. 방법 1 + 상수표를 **생성한다**

`docs/menu-route-map.md`(또는 커밋된 json)를 원본으로 빌드 때 상수 클래스를
만든다. 소스 제너레이터 또는 MSBuild 타깃.

**장점**

- `web/CLAUDE.md` 가 "가장 자주 밟는 함정" 이라 적어 둔 **`@page` ↔ DB 메뉴
  경로 불일치가 원천적으로 사라진다.** 지금은 어긋나도 각 파일만 보면 둘 다
  정상으로 보이고 테스트가 사후에 잡는데, 이 방식은 어긋날 수가 없다.
- 경로 정본이 문서가 아니라 **빌드 입력**이 된다.
- 나중에 `RouteAliases` 를 지울 수 있다.

**단점**

- 빌드에 생성 단계가 붙는다(생성기 한 벌 유지 부담).
- **DB 를 직접 원본으로 삼으면 빌드가 DB 에 묶인다.** 커밋된 지도 파일을
  원본으로 두고 DB 대조는 지금처럼 테스트에 맡기는 편이 낫다.
- 경로가 바뀌면 재빌드·재배포가 필요하다(1번과 같다).

### 방법 3. 모듈이 라우트를 신고한다

`IPortalModule` 에 `(경로, 타입)` 목록을 얹고, 셸이 기본 `<Router>` 대신
그 표를 보는 라우터를 쓴다. 화면에는 어트리뷰트가 없다.

**장점**

- 이미 있는 MFE 계약과 결이 같다(모듈이 자기 것을 신고한다).
- 한 업무의 화면 전부가 한 파일에서 보인다.
- 접두사 규칙을 코드로 강제할 수 있다.

**단점**

- **화면과 라우트가 떨어져 있어 짝이 풀린다.** 새 화면을 만들고 신고를
  빠뜨리면 조용히 안 열린다 — 이 저장소가 크게 밟은 "모듈 DLL 이 없는데
  빌드는 통과" 와 같은 종류의 실패다.
- 라우터를 직접 짜야 한다. 매개변수 바인딩과 우선순위(리터럴 > 매개변수 >
  포괄)를 손으로 구현하게 된다.
- 엔드포인트 라우팅은 여전히 어트리뷰트를 보므로 포괄 라우트에 기대야 한다.
- 아키텍처 테스트 4종을 다시 짠다.

### 방법 4. 포괄 라우트 + `DynamicComponent` (DB 가 라우트를 소유)

`_Pending.razor` 자리를 디스패처로 바꾼다. 나머지 경로를 DB 메뉴에서 찾아
컴포넌트 타입을 정하고 `<DynamicComponent>` 로 그린다. Vue 시절
`component` 컬럼이 하던 일이다.

**장점**

- 화면에 URL 이 정말로 하나도 없다.
- **배포 없이 DB 만 고쳐 경로를 바꿀 수 있다.**
- 라우트 소유권이 Vue 때와 같아져 옛 운영 방식이 그대로 이어진다.

**단점**

- 2026-09-05 에 **반대 방향으로 끝낸 이행을 되돌리는 것**이다.
- **화면별 렌더 모드를 못 준다.** `DynamicComponent` 로 실린 자식은 부모의
  모드를 따르므로, 로그인·로그아웃의 `[ExcludeFromInteractiveRouting]`
  (정적 SSR) 같은 구분이 불가능하다. 그 화면들은 예외로 남겨야 한다.
- `[Parameter]` 자동 바인딩이 없다 — 경로 조각을 직접 파싱해 `Parameters`
  사전으로 넘긴다.
- **메뉴에 없는 화면은 열 방법이 없어진다.** 지금은 주소만 알면 열린다.
- 화면이 없는 메뉴가 런타임에야 드러난다. 컴파일러도 테스트도 못 막는다.
- 타입 이름을 DB 문자열로 찾으므로 클래스 이름을 바꾸면 조용히 깨진다.

### 방법 5. 관례 기반 (폴더·타입 이름 → URL)

`Admin/Components/Pages/NoticeList.razor` → `/admin/notice-list`.

**장점**

- 적을 것이 아예 없다. 파일을 놓을 자리만 맞추면 라우트가 생긴다.

**단점**

- **이 프로젝트에는 안 맞는다.** DB 메뉴 179건이 관례를 따르지 않는다
  (`DbTester.razor` ↔ `/projmng/db/tester`).
- 맞추려면 파일 이름을 URL 에 맞춰 전부 바꿔야 하고, 그러면 이번엔 파일
  이름이 URL 문자열이 된다.
- 파일 이름을 바꾸면 **주소가 조용히 바뀐다.** 즐겨찾기와 권한이 깨진다.

### 방법 6. 라우팅을 쓰지 않는다 (탭 · 메뉴 구동)

셸 한 화면에서 메뉴 선택에 따라 `DynamicComponent` 를 갈아 끼운다.

**장점**

- 남은 일의 **멀티탭 레이아웃**과 가장 잘 맞는다. 문서가 새로 로드되지 않으니
  탭 상태를 레이아웃이 온전히 들고 있을 수 있다.

**단점**

- 딥링크 · 북마크 · 뒤로가기 · F5 가 전부 죽는다.
- 권한표와 즐겨찾기의 열쇠가 `MenuNode.Path` 라 그 구조와 어긋난다.
- 업무 포털에서 "이 화면 주소 좀" 이 안 되는 것은 실무적으로 큰 손해다.

### 견주기

| | URL 이 사는 곳 | 배포 없이 변경 | 렌더 모드 | 매개변수 바인딩 | 기존 테스트 | 작업량 |
|---|---|---|---|---|---|---|
| 1 상수 | C# 상수 | ✗ | 그대로 | 그대로 | 그대로 통과 | 소 |
| 2 생성 | 지도 파일 | ✗ | 그대로 | 그대로 | 그대로 통과 | 중 |
| 3 모듈 신고 | 매니페스트 | ✗ | 그대로 | 직접 구현 | 재작성 | 중 |
| 4 DB 디스패처 | DB | ✓ | **잃음** | 직접 구현 | 재작성 | 대 |
| 5 관례 | 파일 경로 | ✗ | 그대로 | 그대로 | 재작성 | 대 |
| 6 무라우팅 | 없음 | ✓ | **잃음** | 없음 | 대부분 무의미 | 대 |

## 2부 — DB 가 어디까지 화면을 관리할 수 있나

1부와 겹쳐 보이지만 **다른 질문이다.** 1부는 "URL 을 어디 적나", 이쪽은
"배포 없이 무엇을 바꿀 수 있나" 다. 네 단이 있고 위로 갈수록 배포가 덜 필요하다.

### 1단 — 노출과 권한만 (**지금**)

DB 가 정하는 것: 메뉴에 보이는가 · 누구에게 보이는가 · 어떤 이름으로 ·
어느 묶음 아래.
화면과 경로는 코드가 소유한다.

- 배포 없이: 메뉴 추가·삭제·순서·권한
- 배포 필요: 새 화면, 경로 변경
- 어긋나면: 메뉴는 보이는데 눌러도 404 → 아키텍처 테스트가 빌드 때 잡는다

### 2단 — 경로까지 DB

1부 방법 4. DB `path` 가 곧 라우트다.

- 배포 없이: 경로 변경, 화면 갈아 끼우기(같은 메뉴에 다른 화면 물리기)
- 배포 필요: 새 화면
- 대가: 렌더 모드, 딥링크 검증, 빌드 시점 대조

### 3단 — 화면 조립을 DB 가 (**메타 구동**)

화면 **종류**를 몇 가지로 줄이고(목록 · 목록+상세 · 등록폼 · 보고서),
DB 에는 "어느 종류를, 어떤 자료원으로, 어떤 칸으로" 만 적는다.

**이 저장소에 이미 있다** — ProjMng 가 그렇다. 저장 프로시저 이름을 실어
보내면 결과와 컬럼 메타를 함께 돌려주고, `DynamicGrid.razor` 가 그대로 그린다.
`Wbs.razor` 가 60줄, `CommonCode.razor` 가 90줄인 이유다.

- 배포 없이: **보통 CRUD 화면이면 새 화면까지** (프로시저 + 메타 등록으로 끝)
- 배포 필요: 새 화면 **종류**
- 대가:
  - 업무 로직이 DB(프로시저)로 간다. 형상 관리·리뷰·롤백이 코드보다 약하다.
  - 화면이 특별해지는 순간(장례식장 빈소현황 같은 것) 이 틀을 벗어난다.
  - 틀린 메타는 런타임에야 드러난다.
  - 컴파일 타임 타입 안전이 없다 — `DataTable` 로 다닌다.

### 4단 — 화면 정의를 전부 DB 에 (폼 빌더)

칸 배치·유효성·이벤트까지 DB 에 적고 해석기가 그린다.

- 배포 없이: 거의 전부
- 대가: **해석기 자체가 제품이 된다.** 업무 화면 145개를 옮기는 것보다
  해석기를 만드는 쪽이 크다. 권하지 않는다 — 3단에서 멈추는 것이 실용적이다.

### 단을 섞는 것이 정상이다

지금도 섞여 있다 — ProjMng 는 3단, 나머지는 1단이다.
**화면이 얼마나 자주 보이고 얼마나 특별하냐로 단을 정한다.**

| 화면 | 알맞은 단 | 왜 |
|---|---|---|
| 빈소현황 · 대시보드 | 1단 | 생김새가 업무 그 자체다 |
| 매일 보는 관리 화면 | 1단 | 손으로 칸을 적을 값어치가 있다 |
| 보고서 · 수집 로그 | 3단 | 서버가 준 대로 보면 된다 |
| 헬프데스크 35화면 | 3단 | 엔드포인트가 40개 — DTO 를 40개 만들면 백엔드가 칸을 더할 때마다 화면이 아니라 DTO 를 고치러 간다 |

## 권하는 것

**1 → 2 로 간다. 2부는 3단을 지금처럼 화면 단위로 골라 쓴다.**

이유는 셋이다.

1. 1번은 잃는 것이 없고 되돌리기 쉽다. 화면 하나로 시험해 보고 결정해도 된다.
2. 2번까지 가면 이 저장소가 열몇 번 밟았다고 적어 둔 **경로 불일치 함정
   자체가 사라진다.** URL 을 안 적는 것보다 이쪽이 실익이 크다.
3. 4·6번은 "URL 을 안 적는다" 는 목적은 가장 확실히 이루지만, 값으로 치르는
   것이 렌더 모드 · 딥링크 · 빌드 시점 검증이다. 배포 없이 경로를 바꿔야 할
   일이 얼마나 자주 있었는지로 판단해야 하는데, **지금까지 한 번도 없었다**
   (`menu-path-cutover.sql` 도 아직 안 돌렸다).

### 1번을 고른다면 순서

1. 모듈마다 `Routes.cs` 를 하나 두고 상수를 모은다 (`{모듈}Routes`).
2. 화면 하나를 옮겨 빌드·테스트를 돌린다. **여기까지가 되돌릴 수 있는 지점.**
3. 나머지를 모듈 단위로 옮긴다. 섞여 있어도 도므로 한 번에 안 해도 된다.
4. 로그인 · 로그아웃 · `_Pending.razor` 는 `@page` 리터럴로 **남긴다** —
   메뉴에서 오는 화면이 아니라 지도 문서에 대응 항목이 없다.
5. 아키텍처 테스트에 "모듈 안에 `@page` 리터럴이 남아 있지 않다"(예외 목록
   제외) 를 한 건 더한다. 없으면 새 화면이 옛 방식으로 슬금슬금 돌아온다.

### 2번으로 이어 간다면
