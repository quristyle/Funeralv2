## 이번에 무엇을 했나 — 메뉴 화면 전수 점검

메뉴에 걸린 화면 **139개를 전부 열어 보고**, 화면이 부르는 주소를
게이트웨이에 직접 던져 대조했다. 옛 Vue 소스와도 화면별로 견줬다.

### 결과

| | 시작 | 지금 |
|---|---|---|
| 자료가 정상으로 뜨는 화면 | 119 | **138** |
| 호출 실패 | 12 | 1 (도커 소켓 — 아래 D16) |
| 오류(500) | 8 | 0 |

남은 하나는 이 개발 장비에 도커 소켓이 없어서 나는 **정상적인 안내**다.

### 찾아낸 것 — 종류별

**① 자료를 안 부르고 보기 자료를 그리던 화면 8건**

게이트웨이를 한 번도 부르지 않고 코드에 박아 둔 줄을 그리고 있었다.
숫자와 이름이 그럴듯해서 **화면만 봐서는 알 수 없는** 종류다.

    계정 관리 · 역할 관리 · 메뉴 관리 · 공통코드 · 배포 도구
    헬프데스크 현황 · 내 요청 · 소개사이트 배너/게시판/팝업

앞의 일곱은 실제 API 에 붙였다. 소개사이트 셋은 DB 메뉴에 없고 백엔드에
그 API 가 없어 지웠다(포괄 라우트가 「준비 중」으로 받는다).

**② 스쳐 지나갈 401 하나가 화면 전체를 로그아웃시키고 있었다**

가장 크게 잡힌 것이다. 한 화면을 그리는 동안 게이트웨이를 네댓 번 부르는데,
그중 하나라도 401 을 받으면 토큰을 버리고 **그 뒤의 모든 호출이 토큰 없이**
나갔다. 증상이 들쭉날쭉해 화면 잘못처럼 보이지 않았다.

**③ 서버에 없는 주소를 부르던 화면 13건** — 전부 헬프데스크.
통계가 `dashboard/*` 밑인데 자원 밑에서 부르면 404 가 아니라 **500** 이 난다.

**④ 열 때 죽는 실수 셋** — 라우트 매개변수를 받는 속성이 없거나, 컴포넌트에
없는 매개변수를 넘기거나, 자식을 잘못 넣은 것. **컴파일도 테스트도 통과하고
열 때만 죽는다.** 그래서 검사를 하나 더했다(아키텍처 테스트 66건).

특히 **포괄 라우트 여섯이 전부 500** 이었다 — 「준비 중」 안내가 한 번도 뜬
적이 없었다는 뜻이고, 그 안내를 둔 이유 자체가 사라져 있었다.

**⑤ 눌러도 아무 일 없는 단추 8개** — 배선이 아예 없는 것 6, `Click` 은
있는데 몸통이 빈 메서드 2. 뒤엣것이 더 나쁘다(코드를 훑어봐서는 정상).

**⑥ 읽기만 하고 쓰기가 없던 화면 20여 건** — 클라이언트에는 메서드가 다
있었고 화면만 안 부르고 있었다. Q&A 인데 글을 쓸 수 없는 식이었다.

### 곁가지로 고친 백엔드 한 곳

헬프데스크 전용 DB 로 옮기면서 EF 모델이 스키마를 `jsini` 로 박아 두고 있어
**모든 헬프데스크 요청이 500** 이었다. 화면 서른다섯이 통째로 비어 있었고
원인이 프런트처럼 보였다. 스키마를 설정(`Database:Schema`)으로 뺐다 —
**기본값은 옛 이름 그대로**라 운영은 지금과 똑같이 동작한다.

## 2차 점검 — 「화면은 뜨는데 그 일을 못 하는」 것 찾기

1차는 **화면이 자료를 못 읽는 것**을 잡았다(500 · 404 · 빈 표). 그것을 다
고치고 나니 139개가 전부 열렸다. 그런데 열리는 것과 **쓸 수 있는 것**은
다른 문제다.

그래서 방향을 바꿔 다시 훑었다.

### 어떻게 찾았나 — 도구 셋을 새로 만들었다

**① 클라이언트에는 있는데 아무 화면도 안 부르는 메서드**

이번에 나온 빠짐의 대부분이 이 모양이었다. 서버도 있고 클라이언트 메서드도
있는데 화면이 부르지 않는다. 옛 화면의 주소 문자열과 견주는 1차 방식은
클라이언트를 거치는 호출을 못 봐서 이 종류를 통째로 놓쳤다.

**② 서버에는 있는데 아무 화면도 안 부르는 쓰기 통로**

조회가 빠지면 화면이 비어 눈에 띈다. **저장·삭제가 빠지면 눈에 안 띈다** —
목록은 잘 뜨고, 고칠 자리가 없다는 것은 그 화면으로 무엇을 하려고 해 봐야 안다.

**③ 인자를 자리로 넘겨 밀린 호출**

선택 인자가 줄줄이 있는 메서드에 값을 자리로 넘기면 하나만 밀려도 조건이
통째로 어긋난다. **빌드도 통과하고 화면도 정상으로 보인다** — 목록이
안 줄어들 뿐이다.

### 찾아낸 것

**되돌릴 수 없는 종류의 빠짐 — 업무를 시작할 수가 없었다**

| 화면 | 없던 것 |
|---|---|
| 고인 관리 | **등록·수정** (호실 이동·발인·삭제만 있었다) |
| 기기 관리 | **등록·수정·삭제**, 화면 표시 설정 전부, 장식·문구, 동작 설정, 원격 업데이트 |
| 부서 관리 | **등록·수정·삭제** |
| 회사 목록 | **등록·수정·삭제**, 사용처 |
| 계정 연결 | **연결·해제** (「계정 연결」인데 연결할 수 없었다) |
| 내 정보 | **비밀번호 변경** |

고인 등록이 없다는 것은 장례식장 업무의 **시작**이 없다는 뜻이다.
기기 표시 설정이 없다는 것은 플레이어가 무엇을 어떻게 보여 줄지 정할 곳이
포털 어디에도 없었다는 뜻이다.

**조용히 어긋나 있던 것 — 화면만 봐서는 알 수 없다**

| 무엇 | 증상 | 왜 안 보이나 |
|---|---|---|
| `GetRoomsAsync(건물, 층)` | **건물을 고르면 호실이 0건** | 첫 인자가 `companyId` 다. 자리로 밀려 회사 자리에 건물이 들어갔다. 셋 다 `string?` 이라 빌드가 통과한다. 조건줄 부품이라 장례식장 화면 **대부분**이 같이 비었다 |
| `GetDevicesAsync(건물, 층, 호실)` | 기기 목록이 안 걸러짐 | 위와 같은 이유 |
| 메뉴롤 저장 | **사용자 정의 권한 8개가 저장할 때마다 지워짐** | 저장이 목록을 통째로 덮어쓰는데, 읽어 오는 DTO 에 그 8칸이 없었다 |
| 역할에 사람 걸기 | **아무도 안 걸리고 200** | 본문 이름이 `accountIds` 인데 `userIds` 로 보냈다 |
| 프로젝트 진행 현황 | 연결 DB 가 늘 12건(전체) | `sp_projdblist` 만 거르는 열쇠가 `proj_rid` 인데 `prj_rid` 를 넘겼다 |
| 소스 추적 | 늘 500 | `url_pattern` 칸이 `src_pattern_grp` 에 따라 경로이기도 정규식이기도 한데, 확장자만 보고 첫 행을 집어 정규식을 경로로 들고 갔다 |

**이름이 서버와 달라 조용히 무시되던 것**

가장 알아채기 어려운 종류다. ASP.NET Core 는 **모르는 조회 조건과 본문 칸을
말없이 버린다.** 오류도 경고도 없고, 조회는 전체가 나오고 저장은 200 이 온다.
「검색이 안 걸린다」를 알려면 자료를 미리 알고 있어야 한다.

| 무엇 | 보내던 이름 | 서버가 받는 이름 | 증상 |
|---|---|---|---|
| 고인명 검색(고인 관리 · 고인 현황) | `keyword` | `name` | 무엇을 쳐도 전체가 나온다 |
| 전문 파서 둘(ASCII · 바이너리) | `raw` | `content` | 무엇을 넣어도 「Content is empty」 400 |
| 역할에 사람 걸기 | `userIds` | `accountIds` | 아무도 안 걸린 채 200 |

**같은 이름이 다른 곳에서는 맞다** — `info/deceased-search` 와
`info/room-history` 는 실제로 `keyword` 를 받는다. 그래서 한꺼번에 바꾸지 않고
어긋난 곳만 고쳤다.

찾는 도구를 둘 만들어 두었다. 클라이언트가 만드는 **조회 조건 이름**과
**본문 칸 이름**을 긁어 서버 DTO·핸들러의 이름과 견준다. 지금은 어긋난 곳이 없다.

**개발 도구 통로의 값 이름이 통째로 틀렸던 것**

프로젝트관리의 개발 도구는 `db`(종류) · `dbnick`(별칭)으로 접속을 찾는다.

| 화면 | 무엇이 틀렸나 | 증상 |
|---|---|---|
| 테이블·컬럼 설명 관리 | `db_ip` · `db_port` · `db_user` … 를 **있지도 않은 공통코드 칸**에서 꺼내 보냄 | 조회가 늘 500. 화면에 안내 자리도 없어 빈 표로 보였다 |
| ERD · 업무 흐름 | `tablelist` 를 `isProjDb: true` 로 부름 — 그 길은 **그 DB 의 속성에 저장된 사용자 질의**를 찾는데 그런 속성이 어느 DB 에도 없다 | 500 을 클라이언트가 삼켜 빈 목록. 「그림은 뜨는데 새 테이블이 안 붙는다」 |

**방향이 거꾸로였던 것**

| 화면 | 무엇을 보여 주고 있었나 | 무엇을 보여 줘야 하나 |
|---|---|---|
| 메뉴롤 | 역할 → 메뉴 (역할 관리가 하는 일) | **메뉴 → 누가 쓸 수 있나** |
| 프로젝트 참여자 | 프로젝트 한 줄 | **사람 목록과 그 사람의 참여 프로젝트** |
| Glue 서비스 추적 | 프로젝트 목록 | **쌓인 Glue 자료 3,947건** |
| 소스 추적 | 등록된 소스 묶음 목록 | **훑은 파일과 그 내용** |

**주석은 있는데 기능이 없던 것**

화면 머리에 「…한다」고 적혀 있는데 그 일을 하는 코드가 없었다. 주석을 믿고
읽으면 놓친다.

    기상 현황판   「선택한 지역의 주간 예보 및 추이를 시각화한다」 → 카드 테두리만 바뀜
    고인 관리     「고인 자료를 등록하고 고친다」                → 등록·수정 없음
    내 정보       「비밀번호 변경은 쿠키를 다시 굽는 흐름이라…」  → 서버는 새 토큰을 주지 않는다

마지막 것은 **판단 자체가 틀렸다.** 서버를 읽어 보면 비밀번호 변경은
해시와 만료 시계만 고치고 새 토큰을 주지 않는다. 회로 안에서 그냥 부르면 된다.

### 점검 중 자료를 건드린 일 — 되돌렸다 (2026-09-06)

**무슨 일** — 프로젝트관리 화면이 부르는 프로시저를 하나씩 실제로 던져 보는
도구를 만들었는데, 긁어낸 이름을 **가려내지 않고 전부** 던졌다. 그 안에
쓰기 프로시저 둘이 섞여 있었다.

| 프로시저 | 무슨 일이 벌어졌나 | 되돌린 방법 |
|---|---|---|
| `sp_projdbdel` | `projmng.devdbinfo` 에서 **`db_rid=4`(jsini) 한 줄이 지워졌다.** 프로젝트 3 의 DB 드롭다운이 비고, DB 도구 화면들이 그 DB 를 못 찾게 된다 | 앞선 조회로 남아 있던 값 12칸을 그대로 다시 넣었다. 딸린 속성 7건(`erd`·`flow`·`sp_fmt` …)은 다른 표라 지워지지 않았다 |
| `sp_home_todo_make` | `projmng.home_todo` 에 **16줄이 새로 만들어졌다**(대상 날짜 없음, 만든이 `system`) | 그 16줄만 골라 지웠다. 130줄로 원래대로 |

**지금 상태** — 둘 다 되돌렸다. 등록 DB 12건(4번 포함), 할일 130건
(마지막 생성일 2025-05-18)로 점검 전과 같다.

**왜 일어났나** — 이 앱의 통로는 **받은 이름을 그대로 실행한다.** 화면 코드에서
긁은 이름이라 「화면이 조회에 쓰는 것」이라고 여겼는데, 같은 화면이 저장·삭제도
같은 통로로 부른다. 이름만 보고 조회일 것이라고 여기면 안 되는 구조다.

**막은 방법** — 도구가 이름에 `del` · `save` · `make` 같은 조각이 들어간
프로시저는 **던지지 않고 따로 적어 두게** 했다. 그 사연을 도구 머리말에도 남겼다.

### 헬프데스크 기준자료 화면 — D6 에 딸린 빠짐

서버에는 등록·수정·삭제가 다 있는데 화면에 그 자리가 없는 헬프데스크 화면이
아래와 같다. **일부러 손대지 않았다** — 폼을 만들려면 어느 칸을 어떤 이름으로
보여 줄지 정해야 하고, 그것이 곧 D6(「35화면의 칸을 손으로 적을까」)의 답이다.
D6 을 정해 주시면 그 방침대로 한 번에 붙이겠다.

| 화면 | 서버에 있는 것 |
|---|---|
| 담당자 목록 · 담당자 역량 | `admins` 등록·수정·삭제 |
| 팀 목록 · 팀-회사 | `teams` 등록·수정·삭제 |
| 체크리스트 | `checklists` 등록·수정·삭제 |
| 내 일정 · 전체 일정 | `schedules` 등록·수정·삭제 |
| WBS 목록 · 간트 · 다이어그램 | `wbs` 등록·수정·삭제 |
| 프로젝트 정보 · 관리 · 간트 | `project` 등록·수정·삭제 |
| 전문 파서(MC 모델) | `utils/parse-items` · `ack-finds` · `tag-items` |

**「요청 상세」의 처리 내용 남기기는 예외로 먼저 붙였다** — 칸이 하나뿐이고

## D7. 잠금화면을 되살릴까

**무엇** — vben 에 `LockScreen` 이 있었다. 자리를 비울 때 화면을 덮고,
돌아와서 비밀번호를 넣어야 풀린다.

**지금** — 없다.

**만들려면** — 비밀번호를 확인하는 엔드포인트가 필요하다. AuthServer 에
`/user/change-password` 는 있지만 **확인만 하는** 것은 없다. 로그인 API 를
다시 부르는 방법도 있는데, 그러면 새 토큰이 발급되고 기존 세션과 섞인다.

**정할 것** — 되살릴지, 되살린다면 확인을 어떻게 할지.

- 백엔드에 확인 전용 엔드포인트를 하나 만든다 (권장, 작다)
- 실제로 잠그지 않고 화면만 덮는다 (보안이 아니라 예의 수준)
- 만들지 않는다

**결정:lockScreen 화면은 필요하다. 백엔드에 확인 전용 엔드포인트를 하나 만든다**
— 2026-09-06 반영.

**한 일**

- AuthServer 에 `POST auth/user/verify-password` 를 만들었다. **아무것도 바꾸지
  않는다** — 맞는지만 보고 참·거짓을 준다. 로그인에 딸린 곁일(해시 승격 ·
  접속 기록 · 만료 시계)을 일부러 하지 않는다. 하면 잠금을 푼 것이 로그인
  기록으로 남아 「접속 기록」 화면이 실제와 달라진다.
- **틀렸을 때 401 이 아니라 200 + `false` 다.** 401 을 주면 프런트의
  `AuthTokenHandler` 가 세션이 죽은 것으로 읽고 토큰을 버려서, 비밀번호를
  한 번 잘못 치면 **화면 전체가 로그아웃된다.**
- 게이트웨이에서 **로그인과 같은 시도 제한**(`auth-attempts`, IP 당 분당 10회)을
  건다. 안 걸면 로그인에 걸어 둔 제한을 이 경로로 우회할 수 있다. 실제로
  14번 두드려 429 가 나는 것을 확인했다.
- 비밀번호 만료 차단의 예외 목록에도 넣었다 — 잠긴 상태에서 푸는 길은 늘 열려
  있어야 한다.
- 화면은 [`LockScreen.razor`](../src/Shared/JSini.Web.Components/Layout/LockScreen.razor).
  레이아웃 격자 **바깥**에 덮는다(안에 두면 본문 자리에만 깔린다).
  잠그는 자리는 오른쪽 위 사용자 차림표의 「화면 잠금」이다.
- 표시를 `sessionStorage` 에 남겨 **새로고침해도 덮개가 다시 덮인다.**
  `localStorage` 가 아닌 이유는 창을 닫으면 잠금도 사라져야 하기 때문이다.

**밟은 것** — 처음에 `EditForm` 으로 만들었더니 잠금 해제가 회로 안에서
처리되지 않고 **진짜 POST 로 나가** 「어느 폼이 제출됐는지 모르겠다」 오류
화면으로 바뀌었다. 이 부품은 레이아웃에 얹혀 정적 SSR 로 그려지는 순간이 있다.
폼을 걷어내고 단추 하나 + 엔터(keydown)로 바꿨다.

**밝혀 둔 한계** — 이것은 **보안 경계가 아니다.** 잠긴 동안에도 토큰은 살아
있고 API 는 부를 수 있다(개발자 도구로 우회 가능). 막으려는 것은 지나가는
사람이지 공격자가 아니다. vben 도 같은 수준이었다. 그 말을 잠금 화면 안에도
적고 로그아웃 단추를 나란히 두었다.

**한 일**

- 토큰을 만드는 코드를 [`AccessTokenFactory`](../../microservices/AuthServer/Services/AccessTokenFactory.cs)

- 갱신할 때 **역할·이메일을 다시 읽는다.** 갱신 토큰에 얼려 두면 역할을
  바꿔도 옛 권한이 만료일까지 따라다닌다.
- 파일 읽기 쿠키(`jsini_file_at`)도 함께 갱신한다. 안 하면 갱신 뒤에
  **글은 보이는데 사진만 안 나온다.**
- 수명은 설정이다 — `Auth:AccessTokenDays`(7) · `Auth:RefreshTokenDays`(30).
  뒤엣것을 0 으로 두면 갱신이 통째로 꺼진다(코드 수정 없이 되돌리는 길).

**곁가지로 고친 것** — 셸의 `LoginService` 가 `Set-Cookie` 의 **첫 번째** 것을
리프레시 쿠키로 집고 있었다. 로그인 응답에는 파일 읽기 쿠키도 함께 실려 있어서,
갱신 쿠키가 생기는 순간 **파일 쿠키를 갱신 쿠키로 착각**할 수 있는 상태였다.
이름으로 찾도록 고치고, 못 찾으면 경고를 남긴다.

## D17. 쌓인 도커 이미지 정리를 화면에 붙일까

**무엇** — 배포를 거듭하면 옛 태그 이미지가 쌓인다. 서버에 정리하는 주소가
있다(`auth/deploy-status/cleanup` — 사용 중 태그와 최근 몇 개만 남긴다).

**지금** — 화면에는 **얼마나 쌓였는지만** 보여 준다(「쌓인 이미지」 표에
용량과 사용 여부). 지우는 단추는 붙이지 않았다 — 되돌릴 수 없고, 되돌리려면
다시 빌드해야 한다.

**정할 것**

1. 붙인다 (관리자만, 지울 목록을 먼저 보여 주고 확인받는다)
2. 안 붙인다 (서버에서 직접 돌린다)

**결정:기존 배포현황(/system/deploy-status) 화면에서 상태를 확인하고 쌓인 이미지를 정리하는 버튼을 제공 했었다. 개선한 화면도 동일하게 처리하기를 기대한다.**
— 2026-09-06 반영.

**어느 화면에 붙였나** — 「쌓인 이미지」 표가 있는 곳, 곧
**MSA 서버 상태**(`/admin/status/server`, DB 메뉴 `/system/server-status`)다.
옛 Vue 화면은 상태와 이미지를 한 화면에 담았는데 이식하면서 둘로 갈렸다
(배포 현황 = 워크플로 실행 이력, MSA 서버 상태 = 컨테이너·이미지).
단추는 지울 대상이 보이는 자리에 있어야 한다.

**한 일**

- 서버에 `?dryRun=true` 를 더했다. 참이면 **지우지 않고 지울 목록만** 준다.
  화면이 그 목록을 확인 창에 그대로 띄우고, 「지운다」를 눌러야 실제로 지운다.
- **목록을 화면이 계산하지 않는다.** 계산하면 「무엇을 남길지」 규칙이 서버와
  화면 두 곳에 생기고, 한쪽만 고치는 날 **보여 준 것과 지워지는 것이 달라진다.**
  되돌릴 수 없는 동작에서 그 어긋남은 그냥 사고다.
- 미리보기의 용량은 「최대 …MB」로 적는다. 도커의 이미지 크기는 공유 레이어를
  저마다 온전히 세므로 합이 실제 회수량보다 크다. 부풀린 숫자를 확정처럼
  보여 주지 않는다.
- 끝나면 **상태를 다시 읽은 뒤** 결과를 말한다(순서가 반대면 다시 읽는 쪽이
  안내 줄을 비워 결과가 사라진다). 일부만 지워졌으면 실패 건수도 함께 말한다 —
  「정리했습니다」로 뭉뚱그리면 표가 안 줄어든 이유를 알 수 없다.
- 권한 판정은 서버가 한다(ADMINISTRATOR 계열). **화면에서 단추를 감추지
  않았다** — 권한표 이름과 서버 판정이 어긋나면 단추가 사라져 원인을 찾을 수
  없다. 권한이 없으면 눌렀을 때 서버가 이유를 말해 준다.

**개발 장비에서는 눌러도 「이 환경에는 Docker 소켓이 없습니다」가 뜬다**(D16).
그것이 정상이고, 실제 동작 확인은 운영에서만 할 수 있다.
